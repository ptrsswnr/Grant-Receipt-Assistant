ขั้นตอน:
1. เข้าสู่ระบบ — เห็นเฉพาะข้อมูลใบเสร็จ/โครงการของตนเองเท่านั้น
   ([[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-12]],
   [[20260816-01-grant-receipt-verification#5. Non-Functional Requirements|NFR-05]])
2. ตามสถานการณ์: ถ้า**ยังไม่เคย**ให้ความยินยอมมาก่อน (ใช้งานครั้งแรก/ก่อนอัปโหลดใบเสร็จครั้งแรก) →
   ระบบแสดงประกาศความเป็นส่วนตัว (Privacy Notice) แจ้งวัตถุประสงค์การเก็บ/ใช้ข้อมูล ตัวตนผู้ควบคุม
   ข้อมูล ระยะเวลาเก็บข้อมูล และสิทธิ์ของเจ้าของข้อมูล (รวมถึงว่า Admin อ่านข้อมูลใบเสร็จได้แบบอ่านอย่างเดียว)
   แล้วขอความยินยอมชัดแจ้ง (Explicit Consent) ก่อนเริ่มเก็บ/ประมวลผลข้อมูลใบเสร็จ — ปัจจุบันในแอปเป็นการ
   ยินยอมแบบเบา (ติ๊กครั้งเดียวก่อนอัปโหลดครั้งแรก) ถ้า**เคยให้**ความยินยอมแล้ว → ข้ามไปขั้นตอนตรวจสอบ
   โครงการวิจัยได้เลย
   ([[20260816-02-pdpa-compliance#4. Functional Requirements|FR-13]],
   [[20260816-02-pdpa-compliance#4. Functional Requirements|FR-14]])
3. ตามสถานการณ์ (เฉพาะกรณีเป็นครั้งแรก): ถ้า**ให้ความยินยอม** → ระบบบันทึกหลักฐานการให้ความยินยอม
   (วันที่ให้, เวอร์ชัน Privacy Notice) แล้วไปขั้นตอนตรวจสอบโครงการวิจัย ถ้า**ไม่ให้ความยินยอม** → ไม่
   สามารถอัปโหลดใบเสร็จเข้าสู่ระบบได้ จบ flow นี้ (ดูวิธีถอนความยินยอมภายหลังที่ Journey 5)
   ([[20260816-02-pdpa-compliance#4. Functional Requirements|FR-14]],
   [[20260816-02-pdpa-compliance#4. Functional Requirements|FR-15]])
4. ตามสถานการณ์: ถ้า**ยังไม่มี**โครงการวิจัยที่ผูกกับแหล่งทุนไว้เลย (หรือต้องการเพิ่มโครงการใหม่) →
   สร้าง/จัดการข้อมูลโครงการวิจัยของตนเอง (อย่างน้อยชื่อโครงการ) แล้วเลือกผูกโครงการเข้ากับแหล่งทุน
   (fund source) ที่โครงการได้รับจากรายการที่ Admin นำเข้าไว้ (ดู Journey 4) เพื่อให้ระบบทราบว่า
   ใบเสร็จของโครงการนี้ต้องตรวจตามระเบียบของแหล่งทุนใด ถ้า**มีแล้ว** → ข้ามไปขั้นตอนถัดไปได้
   เลยโดยเลือกโครงการที่มีอยู่แล้วเป็นตัวที่จะผูกใบเสร็จ
   ([[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-23]])
5. ตามสถานการณ์: ถ้าโครงการ**ยังไม่มี**ประมาณการ → นำเข้าไฟล์ตารางประมาณการ 17.2 ของมหาวิทยาลัย
   (.xlsx/.csv) ที่หน้าโครงการ (ปุ่ม "ประมาณการ" บนการ์ดโครงการ) ระบบแปลงเป็นรายการประมาณการ อ่านจำนวนหน่วยจากช่อง
   ตัวคูณ จับคู่หมวดระเบียบให้ นักวิจัยตรวจ/แก้การจับคู่ก่อนบันทึก (พฤติกรรมปัจจุบัน: การนำเข้าซ้ำจะแทนที่รายการทั้งหมด ส่วนการนำเข้าซ้ำแบบเก็บ
   เวอร์ชันเก่าและย้ายใบเสร็จไปรายการล่าสุด **ยังไม่ได้สร้าง** ดู Journey 8 ขั้นตอนที่ 5-8) ถ้า
   **มีแล้ว** → ข้ามไปขั้นตอนถัดไป (ติดตามยอดใช้ไป/คงเหลือ ดู Journey 8) — **ตั้งแต่ 2026-11-24 ต้องมีประมาณการก่อนจึงอัปโหลดใบเสร็จได้**
   (หน้าอัปโหลดแจ้งพร้อมลิงก์ไปหน้าประมาณการ และปุ่มอัปโหลดไม่ทำงานจนกว่าจะนำเข้า)
   ([[20261117-01-implemented-rule-engine-ai-and-admin#2. Functional Requirements|FR-26]],
   [[20261117-02-fund-source-deactivation-estimate-versioning-drive-privacy#2. Functional Requirements|FR-36]])
6. ตามสถานการณ์: ถ้า**ต้องการแนบไฟล์จริง** → กด "เชื่อมต่อ Google Drive" เพื่ออนุญาตบัญชี Google ของตนเอง
   (สิทธิ์ `drive.file` เท่านั้น) ไฟล์จะเก็บในโฟลเดอร์แยกตามรหัสใบเสร็จ ถ้า**ไม่ต้องการ** → ข้ามไป (โทเค็นหมดอายุ
   ประมาณ 1 ชั่วโมง ต้องกดเชื่อมต่อใหม่ ระบบจะเตือนถ้าแนบไฟล์แต่ยังไม่ได้เชื่อมต่อ) — **ยังไม่ได้สร้าง (FR-37):** ไฟล์จะดูได้เฉพาะเจ้าของและ Admin
   (ปัจจุบันใครมีลิงก์เปิดดูได้) และถูกลบตามเมื่อลบใบเสร็จ/ถอนความยินยอม ดู Journey 7 และ 5
   ([[20261117-01-implemented-rule-engine-ai-and-admin#2. Functional Requirements|FR-32]],
   [[20261117-02-fund-source-deactivation-estimate-versioning-drive-privacy#2. Functional Requirements|FR-37]])
7. อัปโหลดไฟล์ใบเสร็จของค่าใช้จ่าย 1 เรื่อง (jpg/png หรือ PDF สแกน) ผูกกับ**โครงการวิจัย**ของตนเอง
   (ไม่ใช่ผูกตรงกับแหล่งทุนโดยตรง) — 1 รายการใบเสร็จ (ชุดเอกสารหลักฐานของค่าใช้จ่าย 1 เรื่อง) อาจ
   ประกอบด้วยมากกว่า 1 ไฟล์/แผ่น (เช่น ค่ารถตู้ตามระเบียบมหาวิทยาลัยต้องมี "ใบสำคัญรับเงิน" +
   "สำเนาบัตรผู้รับเงิน" รวมกัน) สูงสุด **5 ไฟล์ต่อรายการ** ต้องอัปโหลดไฟล์ทั้งหมดของค่าใช้จ่ายเรื่อง
   เดียวกันพร้อมกันในครั้งเดียวและผูกกับ record เดียวกัน ไม่ใช่แยกเป็นใบเสร็จคนละรายการ (ใบเสร็จ 1
   แผ่นที่มีสินค้าหลายชิ้นจากร้านเดียวกันยังนับเป็นรายการเดียว ไม่ต้องแยก) ระหว่างขั้นตอนนี้ระบบต้อง
   แสดงข้อความเตือน/คำแนะนำให้อัปโหลดครั้งละ 1 รายการเท่านั้น เพื่อป้องกันความสับสนอัปโหลดใบเสร็จ
   หลายรายการปนกันในครั้งเดียว
   ([[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-01]],
   [[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-22]])
8. ระบบตรวจสอบความถูกต้องของไฟล์ที่อัปโหลดก่อนส่งเข้า OCR เสมอ (ชนิดไฟล์ที่รองรับ, ไฟล์ไม่เสียหาย/
   เปิดได้, ไม่เกินขนาดสูงสุด 5 MB ต่อไฟล์, จำนวนไฟล์ไม่เกิน 5 ไฟล์ต่อรายการ) — ตามสถานการณ์: ถ้า
   **ไฟล์ไม่ถูกต้องหรือมีจำนวนไฟล์เกินที่กำหนด** → ระบบปฏิเสธการอัปโหลด (หรือไฟล์ส่วนเกิน) ทันทีพร้อม
   ข้อความ error ภาษาไทยที่ชัดเจนระบุสาเหตุ แนะนำให้ลดจำนวนไฟล์หรือแยกเป็นรายการใหม่ตามความเหมาะสม
   แล้ววนกลับไปขั้นตอนที่ 7 ให้อัปโหลดใหม่ ถ้า**ไฟล์ถูกต้องครบตามเงื่อนไข** → ไปขั้นตอนถัดไป
   ([[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-19]],
   [[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-22]])
9. ระบบอ่านข้อมูลจากใบเสร็จอัตโนมัติ (ยอดเงิน วันที่ หมวดค่าใช้จ่าย ชื่อร้าน/ผู้ขาย) — AI อ่านภาพ/PDF หน้าแรก
   พร้อมป้าย "AI suggestion" เฉพาะเมื่อ AI ทำงานจริง ผู้ให้บริการสลับได้ (OpenRouter / Ollama ในเครื่อง / proxy /
   custom) และถ้ามี OCR ภาษาไทยในเครื่องเปิดอยู่ ระบบส่งข้อความที่ OCR อ่านได้เข้า AI ประกอบภาพ (ใบเสร็จไม่ออกจากเครื่อง
   ถ้าใช้ AI ในเครื่อง) หรือสกัดยอด/วันที่ (พ.ศ.→ค.ศ.)/ชื่อร้านเองเมื่อไม่มี AI ถ้าไม่มี AI/OCR หรือเรียกล้มเหลว → ถอยกลับเป็น
   กรอกเองหรือข้อมูลสาธิตพร้อมแจ้งว่าใช้เส้นทางใด — หากผู้ให้บริการ OCR/AI ประมวลผลข้อมูลนอกราชอาณาจักรไทย ต้องมี
   มาตรการคุ้มครอง cross-border transfer และข้อตกลงประมวลผลข้อมูล (DPA) ตามเงื่อนไขที่กำหนด
   ([[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-02]],
   [[20261117-01-implemented-rule-engine-ai-and-admin#2. Functional Requirements|FR-30]],
   [[20260816-01-grant-receipt-verification#5. Non-Functional Requirements|NFR-01]],
   [[20260816-01-grant-receipt-verification#5. Non-Functional Requirements|NFR-06]],
   [[20260816-02-pdpa-compliance#5. Non-Functional Requirements|NFR-08]],
   [[20260816-02-pdpa-compliance#5. Non-Functional Requirements|NFR-09]],
   [[20261117-01-implemented-rule-engine-ai-and-admin#3. Non-Functional Requirements|NFR-12]],
   [[20261117-01-implemented-rule-engine-ai-and-admin#3. Non-Functional Requirements|NFR-14]])
10. **ไม่มีขั้นตรวจ/แก้ค่าที่อ่านได้** — ค่าที่ OCR/AI อ่านถูกใช้ตรวจทันที หน้าจอขั้นที่ 2 แสดงเพียง "กำลังตรวจสอบ"
    (แผนแรกให้นักวิจัยตรวจแก้ได้ทุกค่าตาม FR-03 ดูภาคผนวก) ถ้าอ่านยอดไม่ได้จะบันทึกเป็นค่าว่าง ไม่ใช่ตัวเลขผิด
    ([[20261127-02-llm-verdict-research-direction#2. Functional Requirements|FR-39]])
11. ระบบจับรายการในประมาณการจากหมวดค่าใช้จ่ายที่อ่านได้เอง (แผนแรกให้นักวิจัยเลือกรายการหรือ "ไม่อยู่ในประมาณการ" เอง)
    ([[20261117-01-implemented-rule-engine-ai-and-admin#2. Functional Requirements|FR-26]])
12. ระบบจำแนกประเภทเอกสารของแต่ละไฟล์ และหาตรา ("จ่ายแล้ว", "ตรวจรับพัสดุ"/"ได้รับพัสดุ") จากข้อความ OCR เอง
    แล้วใช้เป็นเอกสาร/ตราที่มีสำหรับตรวจกับชุดเอกสารของหมวดนั้น (แผนแรกให้นักวิจัยติ๊กเอง) — เป็นการจับคำสำคัญ ไม่ใช่โมเดลจำแนกจริง
    และ**ตรวจรูปถ่ายพัสดุไม่ได้**
    ([[20261117-01-implemented-rule-engine-ai-and-admin#2. Functional Requirements|FR-27]],
    [[20261127-02-llm-verdict-research-direction#2. Functional Requirements|FR-39]])
13. ยอดในใบสรุปรายรับ-จ่าย (ไม่บังคับ) กรอกพร้อมอัปโหลดในขั้นตอนที่ 7 — เป็นข้อมูลเดียวที่นักวิจัยกรอกเอง
    ([[20261117-01-implemented-rule-engine-ai-and-admin#2. Functional Requirements|FR-28]])
14. ตรวจ: Rule Engine ตรวจทุกใบตามลำดับ ประมาณการ → ระเบียบ → ใบสรุป → เอกสารแนบ และบันทึกใน `receipt.ruleCheck` เสมอ
    จากนั้น (โหมดตั้งต้น `llm`) LLM ตัดสิน pass/fail จากข้อความ OCR ระเบียบเป็นข้อความ และประมาณการพร้อมตัวเลขที่คำนวณไว้
    โดยกรอก checklist 4 ข้อ (ประมาณการ / เพดานระเบียบ / เอกสาร / ตรา) พร้อมข้อความ OCR ที่ใช้เป็นหลักฐาน — ถ้า LLM ล้มเหลว
    ใช้ผล Rule Engine แทน; โหมด `rule` ให้ Rule Engine ตัดสินเหมือนแผนแรก
    ([[20261117-01-implemented-rule-engine-ai-and-admin#2. Functional Requirements|FR-24]],
    [[20261117-01-implemented-rule-engine-ai-and-admin#2. Functional Requirements|FR-25]],
    [[20261127-02-llm-verdict-research-direction#2. Functional Requirements|FR-38]])
15. คำอธิบาย: โหมด `llm` ใช้คำแนะนำและข้อสังเกตของ LLM แสดงเป็นภาษาไทย; AI agent ที่อธิบายผลของกฎ (FR-31) ทำงานเฉพาะโหมด `rule`
    ([[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-05]],
    [[20261117-01-implemented-rule-engine-ai-and-admin#2. Functional Requirements|FR-31]],
    [[20261127-02-llm-verdict-research-direction#2. Functional Requirements|FR-38]])
16. ระบบแสดงสถานะใบเสร็จด้วยสี+ไอคอน+ข้อความ (โหมด `llm`: ผ่าน / ต้องแก้ไข; โหมด `rule`: 4 ระดับ) พร้อมคำแนะนำ
    ([[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-06]],
    [[20261117-01-implemented-rule-engine-ai-and-admin#2. Functional Requirements|FR-25]],
    [[20260816-01-grant-receipt-verification#5. Non-Functional Requirements|NFR-02]],
    [[20260816-01-grant-receipt-verification#5. Non-Functional Requirements|NFR-03]],
    [[20261117-01-implemented-rule-engine-ai-and-admin#3. Non-Functional Requirements|NFR-13]])
17. ตามสถานการณ์: ถ้า**ผ่าน** → ใบเสร็จพร้อมสำหรับนำไป export (ดู Journey 3) จบ flow นี้
    ถ้า**ไม่ผ่าน** → กด "ส่งฉบับแก้ไข" เลือกเพิ่มเอกสารที่ขาดหรือแทนที่ทั้งชุด
    (รายละเอียดดู Journey 2 ขั้นตอนที่ 4-7; กรณีต้องชี้แจง/ขออนุมัติ ให้ดำเนินการกับการเงินนอกระบบ) แล้วระบบตรวจซ้ำเหมือนขั้นตอนที่ 14 จนกว่าจะผ่าน
    ([[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-07]])

ขั้นตอน:
1. เข้าสู่ระบบ — เห็นเฉพาะโครงการของตนเอง
   ([[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-12]])
2. รับการแจ้งเตือนเมื่อมีใบเสร็จสถานะ "ต้องแก้ไข"/"ต้องชี้แจง/ขออนุมัติ"/"ไม่เข้าเงื่อนไข" ค้างอยู่ยังไม่ได้รับการแก้ไข
   (ไม่รวมการแจ้งเตือนตามกำหนดเวลาส่งหลักฐาน ซึ่งตัดออกจากขอบเขต MVP นี้) — ยังเป็น Backlog
   ([[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-09]])
3. เปิดดู Dashboard สรุปภาพรวมสถานะใบเสร็จของแต่ละ**โครงการวิจัย**ที่เป็นเจ้าของ (จำนวนที่ผ่าน/
   ต้องแก้ไข/ต้องชี้แจง-ขออนุมัติ/ไม่เข้าเงื่อนไข) — ปัจจุบันนักวิจัยดูได้ผ่านหน้ารายการใบเสร็จรายโครงการ (ตัวกรองตามโครงการ)
   ส่วน Dashboard สรุปข้ามผู้ใช้มีเฉพาะฝั่ง Admin (ดู Journey 9) ([[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-08]])
4. ตามสถานการณ์: ถ้า**มี**ใบเสร็จที่ยังไม่ผ่าน (ต้องแก้ไข/ต้องชี้แจง-ขออนุมัติ/ไม่เข้าเงื่อนไข) → กดปุ่ม
   "ส่งฉบับแก้ไข" ที่ใบเสร็จนั้น (มีในหน้า "ใบเสร็จของฉัน" และ "ประมาณการและใบเสร็จ"; ใบเสร็จที่ผ่านแล้วไม่มีปุ่มนี้) ระบบเปิดหน้าอัปโหลดใน
   โหมดฉบับแก้ไข แสดงสถานะ ยอด วันที่ หมวด ร้านค้า และคำแนะนำเดิม โดยใช้ใบเสร็จรหัสเดิม และล็อกโครงการไว้
   (ต่อยอดจาก Journey 1 ขั้นตอนที่ 17) ถ้า**ไม่มี** → ใบเสร็จทั้งหมดของโครงการผ่านตรวจแล้ว พร้อมสำหรับ export
   ([[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-07]])
5. เลือกวิธีส่งฉบับแก้ไข 1 ใน 2 แบบต่อการส่งแต่ละครั้ง (ไม่มีขั้นตอนแก้ไขช่องข้อมูลด้วยมือ ผู้ใช้กรอกเองได้เพียงยอดในใบสรุปรายรับ-จ่ายแบบไม่บังคับ):
   - **เพิ่มเอกสารที่ขาด** — แนบเฉพาะเอกสารที่ขาด ระบบ OCR เฉพาะไฟล์ใหม่ แล้วรวมกับข้อความ OCR ที่เก็บไว้ของไฟล์เดิมเพื่อตรวจ
     ส่วนยอด/วันที่/หมวด/ร้านค้ายังคงตามใบเดิม
   - **แทนที่ทั้งชุด** — แนบไฟล์ใหม่ทั้งชุด ระบบอ่านและตรวจเหมือนอัปโหลดใหม่ ไฟล์เดิมถูกซ่อนแต่ไม่ลบ (ทำเครื่องหมายว่าถูกแทนที่
     และเก็บไฟล์ใน Drive ไว้เป็นประวัติ)

   ต้องแนบไฟล์อย่างน้อย 1 ไฟล์ทุกครั้ง
   ([[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-07]])
6. ระบบตรวจซ้ำด้วยวิธีเดียวกับการอัปโหลดใหม่ (Rule Engine + LLM) โดยประมาณการไม่นับยอดเดิมของใบเสร็จใบนี้ซ้ำ แล้วแสดงผลใหม่
   พร้อมข้อความ "ฉบับแก้ไขครั้งที่ n · ผลก่อนแก้ไข: ..." ผลก่อนหน้าถูกเก็บเป็นประวัติ และใบเสร็จแสดง "แก้ไขแล้ว n ครั้ง"
   ([[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-07]])
7. ตามสถานการณ์: ถ้า**ผ่าน** → ปุ่มหายไป ใบเสร็จพร้อม export ถ้า**ยังไม่ผ่าน** → กด "ส่งฉบับแก้ไข" ซ้ำได้ไม่จำกัดครั้งจนกว่าจะผ่าน
   — ข้อจำกัดปัจจุบัน: ระบบตรวจรูปถ่ายตรวจรับพัสดุจากไฟล์ไม่ได้ (ตรวจจากข้อความ OCR เท่านั้น) จึงอาจยังแสดงว่ารูปถ่ายขาด
   แม้แนบมาในฉบับแก้ไขแล้ว (เจ้าของโครงการยังไม่ตัดสินใจแนวทางแก้)
   ([[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-07]])

ขั้นตอน:
1. เข้าสู่ระบบและเลือกทุนที่ต้องการยื่นเบิก
   ([[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-12]])
2. เปิดดูสถานะใบเสร็จของทุนผ่าน Dashboard
   ([[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-08]])
3. ตามสถานการณ์: ถ้า**ไม่มี**ใบเสร็จสถานะผ่านแม้แต่ใบเดียว → ระบบปิดการใช้งาน (disable) ปุ่ม Export
   ของทุนนั้นไว้ก่อน พร้อมข้อความแจ้งเหตุผลที่กดไม่ได้ (เช่น "ยังไม่มีใบเสร็จที่ผ่านการตรวจสำหรับทุนนี้")
   แทนการปล่อยให้กดแล้วได้รายงานเปล่า แล้วกลับไปแก้ไขใบเสร็จที่ยังไม่ผ่านก่อน (ต่อยอดจาก Journey 1
   ขั้นตอนที่ 17) ถ้า**มี**ใบเสร็จสถานะผ่านอย่างน้อย 1 ใบ → ปุ่ม Export ใช้งานได้ตามปกติ ไปขั้นตอนถัดไป
   ([[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-21]],
   [[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-07]])
4. กด Export รายงานสรุปใบเสร็จที่ผ่านการตรวจแล้วของทุน — ยังเป็น Backlog (ยังไม่ได้สร้างในแอป)
   ([[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-10]])
5. ดาวน์โหลดไฟล์รายงานและนำไปยื่นต่อเจ้าหน้าที่การเงินของมหาวิทยาลัยเอง (เจ้าหน้าที่การเงินรับไฟล์
   ภายนอกระบบเท่านั้น ไม่ใช่ user ของระบบนี้) — หมายเหตุ: ใบเสร็จที่ถูก export ไปแล้วในขั้นตอนนี้จะ
   ถูกล็อกไม่ให้ลบด้วยตนเองผ่าน UI อีกต่อไป (ดู Journey 7: ลบข้อมูลใบเสร็จของตนเองด้วยตนเอง, FR-18)
   ([[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-10]])

## Journey 4: Admin นำเข้า/อัปเดตระเบียบของแหล่งทุนเข้าสู่ Rule Engine

บทบาท: Admin (ผู้ดูแลระบบ/ผู้อัปเดตระเบียบ)

```mermaid
flowchart TD
    A["เข้าสู่ระบบด้วยบทบาท Admin เห็นเมนู Admin เฉพาะบัญชี Admin สิทธิ์ใบเสร็จของผู้อื่นเป็นอ่านอย่างเดียว (FR-12, FR-33, NFR-05)"]
    B["เพิ่ม/ลบแหล่งทุน และเพิ่ม/แก้/ลบกฎรายหมวดของแหล่งทุนนั้น (FR-11, FR-33)"]

    C["ระบบบันทึกเวอร์ชันระเบียบของแหล่งทุนนั้นไว้ใน Audit Trail (NFR-04)"]

    A --> B --> B1
    B1 -->|ไม่ใช้แล้ว| B3 --> B2
    B1 -->|ยังใช้อยู่| B2
```

ขั้นตอน:
1. เข้าสู่ระบบด้วยบทบาท Admin — เห็นเมนู Admin (ผู้ใช้ทั่วไปไม่เห็น) จัดการแหล่งทุน/ระเบียบ/กฎใน Rule Engine ได้
   และอ่านใบเสร็จของทุกคนได้**แบบอ่านอย่างเดียว** (ดู Journey 9) เขียน/แก้ใบเสร็จของผู้อื่นไม่ได้ — การเลื่อนสิทธิ์
   เป็น Admin ทำผ่านคอนโซลเท่านั้น (สิทธิ์ส่วนนี้กลับคำตัดสินใจเดิมของสเปคแรก ตาม FR-33)
   ([[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-12]],
   [[20261117-01-implemented-rule-engine-ai-and-admin#2. Functional Requirements|FR-33]],
   [[20260816-01-grant-receipt-verification#5. Non-Functional Requirements|NFR-05]])
2. รับทราบว่าระเบียบของ**แหล่งทุน (fund source)** แหล่งใดแหล่งหนึ่งมีการเปลี่ยนแปลง (แต่ละแหล่งทุนมี
   รหัส/ระเบียบใบเสร็จเป็นของตัวเอง) แล้วเพิ่ม/ลบแหล่งทุน และเพิ่ม/แก้/ลบกฎรายหมวด (ประเภทอัตรา เพดานตามจริง/
   เหมาจ่าย/ต่อหน่วย/ตามข้อเสนอโครงการ) โดยไม่ต้อง retrain LLM
   ([[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-11]],
   [[20261117-01-implemented-rule-engine-ai-and-admin#2. Functional Requirements|FR-33]])
3. ตามสถานการณ์ (**ยังไม่ได้สร้าง** — FR-35 สถานะ Backlog): ถ้า**แหล่งทุนไม่ใช้แล้ว** → "ปิดใช้งาน" แทนการลบถาวร แหล่งทุนที่ปิดใช้งาน
   เก็บกฎ (`ruleVersions`/`ruleItems`) ไว้ครบเพื่อย้อนตรวจใบเสร็จเก่า ไม่แสดงในรายการเลือกแหล่งทุนตอนสร้างโครงการใหม่ (Journey 1 ขั้นตอนที่ 4)
   โครงการเดิมยังแสดงชื่อแหล่งทุนตามปกติ และ Admin เปิดใช้งานกลับได้ (พฤติกรรมของใบเสร็จใหม่ในโครงการเดิมที่ผูกกับแหล่งทุนที่ปิดใช้งานยังไม่ได้กำหนด)
   ถ้า**ยังใช้อยู่** → ข้ามไป (พฤติกรรมปัจจุบัน: ลบแหล่งทุนแบบ cascade ถาวร ไม่ตรวจโครงการที่ใช้อยู่)
   ([[20261117-02-fund-source-deactivation-estimate-versioning-drive-privacy#2. Functional Requirements|FR-35]])
4. ผลักชุดกฎตามคู่มือจริง (ปัจจุบัน rule set 2570.4 ครอบคลุม 28 หมวด แต่ละกฎอ้างอิงข้อ/หน้าของคู่มือ) เข้าฐานข้อมูลจริง
   ผ่านปุ่ม "อัปเดตเฉพาะระเบียบ/กฎ" — กฎที่แก้ในไฟล์ตั้งต้นยังไม่มีผลกับข้อมูลจริงจนกว่า Admin จะกดปุ่มนี้
   ([[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-11]],
   [[20261117-01-implemented-rule-engine-ai-and-admin#2. Functional Requirements|FR-29]])
5. ระบบบันทึกเวอร์ชันระเบียบของแหล่งทุนนั้นที่นำเข้าไว้ใน Audit Trail เพื่อรองรับการตรวจสอบย้อนหลัง
   เมื่อระเบียบมีการเปลี่ยนแปลงตามเวลา
   ([[20260816-01-grant-receipt-verification#5. Non-Functional Requirements|NFR-04]])
6. Rule Engine ใช้ระเบียบเวอร์ชันใหม่ของแหล่งทุนนี้ตรวจใบเสร็จของทุกโครงการที่ผูกกับแหล่งทุนนี้
   (ดู Journey 1 ขั้นตอนที่ 4 เรื่องการผูกโครงการกับแหล่งทุน) ต่อจากนี้ (เชื่อมต่อกับ Journey 1
   ขั้นตอนที่ 14)
   ([[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-04]],
   [[20261117-01-implemented-rule-engine-ai-and-admin#2. Functional Requirements|FR-24]])

## Journey 5: นักวิจัยถอนความยินยอม (Withdraw Consent) และผลกระทบต่อการใช้งานระบบ

บทบาท: นักวิจัย/เจ้าของโครงการ

```mermaid
flowchart TD
    A["เข้าสู่ระบบ (FR-12)"]
    B["เปิดหน้าจัดการความยินยอม (FR-16)"]
    C["กดถอนความยินยอมที่เคยให้ไว้ (FR-16)"]
    D["ระบบระงับการอัปโหลด/ประมวลผลใบเสร็จใหม่ทันที (FR-16)"]
    E["ระบบลบข้อมูลใบเสร็จ/ผลตรวจทั้งหมดของนักวิจัยคนนั้นทันที ไม่แยกตามสถานะ export (FR-20)"]
    F["ระบบลบไฟล์ใน Google Drive ทั้งหมดของผู้ใช้ที่ระบบสร้างด้วย ถ้าลบไม่สำเร็จต้องแจ้งผู้ใช้ (FR-37, NFR-15 ยังไม่ได้สร้าง)"]

    A --> B --> C --> D --> E --> F
```

ขั้นตอน (ยังเป็น Backlog — ยังไม่ได้สร้างการถอนความยินยอมในแอป):
1. เข้าสู่ระบบ
   ([[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-12]])
2. เปิดหน้าจัดการความยินยอม (ต่อยอดจากการให้ความยินยอมครั้งแรกใน Journey 1 ขั้นตอนที่ 2-3)
   ([[20260816-02-pdpa-compliance#4. Functional Requirements|FR-16]])
3. กดถอนความยินยอมที่เคยให้ไว้ — ทำได้ทุกเมื่อผ่าน UI ของระบบ
   ([[20260816-02-pdpa-compliance#4. Functional Requirements|FR-16]])
4. ระบบระงับการอัปโหลด/ประมวลผลใบเสร็จใหม่ของนักวิจัยคนนั้นทันที
   ([[20260816-02-pdpa-compliance#4. Functional Requirements|FR-16]])
5. ระบบลบข้อมูลใบเสร็จ/ผลตรวจทั้งหมดของนักวิจัยคนนั้นที่ระบบเก็บไว้ทันที โดยไม่แยกตามสถานะ export
   (เดิมเป็น open point ในรอบก่อน ยืนยันคำตอบแล้วโดยผู้ใช้เมื่อ 2026-08-16 รอบ 3) — เหตุผล: ระบบ
   Grant Receipt Assistant เป็นเพียง "ด่านตรวจก่อนสอบ" (pre-check gate) ไม่ใช่ archival/official
   retention system ของหลักฐานทางการเงิน เมื่อถอนความยินยอม (ฐานทางกฎหมายเดียวที่ใช้เก็บข้อมูลนี้)
   ระบบจึงไม่มีฐานทางกฎหมายเหลืออยู่ที่จะเก็บข้อมูลต่อได้อีก — ต่างจากการลบเฉพาะรายการใบเสร็จผ่าน UI
   ใน Journey 7 (Right to Erasure, FR-18) ซึ่งยังคงเงื่อนไขจำกัดไม่ให้ลบใบเสร็จที่ export ไปแล้ว
   เพราะนักวิจัยยังไม่ได้ถอนความยินยอมทั้งหมดในกรณีนั้น
   ([[20260816-02-pdpa-compliance#4. Functional Requirements|FR-20]])
6. **ยังไม่ได้สร้าง (FR-37/NFR-15 สถานะ Backlog):** ระบบลบไฟล์ใน Google Drive ทั้งหมดของผู้ใช้ที่ระบบสร้างด้วย (ต่อจากข้อมูลใน
   ระบบ) ถ้าลบไม่สำเร็จ (เช่น โทเค็นหมดอายุ) ต้องแจ้งผู้ใช้ ไม่ล้มเหลวเงียบ
   ([[20261117-02-fund-source-deactivation-estimate-versioning-drive-privacy#2. Functional Requirements|FR-37]],
   [[20261117-02-fund-source-deactivation-estimate-versioning-drive-privacy#3. Non-Functional Requirements|NFR-15]])

   ([[20260816-02-pdpa-compliance#4. Functional Requirements|FR-17]])

## Journey 7: นักวิจัยลบข้อมูลใบเสร็จของตนเองด้วยตนเอง (Right to Erasure)

บทบาท: นักวิจัย/เจ้าของโครงการ

```mermaid
flowchart TD
    A["เข้าสู่ระบบ (FR-12)"]
    B["เลือกใบเสร็จที่ต้องการลบ (FR-18)"]
    C{"ใบเสร็จนี้ถูก Export ส่งเจ้าหน้าที่การเงินไปแล้วหรือไม่? (FR-18)"}
    D["ระบบปิดกั้นการลบเอง แจ้งให้ยื่นคำร้องผ่าน Admin/DPO ภายนอกระบบแทน (FR-18)"]
    E["ยืนยันการลบ ระบบลบข้อมูลใบเสร็จนั้นทันที (FR-18)"]
    F["ระบบลบไฟล์ใบเสร็จที่เกี่ยวข้องใน Google Drive ด้วย (FR-37, NFR-15 ยังไม่ได้สร้าง)"]
    G{"ลบไฟล์ใน Drive สำเร็จหรือไม่? (FR-37)"}
    H["ไฟล์ถูกลบครบ จบ flow (FR-37)"]
    I["แจ้งผู้ใช้ว่าลบไฟล์ใน Drive ไม่สำเร็จ เช่น โทเค็นหมดอายุ ไม่ล้มเหลวเงียบ (FR-37)"]

    A --> B --> C
    C -->|ถูก Export แล้ว| D
    C -->|ยังไม่ถูก Export| E --> F --> G
    G -->|สำเร็จ| H
    G -->|ไม่สำเร็จ| I
```

ขั้นตอน (สร้างแล้วบางส่วน: ปุ่มลบใบเสร็จลบถาวรทันทีทั้งใบเสร็จและเอกสารไฟล์ใน Firestore ยังไม่มีเงื่อนไขบล็อกกรณี export
เพราะ Export ยังไม่ได้สร้าง ไม่ลบไฟล์จริงใน Google Drive และไม่มี Audit Trail):
1. เข้าสู่ระบบ
   ([[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-12]])
2. เลือกใบเสร็จของตนเองที่ต้องการลบ
   ([[20260816-02-pdpa-compliance#4. Functional Requirements|FR-18]])
3. ตามสถานการณ์: ถ้าใบเสร็จนั้น**ถูก export ไปแล้ว** (รวมอยู่ใน export รายงานที่ส่งเจ้าหน้าที่การเงิน
   ไปแล้ว — ดู Journey 3 ขั้นตอนที่ 5) → ระบบปิดกั้นการลบเองผ่าน UI และแจ้งให้ยื่นคำร้องผ่านช่องทาง
   Admin/DPO ภายนอกระบบแทน เพื่อรักษา Audit Trail/ป้องกันการลบหลักฐานหนีความรับผิดหลังยื่นเบิกไปแล้ว
   (เหตุผลปรับปรุงเมื่อ 2026-08-16 รอบ 3 — ไม่ใช่เพราะข้อกำหนดเก็บหลักฐานทางการเงินอย่างเป็นทางการ
   อีกต่อไป เทียบกับ Journey 5 ซึ่งเป็นการถอนความยินยอมทั้งหมด จึงลบได้ทันทีไม่มีเงื่อนไขนี้)

ขั้นตอน:
1. เข้าสู่ระบบ — เห็นเฉพาะข้อมูลใบเสร็จ/โครงการของตนเองเท่านั้น
   ([[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-12]],
   [[20260816-01-grant-receipt-verification#5. Non-Functional Requirements|NFR-05]])
2. ตามสถานการณ์: ถ้า**ยังไม่เคย**ให้ความยินยอมมาก่อน (ใช้งานครั้งแรก/ก่อนอัปโหลดใบเสร็จครั้งแรก) →
   ระบบแสดงประกาศความเป็นส่วนตัว (Privacy Notice) แจ้งวัตถุประสงค์การเก็บ/ใช้ข้อมูล ตัวตนผู้ควบคุม
   ข้อมูล ระยะเวลาเก็บข้อมูล และสิทธิ์ของเจ้าของข้อมูล (รวมถึงว่า Admin อ่านข้อมูลใบเสร็จได้แบบอ่านอย่างเดียว)
   แล้วขอความยินยอมชัดแจ้ง (Explicit Consent) ก่อนเริ่มเก็บ/ประมวลผลข้อมูลใบเสร็จ — ปัจจุบันในแอปเป็นการ
   ยินยอมแบบเบา (ติ๊กครั้งเดียวก่อนอัปโหลดครั้งแรก) ถ้า**เคยให้**ความยินยอมแล้ว → ข้ามไปขั้นตอนตรวจสอบ
   โครงการวิจัยได้เลย
   ([[20260816-02-pdpa-compliance#4. Functional Requirements|FR-13]],
   [[20260816-02-pdpa-compliance#4. Functional Requirements|FR-14]])
3. ตามสถานการณ์ (เฉพาะกรณีเป็นครั้งแรก): ถ้า**ให้ความยินยอม** → ระบบบันทึกหลักฐานการให้ความยินยอม
   (วันที่ให้, เวอร์ชัน Privacy Notice) แล้วไปขั้นตอนตรวจสอบโครงการวิจัย ถ้า**ไม่ให้ความยินยอม** → ไม่
   สามารถอัปโหลดใบเสร็จเข้าสู่ระบบได้ จบ flow นี้ (ดูวิธีถอนความยินยอมภายหลังที่ Journey 5)
   ([[20260816-02-pdpa-compliance#4. Functional Requirements|FR-14]],
   [[20260816-02-pdpa-compliance#4. Functional Requirements|FR-15]])
4. ตามสถานการณ์: ถ้า**ยังไม่มี**โครงการวิจัยที่ผูกกับแหล่งทุนไว้เลย (หรือต้องการเพิ่มโครงการใหม่) →
   สร้าง/จัดการข้อมูลโครงการวิจัยของตนเอง (อย่างน้อยชื่อโครงการ) แล้วเลือกผูกโครงการเข้ากับแหล่งทุน
   (fund source) ที่โครงการได้รับจากรายการที่ Admin นำเข้าไว้ (ดู Journey 4) เพื่อให้ระบบทราบว่า
   ใบเสร็จของโครงการนี้ต้องตรวจตามระเบียบของแหล่งทุนใด ถ้า**มีแล้ว** → ข้ามไปขั้นตอนถัดไปได้
   เลยโดยเลือกโครงการที่มีอยู่แล้วเป็นตัวที่จะผูกใบเสร็จ
   ([[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-23]])
5. ตามสถานการณ์: ถ้าโครงการ**ยังไม่มี**ประมาณการ → นำเข้าไฟล์ตารางประมาณการ 17.2 ของมหาวิทยาลัย
   (.xlsx/.csv) ที่หน้าโครงการ (ปุ่ม "ประมาณการ" บนการ์ดโครงการ) ระบบแปลงเป็นรายการประมาณการ อ่านจำนวนหน่วยจากช่อง
   ตัวคูณ จับคู่หมวดระเบียบให้ นักวิจัยตรวจ/แก้การจับคู่ก่อนบันทึก (พฤติกรรมปัจจุบัน: การนำเข้าซ้ำจะแทนที่รายการทั้งหมด ส่วนการนำเข้าซ้ำแบบเก็บ
   เวอร์ชันเก่าและย้ายใบเสร็จไปรายการล่าสุด **ยังไม่ได้สร้าง** ดู Journey 8 ขั้นตอนที่ 5-8) ถ้า
   **มีแล้ว** → ข้ามไปขั้นตอนถัดไป (ติดตามยอดใช้ไป/คงเหลือ ดู Journey 8)
   ([[20261117-01-implemented-rule-engine-ai-and-admin#2. Functional Requirements|FR-26]],
   [[20261117-02-fund-source-deactivation-estimate-versioning-drive-privacy#2. Functional Requirements|FR-36]])
6. ตามสถานการณ์: ถ้า**ต้องการแนบไฟล์จริง** → กด "เชื่อมต่อ Google Drive" เพื่ออนุญาตบัญชี Google ของตนเอง
   (สิทธิ์ `drive.file` เท่านั้น) ไฟล์จะเก็บในโฟลเดอร์แยกตามรหัสใบเสร็จ ถ้า**ไม่ต้องการ** → ข้ามไป (โทเค็นหมดอายุ
   ประมาณ 1 ชั่วโมง ต้องกดเชื่อมต่อใหม่ ระบบจะเตือนถ้าแนบไฟล์แต่ยังไม่ได้เชื่อมต่อ) — **ยังไม่ได้สร้าง (FR-37):** ไฟล์จะดูได้เฉพาะเจ้าของและ Admin
   (ปัจจุบันใครมีลิงก์เปิดดูได้) และถูกลบตามเมื่อลบใบเสร็จ/ถอนความยินยอม ดู Journey 7 และ 5
   ([[20261117-01-implemented-rule-engine-ai-and-admin#2. Functional Requirements|FR-32]],
   [[20261117-02-fund-source-deactivation-estimate-versioning-drive-privacy#2. Functional Requirements|FR-37]])
7. อัปโหลดไฟล์ใบเสร็จของค่าใช้จ่าย 1 เรื่อง (jpg/png หรือ PDF สแกน) ผูกกับ**โครงการวิจัย**ของตนเอง
   (ไม่ใช่ผูกตรงกับแหล่งทุนโดยตรง) — 1 รายการใบเสร็จ (ชุดเอกสารหลักฐานของค่าใช้จ่าย 1 เรื่อง) อาจ
   ประกอบด้วยมากกว่า 1 ไฟล์/แผ่น (เช่น ค่ารถตู้ตามระเบียบมหาวิทยาลัยต้องมี "ใบสำคัญรับเงิน" +
   "สำเนาบัตรผู้รับเงิน" รวมกัน) สูงสุด **5 ไฟล์ต่อรายการ** ต้องอัปโหลดไฟล์ทั้งหมดของค่าใช้จ่ายเรื่อง
   เดียวกันพร้อมกันในครั้งเดียวและผูกกับ record เดียวกัน ไม่ใช่แยกเป็นใบเสร็จคนละรายการ (ใบเสร็จ 1
   แผ่นที่มีสินค้าหลายชิ้นจากร้านเดียวกันยังนับเป็นรายการเดียว ไม่ต้องแยก) ระหว่างขั้นตอนนี้ระบบต้อง
   แสดงข้อความเตือน/คำแนะนำให้อัปโหลดครั้งละ 1 รายการเท่านั้น เพื่อป้องกันความสับสนอัปโหลดใบเสร็จ
   หลายรายการปนกันในครั้งเดียว
   ([[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-01]],
   [[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-22]])
8. ระบบตรวจสอบความถูกต้องของไฟล์ที่อัปโหลดก่อนส่งเข้า OCR เสมอ (ชนิดไฟล์ที่รองรับ, ไฟล์ไม่เสียหาย/
   เปิดได้, ไม่เกินขนาดสูงสุด 5 MB ต่อไฟล์, จำนวนไฟล์ไม่เกิน 5 ไฟล์ต่อรายการ) — ตามสถานการณ์: ถ้า
   **ไฟล์ไม่ถูกต้องหรือมีจำนวนไฟล์เกินที่กำหนด** → ระบบปฏิเสธการอัปโหลด (หรือไฟล์ส่วนเกิน) ทันทีพร้อม
   ข้อความ error ภาษาไทยที่ชัดเจนระบุสาเหตุ แนะนำให้ลดจำนวนไฟล์หรือแยกเป็นรายการใหม่ตามความเหมาะสม
   แล้ววนกลับไปขั้นตอนที่ 7 ให้อัปโหลดใหม่ ถ้า**ไฟล์ถูกต้องครบตามเงื่อนไข** → ไปขั้นตอนถัดไป
   ([[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-19]],
   [[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-22]])
9. ระบบอ่านข้อมูลจากใบเสร็จอัตโนมัติ (ยอดเงิน วันที่ หมวดค่าใช้จ่าย ชื่อร้าน/ผู้ขาย) — AI อ่านภาพ/PDF หน้าแรก
   พร้อมป้าย "AI suggestion" เฉพาะเมื่อ AI ทำงานจริง ผู้ให้บริการสลับได้ (OpenRouter / Ollama ในเครื่อง / proxy /
   custom) และถ้ามี OCR ภาษาไทยในเครื่องเปิดอยู่ ระบบส่งข้อความที่ OCR อ่านได้เข้า AI ประกอบภาพ (ใบเสร็จไม่ออกจากเครื่อง
   ถ้าใช้ AI ในเครื่อง) หรือสกัดยอด/วันที่ (พ.ศ.→ค.ศ.)/ชื่อร้านเองเมื่อไม่มี AI ถ้าไม่มี AI/OCR หรือเรียกล้มเหลว → ถอยกลับเป็น
   กรอกเองหรือข้อมูลสาธิตพร้อมแจ้งว่าใช้เส้นทางใด — หากผู้ให้บริการ OCR/AI ประมวลผลข้อมูลนอกราชอาณาจักรไทย ต้องมี
   มาตรการคุ้มครอง cross-border transfer และข้อตกลงประมวลผลข้อมูล (DPA) ตามเงื่อนไขที่กำหนด
   ([[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-02]],
   [[20261117-01-implemented-rule-engine-ai-and-admin#2. Functional Requirements|FR-30]],
   [[20260816-01-grant-receipt-verification#5. Non-Functional Requirements|NFR-01]],
   [[20260816-01-grant-receipt-verification#5. Non-Functional Requirements|NFR-06]],
   [[20260816-02-pdpa-compliance#5. Non-Functional Requirements|NFR-08]],
   [[20260816-02-pdpa-compliance#5. Non-Functional Requirements|NFR-09]],
   [[20261117-01-implemented-rule-engine-ai-and-admin#3. Non-Functional Requirements|NFR-12]],
   [[20261117-01-implemented-rule-engine-ai-and-admin#3. Non-Functional Requirements|NFR-14]])
10. ตรวจสอบและแก้ไขข้อมูลที่ AI/OCR อ่านได้ ก่อนกดส่งเข้าตรวจ (ทุกค่าแก้ไขได้)
    ([[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-03]])
11. ตามสถานการณ์: ถ้าโครงการ**มี**ประมาณการ → เลือก "ตัดจากรายการไหนในประมาณการ" (เลือกรายการแล้วระบบตั้งหมวด
    ให้ตามรายการนั้น) หรือเลือก "ไม่อยู่ในประมาณการ" — ต้องเลือกอย่างใดอย่างหนึ่งเสมอ ถ้า**ไม่มี**ประมาณการ → ข้ามไป
    (ผลตรวจจะแจ้งให้ไปอัปโหลดประมาณการแทนการปล่อยผ่านเงียบๆ)
    ([[20261117-01-implemented-rule-engine-ai-and-admin#2. Functional Requirements|FR-26]])
12. ติ๊กเอกสารแนบที่มีครบตามรายการตรวจสอบของหมวดค่าใช้จ่ายนั้น (ตรา "จ่ายแล้ว", ตราตรวจรับพัสดุ, รูปถ่ายพัสดุ,
    หนังสืออนุมัติก่อนดำเนินการ, กรรมการตรวจรับ 3 คนเมื่อยอดเกิน 100,000 บาท ฯลฯ ตามชุดเอกสารของหมวดนั้น) —
    ปัจจุบันเป็นการยืนยันด้วยตนเอง ยังไม่ตรวจจากไฟล์ที่แนบจริง
    ([[20261117-01-implemented-rule-engine-ai-and-admin#2. Functional Requirements|FR-27]])
13. ตามสถานการณ์ (ไม่บังคับ): ถ้า**ต้องการ** → กรอกยอดที่ลงไว้ในใบสรุปรายรับ-จ่ายโครงการเพื่อให้ระบบเทียบกับยอดใบเสร็จ
    ถ้า**ไม่กรอก** → ข้าม ไม่มีข้อค้นพบเรื่องนี้
