  (ต่างกันที่หน้าที่) ดูหัวข้อ 5.4

## 1. ภาพรวมสถาปัตยกรรม

**Grant Receipt Assistant** เป็นระบบ "ด่านตรวจก่อนสอบ" ให้นักวิจัยตรวจใบเสร็จก่อนยื่นเบิกจริงกับเจ้าหน้าที่การเงินของ
มหาวิทยาลัย (ซึ่งอยู่นอกระบบ) มี 2 บทบาทในแอป: **นักวิจัย/เจ้าของโครงการ** และ **Admin**
(ดู [[20260816-01-grant-receipt-verification#3. บทบาทผู้ใช้ (User Roles)]]) บวก**เครื่องมือนอกแอป**สำหรับผู้วิจัย/เจ้าของระบบ
(ชุดประเมินผล FR-34 — ไม่ใช่บทบาทที่ 3 ในแอป) หลักการออกแบบที่มีผลต่อโครงสร้าง:

- **โมเดลข้อมูลแยก 3 concept:** **แหล่งทุน (FundSource)** — Admin นำเข้า/ดูแลระเบียบ 1 แหล่งให้ทุนได้หลายโครงการ;
  **โครงการวิจัย (Project)** — นักวิจัยสร้างเอง เจ้าของ 1 คน ผูกกับแหล่งทุน (FR-23); **นักวิจัย (Researcher)** — ใบเสร็จผูกกับ
  Project ไม่ใช่ FundSource ตรงๆ Rule Engine ตรวจตามระเบียบของ FundSource ที่ Project สังกัด เวอร์ชัน active ณ วันที่ตรวจ
- **กฎตัดสิน AI ไม่ตัดสิน:** Rule Engine เป็น**โมดูลบริสุทธิ์** (ไม่แตะที่เก็บข้อมูล/หน้าจอ/เครือข่าย) ตัดสินผลทั้งหมด AI มีหน้าที่ 2 อย่างเท่านั้น
  คือ **เสนอค่าที่อ่านจากใบเสร็จ** (ผู้ใช้ตรวจแก้ได้ทุกค่า) และ **อธิบายผล** ที่กฎตัดสินแล้ว (ห้ามเปลี่ยนสถานะ ห้ามใช้ความรู้ภายนอก
  ห้ามอ้างว่าตรวจไฟล์ที่แนบ) — ความล้มเหลวของ AI ต้องไม่ขวางการบันทึกใบเสร็จ
- **ตรวจตามลำดับและแสดงข้อค้นพบทุกกลุ่ม:** ประมาณการที่อนุมัติ → ระเบียบแหล่งทุน → ใบสรุปรายรับ-จ่าย → เอกสารแนบ (Evidence Chain)
  สถานะที่แสดงคือข้อค้นพบที่รุนแรงที่สุด ทุกผลตรวจบันทึก reasonCode, เวอร์ชัน engine และกฎที่ใช้ (FR-24/FR-25, NFR-04)
- **ข้อมูลอ้างอิงที่กฎใช้อยู่ในที่เก็บข้อมูลหลัก** (แหล่งทุน/เวอร์ชันระเบียบ/รายการกฎ, ชุดเอกสาร, ประเภทเอกสาร) agent อธิบายผลดึงจากข้อมูลนี้
  เท่านั้น ทำให้ "ไม่แต่งกฎเอง" เป็นจริงโดยโครงสร้าง ไม่ใช่แค่คำสั่งใน prompt
- **ข้อมูลใบเสร็จของนักวิจัยอ่านได้โดยเจ้าของ และโดย Admin แบบอ่านอย่างเดียว (FR-33, NFR-05)** นักวิจัยต้องได้รับแจ้งเรื่องนี้ก่อนอัปโหลดครั้งแรก
  (ยินยอมแบบเบา FR-13/FR-14) ผู้ใช้ทั่วไปไม่เห็นเมนู Admin และการเลื่อนสิทธิ์เป็น Admin ทำนอกระบบเท่านั้น
- **ความเป็นส่วนตัวของเนื้อหาใบเสร็จ:** ผู้ให้บริการ AI/OCR เป็นของภายนอกหรือรันในเครื่องผู้ใช้ก็ได้ — ทางเลือกที่รันในเครื่องทำให้ใบเสร็จ
  ไม่ออกจากเครื่อง (NFR-14) ส่วนทางเลือกภายนอกยังต้องพิจารณา NFR-08/NFR-09 ที่ตั้งผู้ให้บริการยังเป็น open point
- **ไฟล์จริงของใบเสร็จอยู่ในที่เก็บไฟล์ภายนอกที่เป็นของผู้ใช้เอง** (FR-32) ไม่ใช่ในที่เก็บข้อมูลหลัก ที่เก็บข้อมูลหลักเก็บเพียงข้อมูลอ้างอิงไฟล์
- **ไม่มีบทบาท "เจ้าหน้าที่การเงิน"/"ผู้อนุมัติ" ในระบบ** (ตัดออกจากขอบเขตแล้ว) การ "ชี้แจง/ขออนุมัติ" เกิดนอกระบบ จุดสิ้นสุดของ flow
  คือไฟล์ export ที่ดาวน์โหลดออกไปนอกระบบ (FR-10 ยังเป็น Backlog)

### 2.3 แนวคิดข้อมูลหลักใน Primary Data Store (ระดับ conceptual — โครงสร้างจริงอยู่ที่ [[db-spec]])

- **Researcher/ผู้ใช้**, **FundSource** (+ เวอร์ชันระเบียบ + รายการกฎต่อหมวด, ปัจจุบันบางหมวดอ้างชุดเอกสาร), **Project** (เจ้าของ 1 คน, ผูก FundSource)
- **รายการประมาณการของโครงการ** (กลุ่ม/ชื่อรายการ/ตัวคูณ/หน่วยราคา/จำนวน/ยอดรวม/หมวดระเบียบที่จับคู่) — ปลายทาง FR-36: มี**เวอร์ชัน**ของประมาณการและเวอร์ชันล่าสุดเป็นตัวที่ใช้ตรวจ
- **ใบเสร็จ** (ผูก Project, ผูกรายการประมาณการหรือ "ไม่อยู่ในประมาณการ", ยอด/วันที่/หมวด/ร้าน, ยอดตามใบสรุป, เอกสารแนบที่ผู้ใช้ยืนยัน, คำอธิบาย, ผลตรวจพร้อมร่องรอยย้อนไปยังกฎ/เวอร์ชัน engine/ข้อค้นพบ) → ข้อมูลอ้างอิงไฟล์ (1:N, ลิงก์ในที่เก็บไฟล์ภายนอก) และ **agent log** (ประวัติการทำงานของ agent ต่อใบเสร็จ)
- **ชุดเอกสาร (Evidence Chain)** — ลำดับขั้นของประเภทเอกสาร/ตราที่ต้องมีตามหมวด (ก่อน/หลัง/พร้อมกัน, ทางเลือก, บังคับหรือไม่, ขั้นแบบมีเงื่อนไขตามยอด เช่น กรรมการตรวจรับเมื่อยอดเกินเกณฑ์) และ**ประเภทเอกสาร** (ฟิลด์ที่ต้องมี/ข้อตรวจความถูกต้อง/ที่มาของข้อกำหนด) — ใช้ร่วมข้ามแหล่งทุน
- **สถานะการยินยอมแบบเบา** (เวลาที่ยอมรับ) — ปลายทาง FR-15: Consent Record พร้อมเวอร์ชัน Privacy Notice
- **แหล่งทุน: สถานะใช้งาน/ปิดใช้งาน** (FR-35 Backlog) — แหล่งทุนที่ปิดใช้งานเก็บกฎไว้ครบ ไม่ปรากฏในรายการเลือกของโครงการใหม่ โครงการเดิมแสดงชื่อต่อได้

### 3.1 Journey 1 — อัปโหลดใบเสร็จ ตรวจ 4 กลุ่ม และรับคำอธิบายจนผ่านเกณฑ์

ลำดับตามการใช้งานจริง: เลือกโครงการ → (นำเข้าประมาณการ) → (เชื่อมต่อที่เก็บไฟล์) → อัปโหลด → อ่านด้วย AI/OCR → ตรวจทาน + เลือกรายการประมาณการ
+ ติ๊กเอกสาร + ยอดใบสรุป → กฎตัดสิน → agent อธิบาย ส่วนการตรวจไฟล์ (FR-19/FR-22 ตรวจที่ Client ตามมติผสม 5.4) ยังเป็น Backlog จึงวาดเป็นกล่องแยก

```mermaid
sequenceDiagram
    actor R as นักวิจัย
    participant C as Client
    participant DS as Primary Data Store
    participant EM as Estimate Manager
    participant EF as User-owned External File Store
    participant RD as Receipt Reader
    participant LO as Local OCR
    participant AG as AI Gateway
    participant LLM as ผู้ให้บริการ LLM
    participant RE as Rule Engine
    participant EA as Explanation Agent

    R->>C: เข้าสู่ระบบ
    C->>DS: อ่านสถานะยินยอมแบบเบา (FR-13, FR-14)
    alt ยังไม่เคยยินยอม
        C-->>R: แจ้งว่า Admin อ่านข้อมูลใบเสร็จได้แบบอ่านอย่างเดียว ขอติ๊กยืนยัน
        C->>DS: บันทึกเวลายินยอม
    end
    R->>C: เลือก/สร้างโครงการและผูกแหล่งทุน (FR-23)
    C->>DS: อ่านรายการแหล่งทุนที่ใช้งานอยู่ (FR-35 ปลายทาง ซ่อนแหล่งทุนที่ปิดใช้งานจากรายการเลือกโครงการใหม่)
    Note over C,DS: FR-35 ปลายทาง ถ้าโครงการเดิมผูกแหล่งทุนที่ปิดใช้งาน ยังตรวจต่อด้วยกฎที่เก็บไว้ แต่แสดงคำเตือนว่าแหล่งทุนปิดใช้งาน
    opt โครงการยังไม่มีประมาณการ
        R->>C: นำเข้าไฟล์ประมาณการ 17.2 (FR-26)
        C->>EM: แปลงเป็นรายการ + หน่วยราคา/จำนวน + เสนอหมวดระเบียบ
        R->>C: ตรวจ/แก้การจับคู่แล้วบันทึก
        EM->>DS: บันทึกรายการประมาณการ
    end
    opt ต้องการแนบไฟล์จริง
        R->>C: เชื่อมต่อที่เก็บไฟล์ของตนเอง (FR-32)
        C->>EF: ขออนุญาตแบบขอบเขตแคบ
    end
    Note over C,R: เตือนให้อัปโหลดครั้งละ 1 รายการ (FR-22 Backlog) และตรวจไฟล์ที่จุดเดียว (FR-19 Backlog)
    R->>C: เลือกไฟล์ใบเสร็จ
    C->>RD: ส่งไฟล์ให้อ่านข้อมูล (FR-02, FR-30)
    RD->>LO: ตรวจสถานะแล้วขอข้อความ OCR (เวลาจำกัดสั้น)
    alt Local OCR ใช้ได้
        LO-->>RD: บรรทัดข้อความ + ความมั่นใจ
    else ใช้ไม่ได้
        RD-->>RD: ข้าม OCR
    end
    alt มีผู้ให้บริการ AI ที่ตั้งไว้
        RD->>AG: ภาพ + ข้อความ OCR ขอค่า ยอด/วันที่/หมวด/ร้าน
        AG->>LLM: ส่งผ่านเส้นทางที่เลือก (ถ้าผ่านตัวกลางจะส่งตั๋วผู้ใช้แทนคีย์)
        LLM-->>AG: ค่าที่เสนอ
        AG-->>RD: ค่าที่เสนอ
        RD-->>C: แสดงพร้อมป้าย AI suggestion
    else ไม่มี AI หรือเรียกล้มเหลว
        RD-->>C: สกัดจากข้อความ OCR เอง หรือถอยกลับเป็นกรอกเอง/ข้อมูลสาธิต พร้อมแจ้งเส้นทางที่ใช้
    end
    R->>C: ตรวจ/แก้ทุกค่า (FR-03)
    opt โครงการมีประมาณการ
        R->>C: เลือกรายการที่จะตัดยอด หรือ ไม่อยู่ในประมาณการ (บังคับเลือก)
        C->>DS: อ่านยอดสะสมของรายการนั้น
    end
    R->>C: ติ๊กเอกสารแนบตามรายการของหมวด (FR-27) และกรอกยอดใบสรุป (FR-28 ไม่บังคับ)
    R->>C: กดส่งตรวจ
    C->>DS: โหลดกฎของแหล่งทุนที่โครงการสังกัด เวอร์ชัน active ณ วันนี้ + ชุดเอกสารของหมวด
    DS-->>C: ชุดกฎ (ทั้งเวอร์ชัน active)
    Note over C,RE: ปัจจุบัน Client เรียกโมดูลและบันทึกผลเอง ปลายทาง (Backlog) Client ส่งข้อมูลให้ Trusted Server Service เรียกโมดูลและบันทึกผลแทน กันการแก้ผลจากเบราว์เซอร์
    C->>RE: ใบเสร็จ + ชุดกฎ + ประมาณการ + ยอดใบสรุป + เอกสารที่ติ๊ก
    RE-->>C: สถานะ 4 ระดับ + reasonCode + ข้อค้นพบรายกลุ่ม + อ้างอิงระเบียบ + เวอร์ชัน engine
    C->>DS: บันทึกใบเสร็จพร้อมร่องรอยการตรวจ (NFR-04)
    opt แนบไฟล์จริง
        C->>EF: อัปโหลดไฟล์ในโฟลเดอร์ตามรหัสใบเสร็จ
        C->>DS: บันทึกข้อมูลอ้างอิงไฟล์
    end
    C->>EA: ขออธิบายผล (แยกขอบเขต ล้มเหลวได้โดยไม่ขวางการบันทึก)
    EA->>DS: อ่านชุดเอกสาร + ประเภทเอกสารของหมวดนั้น
    EA->>AG: ขอสรุปเป็นไทย ห้ามใช้ความรู้ภายนอก ห้ามเปลี่ยนสถานะ
    AG->>LLM: ส่งต่อ
    LLM-->>AG: คำอธิบาย
    AG-->>EA: คำอธิบาย
    EA->>DS: เขียนคำอธิบาย (ไม่แตะสถานะ) + บันทึก agent log
    C-->>R: แสดงสถานะ 4 ระดับ ข้อค้นพบ คำอธิบาย และอ้างอิงระเบียบ (FR-06)
    opt สถานะไม่ใช่ผ่าน
        R->>C: แก้ข้อมูล/ติ๊กเอกสารเพิ่ม/อัปโหลดใหม่ หรือไปชี้แจงขออนุมัติกับการเงินนอกระบบ (FR-07)
        Note over C,RE: วนกลับไปขั้นตอนกดส่งตรวจ
    end
```

```mermaid
sequenceDiagram

    participant C as Client
    participant B as Trusted Server Service (Backlog)
```

### 3.5 Journey 5 และ 7 — ถอนความยินยอม / ลบใบเสร็จของตนเอง (ปลายทางตาม FR-37)

ปัจจุบันสร้างเพียงปุ่มลบใบเสร็จ (ลบข้อมูลและข้อมูลอ้างอิงไฟล์ในที่เก็บข้อมูลหลักทันที ไม่ลบไฟล์จริง ไม่มีเงื่อนไข export-lock เพราะ Export ยังไม่มี ไม่มี Audit Trail)
การถอนความยินยอม (FR-16/FR-20) ยังเป็น Backlog แผนภาพนี้คือพฤติกรรมปลายทางที่ spec กำหนด

```mermaid
sequenceDiagram
    actor R as นักวิจัย
    participant C as Client
    participant B as Trusted Server Service (Backlog)
    participant EF as User-owned External File Store
    participant DS as Primary Data Store
    participant AT as Audit Trail Store

    alt ลบใบเสร็จรายใบ (FR-18) — ทำที่ Client
        R->>C: เลือกใบเสร็จที่จะลบ
        C->>DS: ตรวจสถานะ ถูก export แล้วหรือไม่
        alt ถูก export แล้ว
            C-->>R: ปิดกั้นการลบเอง แจ้งให้ยื่นคำร้องผ่านช่องทางภายนอกระบบ
        else ยังไม่ถูก export
            R->>C: ยืนยันลบ
            C->>EF: ลบไฟล์ของใบเสร็จนั้นด้วยสิทธิ์ระยะสั้นของผู้ใช้เอง (FR-37)
            alt ลบไฟล์ไม่สำเร็จ เช่น สิทธิ์หมดอายุ
                C-->>R: แจ้งเหตุผล ขอให้เชื่อมต่อใหม่แล้วลองอีกครั้ง ยังไม่ลบข้อมูลใดๆ ไม่มีไฟล์กำพร้า
            else ลบไฟล์สำเร็จ
                C->>DS: ลบใบเสร็จ ผลตรวจ agent log และข้อมูลอ้างอิงไฟล์
                C-->>R: แจ้งผลสำเร็จ
            end
        end
    else ถอนความยินยอม (FR-16/FR-20) — ลำดับบังคับ
        R->>C: กดถอนความยินยอม ระงับการอัปโหลดใหม่ทันที
        C->>EF: ขั้นที่ 1 ลบไฟล์ทั้งชุดที่ระบบสร้าง ด้วยสิทธิ์ระยะสั้นของผู้ใช้เอง (FR-37)
        alt ลบไฟล์ไม่สำเร็จ เช่น สิทธิ์หมดอายุ
            C-->>R: แจ้งเหตุผล ขอให้เชื่อมต่อใหม่แล้วลองอีกครั้ง ยังไม่ส่งคำสั่งลบข้อมูลในระบบ
        else ลบไฟล์สำเร็จครบ
            C->>B: ขั้นที่ 2 สั่งลบข้อมูลทั้งหมดของผู้ใช้
            B->>DS: ลบใบเสร็จ ผลตรวจ agent log ข้อมูลอ้างอิงไฟล์ จนเสร็จ แม้ผู้ใช้ปิดหน้าจอไปแล้ว
            B->>AT: บันทึกเหตุการณ์ถอน consent/ลบข้อมูล (NFR-04)
            B-->>C: แจ้งผลสำเร็จ (ถ้ายังเปิดหน้าจออยู่)
        end
    end
```

## 5. ประเด็นรอตัดสินใจ

### 5.1 ตำแหน่งของการตรวจสอบไฟล์อัปโหลด (FR-19) — มติ 2026-08-23 (เก็บเป็นประวัติ ถูกแทนที่บางส่วนโดย 5.4)

> **ถูกแทนที่ 2026-11-17:** มติผสมในหัวข้อ 5.4 ไม่สร้าง Backend Service เต็มรูปแบบ ผลคือการตรวจไฟล์ (FR-19/FR-22) อยู่ที่ Client
> ไม่ใช่เซิร์ฟเวอร์ — เนื้อหาด้านล่างเป็นประวัติการตัดสินใจเดิมเท่านั้น

เลือกในครั้งนั้น **แนวทาง B: Backend Service ตรวจสอบเท่านั้น (authoritative จุดเดียว)** Client ไม่ pre-check ขนาดไฟล์สูงสุด **5 MB ต่อไฟล์** และ
**5 ไฟล์ต่อรายการ** (FR-19/FR-22, เชื่อม NFR-06) ตัวเลือกที่เคยพิจารณา:

| แนวทาง | ข้อดี | ข้อเสีย |
|---|---|---|
| A. ตรวจที่ Client เท่านั้น | feedback เร็วที่สุด | หลีกเลี่ยง/ปลอมแปลงได้ ไม่ authoritative |
| **B. ตรวจที่ Backend Service เท่านั้น — เลือก** | เชื่อถือได้ จุดเดียวดูแลง่าย | ต้องรออัปโหลดเสร็จก่อนรู้ว่าผิด — บรรเทาด้วยขนาดสูงสุดที่เหมาะสม |
| C. ทั้งสองฝั่ง | UX เร็วและปลอดภัย | logic 2 ที่ต้องตรงกัน |

### 5.2 รูปแบบการสื่อสารกับ OCR/Rule Engine/LLM — ตัดสินใจแล้ว 2026-08-23: Synchronous

ยืนยัน **แนวทาง A: Synchronous request-response** ตลอด pipeline (ปัจจุบัน flow ที่สร้างแล้วเป็นแบบนี้ และมีทางถอยกลับเมื่อ AI/OCR ล้มเหลว)
แนวทาง B (asynchronous + สถานะกำลังประมวลผล) และ C (hybrid) เก็บไว้ทบทวนเมื่อ NFR-06/NFR-07 มีตัวเลขเป้าหมาย

### 5.3 ประเด็นสืบทอดจาก [[backlog]]

- ที่ตั้งผู้ให้บริการ OCR/LLM จริง (ในไทย/ต่างประเทศ) — กระทบ NFR-08/NFR-09
- ตัวเลขระยะเวลาเก็บข้อมูล (NFR-11) ยังเป็น TBD
- **[[technology-stack]] ยังไม่มีเนื้อหา** — เอกสารนี้ต้องคงความเป็น logical/conceptual แม้ตัดสิน stack แล้ว

### 5.4 ตำแหน่งฝั่งเซิร์ฟเวอร์ — **ตัดสินใจแล้ว 2026-11-17: แบบผสม** (ยืนยันโดยผู้ใช้ผ่าน AskUserQuestion)

เลือก **ตัวเลือก ค (ผสม)** "ผสม: 3 เรื่องนี้ไปเซิร์ฟเวอร์" — **แทนที่แผน Backend Service เต็มรูปแบบของ 5.1/5.2** (เก็บ 5.1/5.2 ไว้เป็นประวัติ)
ตัวเลือกที่เสนอ: ก) Backend Service เต็มรูปแบบ (บังคับกฎได้จริง แต่ต้องสร้าง/ดูแลมาก), ข) Client ทั้งหมด (ง่ายแต่ผลตรวจและการลบพึ่งเบราว์เซอร์),
ค) ผสม (สมดุล แต่มี 2 รูปแบบให้ดูแลคู่กัน)

**ไปอยู่ที่ Trusted Server Service ขนาดเล็ก (3 เรื่อง — ทั้งหมด Backlog ยังไม่ได้สร้าง):**
1. **คำนวณและบันทึกผลตรวจใบเสร็จ** เพื่อให้เบราว์เซอร์แก้ผลไม่ได้ (ปัจจุบันคำนวณที่ Client)
2. **ลบข้อมูลทั้งหมดเมื่อถอนความยินยอม** ให้เสร็จแม้ผู้ใช้ปิดหน้าจอ (FR-20)
3. **ส่งอีเมลแจ้งเตือน** (FR-09)

**ที่เหลือทั้งหมดอยู่ที่ Client** โดยกฎสิทธิ์ของที่เก็บข้อมูลหลักบังคับสิทธิ์เหมือนเดิม รวมถึงการตรวจไฟล์ (FR-19/FR-22), Export, Dashboard, สำเนาข้อมูล และการลบรายใบ
"ตัวกลางถือคีย์ AI" (NFR-12) เป็น component ฝั่งเซิร์ฟเวอร์ขนาดเล็กชนิดเดียวกัน (คนละหน้าที่) — ยอมรับข้อจำกัดว่าการตรวจไฟล์ที่ authoritative ฝั่งเซิร์ฟเวอร์ตามมติ 5.1 เดิมไม่เกิดขึ้น

**ลำดับบังคับของการถอนความยินยอม (FR-37 ข้อ 4):** Client ลบไฟล์ในที่เก็บไฟล์ภายนอกด้วยสิทธิ์ของนักวิจัยเอง **ก่อน** เมื่อสำเร็จครบจึงสั่ง Trusted Server Service
ลบข้อมูลในระบบ (เซิร์ฟเวอร์ลบเฉพาะข้อมูลในระบบ ไม่ถือข้อมูลรับรองของผู้ใช้) ถ้าลบไฟล์ไม่สำเร็จ ไม่ลบข้อมูลใดๆ ให้ผู้ใช้เชื่อมต่อใหม่แล้วลองอีกครั้ง

### 5.5 การตัดสินใจเรื่องฟีเจอร์ที่ยังเป็น Backlog (2026-11-17)

1. **FR-35 — ตัดสินแล้ว "ตรวจต่อ แต่เตือน":** ใบเสร็จใหม่ในโครงการเดิมที่ผูกแหล่งทุนที่ปิดใช้งานแล้ว ตรวจต่อด้วยกฎที่เก็บไว้ พร้อมคำเตือนว่าแหล่งทุนปิดใช้งาน
2. **FR-36 — ยังเปิด (ส่งต่อ db-spec):** รูปแบบเก็บเวอร์ชันประมาณการ (เก็บทั้งชุดต่อเวอร์ชัน หรือเก็บเฉพาะส่วนต่าง) และการแสดงประวัติ ตัดสินตอนออกแบบ [[db-spec]]
3. **FR-37 — ตัดสินแล้ว "ใช้สิทธิ์ของนักวิจัยเอง":** Client ลบไฟล์ด้วยสิทธิ์ระยะสั้นของนักวิจัย ถ้าหมดอายุให้เชื่อมต่อใหม่ ไม่เก็บข้อมูลรับรองผู้ใช้ไว้ที่เซิร์ฟเวอร์
   **ยังเปิด (รายละเอียด):** วิธีที่ Admin ดูไฟล์เมื่อเลิกแชร์แบบลิงก์ — ค่าเริ่มต้นออกแบบคือ**แชร์ตรงให้บัญชี Admin** (ยังไม่ได้ถามผู้ใช้ ต้องยืนยันรายละเอียดภายหลัง)
4. **NFR-10/NFR-04:** ไม่มีการบันทึกการเข้าถึงของ Admin ต่อใบเสร็จของนักวิจัยเป็นรายการ — ถ้าต้องการต้องเสนอเป็น requirement ผ่านผู้ใช้
