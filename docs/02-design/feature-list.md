# Feature List — Grant Receipt Assistant

จัดกลุ่ม Functional/Non-Functional Requirements จาก [[backlog]] (อ้างอิงต้นทางที่
[[20260816-01-grant-receipt-verification]] และ [[20260816-02-pdpa-compliance]]) เป็น "ฟีเจอร์"
ที่มีความหมายต่อผู้ใช้งานจริง สำหรับทีมออกแบบ/พัฒนาอ่านต่อได้ทันที ระบบมี 2 บทบาทผู้ใช้เท่านั้น:
**นักวิจัย/เจ้าของโครงการ** (ผู้ใช้หลัก) และ **Admin (ผู้ดูแลระบบ/ผู้อัปเดตระเบียบ)** (ดู
[[20260816-01-grant-receipt-verification#3. บทบาทผู้ใช้ (User Roles)]]) — ฟีเจอร์ด้าน PDPA/การ
คุ้มครองข้อมูลส่วนบุคคล (ฟีเจอร์ที่ 10-12) ไม่มีบทบาทใหม่เพิ่มเติม เป็นสิทธิ์/หน้าที่ที่ผูกกับบทบาท
นักวิจัย/เจ้าของโครงการเดิมทั้งหมด (ดู [[20260816-02-pdpa-compliance#3. บทบาทผู้ใช้ที่เกี่ยวข้อง]])

ระดับความสำคัญ MoSCoW แต่ละฟีเจอร์ map ตรงจากระดับความสำคัญของ backlog เสมอ: **สูง → Must
have, กลาง → Should have, ต่ำ → Could have** (ปัจจุบัน backlog ยังไม่มีรายการระดับ "ต่ำ" เลย
จึงยังไม่มีฟีเจอร์ใดเป็น Could have หรือ Won't have ในรอบนี้)

> **อัปเดต 2026-09-03:** ปรับคำศัพท์ทั้งไฟล์จาก "ทุนวิจัย/เจ้าของทุน" เป็น "โครงการวิจัย

## 1. อัปโหลดใบเสร็จและอ่านข้อมูลอัตโนมัติด้วย OCR

คำอธิบาย: นักวิจัยอัปโหลดไฟล์ภาพถ่าย (jpg/png) หรือไฟล์ PDF สแกนของใบเสร็จ ผูกกับ**โครงการวิจัย**
ของตนเอง ไม่ใช่ผูกตรงกับแหล่งทุน (fund source) โดยตรง — โครงการต้องถูกสร้าง/ผูกกับแหล่งทุนไว้ก่อน
แล้วผ่านฟีเจอร์ที่ 13 (Project Setup) — 1 รายการใบเสร็จ (ชุดเอกสารหลักฐานของค่าใช้จ่าย 1 เรื่อง) อาจประกอบด้วยมากกว่า 1 ไฟล์/แผ่น
(เช่น ค่ารถตู้ตามระเบียบมหาวิทยาลัยต้องมี "ใบสำคัญรับเงิน" + "สำเนาบัตรผู้รับเงิน" รวมกัน) สูงสุด
**5 ไฟล์ต่อรายการ** โดยต้องอัปโหลดไฟล์ทั้งหมดของค่าใช้จ่ายเรื่องเดียวกันพร้อมกันในครั้งเดียวและผูก
กับ record เดียวกัน ไม่ใช่แยกเป็นใบเสร็จคนละรายการ (ใบเสร็จ 1 แผ่นที่มีสินค้าหลายชิ้นจากร้านเดียวกัน
ยังนับเป็นรายการเดียว ไม่ต้องแยก) ระหว่างขั้นตอนอัปโหลด ระบบต้องแสดงข้อความเตือน/คำแนะนำให้นักวิจัย
เห็นว่าให้อัปโหลดครั้งละ 1 รายการเท่านั้น เพื่อป้องกันความสับสนอัปโหลดใบเสร็จหลายรายการปนกันในครั้ง
เดียว จากนั้นระบบอ่านข้อมูลสำคัญจากใบเสร็จภาษาไทยอัตโนมัติ ได้แก่ ยอดเงิน วันที่ หมวดค่าใช้จ่าย
และชื่อร้าน/ผู้ขาย (ถ้ามี) เพื่อลดภาระการกรอกข้อมูลเองและใช้เป็น input เข้า Rule Engine ต่อไป
ก่อนส่งไฟล์เข้าสู่กระบวนการ OCR ระบบต้องตรวจสอบความถูกต้องของไฟล์ก่อนเสมอ (ชนิดไฟล์ที่รองรับ,
ไฟล์ไม่เสียหาย/เปิดได้, ไม่เกินขนาดสูงสุด **5 MB ต่อไฟล์**, จำนวนไฟล์ไม่เกิน **5 ไฟล์ต่อรายการ**)
หากไม่ผ่านเงื่อนไขใดเงื่อนไขหนึ่ง ต้องปฏิเสธการอัปโหลด (หรือไฟล์ส่วนเกิน) ทันทีพร้อมข้อความ error
ภาษาไทยที่ชัดเจน แทนที่จะส่งต่อเข้า OCR แล้วเกิดผลลัพธ์ที่อธิบายไม่ได้
**สถานะที่สร้างแล้ว (FR-01/FR-02 เสร็จบางส่วน):** แนบไฟล์จริงผ่าน Google Drive ของผู้ใช้ (ฟีเจอร์ที่ 21) และการอ่านใบเสร็จ
ใช้ AI/OCR ในเครื่อง (ฟีเจอร์ที่ 17) — ส่วนการตรวจไฟล์ (FR-19) และหลายไฟล์ต่อรายการ (FR-22) ยังเป็น Backlog

## 3. ตรวจสอบใบเสร็จด้วย Rule Engine พร้อมคำอธิบายจาก LLM

คำอธิบาย: ระบบตรวจใบเสร็จเทียบกับระเบียบของ**แหล่งทุนที่โครงการของใบเสร็จนั้นสังกัดอยู่** (ไม่ใช่
ระเบียบเดียวรวมทั้งมหาวิทยาลัย) ที่ถูก encode ไว้ใน Rule-based Engine (เช่น หมวดค่าใช้จ่ายที่อนุญาต
วงเงินสูงสุดต่อหมวด เอกสารประกอบที่ต้องมี) โดยระเบียบที่ใช้ตรวจคือ**เวอร์ชันที่ active ณ วันที่ตรวจ
ใบเสร็จนั้น** ไม่ใช่เวอร์ชัน ณ วันเริ่มโครงการ — **Rule Engine
เป็นผู้ตัดสินใจ ไม่ใช่ LLM** จากนั้น LLM ทำหน้าที่แปลผลลัพธ์เป็นภาษาไทยที่คนไม่มีพื้นฐานการเงินเข้าใจ
ง่าย พร้อมคำแนะนำแก้ไขที่เป็นรูปธรรม และระบบแสดงสถานะใบเสร็จแต่ละใบ **4 ระดับ** (ผ่าน / ต้องแก้ไข /
ต้องชี้แจง/ขออนุมัติ / ไม่เข้าเงื่อนไข — เพิ่ม "ต้องชี้แจง/ขออนุมัติ" เมื่อ 2026-11-17 ดูฟีเจอร์ที่ 18)
พร้อมอ้างอิงข้อระเบียบที่ใช้ตัดสิน เพื่อความโปร่งใสและรองรับการโต้แย้ง (dispute) การ
ออกแบบนี้ตั้งใจกัน hallucination จาก LLM โดยตรง สถานะแสดงด้วยสี+ไอคอน+ข้อความเสมอ ไม่พึ่งสีอย่างเดียว
(NFR-13) — รายละเอียดการตัดสินอยู่ที่ฟีเจอร์ที่ 14–16, 18 และคำอธิบายจาก AI อยู่ที่ฟีเจอร์ที่ 19

## 4. แก้ไขและส่งใบเสร็จที่ไม่ผ่านตรวจซ้ำ

คำอธิบาย: เมื่อใบเสร็จมีสถานะ "ต้องแก้ไข" "ต้องชี้แจง/ขออนุมัติ" หรือ "ไม่เข้าเงื่อนไข" นักวิจัยกดปุ่ม "ส่งฉบับแก้ไข"
(มีในหน้า "ใบเสร็จของฉัน" และ "ประมาณการและใบเสร็จ"; ใบเสร็จที่ผ่านแล้วไม่มีปุ่ม) ซึ่งเปิดหน้าอัปโหลดในโหมดฉบับแก้ไข
แสดงสถานะ ยอด วันที่ หมวด ร้านค้า และคำแนะนำเดิม แล้วเลือก 1 ใน 2 วิธีต่อการส่งแต่ละครั้ง:
- **เพิ่มเอกสารที่ขาด** — แนบเฉพาะเอกสารที่ขาด ระบบ OCR เฉพาะไฟล์ใหม่ รวมกับข้อความ OCR ที่เก็บไว้ของไฟล์เดิมเพื่อตรวจ
  ยอด/วันที่/หมวด/ร้านค้ายังคงตามใบเดิม
- **แทนที่ทั้งชุด** — แนบไฟล์ใหม่ทั้งชุด อ่านและตรวจเหมือนอัปโหลดใหม่ ไฟล์เดิมถูกซ่อนแต่ไม่ลบ (ทำเครื่องหมายว่าถูกแทนที่
  และเก็บไฟล์ใน Drive ไว้เป็นประวัติ)

ใช้ใบเสร็จรหัสเดิม ล็อกโครงการ ต้องแนบไฟล์อย่างน้อย 1 ไฟล์ ไม่มีขั้นตอนแก้ไขช่องข้อมูลด้วยมือ (ตัดออกตั้งแต่ 2026-11-24 — ผู้ใช้
กรอกเองได้เพียงยอดในใบสรุปรายรับ-จ่ายแบบไม่บังคับ) ตรวจด้วยวิธีเดียวกับการอัปโหลดใหม่ (Rule Engine + LLM verdict) โดยประมาณการ
ไม่นับยอดเดิมของใบเสร็จใบนี้ซ้ำ จากนั้นหน้าผลลัพธ์แสดง "ฉบับแก้ไขครั้งที่ n · ผลก่อนแก้ไข: ..." ผลก่อนหน้าเก็บเป็นประวัติ และใบเสร็จแสดง
"แก้ไขแล้ว n ครั้ง" ส่งซ้ำได้จนกว่าจะผ่าน (วนกลับไปยังฟีเจอร์ที่ 3)

**สถานะที่สร้างแล้ว (2026-11-26):** สร้างเสร็จทั้งสองโหมด
**ข้อจำกัดปัจจุบัน:** ระบบตรวจรูปถ่ายตรวจรับพัสดุจากไฟล์ไม่ได้ (ตรวจจากข้อความ OCR เท่านั้น) รูปถ่ายที่แนบในฉบับแก้ไขจึงอาจยังแสดงว่าขาด — เจ้าของโครงการยังไม่ตัดสินใจแนวทางแก้

รหัส FR/NFR:

## 6. แจ้งเตือนใบเสร็จที่มีปัญหาค้างอยู่

คำอธิบาย: ระบบแจ้งเตือนนักวิจัยเมื่อมีใบเสร็จสถานะ "ต้องแก้ไข"/"ต้องชี้แจง/ขออนุมัติ"/"ไม่เข้าเงื่อนไข" ค้างอยู่ยังไม่ได้รับ
การแก้ไข เพื่อกระตุ้นให้แก้ก่อนสาย (ไม่รวมการแจ้งเตือนตามกำหนดเวลาส่งหลักฐานรายทุน ซึ่งถูกตัดออก
จากขอบเขต MVP นี้แล้ว — ดู [[20260816-01-grant-receipt-verification#2.2 ตัดออกจากขอบเขต MVP นี้ (ยืนยันโดยผู้ใช้เมื่อ 2026-08-16 — ดูหัวข้อ 7)]])

รหัส FR/NFR:
- [[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-09]] — แจ้งเตือนใบเสร็จที่มีปัญหายังไม่แก้ไข

บทบาทผู้ใช้: นักวิจัย/เจ้าของโครงการ
ระดับความสำคัญ (MoSCoW): Should have

## 7. Export รายงานสรุปใบเสร็จที่ผ่านตรวจแล้ว

คำอธิบาย: ระบบสร้าง/export ไฟล์รายงานสรุปใบเสร็จที่ผ่านการตรวจแล้วของทุน สำหรับให้นักวิจัยนำไป
ยื่นต่อเจ้าหน้าที่การเงินของมหาวิทยาลัยเอง เจ้าหน้าที่การเงิน**ไม่ใช่ user ของระบบนี้** เป็นเพียงผู้รับ
ไฟล์ที่ export ออกไปภายนอกระบบเท่านั้น (ตัดบทบาทนี้ออกจากระบบทั้งหมดแล้ว ยืนยันโดยผู้ใช้) หากทุนที่
เลือกยังไม่มีใบเสร็จสถานะ "ผ่าน" แม้แต่ใบเดียว ระบบต้องปิดการใช้งาน (disable) ปุ่ม Export ไว้ก่อน
พร้อมข้อความแจ้งเหตุผลที่กดไม่ได้ (เช่น "ยังไม่มีใบเสร็จที่ผ่านการตรวจสำหรับทุนนี้") เพื่อป้องกันไม่ให้
นักวิจัยส่งรายงานเปล่าให้เจ้าหน้าที่การเงินโดยไม่ตั้งใจ

รหัส FR/NFR:
- [[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-10]] — Export รายงานสรุปใบเสร็จที่ผ่านตรวจแล้ว
- [[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-21]] — ป้องกันการ Export รายงานเมื่อยังไม่มีใบเสร็จสถานะผ่าน

บทบาทผู้ใช้: นักวิจัย/เจ้าของโครงการ
ระดับความสำคัญ (MoSCoW): Must have

## 8. นำเข้า/อัปเดตระเบียบของแหล่งทุนเข้าสู่ Rule Engine (Admin)

คำอธิบาย: Admin นำเข้าและอัปเดตกฎ/เงื่อนไขจากระเบียบ**ต่อแหล่งทุนแต่ละแหล่ง** (แต่ละแหล่งทุนมีรหัส/
ระเบียบใบเสร็จเป็นของตัวเอง) เข้าสู่ Rule Engine เมื่อระเบียบของแหล่งทุนนั้นมีการเปลี่ยนแปลง โดยไม่ต้อง
retrain LLM ระบบบันทึกเวอร์ชันระเบียบที่ใช้ไว้เพื่อรองรับการตรวจสอบย้อนหลังเมื่อระเบียบเปลี่ยนแปลงตามเวลา
**สถานะที่สร้างแล้ว (เสร็จบางส่วน):** Admin เพิ่ม/ลบแหล่งทุนและแก้กฎรายหมวดผ่านหน้าจอ (ฟีเจอร์ที่ 22) และผลักชุดกฎ
เข้าระบบจริงผ่านปุ่มอัปเดตระเบียบ (ฟีเจอร์ที่ 20) — ยังไม่มี UI ประวัติเวอร์ชันและยังไม่มีการนำเข้าจากไฟล์ระเบียบโดยตรง

รหัส FR/NFR:
- [[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-11]] — นำเข้า/อัปเดตระเบียบทุนวิจัยเข้าสู่ Rule Engine (ต่อแหล่งทุนแต่ละแหล่ง)
- [[20260816-01-grant-receipt-verification#5. Non-Functional Requirements|NFR-04]] — Audit Trail: บันทึกเวอร์ชันระเบียบที่ใช้ตรวจ

บทบาทผู้ใช้: Admin (ผู้ดูแลระบบ/ผู้อัปเดตระเบียบ)
ระดับความสำคัญ (MoSCoW): Must have

## 9. จำกัดสิทธิ์การเข้าถึงข้อมูลตามเจ้าของ (Access Control)

คำอธิบาย: นักวิจัยเห็นและเข้าถึงได้เฉพาะใบเสร็จของ**โครงการที่ตนเองเป็นเจ้าของ**เท่านั้น (ไม่ใช่
"ใบเสร็จและทุนของตนเอง" เพราะกรรมสิทธิ์ที่แท้จริงอยู่ที่ระดับโครงการ ไม่ใช่แหล่งทุน) ส่วน Admin
**อ่านใบเสร็จของทุกคนได้แบบอ่านอย่างเดียว** (ระบุเจ้าของ) เพื่อรายงานเชิงบริหาร แต่เขียน/แก้ใบเสร็จของผู้อื่นไม่ได้
และผู้ใช้ทั่วไปไม่เห็นเมนู Admin — **นี่คือการกลับคำตัดสินใจเดิมของสเปคแรก** (เดิม Admin ไม่มีสิทธิ์เข้าถึงข้อมูลใบเสร็จ
ส่วนบุคคลเลย) ที่เจ้าของโปรเจกต์สั่งเมื่อ 2026-09-10 ดังนั้นนักวิจัยต้องได้รับแจ้งก่อนอัปโหลดครั้งแรกว่า Admin อ่านข้อมูลได้
(ผ่านการยินยอมแบบเบา ดูฟีเจอร์ที่ 10) การเลื่อนสิทธิ์เป็น Admin ทำผ่านคอนโซลเท่านั้น ไม่มี UI ให้ยกสิทธิ์ตนเอง
ฟีเจอร์นี้เป็นข้อจำกัดที่ครอบคลุมทุกฟีเจอร์ข้างต้น (cross-cutting) ไม่ใช่หน้าจอเฉพาะของตัวเอง
(หน้าจอ Admin อยู่ที่ฟีเจอร์ที่ 22)

รหัส FR/NFR:
- [[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-12]] — จำกัดสิทธิ์การเข้าถึงข้อมูลใบเสร็จตามเจ้าของโครงการ (แก้ตาม FR-33)
- [[20261117-01-implemented-rule-engine-ai-and-admin#2. Functional Requirements|FR-33]] — Admin อ่านใบเสร็จทุกคนแบบอ่านอย่างเดียว และจัดการกฎ/แหล่งทุน
- [[20260816-01-grant-receipt-verification#5. Non-Functional Requirements|NFR-05]] — Security/Access Control
- [[20260816-02-pdpa-compliance#5. Non-Functional Requirements|NFR-10]] — Data Breach Notification (Organizational/Process) เกี่ยวข้องกับมาตรการความปลอดภัยของข้อมูลใบเสร็จโดยรวม

บทบาทผู้ใช้: นักวิจัย/เจ้าของโครงการ, Admin (ผู้ดูแลระบบ/ผู้อัปเดตระเบียบ)
ระดับความสำคัญ (MoSCoW): Must have

## 10. แจ้ง Privacy Notice และจัดการความยินยอม (Consent Management)

คำอธิบาย: ก่อนใช้งานระบบครั้งแรกและก่อนอัปโหลดใบเสร็จครั้งแรก ระบบต้องแสดงประกาศความเป็นส่วนตัว
(Privacy Notice) แจ้งวัตถุประสงค์การเก็บ/ใช้ข้อมูล ตัวตนผู้ควบคุมข้อมูล (มหาวิทยาลัย) ระยะเวลาเก็บ
ข้อมูล (อ้างอิงนโยบายใน NFR-11) และสิทธิ์ของเจ้าของข้อมูล จากนั้นขอความยินยอมชัดแจ้ง (Explicit
Consent) ก่อนเริ่มเก็บ/ประมวลผลข้อมูลใบเสร็จ — นักวิจัยที่ไม่ให้ความยินยอมจะอัปโหลดใบเสร็จเข้าสู่ระบบ
ไม่ได้ ระบบบันทึกหลักฐานการให้ความยินยอม (วันที่ให้ความยินยอม, เวอร์ชัน Privacy Notice) ไว้เพื่อรองรับ
หลักความรับผิดชอบ (Accountability) และนักวิจัยสามารถถอนความยินยอมที่เคยให้ไว้ได้ทุกเมื่อผ่าน UI ซึ่ง
จะทำให้ระบบระงับการอัปโหลด/ประมวลผลใบเสร็จใหม่ทันที **และลบข้อมูลใบเสร็จ/ผลตรวจทั้งหมดของนักวิจัย
คนนั้นที่ระบบเก็บไว้ทันทีด้วย โดยไม่แยกตามสถานะ export** (เดิมเป็น open point ยืนยันคำตอบแล้วโดย
ผู้ใช้เมื่อ 2026-08-16 รอบ 3) — เหตุผลคือระบบเป็นเพียง "ด่านตรวจก่อนสอบ" (pre-check gate) ไม่ใช่
archival/official retention system ของหลักฐานทางการเงิน เมื่อถอนความยินยอมแล้วจึงไม่มีฐานทางกฎหมาย
เหลืออยู่ที่จะเก็บข้อมูลต่อได้ — ต่างจากการลบเฉพาะรายการในฟีเจอร์ที่ 12 (Right to Erasure) ซึ่งยังคง
เงื่อนไขจำกัดไม่ให้ลบใบเสร็จที่ export ไปแล้ว เพราะนักวิจัยยังไม่ได้ถอนความยินยอมทั้งหมดในกรณีนั้น
**สถานะที่สร้างแล้ว (เสร็จบางส่วน FR-13/FR-14):** เป็นการยินยอมแบบเบา — ติ๊กยืนยันครั้งเดียวก่อนอัปโหลดครั้งแรก
เก็บ `privacyConsentAcceptedAt` และแจ้งว่า Admin อ่านข้อมูลได้ ยังไม่มีหน้า Privacy Notice แยก ไม่มีบันทึกเวอร์ชันประกาศ
และไม่มีการถอนความยินยอม (FR-15/FR-16/FR-20 ยังเป็น Backlog) เมื่อสร้างการถอนความยินยอมแล้ว ต้องลบไฟล์ใน Google Drive
ของผู้ใช้ที่ระบบสร้างด้วย (ดูฟีเจอร์ที่ 21, FR-37 ยังไม่ได้สร้าง)

รหัส FR/NFR:
- [[20260816-02-pdpa-compliance#4. Functional Requirements|FR-13]] — แสดง Privacy Notice ก่อนใช้งานครั้งแรก/ก่อนอัปโหลดใบเสร็จ
- [[20260816-02-pdpa-compliance#4. Functional Requirements|FR-14]] — ขอความยินยอมชัดแจ้ง (Explicit Consent) ก่อนเก็บ/ประมวลผลข้อมูลใบเสร็จ
- [[20260816-02-pdpa-compliance#4. Functional Requirements|FR-15]] — บันทึกหลักฐานการให้ความยินยอม (Consent Record)
- [[20260816-02-pdpa-compliance#4. Functional Requirements|FR-16]] — ถอนความยินยอม (Withdraw Consent) และจัดการผลกระทบต่อกระบวนการตรวจใบเสร็จ
- [[20260816-02-pdpa-compliance#4. Functional Requirements|FR-20]] — ลบข้อมูลใบเสร็จ/ผลตรวจทั้งหมดทันทีเมื่อถอนความยินยอม (Withdraw Consent — Full Immediate Erasure)
- [[20260816-02-pdpa-compliance#5. Non-Functional Requirements|NFR-11]] — Data Retention & Deletion Policy (อ้างอิงในเนื้อหา Privacy Notice)

บทบาทผู้ใช้: นักวิจัย/เจ้าของโครงการ
ระดับความสำคัญ (MoSCoW): Must have

## 11. ขอเข้าถึง/ขอสำเนาข้อมูลส่วนบุคคลของตนเอง (Data Access & Portability)

คำอธิบาย: นักวิจัยขอสำเนาข้อมูลส่วนบุคคลทั้งหมดที่ระบบเก็บไว้เกี่ยวกับตนเอง (ข้อมูลใบเสร็จ ผลตรวจ
และประวัติการให้ความยินยอม) ผ่าน UI ของระบบ ในรูปแบบที่อ่าน/นำไปใช้ต่อได้ ฟีเจอร์นี้แยกจากฟีเจอร์ที่ 7
(Export รายงานสรุปใบเสร็จที่ผ่านตรวจแล้วสำหรับยื่นเจ้าหน้าที่การเงิน) โดยเจตนา เพราะเป็นสำเนาข้อมูล
ส่วนบุคคลครบถ้วนตามสิทธิ์ PDPA ไม่ใช่รายงานสรุปสำหรับใช้ยื่นภายนอก

รหัส FR/NFR:
- [[20260816-02-pdpa-compliance#4. Functional Requirements|FR-17]] — ขอเข้าถึง/ขอสำเนาข้อมูลใบเสร็จส่วนบุคคลของตนเอง (Data Subject Access & Portability)

บทบาทผู้ใช้: นักวิจัย/เจ้าของโครงการ
ระดับความสำคัญ (MoSCoW): Should have

## 12. ลบข้อมูลใบเสร็จของตนเองด้วยตนเอง (Right to Erasure)

คำอธิบาย: นักวิจัยลบข้อมูลใบเสร็จของตนเองได้เองผ่าน UI โดยตรง **เงื่อนไข:** ลบได้เฉพาะใบเสร็จที่ยังไม่
ถูกรวมอยู่ใน export รายงาน (ฟีเจอร์ที่ 7) ที่ส่งให้เจ้าหน้าที่การเงินไปแล้ว — การลบเองผ่าน UI จะถูก
ปิดกั้นสำหรับกรณีนี้ และต้องยื่นคำร้องผ่านช่องทาง Admin/DPO ภายนอกระบบแทน **(เหตุผลปรับปรุงเมื่อ
2026-08-16 รอบ 3):** ไม่ใช่เพราะต้องเก็บหลักฐานทางการเงินอย่างเป็นทางการ (ระบบนี้เป็นเพียง
"ด่านตรวจก่อนสอบ" ไม่ใช่ archival/official retention system) แต่เพื่อรักษา **Audit Trail และป้องกัน
การลบหลักฐานหนีความรับผิดหลังยื่นเบิกไปแล้ว** เนื่องจากใบเสร็จที่ export ไปแล้วอยู่ระหว่างกระบวนการ
เบิกจ่ายจริงภายนอกระบบที่อาจต้องอ้างอิงย้อนกลับมาตรวจสอบ/รองรับข้อโต้แย้ง (dispute) ได้ (สอดคล้อง
ฟีเจอร์ที่ 3 เรื่อง Explainability/Audit Trail) — ต่างจากฟีเจอร์ที่ 10 (FR-20) ซึ่งเป็นการถอนความยินยอม
ทั้งหมด จึงลบได้ทันทีไม่มีเงื่อนไขนี้ เพราะไม่มีฐานทางกฎหมายเหลืออยู่ที่จะเก็บข้อมูลต่อ
**สถานะที่สร้างแล้ว (เสร็จบางส่วน):** ปุ่มลบใบเสร็จลบถาวรทันทีทั้งใบเสร็จและเอกสารไฟล์ใน Firestore ยังไม่มีเงื่อนไข
"ห้ามลบถ้า export แล้ว" (เพราะ Export ยังไม่ได้สร้าง) ไม่ลบไฟล์จริงใน Google Drive และไม่มี workflow คำขอ/Audit Trail (การลบไฟล์ใน Drive ตามใบเสร็จที่ลบ
เป็นพฤติกรรมที่ยังไม่ได้สร้าง ดูฟีเจอร์ที่ 21, FR-37)

รหัส FR/NFR:
- [[20260816-02-pdpa-compliance#4. Functional Requirements|FR-18]] — ลบ/ขอลบข้อมูลใบเสร็จของตนเองด้วยตนเองผ่าน UI (Right to Erasure)
- [[20260816-02-pdpa-compliance#5. Non-Functional Requirements|NFR-11]] — Data Retention & Deletion Policy (เงื่อนไขจำกัดการลบเองเฉพาะใบเสร็จที่ยังไม่ถูก export)

บทบาทผู้ใช้: นักวิจัย/เจ้าของโครงการ
ระดับความสำคัญ (MoSCoW): Must have

## 13. จัดการข้อมูลโครงการวิจัยและผูกกับแหล่งทุน (Project Setup)

คำอธิบาย: นักวิจัยสร้าง/จัดการข้อมูลโครงการวิจัยของตนเอง (อย่างน้อยชื่อโครงการ) และเลือกผูกโครงการ
เข้ากับ**แหล่งทุน** (fund source) ที่โครงการได้รับ จากรายการแหล่งทุนที่ Admin นำเข้าไว้ใน Rule Engine

## 14. นำเข้าประมาณการโครงการ (ตาราง 17.2) และตรวจกับประมาณการ

คำอธิบาย: การเงินตรวจใบเสร็จกับประมาณการที่อนุมัติของโครงการก่อน แล้วจึงตรวจกับระเบียบ นักวิจัยนำเข้า
ไฟล์ตารางประมาณการ 17.2 ของมหาวิทยาลัย (.xlsx/.csv) ที่หน้าโครงการ ระบบแปลงเป็นรายการประมาณการและจับคู่หมวดระเบียบให้
(แก้เองได้ก่อนบันทึก) เมื่อส่งใบเสร็จ นักวิจัยเลือกว่าตัดจากรายการใดในประมาณการ (หรือ "ไม่อยู่ในประมาณการ")
ระบบตรวจ: ไม่อยู่ในประมาณการ หรือยอดสะสมเกิน 100% ของรายการ → **ต้องชี้แจง/ขออนุมัติ**, อ่านจำนวนหน่วยจากช่องตัวคูณ
แล้วตรวจอัตรา×จำนวนเทียบเพดานระเบียบ และเตือนตอนนำเข้าถ้าหน่วยราคา×จำนวนไม่เท่ายอดรวม มีหน้าแสดงยอดใช้ไป/คงเหลือ/% รายรายการ
ถ้าไม่มีประมาณการหรือรายการไม่มีจำนวนหน่วย ผลตรวจต้องบอกให้อัปโหลด/อัปโหลดใหม่ ไม่ปล่อยผ่านเงียบๆ

**พฤติกรรมที่ยังไม่ได้สร้าง (FR-36 สถานะ Backlog):** เมื่อนำเข้าประมาณการ 17.2 ซ้ำ ต้อง (1) เก็บเวอร์ชันเก่าไว้เป็นประวัติ ไม่เขียนทับ
(2) ย้ายใบเสร็จที่เคยผูกอยู่ไปจับคู่กับรายการของเวอร์ชันล่าสุด โดยจับคู่ด้วยชื่อรายการ + หมวดระเบียบ ถ้าจับคู่ไม่ได้ให้นักวิจัยเลือกรายการเอง
และบล็อกการบันทึกจนกว่าใบเสร็จที่ผูกอยู่ทุกใบจะถูกจับคู่ครบ (3) ยอดใช้ไป/คงเหลือและการตรวจ "เกิน 100%" ใช้เวอร์ชันล่าสุดเสมอ
**พฤติกรรมปัจจุบัน:** การนำเข้าซ้ำแทนที่ทุกรายการตามลำดับ ใบเสร็จเก่าอาจเชื่อมผิดรายการ ระบบแค่เตือน

## 15. ตรวจความครบของเอกสารแนบตามชุดเอกสาร (Evidence Chain)

> **ตั้งแต่ 2026-11-24:** เอกสาร/ตราที่มีมาจากการตรวจพบในข้อความ OCR (FR-39) แทนการติ๊กเอง ซึ่งเป็นแผนแรกที่เก็บไว้

คำอธิบาย: แต่ละหมวดค่าใช้จ่ายผูกกับชุดเอกสารที่ต้องมี ระบบแสดงรายการตรวจสอบ (checklist) ให้นักวิจัยติ๊กว่ามีเอกสารใดแล้ว
และตรวจว่าครบ ครอบคลุมตรา "จ่ายแล้ว" ตราตรวจรับพัสดุ รูปถ่ายพัสดุ หนังสืออนุมัติก่อนดำเนินการ (ค่าตอบแทน/เดินทาง/จ้างตาม TOR/ครุภัณฑ์)
และกรรมการตรวจรับ 3 คนเมื่อยอดเกิน 100,000 บาท (การเงินยืนยัน) ขั้นที่รับเอกสารทางเลือกได้ (เช่น ค่าที่พักเหมาจ่ายใช้ วจ.2 อย่างเดียวได้)

## 21. แนบไฟล์จริงผ่าน Google Drive ของผู้ใช้

"ผู้ที่มีลิงก์ดูได้" (2) เมื่อนักวิจัยลบใบเสร็จ (ฟีเจอร์ที่ 12) ต้องลบไฟล์ที่เกี่ยวข้องใน Drive ด้วย (3) เมื่อถอนความยินยอม
(ฟีเจอร์ที่ 10) ต้องลบไฟล์ใน Drive ทั้งหมดของผู้ใช้ที่ระบบสร้าง (4) ถ้าลบไฟล์ใน Drive ไม่สำเร็จ (เช่น โทเค็นหมดอายุ) ต้องแจ้งผู้ใช้
ไม่ล้มเหลวเงียบ **พฤติกรรมปัจจุบัน:** ใครมีลิงก์เปิดดูได้ และการลบใบเสร็จลบแค่ข้อมูลใน Firestore

รหัส FR/NFR:
- [[20261117-01-implemented-rule-engine-ai-and-admin#2. Functional Requirements|FR-32]] — แนบไฟล์จริงผ่าน Google Drive ของผู้ใช้
- [[20261117-02-fund-source-deactivation-estimate-versioning-drive-privacy#2. Functional Requirements|FR-37]] — จำกัดผู้ดูไฟล์ Drive (เจ้าของ+Admin) และลบไฟล์ตามเมื่อลบใบเสร็จ/ถอนความยินยอม (ยังไม่ได้สร้าง)
- [[20261117-02-fund-source-deactivation-estimate-versioning-drive-privacy#3. Non-Functional Requirements|NFR-15]] — Privacy: ขอบเขตการเข้าถึงและการลบไฟล์แนบ (ยังไม่ได้สร้าง)

บทบาทผู้ใช้: นักวิจัย/เจ้าของโครงการ
ระดับความสำคัญ (MoSCoW): Must have

## 22. Admin Dashboard อ่านใบเสร็จทุกคนแบบอ่านอย่างเดียว และจัดการแหล่งทุน/กฎ

คำอธิบาย: Admin เห็นรายละเอียดใบเสร็จของทุกคน (ระบุเจ้าของ) ผ่าน Admin Dashboard พร้อมสรุปตามสถานะ/หมวด/แหล่งทุน อ่านได้อย่างเดียว
เขียน/แก้ใบเสร็จของผู้อื่นไม่ได้ ผู้ใช้ทั่วไปไม่เห็นเมนู Admin และ Admin จัดการแหล่งทุน (เพิ่ม/ลบ) และกฎรายหมวดได้
(ต่อยอดฟีเจอร์ที่ 8 และ 20) ต้องแจ้งนักวิจัยก่อนอัปโหลดครั้งแรกว่า Admin อ่านข้อมูลได้ (ฟีเจอร์ที่ 10)

**พฤติกรรมที่ยังไม่ได้สร้าง (FR-35 สถานะ Backlog ระดับสูง):** Admin "ปิดใช้งาน" แหล่งทุนแทนการลบถาวร แหล่งทุนที่ปิดใช้งานเก็บกฎ
(`ruleVersions`/`ruleItems`) ไว้ครบเพื่อย้อนตรวจใบเสร็จเก่า ไม่แสดงในรายการเลือกแหล่งทุนตอนสร้างโครงการใหม่ (ฟีเจอร์ที่ 13) โครงการเดิมยังแสดงชื่อ
แหล่งทุนตามปกติ และ Admin เปิดใช้งานกลับได้ ส่วนพฤติกรรมของใบเสร็จใหม่ในโครงการเดิมที่ผูกกับแหล่งทุนที่ปิดใช้งาน (ตรวจต่อหรือบล็อก) **ยังไม่ได้กำหนด**
ต้องตัดสินตอนออกแบบ **พฤติกรรมปัจจุบัน:** ลบแหล่งทุนแบบ cascade ถาวร ไม่ตรวจโครงการที่ใช้อยู่

รหัส FR/NFR:
- [[20261117-01-implemented-rule-engine-ai-and-admin#2. Functional Requirements|FR-33]] — Admin อ่านใบเสร็จทุกคนแบบอ่านอย่างเดียว และจัดการกฎ/แหล่งทุน
- [[20261117-02-fund-source-deactivation-estimate-versioning-drive-privacy#2. Functional Requirements|FR-35]] — ปิดใช้งานแหล่งทุนแทนการลบจริง (ยังไม่ได้สร้าง)

บทบาทผู้ใช้: Admin (ผู้ดูแลระบบ/ผู้อัปเดตระเบียบ)
ระดับความสำคัญ (MoSCoW): Must have

## 23. ชุดประเมินผลสำหรับวิทยานิพนธ์ (รันนอกแอป)

คำอธิบาย: เครื่องมือนอกระบบที่เทียบผลของระบบกับผลที่เจ้าหน้าที่การเงินตัดสินจากไฟล์เคส (CSV) รายงาน accuracy, Cohen's kappa,
macro F1, จำนวนปัญหาที่ระบบพลาด (missed), จำนวนแจ้งเตือนเกิน (false alarm) และเทียบกับ AI ตัดสินเองล้วน (baseline) ที่ได้กฎชุดเดียวกัน
เขียนผลเป็นไฟล์รายงาน ข้อมูลจริงห้ามเข้า git **ข้อจำกัด (เสร็จบางส่วน):** ยังไม่มีข้อมูลจริง (รอ EC) มีแค่เคสสมมติ
และยังไม่ได้รัน baseline กับ API ที่เสียเงิน ผู้ใช้เครื่องมือนี้คือเจ้าของระบบ/ผู้วิจัยเท่านั้น ไม่ใช่บทบาทที่ 3 ในแอป

รหัส FR/NFR:
- [[20261117-01-implemented-rule-engine-ai-and-admin#2. Functional Requirements|FR-34]] — ชุดประเมินผลสำหรับวิทยานิพนธ์

บทบาทผู้ใช้: ผู้วิจัย/เจ้าของระบบ (เครื่องมือนอกแอป ไม่ใช่บทบาทในแอป)
ระดับความสำคัญ (MoSCoW): Should have
