## 1. อัปโหลดใบเสร็จและอ่านข้อมูลอัตโนมัติด้วย OCR

คำอธิบาย: นักวิจัยอัปโหลดไฟล์ภาพถ่าย (jpg/png) หรือไฟล์ PDF สแกนของใบเสร็จ ผูกกับ**โครงการวิจัย**
ของตนเอง ไม่ใช่ผูกตรงกับแหล่งทุน (fund source) โดยตรง — โครงการต้องถูกสร้าง/ผูกกับแหล่งทุนไว้ก่อน
แล้วผ่านฟีเจอร์ที่ 13 (Project Setup) — 1 รายการใบเสร็จ (ชุดเอกสารหลักฐานของค่าใช้จ่าย 1 เรื่อง) อาจประกอบด้วยมากกว่า 1 ไฟล์/แผ่น
(เช่น ค่ารถตู้ตามระเบียบมหาวิทยาลัยต้องมี "ใบสำคัญรับเงิน" + "สำเนาบัตรผู้รับเงิน" รวมกัน) สูงสุด
**5 ไฟล์ต่อรายการ** โดยต้องอัปโหลดไฟล์ทั้งหมดของค่าใช้จ่ายเรื่องเดียวกันพร้อมกันในครั้งเดียวและผูก
กับ record เดียวกัน ไม่ใช่แยกเป็นใบเสร็จคนละรายการ (ใบเสร็จ 1 แผ่นที่มีสินค้าหลายชิ้นจากร้านเดียวกัน
ยังนับเป็นรายการเดียว ไม่ต้องแยก) ระหว่างขั้นตอนอัปโหลด ระบบต้องแสดงข้อความเตือน/คำแนะนำให้นักวิจัย
เห็นว่าให้อัปโหลดครั้งละ 1 รายการเท่านั้น เพื่อป้องกันความสับสนอัปโหลดใบเสร็จหลายรายการปนกันในครั้ง
เดียว จากนั้นระบบอ่านข้อมูลสำคัญจากใบเสร็จภาษาไทยอัตโนมัติ ได้แก่ ยอดเงิน วันที่ หมวดค่าใช้จ่าย
และชื่อร้าน/ผู้ขาย (ถ้ามี) เพื่อลดภาระการกรอกข้อมูลเองและใช้เป็น input เข้า Rule Engine ต่อไป
ก่อนส่งไฟล์เข้าสู่กระบวนการ OCR ระบบต้องตรวจสอบความถูกต้องของไฟล์ก่อนเสมอ (ชนิดไฟล์ที่รองรับ,
ไฟล์ไม่เสียหาย/เปิดได้, ไม่เกินขนาดสูงสุด **5 MB ต่อไฟล์**, จำนวนไฟล์ไม่เกิน **5 ไฟล์ต่อรายการ**)
หากไม่ผ่านเงื่อนไขใดเงื่อนไขหนึ่ง ต้องปฏิเสธการอัปโหลด (หรือไฟล์ส่วนเกิน) ทันทีพร้อมข้อความ error
ภาษาไทยที่ชัดเจน แทนที่จะส่งต่อเข้า OCR แล้วเกิดผลลัพธ์ที่อธิบายไม่ได้

รหัส FR/NFR:
- [[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-01]] — อัปโหลดใบเสร็จ (ผูกกับโครงการวิจัย ไม่ใช่แหล่งทุนโดยตรง)
- [[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-02]] — OCR อ่านข้อมูลใบเสร็จอัตโนมัติ
- [[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-19]] — ตรวจสอบและปฏิเสธไฟล์อัปโหลดที่ไม่ถูกต้อง (File Upload Validation)
- [[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-22]] — อัปโหลดใบเสร็จแบบหลายไฟล์ต่อ 1 รายการ (Multi-file Receipt Bundle)
- [[20260816-01-grant-receipt-verification#5. Non-Functional Requirements|NFR-01]] — OCR ต้องรองรับภาษาไทยเต็มรูปแบบ
- [[20260816-01-grant-receipt-verification#5. Non-Functional Requirements|NFR-06]] — เวลาในการประมวลผล OCR (เป้าหมายตัวเลขยังไม่กำหนด)
- [[20260816-01-grant-receipt-verification#5. Non-Functional Requirements|NFR-07]] — ปริมาณใบเสร็จที่ระบบต้องรองรับ (เป้าหมายตัวเลขยังไม่กำหนด)
- [[20260816-02-pdpa-compliance#5. Non-Functional Requirements|NFR-08]] — Cross-border Data Transfer (conditional หากผู้ให้บริการ OCR ประมวลผลข้อมูลนอกราชอาณาจักรไทย)
- [[20260816-02-pdpa-compliance#5. Non-Functional Requirements|NFR-09]] — Data Processing Agreement กับผู้ให้บริการ OCR ภายนอก (Organizational)

## 2. ตรวจสอบและแก้ไขข้อมูลก่อนส่งตรวจ

คำอธิบาย: ก่อนกดส่งข้อมูลเข้า Rule Engine นักวิจัยตรวจทานและแก้ไขข้อมูลที่ OCR อ่านได้ (ยอดเงิน
วันที่ หมวดค่าใช้จ่าย ชื่อร้าน) เพื่อป้องกันผลตรวจผิดพลาดจากกรณี OCR อ่านตัวเลข/ข้อความผิด ซึ่งจะ
ทำให้ผลตรวจจาก Rule Engine ในขั้นถัดไปคลาดเคลื่อนไปด้วย

รหัส FR/NFR:
- [[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-03]] — ตรวจสอบ/แก้ไขข้อมูลจาก OCR ก่อนส่งตรวจ

บทบาทผู้ใช้: นักวิจัย/เจ้าของโครงการ
ระดับความสำคัญ (MoSCoW): Must have

## 3. ตรวจสอบใบเสร็จด้วย Rule Engine พร้อมคำอธิบายจาก LLM

คำอธิบาย: ระบบตรวจใบเสร็จเทียบกับระเบียบของ**แหล่งทุนที่โครงการของใบเสร็จนั้นสังกัดอยู่** (ไม่ใช่
ระเบียบเดียวรวมทั้งมหาวิทยาลัย) ที่ถูก encode ไว้ใน Rule-based Engine (เช่น หมวดค่าใช้จ่ายที่อนุญาต
วงเงินสูงสุดต่อหมวด เอกสารประกอบที่ต้องมี) โดยระเบียบที่ใช้ตรวจคือ**เวอร์ชันที่ active ณ วันที่ตรวจ
ใบเสร็จนั้น** ไม่ใช่เวอร์ชัน ณ วันเริ่มโครงการ — **Rule Engine
เป็นผู้ตัดสินใจ ไม่ใช่ LLM** จากนั้น LLM ทำหน้าที่แปลผลลัพธ์เป็นภาษาไทยที่คนไม่มีพื้นฐานการเงินเข้าใจ
ง่าย พร้อมคำแนะนำแก้ไขที่เป็นรูปธรรม และระบบแสดงสถานะใบเสร็จแต่ละใบ (ผ่าน / ต้องแก้ไข / ไม่เข้า
เงื่อนไข) พร้อมอ้างอิงข้อระเบียบที่ใช้ตัดสิน เพื่อความโปร่งใสและรองรับการโต้แย้ง (dispute) การ
ออกแบบนี้ตั้งใจกัน hallucination จาก LLM โดยตรง

รหัส FR/NFR:
- [[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-04]] — ตรวจใบเสร็จด้วย Rule-based Engine (อ้างอิงระเบียบของแหล่งทุนที่โครงการสังกัด)
- [[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-05]] — LLM สรุปผลตรวจเป็นภาษาที่เข้าใจง่าย
- [[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-06]] — แสดงสถานะใบเสร็จรายใบพร้อมเหตุผลอ้างอิงระเบียบ
- [[20260816-01-grant-receipt-verification#5. Non-Functional Requirements|NFR-01]] — คำอธิบายจาก LLM ต้องเป็นภาษาไทย

- [[20260816-02-pdpa-compliance#5. Non-Functional Requirements|NFR-09]] — Data Processing Agreement กับผู้ให้บริการ LLM ภายนอก (Organizational)

## 7. Export รายงานสรุปใบเสร็จที่ผ่านตรวจแล้ว

คำอธิบาย: ระบบสร้าง/export ไฟล์รายงานสรุปใบเสร็จที่ผ่านการตรวจแล้วของทุน สำหรับให้นักวิจัยนำไป
ยื่นต่อเจ้าหน้าที่การเงินของมหาวิทยาลัยเอง เจ้าหน้าที่การเงิน**ไม่ใช่ user ของระบบนี้** เป็นเพียงผู้รับ
ไฟล์ที่ export ออกไปภายนอกระบบเท่านั้น (ตัดบทบาทนี้ออกจากระบบทั้งหมดแล้ว ยืนยันโดยผู้ใช้) หากทุนที่
เลือกยังไม่มีใบเสร็จสถานะ "ผ่าน" แม้แต่ใบเดียว ระบบต้องปิดการใช้งาน (disable) ปุ่ม Export ไว้ก่อน
พร้อมข้อความแจ้งเหตุผลที่กดไม่ได้ (เช่น "ยังไม่มีใบเสร็จที่ผ่านการตรวจสำหรับทุนนี้") เพื่อป้องกันไม่ให้
นักวิจัยส่งรายงานเปล่าให้เจ้าหน้าที่การเงินโดยไม่ตั้งใจ

รหัส FR/NFR:
- [[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-10]] — Export รายงานสรุปใบเสร็จที่ผ่านตรวจแล้ว
- [[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-21]] — ป้องกันการ Export รายงานเมื่อยังไม่มีใบเสร็จสถานะผ่าน

บทบาทผู้ใช้: นักวิจัย/เจ้าของโครงการ

## 8. นำเข้า/อัปเดตระเบียบของแหล่งทุนเข้าสู่ Rule Engine (Admin)

คำอธิบาย: Admin นำเข้าและอัปเดตกฎ/เงื่อนไขจากระเบียบ**ต่อแหล่งทุนแต่ละแหล่ง** (แต่ละแหล่งทุนมีรหัส/
ระเบียบใบเสร็จเป็นของตัวเอง) เข้าสู่ Rule Engine เมื่อระเบียบของแหล่งทุนนั้นมีการเปลี่ยนแปลง โดยไม่ต้อง
retrain LLM ระบบบันทึกเวอร์ชันระเบียบที่ใช้ไว้เพื่อรองรับการตรวจสอบย้อนหลังเมื่อระเบียบเปลี่ยนแปลงตามเวลา

รหัส FR/NFR:
- [[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-11]] — นำเข้า/อัปเดตระเบียบทุนวิจัยเข้าสู่ Rule Engine (ต่อแหล่งทุนแต่ละแหล่ง)
- [[20260816-01-grant-receipt-verification#5. Non-Functional Requirements|NFR-04]] — Audit Trail: บันทึกเวอร์ชันระเบียบที่ใช้ตรวจ

บทบาทผู้ใช้: Admin (ผู้ดูแลระบบ/ผู้อัปเดตระเบียบ)

## 9. จำกัดสิทธิ์การเข้าถึงข้อมูลตามเจ้าของ (Access Control)

คำอธิบาย: นักวิจัยเห็นและเข้าถึงได้เฉพาะใบเสร็จของ**โครงการที่ตนเองเป็นเจ้าของ**เท่านั้น (ไม่ใช่
"ใบเสร็จและทุนของตนเอง" เพราะกรรมสิทธิ์ที่แท้จริงอยู่ที่ระดับโครงการ ไม่ใช่แหล่งทุน) ส่วน Admin ไม่มี
สิทธิ์เข้าถึงข้อมูลใบเสร็จส่วนบุคคลของนักวิจัยเลย จำกัดขอบเขตเฉพาะการจัดการแหล่งทุน/ระเบียบ/กฎใน
Rule Engine — ไม่มีบทบาทอื่นใดในระบบที่เห็นข้อมูลใบเสร็จข้ามคนได้ ฟีเจอร์นี้เป็นข้อจำกัดที่ครอบคลุม
ทุกฟีเจอร์ข้างต้น (cross-cutting) ไม่ใช่หน้าจอเฉพาะของตัวเอง

รหัส FR/NFR:
- [[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-12]] — จำกัดสิทธิ์การเข้าถึงข้อมูลใบเสร็จตามเจ้าของโครงการ
- [[20260816-01-grant-receipt-verification#5. Non-Functional Requirements|NFR-05]] — Security/Access Control
- [[20260816-02-pdpa-compliance#5. Non-Functional Requirements|NFR-10]] — Data Breach Notification (Organizational/Process) เกี่ยวข้องกับมาตรการความปลอดภัยของข้อมูลใบเสร็จโดยรวม

บทบาทผู้ใช้: นักวิจัย/เจ้าของโครงการ, Admin (ผู้ดูแลระบบ/ผู้อัปเดตระเบียบ)
ระดับความสำคัญ (MoSCoW): Must have

## 10. แจ้ง Privacy Notice และจัดการความยินยอม (Consent Management)

คำอธิบาย: ก่อนใช้งานระบบครั้งแรกและก่อนอัปโหลดใบเสร็จครั้งแรก ระบบต้องแสดงประกาศความเป็นส่วนตัว
(Privacy Notice) แจ้งวัตถุประสงค์การเก็บ/ใช้ข้อมูล ตัวตนผู้ควบคุมข้อมูล (มหาวิทยาลัย) ระยะเวลาเก็บ
ข้อมูล (อ้างอิงนโยบายใน NFR-11) และสิทธิ์ของเจ้าของข้อมูล จากนั้นขอความยินยอมชัดแจ้ง (Explicit
Consent) ก่อนเริ่มเก็บ/ประมวลผลข้อมูลใบเสร็จ — นักวิจัยที่ไม่ให้ความยินยอมจะอัปโหลดใบเสร็จเข้าสู่ระบบ
ไม่ได้ ระบบบันทึกหลักฐานการให้ความยินยอม (วันที่ให้ความยินยอม, เวอร์ชัน Privacy Notice) ไว้เพื่อรองรับ
หลักความรับผิดชอบ (Accountability) และนักวิจัยสามารถถอนความยินยอมที่เคยให้ไว้ได้ทุกเมื่อผ่าน UI ซึ่ง
จะทำให้ระบบระงับการอัปโหลด/ประมวลผลใบเสร็จใหม่ทันที **และลบข้อมูลใบเสร็จ/ผลตรวจทั้งหมดของนักวิจัย
คนนั้นที่ระบบเก็บไว้ทันทีด้วย โดยไม่แยกตามสถานะ export** (เดิมเป็น open point ยืนยันคำตอบแล้วโดย
ผู้ใช้เมื่อ 2026-08-16 รอบ 3) — เหตุผลคือระบบเป็นเพียง "ด่านตรวจก่อนสอบ" (pre-check gate) ไม่ใช่
archival/official retention system ของหลักฐานทางการเงิน เมื่อถอนความยินยอมแล้วจึงไม่มีฐานทางกฎหมาย
เหลืออยู่ที่จะเก็บข้อมูลต่อได้ — ต่างจากการลบเฉพาะรายการในฟีเจอร์ที่ 12 (Right to Erasure) ซึ่งยังคง
เงื่อนไขจำกัดไม่ให้ลบใบเสร็จที่ export ไปแล้ว เพราะนักวิจัยยังไม่ได้ถอนความยินยอมทั้งหมดในกรณีนั้น

รหัส FR/NFR:
- [[20260816-02-pdpa-compliance#4. Functional Requirements|FR-13]] — แสดง Privacy Notice ก่อนใช้งานครั้งแรก/ก่อนอัปโหลดใบเสร็จ
- [[20260816-02-pdpa-compliance#4. Functional Requirements|FR-14]] — ขอความยินยอมชัดแจ้ง (Explicit Consent) ก่อนเก็บ/ประมวลผลข้อมูลใบเสร็จ
- [[20260816-02-pdpa-compliance#4. Functional Requirements|FR-15]] — บันทึกหลักฐานการให้ความยินยอม (Consent Record)
- [[20260816-02-pdpa-compliance#4. Functional Requirements|FR-16]] — ถอนความยินยอม (Withdraw Consent) และจัดการผลกระทบต่อกระบวนการตรวจใบเสร็จ
- [[20260816-02-pdpa-compliance#4. Functional Requirements|FR-20]] — ลบข้อมูลใบเสร็จ/ผลตรวจทั้งหมดทันทีเมื่อถอนความยินยอม (Withdraw Consent — Full Immediate Erasure)
- [[20260816-02-pdpa-compliance#5. Non-Functional Requirements|NFR-11]] — Data Retention & Deletion Policy (อ้างอิงในเนื้อหา Privacy Notice)

บทบาทผู้ใช้: นักวิจัย/เจ้าของโครงการ
ระดับความสำคัญ (MoSCoW): Must have

## 11. ขอเข้าถึง/ขอสำเนาข้อมูลส่วนบุคคลของตนเอง (Data Access & Portability)

คำอธิบาย: นักวิจัยขอสำเนาข้อมูลส่วนบุคคลทั้งหมดที่ระบบเก็บไว้เกี่ยวกับตนเอง (ข้อมูลใบเสร็จ ผลตรวจ
และประวัติการให้ความยินยอม) ผ่าน UI ของระบบ ในรูปแบบที่อ่าน/นำไปใช้ต่อได้ ฟีเจอร์นี้แยกจากฟีเจอร์ที่ 7
(Export รายงานสรุปใบเสร็จที่ผ่านตรวจแล้วสำหรับยื่นเจ้าหน้าที่การเงิน) โดยเจตนา เพราะเป็นสำเนาข้อมูล
ส่วนบุคคลครบถ้วนตามสิทธิ์ PDPA ไม่ใช่รายงานสรุปสำหรับใช้ยื่นภายนอก

รหัส FR/NFR:
- [[20260816-02-pdpa-compliance#4. Functional Requirements|FR-17]] — ขอเข้าถึง/ขอสำเนาข้อมูลใบเสร็จส่วนบุคคลของตนเอง (Data Subject Access & Portability)

บทบาทผู้ใช้: นักวิจัย/เจ้าของโครงการ
ระดับความสำคัญ (MoSCoW): Should have

## 12. ลบข้อมูลใบเสร็จของตนเองด้วยตนเอง (Right to Erasure)

คำอธิบาย: นักวิจัยลบข้อมูลใบเสร็จของตนเองได้เองผ่าน UI โดยตรง **เงื่อนไข:** ลบได้เฉพาะใบเสร็จที่ยังไม่
ถูกรวมอยู่ใน export รายงาน (ฟีเจอร์ที่ 7) ที่ส่งให้เจ้าหน้าที่การเงินไปแล้ว — การลบเองผ่าน UI จะถูก
ปิดกั้นสำหรับกรณีนี้ และต้องยื่นคำร้องผ่านช่องทาง Admin/DPO ภายนอกระบบแทน **(เหตุผลปรับปรุงเมื่อ
2026-08-16 รอบ 3):** ไม่ใช่เพราะต้องเก็บหลักฐานทางการเงินอย่างเป็นทางการ (ระบบนี้เป็นเพียง
"ด่านตรวจก่อนสอบ" ไม่ใช่ archival/official retention system) แต่เพื่อรักษา **Audit Trail และป้องกัน
การลบหลักฐานหนีความรับผิดหลังยื่นเบิกไปแล้ว** เนื่องจากใบเสร็จที่ export ไปแล้วอยู่ระหว่างกระบวนการ
เบิกจ่ายจริงภายนอกระบบที่อาจต้องอ้างอิงย้อนกลับมาตรวจสอบ/รองรับข้อโต้แย้ง (dispute) ได้ (สอดคล้อง
ฟีเจอร์ที่ 3 เรื่อง Explainability/Audit Trail) — ต่างจากฟีเจอร์ที่ 10 (FR-20) ซึ่งเป็นการถอนความยินยอม
ทั้งหมด จึงลบได้ทันทีไม่มีเงื่อนไขนี้ เพราะไม่มีฐานทางกฎหมายเหลืออยู่ที่จะเก็บข้อมูลต่อ

รหัส FR/NFR:
- [[20260816-02-pdpa-compliance#4. Functional Requirements|FR-18]] — ลบ/ขอลบข้อมูลใบเสร็จของตนเองด้วยตนเองผ่าน UI (Right to Erasure)
- [[20260816-02-pdpa-compliance#5. Non-Functional Requirements|NFR-11]] — Data Retention & Deletion Policy (เงื่อนไขจำกัดการลบเองเฉพาะใบเสร็จที่ยังไม่ถูก export)

บทบาทผู้ใช้: นักวิจัย/เจ้าของโครงการ
ระดับความสำคัญ (MoSCoW): Must have

## 13. จัดการข้อมูลโครงการวิจัยและผูกกับแหล่งทุน (Project Setup)

คำอธิบาย: นักวิจัยสร้าง/จัดการข้อมูลโครงการวิจัยของตนเอง (อย่างน้อยชื่อโครงการ) และเลือกผูกโครงการ
เข้ากับ**แหล่งทุน** (fund source) ที่โครงการได้รับ จากรายการแหล่งทุนที่ Admin นำเข้าไว้ใน Rule Engine
(ดูฟีเจอร์ที่ 8) เพื่อให้ระบบทราบว่าใบเสร็จของโครงการนี้ต้องตรวจตามระเบียบของแหล่งทุนใด (ดูฟีเจอร์ที่
3) — ฟีเจอร์นี้เป็นขั้นตอนเบื้องต้นที่ต้องทำ**ก่อน**อัปโหลดใบเสร็จ (ฟีเจอร์ที่ 1) เนื่องจากใบเสร็จ
จำเป็นต้องผูกกับโครงการที่มีอยู่แล้วเสมอ นิยามความสัมพันธ์ที่ finalize แล้ว: 1 แหล่งทุน ให้ทุนได้
**หลายโครงการ**, ใบเสร็จผูกกับ**โครงการ**ไม่ใช่ผูกตรงกับแหล่งทุน, 1 โครงการมีนักวิจัยเจ้าของ**เพียง
1 คน** — เพิ่มฟีเจอร์นี้ใหม่ทั้งหมดในรอบนี้ เนื่องจากเป็น FR-23 ที่เพิ่งถูกเพิ่มเข้า backlog เมื่อ
2026-09-03 (มาจากการชี้ประเด็นของผู้ใช้ว่าโมเดลข้อมูลเดิมปนแนวคิด "แหล่งทุน" กับ "โครงการ" เข้าด้วยกัน)
ยังไม่เคยมีฟีเจอร์นี้ในไฟล์ก่อนหน้า

รหัส FR/NFR:
- [[20260816-01-grant-receipt-verification#4. Functional Requirements|FR-23]] — จัดการข้อมูลโครงการวิจัยและผูกกับแหล่งทุน (Project Setup)

บทบาทผู้ใช้: นักวิจัย/เจ้าของโครงการ
ระดับความสำคัญ (MoSCoW): Must have
