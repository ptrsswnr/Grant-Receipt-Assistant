รวม 10 user journey ตาม [[user-journey]]:
1. นักวิจัยอัปโหลดใบเสร็จและตรวจสอบผลจนผ่านเกณฑ์ (17 ขั้นตอน: consent → โครงการ → ประมาณการ 17.2 → Google Drive → อัปโหลด → AI/OCR → เลือกรายการประมาณการ/ติ๊กเอกสาร/ใบสรุป → Rule Engine 4 ระดับ → AI agent)
2. นักวิจัยติดตามภาพรวมโครงการและจัดการใบเสร็จที่มีปัญหาผ่าน Dashboard และการแจ้งเตือน
3. นักวิจัย Export รายงานสรุปใบเสร็จที่ผ่านตรวจแล้วเพื่อยื่นเจ้าหน้าที่การเงิน
4. Admin นำเข้า/อัปเดตระเบียบของแหล่งทุนเข้าสู่ Rule Engine
5. นักวิจัยถอนความยินยอม (Withdraw Consent) และผลกระทบต่อการใช้งานระบบ
6. นักวิจัยขอเข้าถึง/ขอสำเนาข้อมูลส่วนบุคคลของตนเอง (Data Access & Portability)
7. นักวิจัยลบข้อมูลใบเสร็จของตนเองด้วยตนเอง (Right to Erasure)
8. นักวิจัยติดตามยอดใช้ไป/คงเหลือตามประมาณการของโครงการ
9. Admin ดูภาพรวมใบเสร็จของทุกคนผ่าน Admin Dashboard (อ่านอย่างเดียว)
10. ผู้วิจัยรันชุดประเมินผลเพื่อเทียบ Rule Engine กับผลของเจ้าหน้าที่การเงิน (เครื่องมือนอกแอป)

### 1.2 นอกขอบเขต (Out of Scope)

ตาม [[backlog#รายการที่ตัดออกจากขอบเขต (Out of Scope — เพื่ออ้างอิง ไม่ใช่ backlog item)]]
รายการต่อไปนี้**ไม่มี**ในระบบและ**ไม่ต้องทดสอบ**เพราะไม่มี role/action ใดๆ รองรับเลย:

- บทบาท/action ของ "เจ้าหน้าที่การเงิน" ในระบบ (รับไฟล์ export ภายนอกระบบเท่านั้น)
- บทบาท/workflow ของ "ผู้อนุมัติทุน" ในระบบ
- Deadline tracking รายทุน และการแจ้งเตือนที่อิงกำหนดเวลาส่งหลักฐาน

รายการต่อไปนี้ **ยังไม่ทดสอบในรอบนี้** เพราะยังไม่มีพฤติกรรมที่ยืนยันแล้ว หรือยังไม่ได้สร้าง:

- ที่ตั้งผู้ให้บริการ OCR/LLM จริง (กระทบ NFR-08 cross-border transfer) — ทดสอบเมื่อมีการตัดสินใจ vendor แล้วเท่านั้น
- ตัวเลขระยะเวลาเก็บข้อมูล (retention) ตาม NFR-11 — ยังเป็น TBD
- การตรวจเอกสารแนบจากไฟล์จริงด้วย OCR (FR-27 ปัจจุบันนักวิจัยติ๊กเอง)
- การตรวจยอดรวมรายหมวดของใบสรุปรายรับ-จ่ายทั้งชุด (FR-28 ตรวจรายใบ)
- การรัน baseline กับ API ที่เสียเงิน และข้อมูลจริงของชุดประเมินผล (FR-34 รอ EC)
- ข้อสังเกตเปิด: กฎกรรมการตรวจรับ 3 คนที่ยอด 100,000 บาท (หน้า 37) ต่างจากตัวอย่างหน้า 50 ของคู่มือฟอร์ม — เก็บเกณฑ์ 100,000 ไว้จนกว่าการเงินยืนยัน test case อ้างตามเกณฑ์ที่การเงินยืนยันแล้ว

**ฟีเจอร์ที่ยังเป็น Backlog (ยังไม่ได้สร้าง) — test case เขียนไว้เป็นเกณฑ์รับมอบ รันไม่ได้จนกว่าจะสร้าง:** FR-07 (ฟีเจอร์ 4),
FR-09 (6), FR-10/FR-21 (7), FR-15/FR-16/FR-20 และ Privacy Notice แยก (10), FR-17 (11), FR-19/FR-22 (1), **FR-36 (14), FR-37/NFR-15 (21, เกี่ยวข้อง 10/12), FR-35 (22) — เพิ่ม 2026-11-17 ระดับสูง**

## 2. ประเภทการทดสอบ (Test Types)

### 2.1 Functional Testing (ต่อกลุ่ม FR)

ทดสอบตาม test case ใน `test-cases/{feature-slug}.md` แต่ละไฟล์ ครอบคลุม happy path (จาก
[[user-journey]]) และ negative/edge case (จาก [[acceptance-criteria]]) ของ FR-01–FR-37 ทั้งหมด
แบ่งตามกลุ่มฟีเจอร์:

- **OCR/อัปโหลด** (FR-01, FR-02, FR-19, FR-22): การอัปโหลดไฟล์ถูกชนิด การตรวจ/ปฏิเสธไฟล์ (ชนิด/เสียหาย/เกิน 5 MB/เกิน 5 ไฟล์) และหลายไฟล์ต่อรายการ
- **ตรวจสอบ/แก้ไขข้อมูล** (FR-03): การแก้ไขค่าที่ AI/OCR อ่านผิดก่อนส่งตรวจ
- **Rule Engine + AI** (FR-04, FR-05, FR-06, FR-24, FR-25): ผลตัดสิน **4 ระดับ** ลำดับการตรวจ ข้อค้นพบรายกลุ่ม และคำอธิบายต้องไม่เปลี่ยนผลของ Rule Engine
- **ประมาณการ** (FR-26, FR-36): นำเข้าตาราง 17.2 ตรวจนอกประมาณการ/เกิน 100% อัตรา×จำนวน ยอดใช้ไป/คงเหลือ และ (FR-36 Backlog) นำเข้าซ้ำแบบเก็บเวอร์ชันเก่า จับคู่ใบเสร็จไปรายการล่าสุด บล็อกบันทึกจนจับคู่ครบ
- **เอกสารแนบและใบสรุป** (FR-27, FR-28): checklist ชุดเอกสาร ตรา "จ่ายแล้ว"/ตรวจรับ หนังสืออนุมัติ และการเทียบยอดใบสรุป
- **ชุดกฎ** (FR-29, FR-11): ความสอดคล้องของ rule set 2570.4 และการผลักกฎโดย Admin
- **AI/OCR/agent** (FR-30, FR-31, NFR-12, NFR-14): การอ่านใบเสร็จ การสลับผู้ให้บริการ ถอยกลับเมื่อล้มเหลว agent ที่ห้ามใช้ความรู้ภายนอกและบันทึก agentLogs
- **แนบไฟล์** (FR-32, FR-37): เชื่อมต่อ Google Drive และเตือนเมื่อไม่ได้เชื่อมต่อ และ (FR-37 Backlog) จำกัดผู้ดูเป็นเจ้าของ+Admin ลบไฟล์ใน Drive ตามเมื่อลบใบเสร็จ/ถอนความยินยอม แจ้งผู้ใช้เมื่อลบไม่สำเร็จ
- **แก้ไข/ส่งซ้ำ** (FR-07): loop กลับเข้า Rule Engine จนกว่าจะผ่าน
- **Dashboard/แจ้งเตือน** (FR-08, FR-09, FR-33): การสรุปจำนวนตามสถานะ การแจ้งเตือนเมื่อมีใบเสร็จค้าง และ Admin Dashboard
- **จัดการแหล่งทุน** (FR-35 Backlog): ปิดใช้งานแทนการลบจริง เก็บกฎไว้ย้อนตรวจ ซ่อนจากรายการเลือกโครงการใหม่ เปิดใช้งานกลับ (จุดเปิด: ใบเสร็จใหม่ในโครงการที่ผูกกับแหล่งทุนที่ปิดใช้งาน ยังไม่กำหนด)
- **Export** (FR-10, FR-21): การสร้างรายงาน เงื่อนไขล็อกการลบหลัง export และการปิดปุ่มเมื่อไม่มีใบเสร็จผ่าน
- **Project Setup** (FR-23): สร้างโครงการและผูกแหล่งทุน
- **Access Control** (FR-12, FR-33): นักวิจัยเห็นเฉพาะของตนเอง Admin อ่านอย่างเดียว เขียนข้ามบัญชีไม่ได้ ยกสิทธิ์ตนเองไม่ได้
- **PDPA** (FR-13–FR-18, FR-20): consent (ปัจจุบันแบบเบา) ถอนความยินยอม ขอสำเนา ลบข้อมูล
- **ชุดประเมินผล** (FR-34): ตัวอ่านเคส ตัวชี้วัด baseline และรายงาน

## 3. Environment (สภาพแวดล้อมการทดสอบ)

`docs/02-design/02-technical/technology-stack.md` **ยังไม่มีไฟล์ และยังไม่มีการตัดสินใจ tech stack อย่างเป็นทางการ**
ดังนั้นเอกสารนี้ **ไม่กำหนดมาตรฐาน tech stack** เอง — ข้อมูลด้านล่างคือสภาพแวดล้อมที่ใช้ทดสอบจริงตามที่บันทึกไว้ใน `CLAUDE.md`
ของโปรเจกต์ ณ วันที่ 2026-11-17 และต้องทบทวนเมื่อมีการตัดสินใจ tech stack:

- **แอป:** HTML/CSS/JavaScript ล้วน (ไม่มี framework/bundler/build step) ใช้ Firebase (Firestore + Auth) เปิดทดสอบผ่านเซิร์ฟเวอร์ static
  ในเครื่อง `powershell -NoProfile -ExecutionPolicy Bypass -File scripts/static-server.ps1 -Port 4173` แล้วเปิด `http://localhost:4173/index.html`
  (หน้าที่ใช้ pdf.js และ Google OAuth ต้องเปิดผ่าน http(s) ไม่ใช่ `file://`)
- **Test อัตโนมัติ:** Node.js built-in test runner ไม่มี `package.json`: `node --test tests/rule-engine.test.js tests/budget-parser.test.js tests/eval.test.js tests/proxy.test.js tests/ocr-client.test.js`
  (ระบุไฟล์ทีละไฟล์ เพราะ `node --test tests/` ใช้ไม่ได้บน Windows)
- **บริการประกอบ (ไม่บังคับ แล้วแต่ test case):** บริการ OCR ภาษาไทยในเครื่อง (`research/ocr/server.py` ที่ 127.0.0.1:8765), Ollama ในเครื่อง,
  Cloudflare Worker proxy (**ยังไม่ deploy**), Google Drive OAuth (ต้องตั้ง Client ID จริง)
- **ฐานข้อมูลทดสอบ:** ใช้โปรเจกต์ Firebase ที่เจ้าของระบบกำหนด ก่อนทดสอบ Access Control/Admin ให้ตรวจว่า Firestore rules และ index ที่ deploy ตรงกับไฟล์ในรีโป
  (`firestore.rules`, `firestore.indexes.json` — กฎส่วน `budgetLines` ถูกบันทึกว่ายังไม่ deploy ณ 2026-11-15 ให้ยืนยันสถานะก่อน)
- **เบราว์เซอร์/ระบบปฏิบัติการ/อุปกรณ์:** **รอกำหนด** (ยังไม่มีเอกสารระบุ) — ขั้นต่ำสำหรับ NFR-13 ให้ตรวจที่ความกว้าง 1440px และ 390px
- **ข้อมูลทดสอบ:** ใบเสร็จภาษาไทยตัวอย่างที่สร้างขึ้น (ห้ามใช้ใบเสร็จจริงที่มีข้อมูลส่วนบุคคลกับผู้ให้บริการ AI ภายนอก) ไฟล์ประมาณการ 17.2 ตัวอย่าง
  `research/eval/cases.example.csv` บัญชีนักวิจัย ≥ 2 บัญชี และบัญชี Admin 1 บัญชี (ตั้ง `isAdmin` ผ่านคอนโซลเท่านั้น) — ข้อมูลเคสจริงของการประเมินผลอยู่ใน
  `research/eval/data/` ซึ่งไม่เข้า git

## 4. Entry Criteria (เกณฑ์เริ่มทดสอบ)

- มีซอร์สโค้ด/build ของฟีเจอร์ที่จะทดสอบพร้อมใช้งานใน environment ทดสอบแล้ว (ฟีเจอร์ที่ [[backlog]] ยังเป็น "Backlog" ยังไม่เข้าเกณฑ์นี้)
- [[acceptance-criteria]] ของฟีเจอร์นั้นเขียนเสร็จและอ้างอิงรหัส FR/NFR ที่ถูกต้องครบถ้วนแล้ว
- Test case ในไฟล์ `test-cases/{feature-slug}.md` ที่เกี่ยวข้องเขียนเสร็จและตรวจทานแล้ว
- รัน test อัตโนมัติผ่านทั้ง 75 ข้อก่อนเริ่มทดสอบด้วยมือ (ถ้าไม่ผ่าน ให้แก้ก่อน ไม่ใช่ทดสอบด้วยมือต่อ)
- ข้อมูลทดสอบและบัญชีทดสอบ 2 บทบาทพร้อม และยืนยันสถานะ Firestore rules/index ที่ deploy แล้ว
- สำหรับ test case ที่ต้องใช้บริการประกอบ (Drive, proxy, OCR ในเครื่อง, AI) บริการนั้นต้องพร้อมใช้ก่อน มิฉะนั้นระบุสถานะ "blocked" ไม่ใช่ "fail"

## 5. Exit Criteria (เกณฑ์ผ่านการทดสอบ)

- Test อัตโนมัติผ่าน 100% (75/75 ณ วันที่เขียน — จำนวนปรับตามที่เพิ่มในอนาคต)
- Test case ที่ผูกกับ FR/NFR ระดับความสำคัญ "สูง" (Must have) ที่ฟีเจอร์สร้างแล้วทั้งหมดต้องผ่าน 100% ก่อนปล่อยใช้งานจริง (MVP)
- Test case ที่ผูกกับ FR ระดับ "กลาง" (Should have) ผ่านอย่างน้อย 90% หรือมีแผนแก้ไข defect ที่เหลือก่อนปล่อยใช้งานจริง
- ไม่มี defect ระดับ Critical/High ที่ยังเปิดอยู่ในฟีเจอร์ด้าน Security/Access Control (FR-12, FR-33, NFR-05, NFR-12) และ PDPA
  (FR-13–FR-18, FR-37, NFR-08–NFR-11, NFR-14, NFR-15) เนื่องจากกระทบข้อกำหนดทางกฎหมายโดยตรง
- test case ที่ "blocked" เพราะฟีเจอร์ยังเป็น Backlog หรือบริการยังไม่ deploy ต้องถูกระบุเหตุผลในผลทดสอบ ไม่นับเป็นผ่าน
- ผลการรันทดสอบถูกบันทึกไว้ใน `docs/03-testing/02-test-result/` ครบถ้วน

## 6. บทบาทผู้ทดสอบ (Test Roles)

ตาม [[20260816-01-grant-receipt-verification#3. บทบาทผู้ใช้ (User Roles)]] ระบบมี 2 บทบาทในแอป
จึงต้องมีบัญชีทดสอบครบทั้ง 2 บทบาทเสมอ:

- **นักวิจัย/เจ้าของโครงการ** (ผู้ใช้หลัก): ทดสอบฟีเจอร์ที่ 1–7, 9 (ฝั่งนักวิจัย), 10–19, 21 — ควรมีบัญชีทดสอบอย่างน้อย 2 บัญชีเพื่อทดสอบ Access Control (FR-12)
  ว่าเห็นข้อมูลแยกจากกันจริง
- **Admin (ผู้ดูแลระบบ/ผู้อัปเดตระเบียบ)**: ทดสอบฟีเจอร์ที่ 8, 20, 22 และฝั่ง Admin ของฟีเจอร์ที่ 9 — ต้องยืนยันว่า **อ่านใบเสร็จของนักวิจัยทุกคนได้แบบอ่านอย่างเดียว**
  (ระบุเจ้าของ) แต่เขียน/แก้/ลบใบเสร็จของผู้อื่นไม่ได้ (กลับคำตัดสินใจเดิมตาม FR-33 — test case เดิมที่คาดว่า Admin ถูกปฏิเสธการอ่านถูกแก้แล้ว)
- **ผู้วิจัย/เจ้าของระบบ (นอกแอป)**: ทดสอบฟีเจอร์ที่ 23 ผ่านบรรทัดคำสั่ง ไม่ใช่บทบาทในแอป

ไม่มีบทบาท "เจ้าหน้าที่การเงิน" หรือ "ผู้อนุมัติทุน" ให้ทดสอบ เพราะไม่มี role/login ในระบบ (ดูหัวข้อ 1.2)
