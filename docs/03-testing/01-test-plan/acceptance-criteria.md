# Acceptance Criteria — Grant Receipt Assistant

เกณฑ์ยอมรับ (Given-When-Then) ต่อ FR/NFR ทุกตัวใน [[backlog]] จัดกลุ่มตาม heading เดียวกับ
[[feature-list]] เป๊ะๆ (ลำดับ/ชื่อหัวข้อตรงกัน 1:1) เพื่อให้ไล่อ่านคู่กันได้ง่าย อ้างอิงรายละเอียด
พฤติกรรมจริงจาก [[20260816-01-grant-receipt-verification]] และ [[20260816-02-pdpa-compliance]]

ระดับความสำคัญ (สูง/กลาง/ต่ำ) ที่กำกับท้ายรหัสแต่ละหัวข้อย่อยดึงมาจาก [[backlog]] โดยตรงเสมอ
สำหรับ FR ทุกตัว backlog มีคอลัมน์ระดับความสำคัญชัดเจนอยู่แล้ว — ส่วน **NFR ทุกตัวใน backlog ปัจจุบัน
ไม่มีคอลัมน์ระดับความสำคัญแยกต่างหาก** (ตาราง "Non-Functional Requirements" มีแค่ รหัส/ด้าน/เอกสาร
อ้างอิง/สถานะ ไม่มีคอลัมน์ระดับความสำคัญ เช่นเดียวกับในเอกสาร spec ต้นทางทั้งสองฉบับ) เพื่อไม่เดาค่า
เอาเอง เอกสารนี้จึงใช้ระดับความสำคัญของ**ฟีเจอร์ที่ NFR นั้นถูกจัดกลุ่มอยู่ใน [[feature-list]]**
เป็นตัวแทน (ฟีเจอร์ MoSCoW มาจากระดับความสำคัญของ FR ในกลุ่มเดียวกันตาม backlog อยู่แล้วตามกฎข้อ 3.1
ของ feature-list) — ในกรณีนี้ทุก NFR ที่มีอยู่ถูกจัดอยู่ในฟีเจอร์ระดับ Must have ทั้งหมด จึงเทียบเท่า
"สูง" ทุกตัวโดยไม่มีข้อขัดแย้งระหว่างจุดที่ NFR ตัวเดียวกันไปปรากฏในหลายฟีเจอร์ **หมายเหตุนี้ไม่ใช่
การเดาระดับความสำคัญเอาเอง แต่เป็นการสืบทอดค่าจาก FR ใน backlog ผ่านการจัดกลุ่มที่มีอยู่แล้วใน
feature-list** — แนะนำให้พิจารณาเพิ่มคอลัมน์ระดับความสำคัญแยกต่างหากสำหรับ NFR ใน backlog.md ใน
อนาคตเพื่อความชัดเจนโดยตรง (ไม่ใช่ปัญหาเร่งด่วนที่ต้องรัน `audit-backlog` ตอนนี้ เพราะ backlog
สอดคล้องกับ spec ต้นทางทุกตัวอักษรอยู่แล้วในประเด็นนี้)

## 1. อัปโหลดใบเสร็จและอ่านข้อมูลอัตโนมัติด้วย OCR

(อ้างอิง [[feature-list#1. อัปโหลดใบเสร็จและอ่านข้อมูลอัตโนมัติด้วย OCR|ฟีเจอร์ที่ 1]])

#### FR-01 (สูง) — [[20260816-01-grant-receipt-verification#4. Functional Requirements|อัปโหลดใบเสร็จ]]

- **AC-1 (Happy path — jpg/png)**
  - **Given**: นักวิจัยเข้าสู่ระบบแล้ว เคยให้ความยินยอม (FR-14) แล้ว และมีทุนวิจัยของตนเองอย่างน้อย 1
    ทุนในระบบ
  - **When**: นักวิจัยเลือกไฟล์ภาพถ่ายใบเสร็จ (.jpg หรือ .png) เลือกทุนวิจัยที่ต้องการผูก แล้วกด
    อัปโหลด
  - **Then**: ระบบรับไฟล์เข้าสู่ระบบสำเร็จ ผูกใบเสร็จกับทุนวิจัยที่เลือก แสดงสถานะอัปโหลดสำเร็จ และ
    ส่งต่อไปยังขั้นตอน OCR (FR-02) โดยอัตโนมัติ
- **AC-2 (Happy path — PDF สแกน)**
  - **Given**: เหมือน AC-1
  - **When**: นักวิจัยเลือกไฟล์ PDF ที่สแกนใบเสร็จ เลือกทุนวิจัยที่ต้องการผูก แล้วกดอัปโหลด
  - **Then**: ระบบรับไฟล์ PDF เข้าสู่ระบบสำเร็จ ผูกกับทุนวิจัยที่เลือก เช่นเดียวกับ AC-1
- **AC-3 (จำกัดสิทธิ์ตามเจ้าของทุน)**
  - **Given**: นักวิจัยมีทุนวิจัยมากกว่า 1 ทุน
  - **When**: นักวิจัยอัปโหลดใบเสร็จและเลือกผูกกับทุนใดทุนหนึ่งของตนเอง
  - **Then**: ใบเสร็จถูกผูกกับทุนที่เลือกเท่านั้น ไม่ปรากฏในทุนอื่นของนักวิจัยคนเดียวกัน

> หมายเหตุ: กรณีอัปโหลดไฟล์ประเภทอื่นที่ไม่ใช่ jpg/png/PDF หรือไฟล์เสีย/เปิดไม่ได้/เกินขนาดสูงสุด —
> เดิมสเปคยังไม่ได้ระบุพฤติกรรมของระบบไว้ ปัจจุบัน**ปิดแล้ว**ด้วย FR-19 (ดูด้านล่าง) ซึ่ง finalize
> เป็นรหัส FR ใหม่แล้ว

#### FR-02 (สูง) — [[20260816-01-grant-receipt-verification#4. Functional Requirements|OCR อ่านข้อมูลใบเสร็จอัตโนมัติ]]

- **AC-1 (Happy path)**
  - **Given**: อัปโหลดใบเสร็จภาษาไทยที่ชัดเจน อ่านง่ายสำเร็จแล้ว (ตาม FR-01)
  - **When**: ระบบเริ่มประมวลผล OCR
  - **Then**: ระบบอ่านและแสดงยอดเงิน วันที่ หมวดค่าใช้จ่าย และชื่อร้าน/ผู้ขาย (ถ้ามีในใบเสร็จ) ให้
    นักวิจัยเห็นก่อนเข้าสู่ขั้นตอนตรวจสอบ/แก้ไข (FR-03)
- **AC-2 (ไม่มีชื่อร้าน/ผู้ขายในใบเสร็จ)**
  - **Given**: ใบเสร็จที่อัปโหลดไม่มีชื่อร้าน/ผู้ขายระบุอยู่ (เช่น ใบเสร็จลายมือที่ตัดขอบ)
  - **When**: ระบบประมวลผล OCR
  - **Then**: ระบบแสดงข้อมูลเท่าที่อ่านได้ (ยอดเงิน วันที่ หมวดค่าใช้จ่าย) และปล่อยช่องชื่อร้านว่างให้
    นักวิจัยกรอกเองในขั้นตอนตรวจสอบ/แก้ไข (สอดคล้องกับ "ถ้ามี" ในนิยาม FR-02)

#### FR-19 (สูง) — [[20260816-01-grant-receipt-verification#4. Functional Requirements|ตรวจสอบและปฏิเสธไฟล์อัปโหลดที่ไม่ถูกต้อง (File Upload Validation)]]

- **AC-1 (ชนิดไฟล์ไม่รองรับ)**
  - **Given**: นักวิจัยกำลังจะอัปโหลดใบเสร็จ (เคยให้ความยินยอมแล้วตาม FR-14)
  - **When**: นักวิจัยเลือกไฟล์ที่ไม่ใช่ชนิดที่รองรับ (ไม่ใช่ .jpg/.png/PDF เช่น .docx หรือ .txt)
    แล้วกดอัปโหลด
  - **Then**: ระบบปฏิเสธการอัปโหลดทันที แสดงข้อความ error ภาษาไทยที่ระบุชนิดไฟล์ที่รองรับอย่างชัดเจน
    (เช่น "รองรับเฉพาะไฟล์ jpg, png หรือ PDF เท่านั้น") โดยไม่ส่งไฟล์นั้นเข้าสู่กระบวนการ OCR (FR-02)
- **AC-2 (ไฟล์เสียหาย/เปิดไม่ได้)**
  - **Given**: นักวิจัยเลือกไฟล์ชนิดที่รองรับ (jpg/png/PDF) แต่ตัวไฟล์เสียหายหรือเปิดไม่ได้ (corrupted)
  - **When**: นักวิจัยกดอัปโหลด
  - **Then**: ระบบตรวจจับว่าไฟล์เปิดไม่ได้ ปฏิเสธการอัปโหลดทันทีพร้อมข้อความ error ภาษาไทยแจ้งให้
    อัปโหลดไฟล์ใหม่ แทนที่จะส่งต่อเข้า OCR แล้วเกิดผลลัพธ์ที่อธิบายไม่ได้
- **AC-3 (ไฟล์เกินขนาดสูงสุดที่กำหนด)**
  - **Given**: นักวิจัยเลือกไฟล์ชนิดที่รองรับ แต่ขนาดไฟล์เกินขนาดสูงสุดที่ระบบกำหนด (ตัวเลขจริงยังเป็น
    TBD ตามหัวข้อ 6 ของสเปคต้นทาง)
  - **When**: นักวิจัยกดอัปโหลด
  - **Then**: ระบบปฏิเสธการอัปโหลดทันทีพร้อมข้อความ error ภาษาไทยแจ้งว่าไฟล์เกินขนาดที่กำหนด ในรูปแบบ
    เดียวกับ AC-1/AC-2 (ทดสอบเชิงพฤติกรรมของการปฏิเสธ ไม่ใช่ทดสอบตัวเลขขนาดที่แน่นอน เนื่องจากตัวเลข
    ยังไม่ finalize)

#### NFR-01 (สูง) — [[20260816-01-grant-receipt-verification#5. Non-Functional Requirements|OCR ต้องรองรับภาษาไทยเต็มรูปแบบ]]

- **AC-1**
  - **Given**: ใบเสร็จที่มีข้อความภาษาไทยทั้งหมด (ยอดเงิน วันที่ หมวดค่าใช้จ่าย ชื่อร้าน)
  - **When**: ระบบประมวลผล OCR
  - **Then**: ระบบอ่านข้อความภาษาไทยได้ถูกต้องครบทุกช่องที่กำหนดไว้ใน FR-02 โดยไม่ต้องแปลง/พึ่งพา
    ภาษาอื่นก่อน

#### NFR-06 (สูง) — [[20260816-01-grant-receipt-verification#5. Non-Functional Requirements|เวลาในการประมวลผล OCR]]

- **AC-1**
  - **Given**: อัปโหลดใบเสร็จสำเร็จแล้ว
  - **When**: ระบบเริ่มประมวลผล OCR
  - **Then**: ระบบประมวลผลเสร็จสิ้นและแสดงผลให้นักวิจัยเห็นได้โดยไม่ค้าง/ไม่ timeout (ยังไม่มีตัวเลข
    เป้าหมายเวลาที่แน่นอน — รอกำหนดเพิ่มเติมตาม NFR-06 ก่อนกำหนดเกณฑ์ตัวเลขจริงในรอบทดสอบถัดไป)

#### NFR-07 (สูง) — [[20260816-01-grant-receipt-verification#5. Non-Functional Requirements|ปริมาณใบเสร็จที่ระบบต้องรองรับ]]

- **AC-1**
  - **Given**: นักวิจัยมีใบเสร็จจำนวนมากสะสมอยู่ในระบบ (เช่น หลายสิบใบต่อทุน)
  - **When**: นักวิจัยอัปโหลดใบเสร็จใบใหม่หรือเปิดดูรายการใบเสร็จเดิม
  - **Then**: ระบบยังทำงานได้ตามปกติไม่ล้มเหลว (ยังไม่มีตัวเลขปริมาณ/ผู้ใช้พร้อมกันที่ยืนยันแล้ว —
    รอกำหนดเพิ่มเติมตาม NFR-07)

#### NFR-08 (สูง) — [[20260816-02-pdpa-compliance#5. Non-Functional Requirements|Cross-border Data Transfer (ส่วนผู้ให้บริการ OCR, Conditional)]]

- **AC-1**
  - **Given**: ผู้ให้บริการ OCR ที่โครงการเลือกใช้จริงประมวลผลข้อมูลนอกราชอาณาจักรไทย (เงื่อนไข — ยัง
    ไม่ตัดสินใจ vendor ณ ตอนนี้ ดู NFR-08)
  - **When**: ระบบส่งข้อมูลใบเสร็จไปประมวลผลกับผู้ให้บริการนั้น
  - **Then**: ต้องมีมาตรการคุ้มครองข้อมูลตามมาตรา 28-29 ของ PDPA พร้อมใช้งานก่อนเริ่มส่งข้อมูลจริง
    (ทดสอบ/ตรวจสอบเมื่อมีการตัดสินใจ vendor แล้วเท่านั้น ปัจจุบันเป็นรายการตรวจสอบเชิง compliance
    ไม่ใช่ functional test ของระบบ)

#### NFR-09 (สูง) — [[20260816-02-pdpa-compliance#5. Non-Functional Requirements|DPA กับผู้ให้บริการ OCR ภายนอก (Organizational)]]

- **AC-1**
  - **Given**: โครงการใช้ผู้ให้บริการ OCR ภายนอก
  - **When**: เริ่มใช้งานบริการ OCR จริงในระบบ production
  - **Then**: ต้องมีข้อตกลง Data Processing Agreement ระหว่างมหาวิทยาลัยกับผู้ให้บริการนั้นตามมาตรา
    40 (ตรวจสอบระดับ organizational/เอกสาร ไม่ใช่ functional test ของตัวระบบ)

## 2. ตรวจสอบและแก้ไขข้อมูลก่อนส่งตรวจ

(อ้างอิง [[feature-list#2. ตรวจสอบและแก้ไขข้อมูลก่อนส่งตรวจ|ฟีเจอร์ที่ 2]])

#### FR-03 (สูง) — [[20260816-01-grant-receipt-verification#4. Functional Requirements|ตรวจสอบ/แก้ไขข้อมูลจาก OCR ก่อนส่งตรวจ]]

- **AC-1 (Happy path — ไม่ต้องแก้ไข)**
  - **Given**: OCR อ่านข้อมูลใบเสร็จได้ถูกต้องครบถ้วน (FR-02)
  - **When**: นักวิจัยตรวจทานข้อมูลแล้วกดยืนยันโดยไม่แก้ไขอะไร
  - **Then**: ระบบส่งข้อมูลชุดเดิมที่ OCR อ่านได้เข้าสู่ Rule Engine (FR-04) ต่อไป
- **AC-2 (แก้ไขค่าที่ OCR อ่านผิด)**
  - **Given**: OCR อ่านยอดเงิน/วันที่/หมวดค่าใช้จ่าย/ชื่อร้านผิดพลาดบางส่วน
  - **When**: นักวิจัยแก้ไขค่าที่ผิดให้ถูกต้องแล้วกดยืนยันเพื่อส่งตรวจ
  - **Then**: ระบบใช้ค่าที่นักวิจัยแก้ไขแล้ว (ไม่ใช่ค่าดิบจาก OCR) เป็น input เข้าสู่ Rule Engine
    (FR-04)

## 3. ตรวจสอบใบเสร็จด้วย Rule Engine พร้อมคำอธิบายจาก LLM

(อ้างอิง [[feature-list#3. ตรวจสอบใบเสร็จด้วย Rule Engine พร้อมคำอธิบายจาก LLM|ฟีเจอร์ที่ 3]])

#### FR-04 (สูง) — [[20260816-01-grant-receipt-verification#4. Functional Requirements|ตรวจใบเสร็จด้วย Rule-based Engine]]

- **AC-1 (ผ่านเกณฑ์)**
  - **Given**: ข้อมูลใบเสร็จที่ยืนยันแล้ว (หลัง FR-03) อยู่ในหมวดค่าใช้จ่ายที่อนุญาตและไม่เกินวงเงิน
    สูงสุดต่อหมวดตามระเบียบทุนที่ Admin นำเข้าไว้ (FR-11)
  - **When**: ระบบส่งข้อมูลเข้าตรวจกับ Rule Engine
  - **Then**: Rule Engine ตัดสินสถานะ "ผ่าน" (ไม่ใช่ LLM เป็นผู้ตัดสิน)
- **AC-2 (ไม่เข้าเงื่อนไข — เกินวงเงิน/ผิดหมวด)**
  - **Given**: ข้อมูลใบเสร็จอยู่ในหมวดค่าใช้จ่ายที่ไม่ได้รับอนุญาต หรือยอดเงินเกินวงเงินสูงสุดของหมวด
    นั้นตามระเบียบที่ใช้ตรวจ
  - **When**: ระบบส่งข้อมูลเข้าตรวจกับ Rule Engine
  - **Then**: Rule Engine ตัดสินสถานะ "ไม่เข้าเงื่อนไข"
- **AC-3 (ต้องแก้ไข — เอกสารประกอบไม่ครบ)**
  - **Given**: ข้อมูลใบเสร็จเข้าเงื่อนไขหมวด/วงเงิน แต่ขาดเอกสารประกอบที่ระเบียบกำหนดให้ต้องมี
  - **When**: ระบบส่งข้อมูลเข้าตรวจกับ Rule Engine
  - **Then**: Rule Engine ตัดสินสถานะ "ต้องแก้ไข"

#### FR-05 (สูง) — [[20260816-01-grant-receipt-verification#4. Functional Requirements|LLM สรุปผลตรวจเป็นภาษาที่เข้าใจง่าย]]

- **AC-1**
  - **Given**: Rule Engine ตัดสินผลใบเสร็จแล้ว (ผ่าน/ต้องแก้ไข/ไม่เข้าเงื่อนไข)
  - **When**: ระบบแสดงผลให้นักวิจัยเห็น
  - **Then**: LLM แปลผลลัพธ์จาก Rule Engine เป็นภาษาไทยที่ไม่ใช้ศัพท์การเงิน/บัญชีโดยไม่มีคำอธิบาย
    ประกอบ พร้อมคำแนะนำแก้ไขที่เป็นรูปธรรม (ถ้าสถานะไม่ผ่าน) — LLM ไม่เปลี่ยนแปลงผลตัดสินที่มาจาก
    Rule Engine

#### FR-06 (สูง) — [[20260816-01-grant-receipt-verification#4. Functional Requirements|แสดงสถานะใบเสร็จรายใบพร้อมเหตุผลอ้างอิงระเบียบ]]

- **AC-1**
  - **Given**: ใบเสร็จผ่านการตรวจจาก Rule Engine แล้วไม่ว่าผลจะเป็นสถานะใด
  - **When**: นักวิจัยเปิดดูรายละเอียดใบเสร็จนั้น
  - **Then**: ระบบแสดงสถานะ (ผ่าน / ต้องแก้ไข / ไม่เข้าเงื่อนไข) พร้อมอ้างอิงข้อระเบียบที่ใช้ตัดสิน
    อย่างชัดเจน เพื่อรองรับการโต้แย้ง (dispute)

#### NFR-01 (สูง) — [[20260816-01-grant-receipt-verification#5. Non-Functional Requirements|คำอธิบายจาก LLM ต้องเป็นภาษาไทย]]

- **AC-1**
  - **Given**: LLM กำลังสร้างคำอธิบายผลตรวจ
  - **When**: ระบบแสดงคำอธิบายให้นักวิจัยเห็น
  - **Then**: ข้อความทั้งหมดเป็นภาษาไทย ไม่มีส่วนที่เป็นภาษาอังกฤษปนโดยไม่จำเป็น

#### NFR-02 (สูง) — [[20260816-01-grant-receipt-verification#5. Non-Functional Requirements|ภาษาที่ใช้ต้องเข้าใจง่ายสำหรับคนไม่มีพื้นฐานการเงิน]]

- **AC-1**
  - **Given**: ผลตรวจมีสถานะ "ต้องแก้ไข" หรือ "ไม่เข้าเงื่อนไข"
  - **When**: LLM อธิบายเหตุผล
  - **Then**: คำอธิบายไม่ใช้ศัพท์เฉพาะทางบัญชี-การเงินโดยไม่มีคำอธิบายประกอบ ผู้ใช้ที่ไม่มีพื้นฐาน
    การเงินอ่านแล้วเข้าใจสาเหตุและวิธีแก้ไขได้

#### NFR-03 (สูง) — [[20260816-01-grant-receipt-verification#5. Non-Functional Requirements|Explainability]]

- **AC-1**
  - **Given**: ผลตรวจจาก Rule Engine ทุกกรณี ไม่ว่าสถานะใด
  - **When**: ระบบแสดงผลให้นักวิจัยเห็น
  - **Then**: ต้องมีข้อระเบียบอ้างอิงกำกับเสมอ ห้ามมีกรณีที่แสดงผลโดยไม่มีเหตุผลอ้างอิงย้อนกลับไปยัง
    ระเบียบที่ใช้ตัดสิน

#### NFR-04 (สูง) — [[20260816-01-grant-receipt-verification#5. Non-Functional Requirements|Audit Trail (ส่วนผลตรวจต่อใบเสร็จ)]]

- **AC-1**
  - **Given**: ใบเสร็จถูกตรวจโดย Rule Engine เสร็จสิ้นแล้ว
  - **When**: มีการเปลี่ยนแปลงระเบียบในภายหลัง (ผ่าน FR-11)
  - **Then**: ระบบยังสามารถตรวจสอบย้อนหลังได้ว่าใบเสร็จนั้นถูกตรวจด้วยกฎข้อใด อ้างอิงระเบียบเวอร์ชัน
    ใด และผลลัพธ์คืออะไร ณ ตอนที่ตรวจ

#### NFR-06 (สูง) — [[20260816-01-grant-receipt-verification#5. Non-Functional Requirements|เวลาในการตรวจ Rule Engine]]

- **AC-1**
  - **Given**: ข้อมูลใบเสร็จที่ยืนยันแล้วถูกส่งเข้า Rule Engine
  - **When**: ระบบประมวลผลการตรวจ
  - **Then**: ระบบตรวจเสร็จสิ้นและแสดงผลได้โดยไม่ค้าง/ไม่ timeout (ยังไม่มีตัวเลขเป้าหมายเวลาที่แน่นอน
    — รอกำหนดเพิ่มเติมตาม NFR-06)

#### NFR-08 (สูง) — [[20260816-02-pdpa-compliance#5. Non-Functional Requirements|Cross-border Data Transfer (ส่วนผู้ให้บริการ LLM, Conditional)]]

- **AC-1**
  - **Given**: ผู้ให้บริการ LLM ที่โครงการเลือกใช้จริงประมวลผลข้อมูลนอกราชอาณาจักรไทย (เงื่อนไข — ยัง
    ไม่ตัดสินใจ vendor)
  - **When**: ระบบส่งข้อมูลผลตรวจ/ข้อมูลใบเสร็จที่เกี่ยวข้องไปให้ LLM ประมวลผล
  - **Then**: ต้องมีมาตรการคุ้มครองข้อมูลตามมาตรา 28-29 ก่อนเริ่มส่งข้อมูลจริง (ตรวจสอบเมื่อมีการ
    ตัดสินใจ vendor แล้วเท่านั้น)

#### NFR-09 (สูง) — [[20260816-02-pdpa-compliance#5. Non-Functional Requirements|DPA กับผู้ให้บริการ LLM ภายนอก (Organizational)]]

- **AC-1**
  - **Given**: โครงการใช้ผู้ให้บริการ LLM ภายนอก
  - **When**: เริ่มใช้งานบริการ LLM จริงใน production
  - **Then**: ต้องมีข้อตกลง Data Processing Agreement ระหว่างมหาวิทยาลัยกับผู้ให้บริการนั้น
    (ตรวจสอบระดับ organizational/เอกสาร)

## 4. แก้ไขและส่งใบเสร็จที่ไม่ผ่านตรวจซ้ำ

(อ้างอิง [[feature-list#4. แก้ไขและส่งใบเสร็จที่ไม่ผ่านตรวจซ้ำ|ฟีเจอร์ที่ 4]])

#### FR-07 (สูง) — [[20260816-01-grant-receipt-verification#4. Functional Requirements|แก้ไขและอัปโหลดใบเสร็จซ้ำ]]

- **AC-1 (แก้ไขข้อมูลเดิมแล้วส่งซ้ำ)**
  - **Given**: ใบเสร็จมีสถานะ "ต้องแก้ไข" หรือ "ไม่เข้าเงื่อนไข"
  - **When**: นักวิจัยแก้ไขข้อมูล (ยอดเงิน/วันที่/หมวดค่าใช้จ่าย) ของใบเสร็จเดิม แล้วกดส่งตรวจซ้ำ
  - **Then**: ระบบส่งข้อมูลที่แก้ไขแล้วเข้า Rule Engine ตรวจใหม่ (FR-04) และอัปเดตสถานะตามผลตรวจล่าสุด
- **AC-2 (อัปโหลดไฟล์ใหม่แทนใบเดิม)**
  - **Given**: ใบเสร็จมีสถานะ "ต้องแก้ไข" หรือ "ไม่เข้าเงื่อนไข"
  - **When**: นักวิจัยอัปโหลดไฟล์ใบเสร็จใหม่แทนใบเดิม แล้วกดส่งตรวจซ้ำ
  - **Then**: ระบบแทนที่ไฟล์เดิมด้วยไฟล์ใหม่ ประมวลผล OCR/ตรวจ Rule Engine ใหม่ทั้งหมด (วนกลับไปยัง
    ฟีเจอร์ที่ 3) จนกว่าจะผ่าน

## 5. Dashboard สรุปภาพรวมใบเสร็จของทุน

(อ้างอิง [[feature-list#5. Dashboard สรุปภาพรวมใบเสร็จของทุน|ฟีเจอร์ที่ 5]])

#### FR-08 (กลาง) — [[20260816-01-grant-receipt-verification#4. Functional Requirements|หน้าสรุปภาพรวมใบเสร็จของทุน (Dashboard)]]

- **AC-1 (มีใบเสร็จหลายสถานะ)**
  - **Given**: ทุนวิจัยของนักวิจัยมีใบเสร็จหลายใบ สถานะแตกต่างกัน (ผ่าน/ต้องแก้ไข/ไม่เข้าเงื่อนไข)
  - **When**: นักวิจัยเปิด Dashboard ของทุนนั้น
  - **Then**: ระบบแสดงจำนวนใบเสร็จแยกตามสถานะให้ถูกต้องตรงกับข้อมูลจริง
- **AC-2 (ยังไม่มีใบเสร็จเลย)**
  - **Given**: ทุนวิจัยที่เพิ่งเริ่มต้น ยังไม่มีใบเสร็จใดถูกอัปโหลดเลย
  - **When**: นักวิจัยเปิด Dashboard ของทุนนั้น
  - **Then**: ระบบแสดงสถานะว่างเปล่า (จำนวนทุกสถานะเป็น 0) ไม่แสดงข้อมูลผิดพลาด

## 6. แจ้งเตือนใบเสร็จที่มีปัญหาค้างอยู่

(อ้างอิง [[feature-list#6. แจ้งเตือนใบเสร็จที่มีปัญหาค้างอยู่|ฟีเจอร์ที่ 6]])

#### FR-09 (กลาง) — [[20260816-01-grant-receipt-verification#4. Functional Requirements|แจ้งเตือนใบเสร็จที่มีปัญหายังไม่แก้ไข]]

- **AC-1 (มีใบเสร็จค้างแก้ไข)**
  - **Given**: นักวิจัยมีใบเสร็จสถานะ "ต้องแก้ไข" หรือ "ไม่เข้าเงื่อนไข" ที่ยังไม่ได้รับการแก้ไข
  - **When**: ระบบตรวจพบใบเสร็จดังกล่าวยังค้างอยู่
  - **Then**: ระบบแจ้งเตือนนักวิจัยว่ามีใบเสร็จที่มีปัญหายังไม่ได้แก้ไข (ไม่เกี่ยวข้องกับกำหนดเวลาส่ง
    หลักฐานรายทุน ซึ่งตัดออกจากขอบเขต MVP นี้แล้ว)
- **AC-2 (ไม่มีใบเสร็จค้างแก้ไข)**
  - **Given**: ใบเสร็จทั้งหมดของนักวิจัยผ่านการตรวจแล้ว ไม่มีสถานะ "ต้องแก้ไข"/"ไม่เข้าเงื่อนไข" ค้างอยู่
  - **When**: ระบบตรวจสอบสถานะใบเสร็จ
  - **Then**: ระบบไม่ส่งการแจ้งเตือนใดๆ เกี่ยวกับใบเสร็จมีปัญหา

## 7. Export รายงานสรุปใบเสร็จที่ผ่านตรวจแล้ว

(อ้างอิง [[feature-list#7. Export รายงานสรุปใบเสร็จที่ผ่านตรวจแล้ว|ฟีเจอร์ที่ 7]])

#### FR-10 (สูง) — [[20260816-01-grant-receipt-verification#4. Functional Requirements|Export รายงานสรุปใบเสร็จที่ผ่านตรวจแล้ว]]

- **AC-1 (มีใบเสร็จผ่านตรวจพร้อม export)**
  - **Given**: ทุนวิจัยของนักวิจัยมีใบเสร็จอย่างน้อย 1 ใบสถานะ "ผ่าน"
  - **When**: นักวิจัยกด Export รายงานสรุปของทุนนั้น
  - **Then**: ระบบสร้างไฟล์รายงานสรุปใบเสร็จที่ผ่านตรวจแล้วให้ดาวน์โหลด เพื่อนำไปยื่นเจ้าหน้าที่การเงิน
    ของมหาวิทยาลัยเอง (นอกระบบ)
- **AC-2 (ใบเสร็จที่ export แล้วถูกล็อกไม่ให้ลบเอง)**
  - **Given**: ใบเสร็จถูกรวมอยู่ในรายงานที่ export ไปแล้วครั้งหนึ่ง
  - **When**: นักวิจัยพยายามลบใบเสร็จนั้นเองผ่าน UI (ดู FR-18)
  - **Then**: ระบบล็อกไม่ให้ลบใบเสร็จนั้นผ่าน UI อีกต่อไป (เชื่อมโยงกับเงื่อนไขใน FR-18)

> หมายเหตุ: กรณีทุนวิจัยยังไม่มีใบเสร็จสถานะ "ผ่าน" เลยแม้แต่ใบเดียว แล้วนักวิจัยพยายามกด Export —
> เดิมสเปคยังไม่ได้ระบุพฤติกรรมของระบบไว้ชัดเจน ปัจจุบัน**ปิดแล้ว**ด้วย FR-21 (ดูด้านล่าง) ซึ่ง
> finalize เป็นรหัส FR ใหม่แล้ว

#### FR-21 (สูง) — [[20260816-01-grant-receipt-verification#4. Functional Requirements|ป้องกันการ Export รายงานเมื่อยังไม่มีใบเสร็จสถานะผ่าน]]

- **AC-1 (ไม่มีใบเสร็จสถานะผ่านเลย — ปิดปุ่ม Export)**
  - **Given**: ทุนวิจัยของนักวิจัยยังไม่มีใบเสร็จสถานะ "ผ่าน" (FR-06) แม้แต่ใบเดียว
  - **When**: นักวิจัยเปิดดูหน้า Export/Dashboard ของทุนนั้น
  - **Then**: ระบบปิดการใช้งาน (disable) ปุ่ม Export ของทุนนั้นไว้ก่อน พร้อมข้อความแจ้งเหตุผลที่กด
    ไม่ได้ (เช่น "ยังไม่มีใบเสร็จที่ผ่านการตรวจสำหรับทุนนี้") แทนการปล่อยให้กดแล้วได้ไฟล์รายงานเปล่า
    หรือ error ที่ไม่มีคำอธิบาย
- **AC-2 (มีใบเสร็จสถานะผ่านอย่างน้อย 1 ใบ — ปุ่ม Export ใช้งานได้ตามปกติ)**
  - **Given**: ทุนวิจัยมีใบเสร็จอย่างน้อย 1 ใบสถานะ "ผ่าน"
  - **When**: นักวิจัยเปิดดูหน้า Export/Dashboard ของทุนนั้น
  - **Then**: ปุ่ม Export ใช้งานได้ตามปกติ ไม่ถูกปิดการใช้งาน (เชื่อมกับ FR-10 AC-1)

## 8. นำเข้า/อัปเดตระเบียบทุนวิจัยเข้าสู่ Rule Engine (Admin)

(อ้างอิง [[feature-list#8. นำเข้า/อัปเดตระเบียบทุนวิจัยเข้าสู่ Rule Engine (Admin)|ฟีเจอร์ที่ 8]])

#### FR-11 (สูง) — [[20260816-01-grant-receipt-verification#4. Functional Requirements|นำเข้า/อัปเดตระเบียบทุนวิจัยเข้าสู่ Rule Engine]]

- **AC-1**
  - **Given**: Admin เข้าสู่ระบบด้วยบทบาท Admin และมีระเบียบทุนวิจัยฉบับใหม่ที่ต้องนำเข้า
  - **When**: Admin นำเข้า/อัปเดตกฎ/เงื่อนไขจากระเบียบใหม่เข้าสู่ Rule Engine
  - **Then**: Rule Engine ใช้กฎเวอร์ชันใหม่ตรวจใบเสร็จของนักวิจัยที่ส่งเข้ามาตั้งแต่จุดนี้เป็นต้นไป
    โดยไม่ต้อง retrain LLM

#### NFR-04 (สูง) — [[20260816-01-grant-receipt-verification#5. Non-Functional Requirements|Audit Trail (ส่วนเวอร์ชันระเบียบที่นำเข้า)]]

- **AC-1**
  - **Given**: Admin นำเข้า/อัปเดตระเบียบใหม่เข้าสู่ Rule Engine สำเร็จ
  - **When**: ระบบบันทึกการเปลี่ยนแปลง
  - **Then**: ระบบบันทึกเวอร์ชันระเบียบที่นำเข้าไว้ใน Audit Trail เพื่อรองรับการตรวจสอบย้อนหลังเมื่อ
    ระเบียบมีการเปลี่ยนแปลงตามเวลา

## 9. จำกัดสิทธิ์การเข้าถึงข้อมูลตามเจ้าของ (Access Control)

(อ้างอิง [[feature-list#9. จำกัดสิทธิ์การเข้าถึงข้อมูลตามเจ้าของ (Access Control)|ฟีเจอร์ที่ 9]])

#### FR-12 (สูง) — [[20260816-01-grant-receipt-verification#4. Functional Requirements|จำกัดสิทธิ์การเข้าถึงข้อมูลใบเสร็จตามเจ้าของ]]

- **AC-1 (นักวิจัยเห็นเฉพาะของตนเอง)**
  - **Given**: นักวิจัย A และนักวิจัย B ต่างมีทุนวิจัยและใบเสร็จของตนเองในระบบ
  - **When**: นักวิจัย A เข้าสู่ระบบและเปิดดูรายการทุน/ใบเสร็จ
  - **Then**: นักวิจัย A เห็นเฉพาะทุน/ใบเสร็จของตนเองเท่านั้น ไม่เห็นข้อมูลของนักวิจัย B
- **AC-2 (นักวิจัยพยายามเข้าถึงข้อมูลของผู้อื่นโดยตรง)**
  - **Given**: นักวิจัย A ทราบ/เดา ID ใบเสร็จหรือทุนของนักวิจัย B
  - **When**: นักวิจัย A พยายามเข้าถึงข้อมูลนั้นโดยตรง (เช่น ผ่าน URL/รหัสอ้างอิง)
  - **Then**: ระบบปฏิเสธการเข้าถึงและไม่แสดงข้อมูลของนักวิจัย B ให้นักวิจัย A เห็น
- **AC-3 (Admin ไม่มีสิทธิ์เข้าถึงข้อมูลใบเสร็จส่วนบุคคล)**
  - **Given**: Admin เข้าสู่ระบบด้วยบทบาท Admin
  - **When**: Admin พยายามเข้าถึงข้อมูลใบเสร็จส่วนบุคคลของนักวิจัยคนใดคนหนึ่ง
  - **Then**: ระบบปฏิเสธการเข้าถึง — สิทธิ์ของ Admin จำกัดเฉพาะการจัดการระเบียบ/กฎใน Rule Engine
    (FR-11) เท่านั้น

#### NFR-05 (สูง) — [[20260816-01-grant-receipt-verification#5. Non-Functional Requirements|Security/Access Control]]

- **AC-1**
  - **Given**: ข้อมูลใบเสร็จของนักวิจัยแต่ละคนถูกจัดเก็บในระบบ
  - **When**: มีความพยายามเข้าถึงข้อมูลจากบัญชีอื่นที่ไม่ใช่เจ้าของ (ไม่ว่าบทบาทใด)
  - **Then**: ระบบต้องปฏิเสธการเข้าถึงเสมอ ไม่มีบทบาทใดในระบบที่เห็นข้อมูลใบเสร็จข้ามคนได้ (สอดคล้อง
    กับ FR-12)

#### NFR-10 (สูง) — [[20260816-02-pdpa-compliance#5. Non-Functional Requirements|Data Breach Notification (Organizational/Process)]]

- **AC-1**
  - **Given**: เกิดเหตุการณ์ข้อมูลใบเสร็จของนักวิจัยรั่วไหล/ถูกเข้าถึงโดยไม่ได้รับอนุญาต
  - **When**: โครงการตรวจพบเหตุการณ์ดังกล่าว
  - **Then**: โครงการต้องมีกลไก/กระบวนการแจ้งเตือนสำนักงานคณะกรรมการคุ้มครองข้อมูลส่วนบุคคล (สคส.)
    ภายใน 72 ชั่วโมงตามมาตรา 37(4) (ตรวจสอบระดับ organizational/process ไม่ใช่ functional test ของ
    ตัวระบบ)

## 10. แจ้ง Privacy Notice และจัดการความยินยอม (Consent Management)

(อ้างอิง [[feature-list#10. แจ้ง Privacy Notice และจัดการความยินยอม (Consent Management)|ฟีเจอร์ที่ 10]])

#### FR-13 (สูง) — [[20260816-02-pdpa-compliance#4. Functional Requirements|แสดง Privacy Notice ก่อนใช้งานครั้งแรก/ก่อนอัปโหลดใบเสร็จ]]

- **AC-1 (ใช้งานระบบครั้งแรก)**
  - **Given**: นักวิจัยเข้าสู่ระบบเป็นครั้งแรก ยังไม่เคยเห็น Privacy Notice มาก่อน
  - **When**: นักวิจัยเข้าสู่ระบบ
  - **Then**: ระบบแสดงประกาศความเป็นส่วนตัว (Privacy Notice) แจ้งวัตถุประสงค์การเก็บ/ใช้ข้อมูล ตัวตน
    ผู้ควบคุมข้อมูล (มหาวิทยาลัย) ระยะเวลาเก็บข้อมูล (อ้างอิง NFR-11) และสิทธิ์ของเจ้าของข้อมูล ก่อน
    ให้ใช้งานฟีเจอร์อื่นต่อ
- **AC-2 (ก่อนอัปโหลดใบเสร็จครั้งแรก)**
  - **Given**: นักวิจัยเคยเห็นและผ่านหน้า Privacy Notice ตอนเข้าระบบครั้งแรกแล้ว แต่ยังไม่เคยอัปโหลด
    ใบเสร็จเลย
  - **When**: นักวิจัยพยายามอัปโหลดใบเสร็จเป็นครั้งแรก (FR-01)
  - **Then**: ระบบยืนยันว่ามีการแสดง Privacy Notice/ขอความยินยอมแล้วก่อนเริ่มเก็บ/ประมวลผลข้อมูล
    ใบเสร็จจริง (เชื่อมกับ FR-14)

#### FR-14 (สูง) — [[20260816-02-pdpa-compliance#4. Functional Requirements|ขอความยินยอมชัดแจ้ง (Explicit Consent) ก่อนเก็บ/ประมวลผลข้อมูลใบเสร็จ]]

- **AC-1 (ให้ความยินยอม)**
  - **Given**: นักวิจัยเห็น Privacy Notice แล้ว (FR-13) และยังไม่เคยให้ความยินยอมมาก่อน
  - **When**: นักวิจัยกดให้ความยินยอมอย่างชัดแจ้ง
  - **Then**: ระบบอนุญาตให้นักวิจัยอัปโหลดใบเสร็จได้ (ไปต่อ FR-01) และบันทึกหลักฐานการให้ความยินยอม
    (FR-15)
- **AC-2 (ไม่ให้ความยินยอม)**
  - **Given**: นักวิจัยเห็น Privacy Notice แล้ว (FR-13)
  - **When**: นักวิจัยเลือกไม่ให้ความยินยอม
  - **Then**: ระบบไม่อนุญาตให้นักวิจัยอัปโหลดใบเสร็จเข้าสู่ระบบ

#### FR-15 (สูง) — [[20260816-02-pdpa-compliance#4. Functional Requirements|บันทึกหลักฐานการให้ความยินยอม (Consent Record)]]

- **AC-1**
  - **Given**: นักวิจัยเพิ่งให้ความยินยอมชัดแจ้ง (FR-14)
  - **When**: ระบบบันทึกเหตุการณ์นี้
  - **Then**: ระบบบันทึกวันที่ให้ความยินยอมและเวอร์ชันของ Privacy Notice ที่นักวิจัยเห็น ณ ตอนนั้น
    ไว้เป็นหลักฐานย้อนหลัง (Accountability)

#### FR-16 (สูง) — [[20260816-02-pdpa-compliance#4. Functional Requirements|ถอนความยินยอม (Withdraw Consent) และจัดการผลกระทบต่อกระบวนการตรวจใบเสร็จ]]

- **AC-1 (ถอนความยินยอม — ผลต่อการอัปโหลด/ประมวลผลใหม่)**
  - **Given**: นักวิจัยเคยให้ความยินยอมไว้แล้วและใช้งานระบบอยู่
  - **When**: นักวิจัยเปิดหน้าจัดการความยินยอมแล้วกดถอนความยินยอม
  - **Then**: ระบบระงับการอัปโหลด/ประมวลผลใบเสร็จ**ใหม่**ของนักวิจัยคนนั้นทันที

> หมายเหตุ: พฤติกรรมของระบบต่อ**ข้อมูลที่เคยประมวลผลไปแล้วก่อนถอนความยินยอม** (เช่น เก็บต่อ/ระงับ
> การเข้าถึง/ลบทันที) — เดิมสเปคและ backlog ระบุไว้ว่าเป็น **Open Point ที่ยังไม่ปิด** ปัจจุบัน
> **ปิดแล้ว**ด้วย FR-20 (ดูด้านล่าง) ซึ่งผู้ใช้ยืนยันคำตอบและ finalize เป็นรหัส FR ใหม่แล้ว

#### FR-20 (สูง) — [[20260816-02-pdpa-compliance#4. Functional Requirements|ลบข้อมูลใบเสร็จ/ผลตรวจทั้งหมดทันทีเมื่อถอนความยินยอม (Withdraw Consent — Full Immediate Erasure)]]

- **AC-1 (ลบข้อมูลทั้งหมดทันที ไม่แยกตามสถานะ export)**
  - **Given**: นักวิจัยเคยให้ความยินยอมไว้และมีข้อมูลใบเสร็จ/ผลตรวจอยู่ในระบบ (ทั้งใบที่เคยถูก export
    ไปแล้วและใบที่ยังไม่ถูก export)
  - **When**: นักวิจัยกดถอนความยินยอมที่เคยให้ไว้ (FR-16)
  - **Then**: ระบบลบข้อมูลใบเสร็จ/ผลตรวจทั้งหมดของนักวิจัยคนนั้นที่ระบบเก็บไว้ทันที โดย**ไม่แยกตาม
    สถานะ export** (ต่างจากเงื่อนไขจำกัดของ FR-18 ที่ยังคงห้ามลบใบเสร็จที่ export ไปแล้วผ่าน UI เอง
    เพราะกรณีนั้นนักวิจัยยังไม่ได้ถอนความยินยอมทั้งหมด)
- **AC-2 (เชื่อมโยงลำดับกับการระงับอัปโหลด/ประมวลผลใหม่)**
  - **Given**: นักวิจัยเพิ่งกดถอนความยินยอม (ต่อยอดจาก FR-16 AC-1)
  - **When**: ระบบประมวลผลการถอนความยินยอม
  - **Then**: ระบบระงับการอัปโหลด/ประมวลผลใบเสร็จใหม่ทันที (FR-16) และลบข้อมูลใบเสร็จ/ผลตรวจเดิม
    ทั้งหมดทันทีในลำดับเดียวกัน (FR-20) เพราะไม่มีฐานทางกฎหมายเหลืออยู่ที่จะเก็บข้อมูลต่อได้อีก

#### NFR-11 (สูง) — [[20260816-02-pdpa-compliance#5. Non-Functional Requirements|Data Retention & Deletion Policy (ส่วนที่อ้างอิงในเนื้อหา Privacy Notice)]]

- **AC-1**
  - **Given**: ระบบแสดง Privacy Notice ให้นักวิจัยเห็น (FR-13)
  - **When**: นักวิจัยอ่านเนื้อหา Privacy Notice
  - **Then**: เนื้อหาต้องระบุถึงระยะเวลาเก็บข้อมูล/นโยบายการเก็บ-ลบข้อมูล แม้ว่าตัวเลขที่แน่นอนยังเป็น
    TBD ก็ต้องระบุว่ามีนโยบายนี้อยู่และจะแจ้งเพิ่มเติมเมื่อกำหนดตัวเลขแล้ว (ไม่ปล่อยว่างเปล่าโดยไม่มี
    ข้อความใดๆ เรื่อง retention)

## 11. ขอเข้าถึง/ขอสำเนาข้อมูลส่วนบุคคลของตนเอง (Data Access & Portability)

(อ้างอิง [[feature-list#11. ขอเข้าถึง/ขอสำเนาข้อมูลส่วนบุคคลของตนเอง (Data Access & Portability)|ฟีเจอร์ที่ 11]])

#### FR-17 (กลาง) — [[20260816-02-pdpa-compliance#4. Functional Requirements|ขอเข้าถึง/ขอสำเนาข้อมูลใบเสร็จส่วนบุคคลของตนเอง (Data Subject Access & Portability)]]

- **AC-1 (Happy path)**
  - **Given**: นักวิจัยเข้าสู่ระบบและมีข้อมูลใบเสร็จ/ผลตรวจ/ประวัติ consent อยู่ในระบบ
  - **When**: นักวิจัยขอสำเนาข้อมูลส่วนบุคคลทั้งหมดของตนเองผ่านหน้าจัดการสิทธิ์ข้อมูลส่วนบุคคล
  - **Then**: ระบบให้นักวิจัยดาวน์โหลด/รับสำเนาข้อมูลใบเสร็จ ผลตรวจ และประวัติการให้ความยินยอมทั้งหมด
    ของตนเอง ในรูปแบบที่อ่าน/นำไปใช้ต่อได้
- **AC-2 (แยกจากรายงาน export ฟีเจอร์ที่ 7)**
  - **Given**: นักวิจัยเคย export รายงานสรุปใบเสร็จที่ผ่านตรวจแล้ว (FR-10) มาก่อน
  - **When**: นักวิจัยขอสำเนาข้อมูลส่วนบุคคลผ่าน FR-17
  - **Then**: สำเนาที่ได้รับครบถ้วนกว่ารายงานสรุปของ FR-10 (รวมใบเสร็จทุกสถานะ ผลตรวจ และประวัติ
    consent ไม่ใช่แค่ใบเสร็จที่ผ่านตรวจแล้ว)

## 12. ลบข้อมูลใบเสร็จของตนเองด้วยตนเอง (Right to Erasure)

(อ้างอิง [[feature-list#12. ลบข้อมูลใบเสร็จของตนเองด้วยตนเอง (Right to Erasure)|ฟีเจอร์ที่ 12]])

#### FR-18 (สูง) — [[20260816-02-pdpa-compliance#4. Functional Requirements|ลบ/ขอลบข้อมูลใบเสร็จของตนเองด้วยตนเองผ่าน UI (Right to Erasure)]]

- **AC-1 (ลบใบเสร็จที่ยังไม่ถูก export)**
  - **Given**: นักวิจัยเลือกใบเสร็จของตนเองที่ยังไม่เคยถูกรวมอยู่ใน export รายงาน (FR-10)
  - **When**: นักวิจัยกดลบและยืนยันการลบ
  - **Then**: ระบบลบข้อมูลใบเสร็จนั้นออกจากระบบทันที
- **AC-2 (พยายามลบใบเสร็จที่ถูก export ไปแล้ว)**
  - **Given**: นักวิจัยเลือกใบเสร็จที่เคยถูกรวมอยู่ใน export รายงานที่ส่งเจ้าหน้าที่การเงินไปแล้ว
    (FR-10)
  - **When**: นักวิจัยพยายามกดลบใบเสร็จนั้นผ่าน UI
  - **Then**: ระบบปิดกั้นการลบเองผ่าน UI และแจ้งให้นักวิจัยยื่นคำร้องผ่านช่องทาง Admin/DPO ภายนอกระบบ
    แทน

#### NFR-11 (สูง) — [[20260816-02-pdpa-compliance#5. Non-Functional Requirements|Data Retention & Deletion Policy (เงื่อนไขจำกัดการลบเองเฉพาะใบเสร็จที่ยังไม่ถูก export)]]

- **AC-1**
  - **Given**: นโยบาย retention ของหลักฐานทางการเงินกำหนดให้ใบเสร็จที่ export ไปแล้วต้องเก็บไว้เป็น
    หลักฐาน
  - **When**: นักวิจัยพยายามลบใบเสร็จที่ export ไปแล้วผ่าน UI (เชื่อมกับ FR-18 AC-2)
  - **Then**: ระบบต้องปฏิบัติตามเงื่อนไข retention นี้เสมอ ไม่อนุญาตให้ลบเองผ่าน UI จนกว่าจะมีตัวเลข
    retention/กระบวนการที่ finalize แล้วมาแทนที่เงื่อนไขนี้
