# Acceptance Criteria — Grant Receipt Assistant

เกณฑ์ยอมรับ (Given-When-Then) ต่อ FR/NFR ทุกตัวใน [[backlog]] จัดกลุ่มตาม heading เดียวกับ
[[feature-list]] เป๊ะๆ (ลำดับ/ชื่อหัวข้อตรงกัน 1:1) เพื่อให้ไล่อ่านคู่กันได้ง่าย อ้างอิงรายละเอียด
พฤติกรรมจริงจาก [[20260816-01-grant-receipt-verification]] และ [[20260816-02-pdpa-compliance]]

ระดับความสำคัญ (สูง/กลาง/ต่ำ) ที่กำกับท้ายรหัสแต่ละหัวข้อย่อยดึงมาจาก [[backlog]] โดยตรงเสมอ
สำหรับ FR ทุกตัว backlog มีคอลัมน์ระดับความสำคัญชัดเจนอยู่แล้ว — ส่วน **NFR ทุกตัวใน backlog ปัจจุบัน
ไม่มีคอลัมน์ระดับความสำคัญแยกต่างหาก** (ตาราง "Non-Functional Requirements" มีแค่ รหัส/ด้าน/เอกสาร
อ้างอิง/สถานะ ไม่มีคอลัมน์ระดับความสำคัญ เช่นเดียวกับในเอกสาร spec ต้นทางทั้งสองฉบับ) เพื่อไม่เดาค่า
เอาเอง เอกสารนี้จึงใช้ระดับความสำคัญของ**ฟีเจอร์ที่ NFR นั้นถูกจัดกลุ่มอยู่ใน [[feature-list]]**
เป็นตัวแทน (ฟีเจอร์ MoSCoW มาจากระดับความสำคัญของ FR ในกลุ่มเดียวกันตาม backlog อยู่แล้วตามกฎข้อ 3.1
ของ feature-list) — ในกรณีนี้ทุก NFR ที่มีอยู่ถูกจัดอยู่ในฟีเจอร์ระดับ Must have ทั้งหมด จึงเทียบเท่า
"สูง" ทุกตัวโดยไม่มีข้อขัดแย้งระหว่างจุดที่ NFR ตัวเดียวกันไปปรากฏในหลายฟีเจอร์ **หมายเหตุนี้ไม่ใช่
การเดาระดับความสำคัญเอาเอง แต่เป็นการสืบทอดค่าจาก FR ใน backlog ผ่านการจัดกลุ่มที่มีอยู่แล้วใน
feature-list** — แนะนำให้พิจารณาเพิ่มคอลัมน์ระดับความสำคัญแยกต่างหากสำหรับ NFR ใน backlog.md ใน
อนาคตเพื่อความชัดเจนโดยตรง (ไม่ใช่ปัญหาเร่งด่วนที่ต้องรัน `audit-backlog` ตอนนี้ เพราะ backlog
สอดคล้องกับ spec ต้นทางทุกตัวอักษรอยู่แล้วในประเด็นนี้)

> **อัปเดต 2026-11-17:** sync ตาม [[feature-list]]/[[user-journey]] ที่เพิ่มฟีเจอร์ 13–23 (FR-23–FR-34,
> NFR-12–NFR-14 — สร้างเสร็จแล้วในแอปจริง ดู [[20261117-01-implemented-rule-engine-ai-and-admin]])
> NFR ใหม่สืบทอดระดับความสำคัญตามฟีเจอร์ที่ผูกอยู่ใน feature-list เช่นเดิม: NFR-12/NFR-14 → ฟีเจอร์ 17

## 1. อัปโหลดใบเสร็จและอ่านข้อมูลอัตโนมัติด้วย OCR

(อ้างอิง [[feature-list#1. อัปโหลดใบเสร็จและอ่านข้อมูลอัตโนมัติด้วย OCR|ฟีเจอร์ที่ 1]])

#### FR-01 (สูง) — [[20260816-01-grant-receipt-verification#4. Functional Requirements|อัปโหลดใบเสร็จ]]

- **AC-1 (Happy path — jpg/png)**
  - **Given**: นักวิจัยเข้าสู่ระบบแล้ว เคยให้ความยินยอม (FR-14) แล้ว และมีโครงการวิจัยของตนเองที่ผูกกับ
    แหล่งทุนไว้อย่างน้อย 1 โครงการ (FR-23)
  - **When**: นักวิจัยเลือกไฟล์ภาพถ่ายใบเสร็จ (.jpg หรือ .png) เลือกโครงการวิจัยที่ต้องการผูก แล้วกด
    อัปโหลด
  - **Then**: ระบบรับไฟล์เข้าสู่ระบบสำเร็จ ผูกใบเสร็จกับโครงการวิจัยที่เลือก (ไม่ผูกตรงกับแหล่งทุน) แสดงสถานะ
    อัปโหลดสำเร็จ และส่งต่อไปยังขั้นตอน AI/OCR อ่านข้อมูล (FR-02, FR-30) โดยอัตโนมัติ
- **AC-2 (Happy path — PDF สแกน)**
  - **Given**: เหมือน AC-1
  - **When**: นักวิจัยเลือกไฟล์ PDF ที่สแกนใบเสร็จ เลือกโครงการวิจัยที่ต้องการผูก แล้วกดอัปโหลด
  - **Then**: ระบบรับไฟล์ PDF เข้าสู่ระบบสำเร็จ ผูกกับโครงการวิจัยที่เลือก เช่นเดียวกับ AC-1
- **AC-3 (จำกัดสิทธิ์ตามเจ้าของโครงการ)**
  - **Given**: นักวิจัยมีโครงการวิจัยมากกว่า 1 โครงการ
  - **When**: นักวิจัยอัปโหลดใบเสร็จและเลือกผูกกับโครงการใดโครงการหนึ่งของตนเอง
  - **Then**: ใบเสร็จถูกผูกกับโครงการที่เลือกเท่านั้น ไม่ปรากฏในโครงการอื่นของนักวิจัยคนเดียวกัน (กรอง
    รายการใบเสร็จรายโครงการได้ผ่านหน้ารายการใบเสร็จ)

> หมายเหตุ: กรณีอัปโหลดไฟล์ประเภทอื่นที่ไม่ใช่ jpg/png/PDF หรือไฟล์เสีย/เปิดไม่ได้/เกินขนาดสูงสุด —
> เดิมสเปคยังไม่ได้ระบุพฤติกรรมของระบบไว้ ปัจจุบัน**ปิดแล้ว**ด้วย FR-19 (ดูด้านล่าง) ซึ่ง finalize
> เป็นรหัส FR ใหม่แล้ว

#### FR-02 (สูง) — [[20260816-01-grant-receipt-verification#4. Functional Requirements|OCR อ่านข้อมูลใบเสร็จอัตโนมัติ]]

- **AC-1 (Happy path)**
  - **Given**: อัปโหลดใบเสร็จภาษาไทยที่ชัดเจน อ่านง่ายสำเร็จแล้ว (ตาม FR-01)
  - **When**: ระบบเริ่มประมวลผล OCR
  - **Then**: ระบบอ่านและแสดงยอดเงิน วันที่ หมวดค่าใช้จ่าย และชื่อร้าน/ผู้ขาย (ถ้ามีในใบเสร็จ) ให้
    นักวิจัยเห็นก่อนเข้าสู่ขั้นตอนตรวจสอบ/แก้ไข (FR-03)
- **AC-2 (ไม่มีชื่อร้าน/ผู้ขายในใบเสร็จ)**
  - **Given**: ใบเสร็จที่อัปโหลดไม่มีชื่อร้าน/ผู้ขายระบุอยู่ (เช่น ใบเสร็จลายมือที่ตัดขอบ)
  - **When**: ระบบประมวลผล OCR
  - **Then**: ระบบแสดงข้อมูลเท่าที่อ่านได้ (ยอดเงิน วันที่ หมวดค่าใช้จ่าย) และปล่อยช่องชื่อร้านว่างให้
    นักวิจัยกรอกเองในขั้นตอนตรวจสอบ/แก้ไข (สอดคล้องกับ "ถ้ามี" ในนิยาม FR-02)

#### FR-19 (สูง) — [[20260816-01-grant-receipt-verification#4. Functional Requirements|ตรวจสอบและปฏิเสธไฟล์อัปโหลดที่ไม่ถูกต้อง (File Upload Validation)]]

- **AC-1 (ชนิดไฟล์ไม่รองรับ)**
  - **Given**: นักวิจัยกำลังจะอัปโหลดใบเสร็จ (เคยให้ความยินยอมแล้วตาม FR-14)
  - **When**: นักวิจัยเลือกไฟล์ที่ไม่ใช่ชนิดที่รองรับ (ไม่ใช่ .jpg/.png/PDF เช่น .docx หรือ .txt)
    แล้วกดอัปโหลด
  - **Then**: ระบบปฏิเสธการอัปโหลดทันที แสดงข้อความ error ภาษาไทยที่ระบุชนิดไฟล์ที่รองรับอย่างชัดเจน
    (เช่น "รองรับเฉพาะไฟล์ jpg, png หรือ PDF เท่านั้น") โดยไม่ส่งไฟล์นั้นเข้าสู่กระบวนการ OCR (FR-02)
- **AC-2 (ไฟล์เสียหาย/เปิดไม่ได้)**
  - **Given**: นักวิจัยเลือกไฟล์ชนิดที่รองรับ (jpg/png/PDF) แต่ตัวไฟล์เสียหายหรือเปิดไม่ได้ (corrupted)
  - **When**: นักวิจัยกดอัปโหลด
  - **Then**: ระบบตรวจจับว่าไฟล์เปิดไม่ได้ ปฏิเสธการอัปโหลดทันทีพร้อมข้อความ error ภาษาไทยแจ้งให้
    อัปโหลดไฟล์ใหม่ แทนที่จะส่งต่อเข้า OCR แล้วเกิดผลลัพธ์ที่อธิบายไม่ได้
- **AC-3 (ไฟล์เกินขนาดสูงสุดที่กำหนด)**
  - **Given**: นักวิจัยเลือกไฟล์ชนิดที่รองรับ แต่ขนาดไฟล์เกินขนาดสูงสุด **5 MB ต่อไฟล์** (finalize แล้วตาม
    FR-19(3)/FR-22 เมื่อ 2026-08-23 — เดิมเป็น TBD)
  - **When**: นักวิจัยกดอัปโหลด
  - **Then**: ระบบปฏิเสธการอัปโหลดทันทีพร้อมข้อความ error ภาษาไทยแจ้งว่าไฟล์เกินขนาดที่กำหนด ในรูปแบบ
    เดียวกับ AC-1/AC-2 (ทดสอบทั้งไฟล์ขนาด 5 MB พอดี ต้องผ่าน และไฟล์เกิน 5 MB ต้องถูกปฏิเสธ)
- **AC-4 (จำนวนไฟล์เกินที่กำหนดต่อรายการ)**
  - **Given**: นักวิจัยกำลังอัปโหลดไฟล์ของใบเสร็จ 1 รายการ และเลือกไฟล์ที่ถูกต้องมากกว่า 5 ไฟล์
  - **When**: นักวิจัยกดอัปโหลด
  - **Then**: ระบบปฏิเสธไฟล์ส่วนเกิน (ไฟล์ที่เกิน 5 ไฟล์) พร้อมข้อความ error ภาษาไทยในรูปแบบเดียวกับ AC-1–AC-3
    แจ้งให้ลดจำนวนไฟล์หรือแยกเป็นรายการใหม่ และไม่ส่งไฟล์ส่วนเกินเข้าสู่กระบวนการ AI/OCR
    (ตามข้อ (4) ของ FR-19)

> หมายเหตุสถานะ: FR-19 ยังเป็น **Backlog** ใน [[backlog]] (ยังไม่ได้สร้างในแอป) — AC ข้างต้นคือเกณฑ์ของ
> พฤติกรรมเต็มตามสเปค ใช้เป็นเกณฑ์รับมอบเมื่อสร้างแล้ว

#### FR-22 (สูง) — [[20260816-01-grant-receipt-verification#4. Functional Requirements|อัปโหลดใบเสร็จแบบหลายไฟล์ต่อ 1 รายการ (Multi-file Receipt Bundle)]]

- **AC-1 (หลายไฟล์ผูก record เดียว)**
  - **Given**: ค่าใช้จ่าย 1 เรื่องมีเอกสาร 2 แผ่น (เช่น ค่ารถตู้: "ใบสำคัญรับเงิน" + "สำเนาบัตรผู้รับเงิน")
  - **When**: นักวิจัยเลือกไฟล์ทั้งสองพร้อมกันในครั้งเดียว (ไม่เกิน 5 ไฟล์) แล้วอัปโหลด
  - **Then**: ระบบสร้างใบเสร็จ **1 รายการ** ที่มีไฟล์แนบทั้งสองไฟล์ผูกอยู่ใน record เดียวกัน ไม่แยกเป็นใบเสร็จ
    สองรายการ
- **AC-2 (ข้อความเตือนให้อัปโหลดครั้งละ 1 รายการ)**
  - **Given**: นักวิจัยเปิดขั้นตอนอัปโหลดใบเสร็จ
  - **When**: ระบบแสดงหน้าอัปโหลด
  - **Then**: ระบบแสดงข้อความเตือน/คำแนะนำให้อัปโหลดครั้งละ 1 รายการ (1 ชุดเอกสารของค่าใช้จ่าย 1 เรื่อง) เท่านั้น
- **AC-3 (ใบเสร็จ 1 แผ่นหลายสินค้านับเป็นรายการเดียว)**
  - **Given**: ใบเสร็จ 1 แผ่นจากร้านเดียวกันมีสินค้าหลายชิ้น (เช่น ปากกา + ลิควิด)
  - **When**: นักวิจัยอัปโหลดไฟล์นั้น
  - **Then**: ระบบนับเป็นใบเสร็จรายการเดียว ไม่บังคับให้แยกรายการสินค้า และ AI/OCR ไม่ต้องแยกสินค้าในไฟล์เดียวออกจากกัน

> หมายเหตุสถานะ: FR-22 ยังเป็น **Backlog** ใน [[backlog]] — แอปปัจจุบันแนบไฟล์ผ่าน Google Drive ได้ (FR-32) แต่ยังไม่มี
> การบังคับเพดาน 5 ไฟล์และข้อความเตือนตามสเปค

#### NFR-01 (สูง) — [[20260816-01-grant-receipt-verification#5. Non-Functional Requirements|OCR ต้องรองรับภาษาไทยเต็มรูปแบบ]]

- **AC-1**
  - **Given**: ใบเสร็จที่มีข้อความภาษาไทยทั้งหมด (ยอดเงิน วันที่ หมวดค่าใช้จ่าย ชื่อร้าน)
  - **When**: ระบบประมวลผล OCR
  - **Then**: ระบบอ่านข้อความภาษาไทยได้ถูกต้องครบทุกช่องที่กำหนดไว้ใน FR-02 โดยไม่ต้องแปลง/พึ่งพา
    ภาษาอื่นก่อน

#### NFR-06 (สูง) — [[20260816-01-grant-receipt-verification#5. Non-Functional Requirements|เวลาในการประมวลผล OCR]]

- **AC-1**
  - **Given**: อัปโหลดใบเสร็จสำเร็จแล้ว
  - **When**: ระบบเริ่มประมวลผล OCR
  - **Then**: ระบบประมวลผลเสร็จสิ้นและแสดงผลให้นักวิจัยเห็นได้โดยไม่ค้าง/ไม่ timeout (ยังไม่มีตัวเลข
    เป้าหมายเวลาที่แน่นอน — รอกำหนดเพิ่มเติมตาม NFR-06 ก่อนกำหนดเกณฑ์ตัวเลขจริงในรอบทดสอบถัดไป)

#### NFR-07 (สูง) — [[20260816-01-grant-receipt-verification#5. Non-Functional Requirements|ปริมาณใบเสร็จที่ระบบต้องรองรับ]]

- **AC-1**
  - **Given**: นักวิจัยมีใบเสร็จจำนวนมากสะสมอยู่ในระบบ (เช่น หลายสิบใบต่อทุน)
  - **When**: นักวิจัยอัปโหลดใบเสร็จใบใหม่หรือเปิดดูรายการใบเสร็จเดิม
  - **Then**: ระบบยังทำงานได้ตามปกติไม่ล้มเหลว (ยังไม่มีตัวเลขปริมาณ/ผู้ใช้พร้อมกันที่ยืนยันแล้ว —
    รอกำหนดเพิ่มเติมตาม NFR-07)

#### NFR-08 (สูง) — [[20260816-02-pdpa-compliance#5. Non-Functional Requirements|Cross-border Data Transfer (ส่วนผู้ให้บริการ OCR, Conditional)]]

- **AC-1**
  - **Given**: ผู้ให้บริการ OCR ที่โครงการเลือกใช้จริงประมวลผลข้อมูลนอกราชอาณาจักรไทย (เงื่อนไข — ยัง

  - **Then**: ต้องมีมาตรการคุ้มครองข้อมูลตามมาตรา 28-29 ของ PDPA พร้อมใช้งานก่อนเริ่มส่งข้อมูลจริง
    (ทดสอบ/ตรวจสอบเมื่อมีการตัดสินใจ vendor แล้วเท่านั้น ปัจจุบันเป็นรายการตรวจสอบเชิง compliance

#### NFR-09 (สูง) — [[20260816-02-pdpa-compliance#5. Non-Functional Requirements|DPA กับผู้ให้บริการ OCR ภายนอก (Organizational)]]

- **AC-1**
  - **Given**: โครงการใช้ผู้ให้บริการ OCR ภายนอก

## 2. ตรวจสอบและแก้ไขข้อมูลก่อนส่งตรวจ

(อ้างอิง [[feature-list#2. ตรวจสอบและแก้ไขข้อมูลก่อนส่งตรวจ|ฟีเจอร์ที่ 2]])

#### FR-03 (สูง) — [[20260816-01-grant-receipt-verification#4. Functional Requirements|ตรวจสอบ/แก้ไขข้อมูลจาก OCR ก่อนส่งตรวจ]]

- **AC-1 (Happy path — ไม่ต้องแก้ไข)**
  - **Given**: OCR อ่านข้อมูลใบเสร็จได้ถูกต้องครบถ้วน (FR-02)
  - **When**: นักวิจัยตรวจทานข้อมูลแล้วกดยืนยันโดยไม่แก้ไขอะไร
  - **Then**: ระบบส่งข้อมูลชุดเดิมที่ OCR อ่านได้เข้าสู่ Rule Engine (FR-04) ต่อไป
- **AC-2 (แก้ไขค่าที่ OCR อ่านผิด)**
  - **Given**: OCR อ่านยอดเงิน/วันที่/หมวดค่าใช้จ่าย/ชื่อร้านผิดพลาดบางส่วน
  - **When**: นักวิจัยแก้ไขค่าที่ผิดให้ถูกต้องแล้วกดยืนยันเพื่อส่งตรวจ
  - **Then**: ระบบใช้ค่าที่นักวิจัยแก้ไขแล้ว (ไม่ใช่ค่าดิบจาก OCR) เป็น input เข้าสู่ Rule Engine
    (FR-04)

## 3. ตรวจสอบใบเสร็จด้วย Rule Engine พร้อมคำอธิบายจาก LLM

(อ้างอิง [[feature-list#3. ตรวจสอบใบเสร็จด้วย Rule Engine พร้อมคำอธิบายจาก LLM|ฟีเจอร์ที่ 3]])

#### FR-04 (สูง) — [[20260816-01-grant-receipt-verification#4. Functional Requirements|ตรวจใบเสร็จด้วย Rule-based Engine]]

> สถานะที่สร้างแล้ว: FR-04 "เสร็จบางส่วน" ใน [[backlog]] (รายละเอียดการตัดสินแต่ละด้านอยู่ที่ฟีเจอร์ 14–16, 18, 20)
> AC ด้านล่างครอบคลุมด้านระเบียบ/วงเงินต่อหมวดและเงื่อนไขตั้งต้นของการตรวจ

- **AC-1 (ผ่านเกณฑ์)**
  - **Given**: ข้อมูลใบเสร็จที่ยืนยันแล้ว (หลัง FR-03) อยู่ในหมวดค่าใช้จ่ายที่มีกฎของแหล่งทุนที่โครงการสังกัด
    ยอดไม่เกินเพดานของกฎนั้น และไม่มีข้อค้นพบด้านอื่น (ประมาณการ/ใบสรุป/เอกสารแนบ)
  - **When**: ระบบส่งข้อมูลเข้าตรวจกับ Rule Engine
  - **Then**: Rule Engine ตัดสินสถานะ "ผ่าน" (ไม่ใช่ LLM เป็นผู้ตัดสิน) ด้วยรหัสเหตุผล `WITHIN_CAP`
- **AC-2 (ต้องแก้ไข — ยอดเกินเพดานทั้งก้อน)**
  - **Given**: หมวดค่าใช้จ่ายมีเพดานแบบทั้งยอด (ไม่มีหน่วย เช่น วัสดุสำนักงาน ไม่เกิน 5,000 บาท) และยอดใบเสร็จมากกว่าเพดานนั้น
  - **When**: ระบบส่งข้อมูลเข้าตรวจกับ Rule Engine
  - **Then**: Rule Engine ตัดสินสถานะ "ต้องแก้ไข" (`AMOUNT_EXCEEDS_CAP`) — ยอดเท่ากับเพดานพอดีต้อง "ผ่าน"
    เพดานแบบเหมาจ่าย (เช่น แท็กซี่ 700 บาท) เปรียบเทียบด้วยวิธีเดียวกัน
- **AC-3 (ไม่เข้าเงื่อนไข — หมวดที่ระเบียบไม่อนุญาต/ไม่มีกฎ)**
  - **Given**: ใบเสร็จอยู่ในหมวดที่แหล่งทุนนั้นไม่มีกฎรองรับ (เช่น "ค่าตอบแทนคณะผู้วิจัย" ซึ่งคู่มือไม่สนับสนุนให้ตั้งงบประมาณ)
  - **When**: ระบบส่งข้อมูลเข้าตรวจกับ Rule Engine
  - **Then**: Rule Engine ตัดสินสถานะ "ไม่เข้าเงื่อนไข" (`CATEGORY_NOT_IN_RULES`) และไม่ตรวจเอกสารแนบต่อ
    (ดู FR-27 AC-10)
- **AC-4 (ไม่เข้าเงื่อนไข — โครงการไม่มีแหล่งทุน/ไม่มีเวอร์ชันกฎที่ใช้งานอยู่)**
  - **Given**: โครงการของใบเสร็จไม่มีแหล่งทุนที่ผูกไว้ หรือแหล่งทุนนั้นไม่มีเวอร์ชันกฎที่ active
  - **When**: ระบบส่งข้อมูลเข้าตรวจกับ Rule Engine
  - **Then**: Rule Engine ตัดสินสถานะ "ไม่เข้าเงื่อนไข" (`NO_FUND_SOURCE` / `NO_ACTIVE_RULE_VERSION`) พร้อมคำอธิบาย
    ไม่ปล่อยผ่านและไม่ล้มเหลวเงียบ
- **AC-5 (ต้องแก้ไข — ยอดไม่ถูกต้อง)**
  - **Given**: ยอดเงินที่ส่งตรวจเป็น 0 ติดลบ หรือไม่ใช่ตัวเลข
  - **When**: ระบบส่งข้อมูลเข้าตรวจกับ Rule Engine
  - **Then**: Rule Engine ตัดสินสถานะ "ต้องแก้ไข" (`INVALID_AMOUNT`) แทนการให้ผ่าน
- **AC-6 (หมวดแบบต่อหน่วย/ตามข้อเสนอโครงการ ที่ไม่มีเพดานตายตัว)**
  - **Given**: หมวดมีประเภทอัตรา "ต่อหน่วย" (เช่น ค่าพาหนะส่วนตัว 4 บาท/กม.) หรือ "ตามข้อเสนอโครงการ" และไม่มีข้อมูลประมาณการ
    มาช่วยตรวจ
  - **When**: ระบบส่งข้อมูลเข้าตรวจกับ Rule Engine
  - **Then**: ผลเป็น "ผ่าน" ตามหมวด แต่ถูกทำเครื่องหมายว่า**ยังไม่ได้ตรวจยืนยันอัตโนมัติ** (`autoVerified = false`,
    `NO_FIXED_CAP`) พร้อมแสดงอัตรา/หมายเหตุให้คนตรวจต่อ ไม่แสดงว่าตรวจจริงแล้ว
- **AC-7 (ใช้กฎเวอร์ชันที่ active ณ วันที่ตรวจ)**
  - **Given**: แหล่งทุนมีเวอร์ชันกฎที่ active อยู่ 1 เวอร์ชัน ณ เวลาที่ตรวจ
  - **When**: ระบบโหลดชุดกฎเพื่อตรวจใบเสร็จ
  - **Then**: Rule Engine ใช้กฎทุกรายการของเวอร์ชัน active ของแหล่งทุนที่โครงการสังกัดเท่านั้น (ไม่ใช้เวอร์ชันเก่า และไม่ใช้
    ระเบียบของแหล่งทุนอื่น)
- **AC-8 (ต้องแก้ไข — เอกสารประกอบไม่ครบ)**
  - **Given**: ข้อมูลใบเสร็จเข้าเงื่อนไขหมวด/วงเงิน แต่ขาดเอกสารประกอบที่ระเบียบกำหนดให้ต้องมี
  - **When**: ระบบส่งข้อมูลเข้าตรวจกับ Rule Engine
  - **Then**: Rule Engine ตัดสินสถานะ "ต้องแก้ไข" (รายละเอียดการตรวจเอกสารแนบดู FR-27)

#### FR-05 (สูง) — [[20260816-01-grant-receipt-verification#4. Functional Requirements|LLM สรุปผลตรวจเป็นภาษาที่เข้าใจง่าย]]

- **AC-1**
  - **Given**: Rule Engine ตัดสินผลใบเสร็จแล้ว (ผ่าน / ต้องแก้ไข / ต้องชี้แจง/ขออนุมัติ / ไม่เข้าเงื่อนไข)
  - **When**: ระบบแสดงผลให้นักวิจัยเห็น
  - **Then**: AI แปลผลลัพธ์จาก Rule Engine เป็นภาษาไทยที่ไม่ใช้ศัพท์การเงิน/บัญชีโดยไม่มีคำอธิบาย
    ประกอบ พร้อมคำแนะนำแก้ไขที่เป็นรูปธรรม (ถ้าสถานะไม่ผ่าน) — AI ไม่เปลี่ยนแปลงผลตัดสินที่มาจาก
    Rule Engine
- **AC-2 (ไม่มี AI หรือเรียก AI ล้มเหลว)**
  - **Given**: ไม่ได้ตั้งค่า AI หรือการเรียก AI ล้มเหลว
  - **When**: ระบบแสดงผลตรวจให้นักวิจัยเห็น
  - **Then**: ระบบยังแสดงสถานะและคำอธิบายจากกฎของ Rule Engine ให้ครบ (ไม่ใช่หน้าว่างหรือ error) และใบเสร็จยังบันทึกได้
    (รายละเอียดพฤติกรรมของ agent ดู FR-31)

#### FR-06 (สูง) — [[20260816-01-grant-receipt-verification#4. Functional Requirements|แสดงสถานะใบเสร็จรายใบพร้อมเหตุผลอ้างอิงระเบียบ]]

- **AC-1**
  - **Given**: ใบเสร็จผ่านการตรวจจาก Rule Engine แล้วไม่ว่าผลจะเป็นสถานะใด
  - **When**: นักวิจัยเปิดดูรายละเอียดใบเสร็จนั้น
  - **Then**: ระบบแสดงสถานะ (ผ่าน / ต้องแก้ไข / ต้องชี้แจง/ขออนุมัติ / ไม่เข้าเงื่อนไข) พร้อมอ้างอิงข้อระเบียบที่ใช้ตัดสิน
    อย่างชัดเจน เพื่อรองรับการโต้แย้ง (dispute) (กติกาลำดับความรุนแรงของสถานะดู FR-25)

#### NFR-01 (สูง) — [[20260816-01-grant-receipt-verification#5. Non-Functional Requirements|คำอธิบายจาก LLM ต้องเป็นภาษาไทย]]

- **AC-1**
  - **Given**: LLM กำลังสร้างคำอธิบายผลตรวจ
  - **When**: ระบบแสดงคำอธิบายให้นักวิจัยเห็น
  - **Then**: ข้อความทั้งหมดเป็นภาษาไทย ไม่มีส่วนที่เป็นภาษาอังกฤษปนโดยไม่จำเป็น

#### NFR-02 (สูง) — [[20260816-01-grant-receipt-verification#5. Non-Functional Requirements|ภาษาที่ใช้ต้องเข้าใจง่ายสำหรับคนไม่มีพื้นฐานการเงิน]]

- **AC-1**
  - **Given**: ผลตรวจมีสถานะ "ต้องแก้ไข" "ต้องชี้แจง/ขออนุมัติ" หรือ "ไม่เข้าเงื่อนไข"
  - **When**: LLM อธิบายเหตุผล
  - **Then**: คำอธิบายไม่ใช้ศัพท์เฉพาะทางบัญชี-การเงินโดยไม่มีคำอธิบายประกอบ ผู้ใช้ที่ไม่มีพื้นฐาน
    การเงินอ่านแล้วเข้าใจสาเหตุและวิธีแก้ไขได้

#### NFR-03 (สูง) — [[20260816-01-grant-receipt-verification#5. Non-Functional Requirements|Explainability]]

- **AC-1**
  - **Given**: ผลตรวจจาก Rule Engine ทุกกรณี ไม่ว่าสถานะใด
  - **When**: ระบบแสดงผลให้นักวิจัยเห็น
  - **Then**: ต้องมีข้อระเบียบอ้างอิงกำกับเสมอ ห้ามมีกรณีที่แสดงผลโดยไม่มีเหตุผลอ้างอิงย้อนกลับไปยัง
    ระเบียบที่ใช้ตัดสิน

#### NFR-04 (สูง) — [[20260816-01-grant-receipt-verification#5. Non-Functional Requirements|Audit Trail (ส่วนผลตรวจต่อใบเสร็จ)]]

- **AC-1**
  - **Given**: ใบเสร็จถูกตรวจโดย Rule Engine เสร็จสิ้นแล้ว
  - **When**: มีการเปลี่ยนแปลงระเบียบในภายหลัง (ผ่าน FR-11)
  - **Then**: ระบบยังสามารถตรวจสอบย้อนหลังได้ว่าใบเสร็จนั้นถูกตรวจด้วยกฎข้อใด อ้างอิงระเบียบเวอร์ชัน
    ใด และผลลัพธ์คืออะไร ณ ตอนที่ตรวจ
- **AC-2 (ข้อมูลตรวจย้อนได้ในตัวใบเสร็จ)**
  - **Given**: ใบเสร็จถูกบันทึกหลังผ่านการตรวจโดย Rule Engine
  - **When**: เปิดดูข้อมูลการตรวจที่บันทึกไว้กับใบเสร็จนั้น (`ruleCheck`)
  - **Then**: พบเวอร์ชัน engine, รหัสเหตุผล, สถานะตรวจอัตโนมัติ, แหล่งทุน, เวอร์ชันกฎ และรหัสกฎที่ใช้ตัดสิน
    (ใบเสร็จที่สร้างก่อน 2026-11-14 ไม่มีข้อมูลนี้ ไม่นับเป็น defect)

#### NFR-06 (สูง) — [[20260816-01-grant-receipt-verification#5. Non-Functional Requirements|เวลาในการตรวจ Rule Engine]]

- **AC-1**
  - **Given**: ข้อมูลใบเสร็จที่ยืนยันแล้วถูกส่งเข้า Rule Engine
  - **When**: ระบบประมวลผลการตรวจ
  - **Then**: ระบบตรวจเสร็จสิ้นและแสดงผลได้โดยไม่ค้าง/ไม่ timeout (ยังไม่มีตัวเลขเป้าหมายเวลาที่แน่นอน
    — รอกำหนดเพิ่มเติมตาม NFR-06)

#### NFR-08 (สูง) — [[20260816-02-pdpa-compliance#5. Non-Functional Requirements|Cross-border Data Transfer (ส่วนผู้ให้บริการ LLM, Conditional)]]

- **AC-1**
  - **Given**: ผู้ให้บริการ LLM ที่โครงการเลือกใช้จริงประมวลผลข้อมูลนอกราชอาณาจักรไทย (เงื่อนไข — ยัง
    ไม่ตัดสินใจ vendor)
  - **When**: ระบบส่งข้อมูลผลตรวจ/ข้อมูลใบเสร็จที่เกี่ยวข้องไปให้ LLM ประมวลผล
  - **Then**: ต้องมีมาตรการคุ้มครองข้อมูลตามมาตรา 28-29 ก่อนเริ่มส่งข้อมูลจริง (ตรวจสอบเมื่อมีการ
    ตัดสินใจ vendor แล้วเท่านั้น)

#### NFR-09 (สูง) — [[20260816-02-pdpa-compliance#5. Non-Functional Requirements|DPA กับผู้ให้บริการ LLM ภายนอก (Organizational)]]

- **AC-1**
  - **Given**: โครงการใช้ผู้ให้บริการ LLM ภายนอก
  - **When**: เริ่มใช้งานบริการ LLM จริงใน production
  - **Then**: ต้องมีข้อตกลง Data Processing Agreement ระหว่างมหาวิทยาลัยกับผู้ให้บริการนั้น
    (ตรวจสอบระดับ organizational/เอกสาร)

#### NFR-13 (สูง) — [[20261117-01-implemented-rule-engine-ai-and-admin#3. Non-Functional Requirements|Accessibility (ผู้ใช้สูงอายุ, ตัวอักษร ≥16px, โหมดกลางคืน, สถานะไม่พึ่งสีอย่างเดียว)]]

- **AC-1 (ขนาดตัวอักษรและพื้นที่กด)**
  - **Given**: นักวิจัยเปิดหน้าใดหน้าหนึ่งของแอป (เดสก์ท็อปและมือถือ)
  - **When**: ตรวจขนาดองค์ประกอบ
  - **Then**: ข้อความเนื้อหา ≥ 16px, ข้อความ UI ≥ 14px, ช่องกรอกและปุ่มสูงอย่างน้อย 44px และหน้าใช้งานได้บนจอมือถือ
    (เมนูเปลี่ยนเป็นแถบด้านล่าง ตารางประมาณการเป็นการ์ด)
- **AC-2 (สถานะไม่พึ่งสีอย่างเดียว)**
  - **Given**: ใบเสร็จมีสถานะต่างกันทั้ง 4 ระดับ
  - **When**: นักวิจัยดูชิปสถานะและกล่องคำอธิบายผลตรวจ
  - **Then**: ทุกสถานะมีทั้งสี ไอคอน (ถูก/ดินสอ/เครื่องหมายคำถาม/กากบาท) และข้อความกำกับ — ผู้ที่แยกสีไม่ได้ยังแยกสถานะได้ครบ 4 ระดับ
- **AC-3 (โหมดสว่าง/มืด/ตามระบบ และสีเน้น)**
  - **Given**: ผู้ใช้เปิดแอปครั้งแรกบนเครื่องนั้น
  - **When**: เปลี่ยนโหมด (สว่าง/มืด/ตามระบบ) และสีเน้นจากตัวเลือกบนแถบนำทาง แล้วโหลดหน้าใหม่
  - **Then**: ค่าเริ่มต้นเป็นโหมดสว่าง ค่าที่เลือกถูกจำต่อเครื่องและไม่เกิดหน้าวูบผิดโหมด ตัวเลือกสีเน้นไม่มีโทนเขียว/เหลือง/ส้ม/แดง
    ที่อาจสับสนกับสีสถานะผลตรวจ และอ่านข้อความได้ชัดในโหมดมืด
- **AC-4 (ลำดับหัวข้อไม่ข้ามระดับ)**
  - **Given**: นักวิจัยเปิดหน้าใดหน้าหนึ่งของแอป
  - **When**: ตรวจโครงสร้างหัวข้อ
  - **Then**: ลำดับหัวข้อเป็น h1 → h2 → h3 ไม่ข้ามระดับ รวมถึงหัวข้อที่สร้างจาก JavaScript

## 4. แก้ไขและส่งใบเสร็จที่ไม่ผ่านตรวจซ้ำ

(อ้างอิง [[feature-list#4. แก้ไขและส่งใบเสร็จที่ไม่ผ่านตรวจซ้ำ|ฟีเจอร์ที่ 4]])

#### FR-07 (สูง) — [[20260816-01-grant-receipt-verification#4. Functional Requirements|แก้ไขและอัปโหลดใบเสร็จซ้ำ]]

> **สถานะการสร้าง (อัปเดต 2026-11-26):** FR-07 สร้างแล้วในรูป "ส่งฉบับแก้ไข" — ปุ่มบนหน้า `receipts.html` และ
> `budget.html` เปิด `new-receipt.html?projectId=…&revise=receiptNNN` มี 2 โหมด (เพิ่มเอกสารที่ขาด / แทนที่ทั้งชุด)
> **ไม่มีขั้นตอนให้นักวิจัยแก้ช่องข้อมูล (ยอดเงิน/วันที่/หมวด/ผู้ขาย) ด้วยมือ** (ตัดออกตั้งแต่ 2026-11-24 — AC-1 เดิม
> "แก้ไขข้อมูลเดิมแล้วส่งซ้ำ" จึงถูกแทนที่) ข้อจำกัดที่ทราบ: ภาพถ่ายการตรวจรับพัสดุตรวจจากข้อความ OCR ไม่ได้ ฉบับแก้ไขที่แนบ
> ภาพถ่ายจึงยังรายงานว่า "ไม่พบภาพถ่ายตรวจรับ" (เจ้าของโครงการเลื่อนไว้ก่อน — บันทึกเป็นข้อจำกัด ไม่ใช่เกณฑ์ที่ผ่าน)

- **AC-1 (ปุ่ม "ส่งฉบับแก้ไข" แสดงเฉพาะใบที่ไม่ผ่าน)**
  - **Given**: นักวิจัยเปิดหน้า "ใบเสร็จของฉัน" หรือ "ประมาณการและใบเสร็จ" ที่มีใบเสร็จหลายสถานะ
  - **When**: ดูรายการใบเสร็จแต่ละใบ
  - **Then**: ใบที่สถานะ "ต้องแก้ไข" "ต้องชี้แจง/ขออนุมัติ" หรือ "ไม่เข้าเงื่อนไข" มีปุ่ม "ส่งฉบับแก้ไข" ที่เปิด
    `new-receipt.html?projectId=…&revise=receiptNNN` ส่วนใบที่ "ผ่าน" ไม่มีปุ่มนี้
- **AC-2 (หน้าฉบับแก้ไขแสดงผลเดิมและบังคับแนบไฟล์)**
  - **Given**: นักวิจัยเปิดหน้าฉบับแก้ไขของใบเสร็จที่ไม่ผ่าน
  - **When**: หน้าโหลดเสร็จ
  - **Then**: แสดงสถานะเดิม ยอดเงิน/วันที่/หมวด/ผู้ขาย และคำแนะนำเดิม, ล็อกช่องเลือกโครงการ, เติมยอดในใบสรุป
    (ไม่บังคับ) ให้ล่วงหน้า, ให้เลือกโหมด "เพิ่มเอกสารที่ขาด" (ค่าเริ่มต้น) หรือ "แทนที่ทั้งชุด" และกดส่งไม่ได้
    จนกว่าจะแนบไฟล์อย่างน้อย 1 ไฟล์
- **AC-3 (โหมด "เพิ่มเอกสารที่ขาด")**
  - **Given**: อยู่ในหน้าฉบับแก้ไขโหมด "เพิ่มเอกสารที่ขาด" และแนบไฟล์ใหม่แล้ว
  - **When**: กดส่ง
  - **Then**: ระบบ OCR เฉพาะไฟล์ใหม่ แล้วรวมกับข้อความ OCR และผลจำแนกประเภทเอกสารที่เก็บไว้ของไฟล์เดิม ตรวจใหม่ด้วย
    Rule Engine/LLM ชุดเดียวกับการอัปโหลดปกติ โดยคงยอดเงิน/วันที่/หมวด/ผู้ขายจากใบเดิม (ไม่อ่านใหม่)
- **AC-4 (โหมด "แทนที่ทั้งชุด")**
  - **Given**: อยู่ในหน้าฉบับแก้ไขโหมด "แทนที่ทั้งชุด" และแนบไฟล์ใหม่แล้ว
  - **When**: กดส่งและอัปโหลดไฟล์ใหม่สำเร็จ
  - **Then**: ระบบอ่านและตรวจจากไฟล์ใหม่ทั้งหมดเต็มกระบวนการ ระเบียน `files` เดิมถูกทำเครื่องหมาย `supersededAt` +
    `supersededByRevision` (หลังอัปโหลดไฟล์ใหม่สำเร็จเท่านั้น) และถูกซ่อนในหน้าใบเสร็จ/ประมาณการ/จำนวนไฟล์ของ
    Admin ส่วนไฟล์ใน Drive ยังคงอยู่
- **AC-5 (อัปเดตใบเดิมในที่เดิม ไม่นับยอดซ้ำ และเก็บประวัติ)**
  - **Given**: ส่งฉบับแก้ไขสำเร็จ (ทั้งสองโหมด)
  - **When**: ระบบบันทึกผลตรวจใหม่
  - **Then**: ใช้เอกสารและรหัสใบเสร็จเดิม (ไม่สร้างใบใหม่) การตรวจประมาณการหักยอดเดิมของใบนี้ออกจากรายการเดิมก่อน
    (ยอดใช้ไปไม่ถูกนับซ้ำ) ผลก่อนหน้าถูกต่อท้าย `verdictHistory` (`kind: "revision"`, เลขครั้ง, โหมด)
    ตั้ง `revisionCount`/`revisedAt` ระเบียน `files` ใหม่มี `revision` หน้าจอแสดง "แก้ไขแล้ว n ครั้ง" และผลขั้นที่ 3
    แสดง "ฉบับแก้ไขครั้งที่ n · ผลก่อนแก้ไข: …" ปุ่ม "อัปโหลดใบเสร็จใหม่" หลังส่งไปหน้าอัปโหลดปกติ (ไม่ใช่โหมดแก้ไข)
- **AC-6 (กรณีที่ส่งฉบับแก้ไขไม่ได้)**
  - **Given**: เปิด URL `revise=` ของใบที่ "ผ่านแล้ว" หรือรหัสใบเสร็จที่ไม่มีอยู่
  - **When**: หน้าโหลด
  - **Then**: ใบที่ผ่านแล้ว: แสดงคำเตือน "ใบเสร็จ … ผ่านแล้ว ไม่ต้องส่งฉบับแก้ไข" และปุ่มส่งกดไม่ได้; รหัสที่ไม่มีในโครงการนี้: แสดงคำเตือน "ไม่พบใบเสร็จ … ในโครงการนี้ — อัปโหลดเป็นใบเสร็จใหม่แทน" แล้วหน้าทำงานเป็นการอัปโหลดใบเสร็จใหม่ตามปกติ (ไม่แก้ใบใดเลย)
- **AC-7 (หน้าอัปโหลดปกติไม่ปนกับโหมดแก้ไข)**
  - **Given**: นักวิจัยเปิด `new-receipt.html` โดยไม่มีพารามิเตอร์ `revise`
  - **When**: หน้าโหลด
  - **Then**: ไม่แสดงการ์ดฉบับแก้ไข/ตัวเลือกโหมด และทำงานเป็นการอัปโหลดใบเสร็จใหม่ตามปกติ (กันบั๊กที่การ์ดโผล่
    ผิดที่ ซึ่งแก้ด้วยกฎ CSS `[hidden]{display:none!important}`)

#### FR-08 (กลาง) — [[20260816-01-grant-receipt-verification#4. Functional Requirements|หน้าสรุปภาพรวมใบเสร็จของโครงการ (Dashboard)]]

- **AC-1 (มีใบเสร็จหลายสถานะ)**
  - **Given**: โครงการวิจัยของนักวิจัยมีใบเสร็จหลายใบ สถานะแตกต่างกัน (ผ่าน/ต้องแก้ไข/ต้องชี้แจง-ขออนุมัติ/ไม่เข้าเงื่อนไข)
  - **When**: นักวิจัยเปิด Dashboard ของโครงการนั้น
  - **Then**: ระบบแสดงจำนวนใบเสร็จแยกตามสถานะทั้ง 4 ระดับให้ถูกต้องตรงกับข้อมูลจริง
- **AC-2 (ยังไม่มีใบเสร็จเลย)**
  - **Given**: โครงการวิจัยที่เพิ่งเริ่มต้น ยังไม่มีใบเสร็จใดถูกอัปโหลดเลย
  - **When**: นักวิจัยเปิด Dashboard ของโครงการนั้น
  - **Then**: ระบบแสดงสถานะว่างเปล่า (จำนวนทุกสถานะเป็น 0) ไม่แสดงข้อมูลผิดพลาด

## 6. แจ้งเตือนใบเสร็จที่มีปัญหาค้างอยู่

(อ้างอิง [[feature-list#6. แจ้งเตือนใบเสร็จที่มีปัญหาค้างอยู่|ฟีเจอร์ที่ 6]])

#### FR-09 (กลาง) — [[20260816-01-grant-receipt-verification#4. Functional Requirements|แจ้งเตือนใบเสร็จที่มีปัญหายังไม่แก้ไข]]

- **AC-1 (มีใบเสร็จค้างแก้ไข)**
  - **Given**: นักวิจัยมีใบเสร็จสถานะ "ต้องแก้ไข" "ต้องชี้แจง/ขออนุมัติ" หรือ "ไม่เข้าเงื่อนไข" ที่ยังไม่ได้รับการแก้ไข
  - **When**: ระบบตรวจพบใบเสร็จดังกล่าวยังค้างอยู่
  - **Then**: ระบบแจ้งเตือนนักวิจัยว่ามีใบเสร็จที่มีปัญหายังไม่ได้แก้ไข (ไม่เกี่ยวข้องกับกำหนดเวลาส่ง
    หลักฐานรายทุน ซึ่งตัดออกจากขอบเขต MVP นี้แล้ว)
- **AC-2 (ไม่มีใบเสร็จค้างแก้ไข)**
  - **Given**: ใบเสร็จทั้งหมดของนักวิจัยผ่านการตรวจแล้ว ไม่มีสถานะ "ต้องแก้ไข"/"ต้องชี้แจง/ขออนุมัติ"/"ไม่เข้าเงื่อนไข" ค้างอยู่
  - **When**: ระบบตรวจสอบสถานะใบเสร็จ
  - **Then**: ระบบไม่ส่งการแจ้งเตือนใดๆ เกี่ยวกับใบเสร็จมีปัญหา

## 7. Export รายงานสรุปใบเสร็จที่ผ่านตรวจแล้ว

(อ้างอิง [[feature-list#7. Export รายงานสรุปใบเสร็จที่ผ่านตรวจแล้ว|ฟีเจอร์ที่ 7]])

#### FR-10 (สูง) — [[20260816-01-grant-receipt-verification#4. Functional Requirements|Export รายงานสรุปใบเสร็จที่ผ่านตรวจแล้ว]]

- **AC-1 (มีใบเสร็จผ่านตรวจพร้อม export)**
  - **Given**: ทุนวิจัยของนักวิจัยมีใบเสร็จอย่างน้อย 1 ใบสถานะ "ผ่าน"
  - **When**: นักวิจัยกด Export รายงานสรุปของทุนนั้น
  - **Then**: ระบบสร้างไฟล์รายงานสรุปใบเสร็จที่ผ่านตรวจแล้วให้ดาวน์โหลด เพื่อนำไปยื่นเจ้าหน้าที่การเงิน
    ของมหาวิทยาลัยเอง (นอกระบบ)
- **AC-2 (ใบเสร็จที่ export แล้วถูกล็อกไม่ให้ลบเอง)**
  - **Given**: ใบเสร็จถูกรวมอยู่ในรายงานที่ export ไปแล้วครั้งหนึ่ง
  - **When**: นักวิจัยพยายามลบใบเสร็จนั้นเองผ่าน UI (ดู FR-18)
  - **Then**: ระบบล็อกไม่ให้ลบใบเสร็จนั้นผ่าน UI อีกต่อไป (เชื่อมโยงกับเงื่อนไขใน FR-18)

> หมายเหตุ: กรณีทุนวิจัยยังไม่มีใบเสร็จสถานะ "ผ่าน" เลยแม้แต่ใบเดียว แล้วนักวิจัยพยายามกด Export —
> เดิมสเปคยังไม่ได้ระบุพฤติกรรมของระบบไว้ชัดเจน ปัจจุบัน**ปิดแล้ว**ด้วย FR-21 (ดูด้านล่าง) ซึ่ง
> finalize เป็นรหัส FR ใหม่แล้ว

#### FR-21 (สูง) — [[20260816-01-grant-receipt-verification#4. Functional Requirements|ป้องกันการ Export รายงานเมื่อยังไม่มีใบเสร็จสถานะผ่าน]]

- **AC-1 (ไม่มีใบเสร็จสถานะผ่านเลย — ปิดปุ่ม Export)**
  - **Given**: ทุนวิจัยของนักวิจัยยังไม่มีใบเสร็จสถานะ "ผ่าน" (FR-06) แม้แต่ใบเดียว
  - **When**: นักวิจัยเปิดดูหน้า Export/Dashboard ของทุนนั้น
  - **Then**: ระบบปิดการใช้งาน (disable) ปุ่ม Export ของทุนนั้นไว้ก่อน พร้อมข้อความแจ้งเหตุผลที่กด
    ไม่ได้ (เช่น "ยังไม่มีใบเสร็จที่ผ่านการตรวจสำหรับทุนนี้") แทนการปล่อยให้กดแล้วได้ไฟล์รายงานเปล่า
    หรือ error ที่ไม่มีคำอธิบาย
- **AC-2 (มีใบเสร็จสถานะผ่านอย่างน้อย 1 ใบ — ปุ่ม Export ใช้งานได้ตามปกติ)**
  - **Given**: ทุนวิจัยมีใบเสร็จอย่างน้อย 1 ใบสถานะ "ผ่าน"
  - **When**: นักวิจัยเปิดดูหน้า Export/Dashboard ของทุนนั้น
  - **Then**: ปุ่ม Export ใช้งานได้ตามปกติ ไม่ถูกปิดการใช้งาน (เชื่อมกับ FR-10 AC-1)

## 8. นำเข้า/อัปเดตระเบียบของแหล่งทุนเข้าสู่ Rule Engine (Admin)

(อ้างอิง [[feature-list#8. นำเข้า/อัปเดตระเบียบของแหล่งทุนเข้าสู่ Rule Engine (Admin)|ฟีเจอร์ที่ 8]])

> สถานะที่สร้างแล้ว: FR-11 "เสร็จบางส่วน" — Admin เพิ่ม/ลบแหล่งทุนและแก้กฎรายหมวดผ่านหน้าจอ (ฟีเจอร์ 22) และผลักชุดกฎเข้าระบบจริง
> ผ่านปุ่มอัปเดตระเบียบ (ฟีเจอร์ 20) ยังไม่มี UI ประวัติเวอร์ชันและยังไม่มีการนำเข้าจากไฟล์ระเบียบโดยตรง

#### FR-11 (สูง) — [[20260816-01-grant-receipt-verification#4. Functional Requirements|นำเข้า/อัปเดตระเบียบทุนวิจัยเข้าสู่ Rule Engine (ต่อแหล่งทุนแต่ละแหล่ง)]]

- **AC-1**
  - **Given**: Admin เข้าสู่ระบบด้วยบทบาท Admin และมีระเบียบของแหล่งทุนแหล่งหนึ่งฉบับใหม่ที่ต้องนำเข้า
  - **When**: Admin นำเข้า/อัปเดตกฎ/เงื่อนไขจากระเบียบใหม่เข้าสู่ Rule Engine ของแหล่งทุนนั้น
  - **Then**: Rule Engine ใช้กฎเวอร์ชันใหม่ตรวจใบเสร็จของโครงการที่สังกัดแหล่งทุนนั้นตั้งแต่จุดนี้เป็นต้นไป
    โดยไม่ต้อง retrain LLM และไม่กระทบแหล่งทุนอื่น
- **AC-2 (จัดการกฎรายหมวดผ่านหน้าจอ)**
  - **Given**: Admin เปิดหน้าจัดการแหล่งทุนของแหล่งทุนหนึ่ง
  - **When**: Admin เพิ่ม แก้ไข และลบกฎรายหมวด โดยเลือกประเภทอัตรา (เพดานตามจริง / เหมาจ่าย / ต่อหน่วย / ตามข้อเสนอโครงการ)
    ระบุจำนวนเงิน หน่วย เอกสารที่ต้องมี และหมายเหตุ
  - **Then**: การเปลี่ยนแปลงบันทึกในกฎของแหล่งทุนนั้น และใบเสร็จที่ส่งตรวจหลังจากนั้นใช้กฎที่แก้แล้ว (รายละเอียดสิทธิ์ ดู FR-33)

#### NFR-04 (สูง) — [[20260816-01-grant-receipt-verification#5. Non-Functional Requirements|Audit Trail (ส่วนเวอร์ชันระเบียบที่นำเข้า)]]

- **AC-1**
  - **Given**: Admin นำเข้า/อัปเดตระเบียบใหม่เข้าสู่ Rule Engine สำเร็จ
  - **When**: ระบบบันทึกการเปลี่ยนแปลง
  - **Then**: ระบบบันทึกเวอร์ชันระเบียบที่นำเข้าไว้ใน Audit Trail เพื่อรองรับการตรวจสอบย้อนหลังเมื่อ
    ระเบียบมีการเปลี่ยนแปลงตามเวลา

## 9. จำกัดสิทธิ์การเข้าถึงข้อมูลตามเจ้าของ (Access Control)

(อ้างอิง [[feature-list#9. จำกัดสิทธิ์การเข้าถึงข้อมูลตามเจ้าของ (Access Control)|ฟีเจอร์ที่ 9]])

#### FR-12 (สูง) — [[20260816-01-grant-receipt-verification#4. Functional Requirements|จำกัดสิทธิ์การเข้าถึงข้อมูลใบเสร็จตามเจ้าของ]]

- **AC-1 (นักวิจัยเห็นเฉพาะของตนเอง)**
  - **Given**: นักวิจัย A และนักวิจัย B ต่างมีโครงการวิจัยและใบเสร็จของตนเองในระบบ
  - **When**: นักวิจัย A เข้าสู่ระบบและเปิดดูรายการโครงการ/ใบเสร็จ
  - **Then**: นักวิจัย A เห็นเฉพาะโครงการ/ใบเสร็จของตนเองเท่านั้น ไม่เห็นข้อมูลของนักวิจัย B
- **AC-2 (นักวิจัยพยายามเข้าถึงข้อมูลของผู้อื่นโดยตรง)**
  - **Given**: นักวิจัย A ทราบ/เดา ID ใบเสร็จหรือโครงการของนักวิจัย B
  - **When**: นักวิจัย A พยายามเข้าถึงข้อมูลนั้นโดยตรง (เช่น ผ่าน URL/รหัสอ้างอิง)
  - **Then**: ระบบปฏิเสธการเข้าถึงและไม่แสดงข้อมูลของนักวิจัย B ให้นักวิจัย A เห็น
- **AC-3 (Admin อ่านข้อมูลใบเสร็จของนักวิจัยได้แบบอ่านอย่างเดียว — แก้ตาม FR-33)**
  - **Given**: Admin เข้าสู่ระบบด้วยบทบาท Admin (กลับคำตัดสินใจเดิม 2026-09-10 ที่เคยห้าม Admin เข้าถึง)
  - **When**: Admin เปิดดูข้อมูลใบเสร็จของนักวิจัยคนใดคนหนึ่ง (ผ่านหน้า Admin Dashboard)
  - **Then**: ระบบแสดงรายละเอียดใบเสร็จและเจ้าของให้ได้ในโหมดอ่านอย่างเดียว — Admin เขียน/แก้/ลบข้อมูลใบเสร็จของผู้อื่นไม่ได้
    (ดู FR-33 AC-2) ส่วนนักวิจัยด้วยกันยังไม่เห็นข้อมูลของกันและกัน (AC-1/AC-2)

#### FR-33 (สูง) — [[20261117-01-implemented-rule-engine-ai-and-admin#2. Functional Requirements|Admin อ่านใบเสร็จทุกคนแบบอ่านอย่างเดียว และจัดการกฎ/แหล่งทุน (ส่วนสิทธิ์การเข้าถึง)]]

> ส่วนหน้าจอ Admin Dashboard และการจัดการแหล่งทุน/กฎ ดู AC ที่หัวข้อ 22

- **AC-1 (Admin อ่านใบเสร็จข้ามผู้ใช้ ระบุเจ้าของ)**
  - **Given**: นักวิจัย A และ B มีใบเสร็จในระบบ และมีบัญชี Admin
  - **When**: Admin เข้าสู่ระบบและเปิดดูใบเสร็จ
  - **Then**: Admin เห็นใบเสร็จของทั้ง A และ B พร้อมชื่อ/อีเมลเจ้าของและโครงการที่สังกัด
- **AC-2 (Admin เขียนข้อมูลใบเสร็จของผู้อื่นไม่ได้)**
  - **Given**: Admin เข้าสู่ระบบ และมีใบเสร็จของนักวิจัย A
  - **When**: Admin พยายามแก้ไขหรือลบใบเสร็จนั้น (เช่น ผ่านการเรียกฐานข้อมูลโดยตรง)
  - **Then**: ระบบปฏิเสธการเขียน/ลบ (สิทธิ์ของ Admin ต่อใบเสร็จของผู้อื่นเป็นอ่านอย่างเดียวเท่านั้น)
- **AC-3 (ผู้ใช้ทั่วไปไม่เห็นเมนู Admin และดึงข้อมูลข้ามผู้ใช้ไม่ได้)**
  - **Given**: นักวิจัยที่ไม่ใช่ Admin เข้าสู่ระบบ
  - **When**: ดูแถบนำทาง และพยายามเปิดหน้า Admin Dashboard/จัดการแหล่งทุนโดยตรง หรือดึงใบเสร็จข้ามผู้ใช้
  - **Then**: ไม่มีลิงก์เมนู Admin แสดง หน้า Admin แสดงข้อความปฏิเสธสิทธิ์แทนเนื้อหา และการดึงข้อมูลข้ามผู้ใช้ถูกฐานข้อมูลปฏิเสธ
- **AC-4 (ไม่มี UI ให้ยกสิทธิ์ตนเองเป็น Admin)**
  - **Given**: นักวิจัยที่ไม่ใช่ Admin เข้าสู่ระบบ
  - **When**: พยายามตั้งค่าสิทธิ์ Admin ให้บัญชีตนเอง (ผ่านการเรียกฐานข้อมูลโดยตรง)
  - **Then**: ระบบปฏิเสธ ขณะที่การแก้ข้อมูลโปรไฟล์ปกติ (เช่น ชื่อ) ยังทำได้ — การเลื่อนสิทธิ์เป็น Admin ทำได้ผ่านคอนโซลของผู้ดูแลเท่านั้น
- **AC-5 (แจ้งนักวิจัยว่า Admin อ่านข้อมูลได้ ก่อนอัปโหลดครั้งแรก)**
  - **Given**: นักวิจัยยังไม่เคยยินยอมแบบเบา (ยังไม่มีบันทึกวันที่ยินยอม)
  - **When**: นักวิจัยเปิดขั้นตอนอัปโหลดใบเสร็จครั้งแรก
  - **Then**: ข้อความยินยอมแจ้งชัดเจนว่า Admin อ่านข้อมูลใบเสร็จได้ (ดู FR-13 AC-3, FR-14 AC-3)

#### NFR-05 (สูง) — [[20260816-01-grant-receipt-verification#5. Non-Functional Requirements|Security/Access Control]]

- **AC-1 (อ่านข้ามบัญชี — แก้ตาม FR-33)**
  - **Given**: ข้อมูลใบเสร็จของนักวิจัยแต่ละคนถูกจัดเก็บในระบบ
  - **When**: มีความพยายามอ่านข้อมูลจากบัญชีอื่นที่ไม่ใช่เจ้าของ
  - **Then**: ระบบต้องปฏิเสธการอ่านเสมอ **ยกเว้นบทบาท Admin ซึ่งอ่านได้แบบอ่านอย่างเดียวตาม FR-33** ไม่มีบทบาทอื่นเห็นข้อมูลใบเสร็จข้ามคนได้
    (สอดคล้องกับ FR-12)
- **AC-2 (เขียนข้ามบัญชีและการเขียนระเบียบ)**
  - **Given**: มีบัญชีนักวิจัยหลายบัญชีและบัญชี Admin
  - **When**: บัญชีใดพยายามเขียน/แก้/ลบข้อมูลใบเสร็จของบัญชีอื่น (รวมถึง Admin) หรือนักวิจัยทั่วไปพยายามเขียนแหล่งทุน/ระเบียบ
  - **Then**: ระบบปฏิเสธทุกกรณี — การเขียนข้อมูลใบเสร็จจำกัดที่เจ้าของเท่านั้น และการเขียนแหล่งทุน/ระเบียบจำกัดที่ Admin เท่านั้น
    (การอ่านรายการแหล่งทุนยังเปิดให้ผู้ที่ล็อกอินเพื่อเลือกผูกโครงการ)

#### NFR-10 (สูง) — [[20260816-02-pdpa-compliance#5. Non-Functional Requirements|Data Breach Notification (Organizational/Process)]]

- **AC-1**
  - **Given**: เกิดเหตุการณ์ข้อมูลใบเสร็จของนักวิจัยรั่วไหล/ถูกเข้าถึงโดยไม่ได้รับอนุญาต
  - **When**: โครงการตรวจพบเหตุการณ์ดังกล่าว
  - **Then**: โครงการต้องมีกลไก/กระบวนการแจ้งเตือนสำนักงานคณะกรรมการคุ้มครองข้อมูลส่วนบุคคล (สคส.)
    ภายใน 72 ชั่วโมงตามมาตรา 37(4) (ตรวจสอบระดับ organizational/process ไม่ใช่ functional test ของ
    ตัวระบบ)

## 10. แจ้ง Privacy Notice และจัดการความยินยอม (Consent Management)

(อ้างอิง [[feature-list#10. แจ้ง Privacy Notice และจัดการความยินยอม (Consent Management)|ฟีเจอร์ที่ 10]])

#### FR-13 (สูง) — [[20260816-02-pdpa-compliance#4. Functional Requirements|แสดง Privacy Notice ก่อนใช้งานครั้งแรก/ก่อนอัปโหลดใบเสร็จ]]

- **AC-1 (ใช้งานระบบครั้งแรก)**
  - **Given**: นักวิจัยเข้าสู่ระบบเป็นครั้งแรก ยังไม่เคยเห็น Privacy Notice มาก่อน
  - **When**: นักวิจัยเข้าสู่ระบบ
  - **Then**: ระบบแสดงประกาศความเป็นส่วนตัว (Privacy Notice) แจ้งวัตถุประสงค์การเก็บ/ใช้ข้อมูล ตัวตน
    ผู้ควบคุมข้อมูล (มหาวิทยาลัย) ระยะเวลาเก็บข้อมูล (อ้างอิง NFR-11) และสิทธิ์ของเจ้าของข้อมูล ก่อน
    ให้ใช้งานฟีเจอร์อื่นต่อ
- **AC-2 (ก่อนอัปโหลดใบเสร็จครั้งแรก)**
  - **Given**: นักวิจัยเคยเห็นและผ่านหน้า Privacy Notice ตอนเข้าระบบครั้งแรกแล้ว แต่ยังไม่เคยอัปโหลด
    ใบเสร็จเลย
  - **When**: นักวิจัยพยายามอัปโหลดใบเสร็จเป็นครั้งแรก (FR-01)
  - **Then**: ระบบยืนยันว่ามีการแสดง Privacy Notice/ขอความยินยอมแล้วก่อนเริ่มเก็บ/ประมวลผลข้อมูล
    ใบเสร็จจริง (เชื่อมกับ FR-14)
- **AC-3 (ยินยอมแบบเบาที่สร้างแล้วในแอป — เสร็จบางส่วน)**
  - **Given**: บัญชีนักวิจัยยังไม่มีบันทึกวันที่ยินยอม (`privacyConsentAcceptedAt`) ในโปรไฟล์
  - **When**: นักวิจัยเปิดขั้นตอนที่ 1 ของหน้าอัปโหลดใบเสร็จ
  - **Then**: ระบบแสดงการ์ดแจ้งความเป็นส่วนตัวพร้อมช่องติ๊กยินยอม ซึ่งระบุว่า Admin อ่านข้อมูลใบเสร็จได้ (FR-33) —
    เมื่อเคยยินยอมแล้วการ์ดนี้ไม่แสดงอีกในครั้งต่อไป (ยังไม่มีหน้า Privacy Notice แยก ไม่มีบันทึกเวอร์ชันประกาศ)

#### FR-14 (สูง) — [[20260816-02-pdpa-compliance#4. Functional Requirements|ขอความยินยอมชัดแจ้ง (Explicit Consent) ก่อนเก็บ/ประมวลผลข้อมูลใบเสร็จ]]

- **AC-1 (ให้ความยินยอม)**
  - **Given**: นักวิจัยเห็น Privacy Notice แล้ว (FR-13) และยังไม่เคยให้ความยินยอมมาก่อน
  - **When**: นักวิจัยกดให้ความยินยอมอย่างชัดแจ้ง
  - **Then**: ระบบอนุญาตให้นักวิจัยอัปโหลดใบเสร็จได้ (ไปต่อ FR-01) และบันทึกหลักฐานการให้ความยินยอม
    (FR-15)
- **AC-2 (ไม่ให้ความยินยอม)**
  - **Given**: นักวิจัยเห็น Privacy Notice แล้ว (FR-13)
  - **When**: นักวิจัยเลือกไม่ให้ความยินยอม
  - **Then**: ระบบไม่อนุญาตให้นักวิจัยอัปโหลดใบเสร็จเข้าสู่ระบบ
- **AC-3 (ยินยอมแบบเบาที่สร้างแล้วในแอป — เสร็จบางส่วน)**
  - **Given**: การ์ดยินยอมแสดงอยู่ในขั้นตอนที่ 1 ของหน้าอัปโหลดใบเสร็จ (ผู้ใช้ยังไม่เคยยินยอม)
  - **When**: นักวิจัยกดดำเนินการต่อโดยยังไม่ติ๊กยินยอม แล้วภายหลังติ๊กยินยอมและกดดำเนินการต่อ
  - **Then**: กรณีไม่ติ๊ก ระบบบล็อกพร้อมข้อความเตือนและไม่ไปขั้นตอนถัดไป กรณีติ๊ก ระบบบันทึกวันที่ยินยอมแล้วไปต่อได้ และการ์ดไม่แสดงอีก
    (ยังไม่ใช่ PDPA เต็มรูปแบบ ไม่มีการถอนความยินยอม)

#### FR-15 (สูง) — [[20260816-02-pdpa-compliance#4. Functional Requirements|บันทึกหลักฐานการให้ความยินยอม (Consent Record)]]

- **AC-1**
  - **Given**: นักวิจัยเพิ่งให้ความยินยอมชัดแจ้ง (FR-14)
  - **When**: ระบบบันทึกเหตุการณ์นี้
  - **Then**: ระบบบันทึกวันที่ให้ความยินยอมและเวอร์ชันของ Privacy Notice ที่นักวิจัยเห็น ณ ตอนนั้น
    ไว้เป็นหลักฐานย้อนหลัง (Accountability)

#### FR-16 (สูง) — [[20260816-02-pdpa-compliance#4. Functional Requirements|ถอนความยินยอม (Withdraw Consent) และจัดการผลกระทบต่อกระบวนการตรวจใบเสร็จ]]

- **AC-1 (ถอนความยินยอม — ผลต่อการอัปโหลด/ประมวลผลใหม่)**
  - **Given**: นักวิจัยเคยให้ความยินยอมไว้แล้วและใช้งานระบบอยู่
  - **When**: นักวิจัยเปิดหน้าจัดการความยินยอมแล้วกดถอนความยินยอม
  - **Then**: ระบบระงับการอัปโหลด/ประมวลผลใบเสร็จ**ใหม่**ของนักวิจัยคนนั้นทันที

> หมายเหตุ: พฤติกรรมของระบบต่อ**ข้อมูลที่เคยประมวลผลไปแล้วก่อนถอนความยินยอม** (เช่น เก็บต่อ/ระงับ
> การเข้าถึง/ลบทันที) — เดิมสเปคและ backlog ระบุไว้ว่าเป็น **Open Point ที่ยังไม่ปิด** ปัจจุบัน
> **ปิดแล้ว**ด้วย FR-20 (ดูด้านล่าง) ซึ่งผู้ใช้ยืนยันคำตอบและ finalize เป็นรหัส FR ใหม่แล้ว

#### FR-20 (สูง) — [[20260816-02-pdpa-compliance#4. Functional Requirements|ลบข้อมูลใบเสร็จ/ผลตรวจทั้งหมดทันทีเมื่อถอนความยินยอม (Withdraw Consent — Full Immediate Erasure)]]

- **AC-1 (ลบข้อมูลทั้งหมดทันที ไม่แยกตามสถานะ export)**
  - **Given**: นักวิจัยเคยให้ความยินยอมไว้และมีข้อมูลใบเสร็จ/ผลตรวจอยู่ในระบบ (ทั้งใบที่เคยถูก export
    ไปแล้วและใบที่ยังไม่ถูก export)
  - **When**: นักวิจัยกดถอนความยินยอมที่เคยให้ไว้ (FR-16)
  - **Then**: ระบบลบข้อมูลใบเสร็จ/ผลตรวจทั้งหมดของนักวิจัยคนนั้นที่ระบบเก็บไว้ทันที โดย**ไม่แยกตาม
    สถานะ export** (ต่างจากเงื่อนไขจำกัดของ FR-18 ที่ยังคงห้ามลบใบเสร็จที่ export ไปแล้วผ่าน UI เอง
    เพราะกรณีนั้นนักวิจัยยังไม่ได้ถอนความยินยอมทั้งหมด)
- **AC-2 (เชื่อมโยงลำดับกับการระงับอัปโหลด/ประมวลผลใหม่)**
  - **Given**: นักวิจัยเพิ่งกดถอนความยินยอม (ต่อยอดจาก FR-16 AC-1)
  - **When**: ระบบประมวลผลการถอนความยินยอม
  - **Then**: ระบบระงับการอัปโหลด/ประมวลผลใบเสร็จใหม่ทันที (FR-16) และลบข้อมูลใบเสร็จ/ผลตรวจเดิม
    ทั้งหมดทันทีในลำดับเดียวกัน (FR-20) เพราะไม่มีฐานทางกฎหมายเหลืออยู่ที่จะเก็บข้อมูลต่อได้อีก

> หมายเหตุ (ยังไม่ได้สร้าง): การลบข้อมูลตาม FR-20 ปัจจุบันครอบคลุมเฉพาะข้อมูลในระบบ — ไฟล์ใน Google Drive ของผู้ใช้ที่ระบบสร้างไว้ต้องถูกลบตามด้วย
> ดู [[acceptance-criteria#21. แนบไฟล์จริงผ่าน Google Drive ของผู้ใช้|FR-37 AC-4]] ที่ฟีเจอร์ 21

#### NFR-11 (สูง) — [[20260816-02-pdpa-compliance#5. Non-Functional Requirements|Data Retention & Deletion Policy (ส่วนที่อ้างอิงในเนื้อหา Privacy Notice)]]

- **AC-1**
  - **Given**: ระบบแสดง Privacy Notice ให้นักวิจัยเห็น (FR-13)
  - **When**: นักวิจัยอ่านเนื้อหา Privacy Notice
  - **Then**: เนื้อหาต้องระบุถึงระยะเวลาเก็บข้อมูล/นโยบายการเก็บ-ลบข้อมูล แม้ว่าตัวเลขที่แน่นอนยังเป็น
    TBD ก็ต้องระบุว่ามีนโยบายนี้อยู่และจะแจ้งเพิ่มเติมเมื่อกำหนดตัวเลขแล้ว (ไม่ปล่อยว่างเปล่าโดยไม่มี
    ข้อความใดๆ เรื่อง retention)

## 11. ขอเข้าถึง/ขอสำเนาข้อมูลส่วนบุคคลของตนเอง (Data Access & Portability)

(อ้างอิง [[feature-list#11. ขอเข้าถึง/ขอสำเนาข้อมูลส่วนบุคคลของตนเอง (Data Access & Portability)|ฟีเจอร์ที่ 11]])

#### FR-17 (กลาง) — [[20260816-02-pdpa-compliance#4. Functional Requirements|ขอเข้าถึง/ขอสำเนาข้อมูลใบเสร็จส่วนบุคคลของตนเอง (Data Subject Access & Portability)]]

- **AC-1 (Happy path)**
  - **Given**: นักวิจัยเข้าสู่ระบบและมีข้อมูลใบเสร็จ/ผลตรวจ/ประวัติ consent อยู่ในระบบ
  - **When**: นักวิจัยขอสำเนาข้อมูลส่วนบุคคลทั้งหมดของตนเองผ่านหน้าจัดการสิทธิ์ข้อมูลส่วนบุคคล
  - **Then**: ระบบให้นักวิจัยดาวน์โหลด/รับสำเนาข้อมูลใบเสร็จ ผลตรวจ และประวัติการให้ความยินยอมทั้งหมด
    ของตนเอง ในรูปแบบที่อ่าน/นำไปใช้ต่อได้
- **AC-2 (แยกจากรายงาน export ฟีเจอร์ที่ 7)**
  - **Given**: นักวิจัยเคย export รายงานสรุปใบเสร็จที่ผ่านตรวจแล้ว (FR-10) มาก่อน
  - **When**: นักวิจัยขอสำเนาข้อมูลส่วนบุคคลผ่าน FR-17
  - **Then**: สำเนาที่ได้รับครบถ้วนกว่ารายงานสรุปของ FR-10 (รวมใบเสร็จทุกสถานะ ผลตรวจ และประวัติ
    consent ไม่ใช่แค่ใบเสร็จที่ผ่านตรวจแล้ว)

## 12. ลบข้อมูลใบเสร็จของตนเองด้วยตนเอง (Right to Erasure)

(อ้างอิง [[feature-list#12. ลบข้อมูลใบเสร็จของตนเองด้วยตนเอง (Right to Erasure)|ฟีเจอร์ที่ 12]])

#### FR-18 (สูง) — [[20260816-02-pdpa-compliance#4. Functional Requirements|ลบ/ขอลบข้อมูลใบเสร็จของตนเองด้วยตนเองผ่าน UI (Right to Erasure)]]

- **AC-1 (ลบใบเสร็จที่ยังไม่ถูก export)**
  - **Given**: นักวิจัยเลือกใบเสร็จของตนเองที่ยังไม่เคยถูกรวมอยู่ใน export รายงาน (FR-10)
  - **When**: นักวิจัยกดลบและยืนยันการลบ
  - **Then**: ระบบลบข้อมูลใบเสร็จนั้นออกจากระบบทันที
- **AC-2 (พยายามลบใบเสร็จที่ถูก export ไปแล้ว)**
  - **Given**: นักวิจัยเลือกใบเสร็จที่เคยถูกรวมอยู่ใน export รายงานที่ส่งเจ้าหน้าที่การเงินไปแล้ว
    (FR-10)
  - **When**: นักวิจัยพยายามกดลบใบเสร็จนั้นผ่าน UI
  - **Then**: ระบบปิดกั้นการลบเองผ่าน UI และแจ้งให้นักวิจัยยื่นคำร้องผ่านช่องทาง Admin/DPO ภายนอกระบบ
    แทน
- **AC-3 (ลบได้เฉพาะใบเสร็จของตนเอง — ส่วนที่สร้างแล้วในแอป; ลบเฉพาะข้อมูลใน Firestore ไม่ลบไฟล์จริงใน Google Drive = พฤติกรรมปัจจุบันที่จะถูกแทนด้วย [[acceptance-criteria#21. แนบไฟล์จริงผ่าน Google Drive ของผู้ใช้|FR-37 AC-3]])**
  - **Given**: นักวิจัย A มีใบเสร็จของตนเอง และมีนักวิจัย B ที่มีใบเสร็จของตนเอง
  - **When**: นักวิจัย A กดลบใบเสร็จของตนเอง และแยกกรณีพยายามลบใบเสร็จของนักวิจัย B โดยตรง
  - **Then**: ใบเสร็จของ A ถูกลบพร้อมเอกสารไฟล์ที่ผูกอยู่ใน Firestore ทันที ส่วนการลบใบเสร็จของ B ถูกฐานข้อมูลปฏิเสธ
    (ปัจจุบันเป็นการลบถาวรทันที ยังไม่มีเงื่อนไขห้ามลบเมื่อ export แล้ว เพราะ Export ยังไม่ได้สร้าง — AC-2 จึงยังทดสอบไม่ได้)

#### NFR-11 (สูง) — [[20260816-02-pdpa-compliance#5. Non-Functional Requirements|Data Retention & Deletion Policy (เงื่อนไขจำกัดการลบเองเฉพาะใบเสร็จที่ยังไม่ถูก export)]]

- **AC-1**
  - **Given**: นโยบาย retention ของหลักฐานทางการเงินกำหนดให้ใบเสร็จที่ export ไปแล้วต้องเก็บไว้เป็น
    หลักฐาน
  - **When**: นักวิจัยพยายามลบใบเสร็จที่ export ไปแล้วผ่าน UI (เชื่อมกับ FR-18 AC-2)
  - **Then**: ระบบต้องปฏิบัติตามเงื่อนไข retention นี้เสมอ ไม่อนุญาตให้ลบเองผ่าน UI จนกว่าจะมีตัวเลข
    retention/กระบวนการที่ finalize แล้วมาแทนที่เงื่อนไขนี้

## 13. จัดการข้อมูลโครงการวิจัยและผูกกับแหล่งทุน (Project Setup)

(อ้างอิง [[feature-list#13. จัดการข้อมูลโครงการวิจัยและผูกกับแหล่งทุน (Project Setup)|ฟีเจอร์ที่ 13]])

#### FR-23 (สูง) — [[20260816-01-grant-receipt-verification#4. Functional Requirements|จัดการข้อมูลโครงการวิจัยและผูกกับแหล่งทุน (Project Setup)]]

- **AC-1 (สร้างโครงการและผูกกับแหล่งทุน)**
  - **Given**: นักวิจัยเข้าสู่ระบบแล้ว และ Admin นำเข้าแหล่งทุนไว้อย่างน้อย 1 แหล่ง
  - **When**: นักวิจัยเปิดหน้าโครงการ กรอกชื่อโครงการ เลือกแหล่งทุนจากรายการ แล้วกดสร้าง
  - **Then**: โครงการใหม่ปรากฏในรายการโครงการของนักวิจัยคนนั้น ผูกกับแหล่งทุนที่เลือก และมีนักวิจัยเป็นเจ้าของ **เพียง 1 คน**
    (คือผู้สร้าง)
- **AC-2 (เลือกได้เฉพาะแหล่งทุนที่ Admin นำเข้าไว้)**
  - **Given**: นักวิจัยเปิดแบบฟอร์มสร้างโครงการ
  - **When**: ดูรายการแหล่งทุนให้เลือก
  - **Then**: รายการประกอบด้วยแหล่งทุนที่มีอยู่ในระบบเท่านั้น และนักวิจัยสร้างแหล่งทุนใหม่จากหน้านี้ไม่ได้
- **AC-3 (1 แหล่งทุน : หลายโครงการ และแยกตามเจ้าของ)**
  - **Given**: นักวิจัย A และ B ต่างสร้างโครงการที่ผูกกับแหล่งทุนเดียวกัน และ A สร้างหลายโครงการ
  - **When**: ต่างคนเปิดรายการโครงการ
  - **Then**: แหล่งทุนเดียวผูกได้หลายโครงการ แต่แต่ละคนเห็นเฉพาะโครงการของตนเอง (เชื่อม FR-12)
- **AC-4 (ยังไม่มีโครงการ — ต้องสร้างก่อนอัปโหลดใบเสร็จ)**
  - **Given**: บัญชีนักวิจัยใหม่ยังไม่มีโครงการใดเลย
  - **When**: นักวิจัยเปิดหน้าอัปโหลดใบเสร็จ (FR-01)
  - **Then**: ระบบไม่ให้ผูกใบเสร็จได้ และนำทางให้ไปสร้างโครงการที่หน้าโครงการก่อน (ใบเสร็จต้องผูกกับโครงการที่มีอยู่เสมอ)
- **AC-5 (ข้อมูลไม่ครบ — ไม่สร้างโครงการ)**
  - **Given**: นักวิจัยเปิดแบบฟอร์มสร้างโครงการ
  - **When**: กดสร้างโดยไม่กรอกชื่อโครงการ หรือไม่ได้เลือกแหล่งทุน
  - **Then**: ระบบไม่สร้างโครงการ และแสดงข้อความเตือนภาษาไทย (สืบเนื่องจากนิยาม "อย่างน้อยชื่อโครงการ" และการผูกแหล่งทุนที่ใช้เลือกระเบียบตรวจ)

## 14. นำเข้าประมาณการโครงการ (ตาราง 17.2) และตรวจกับประมาณการ

(อ้างอิง [[feature-list#14. นำเข้าประมาณการโครงการ (ตาราง 17.2) และตรวจกับประมาณการ|ฟีเจอร์ที่ 14]])

#### FR-26 (สูง) — [[20261117-01-implemented-rule-engine-ai-and-admin#2. Functional Requirements|ตรวจกับประมาณการที่อนุมัติ (นำเข้าตาราง 17.2, อัตรา×จำนวน, ยอดใช้ไป/คงเหลือ)]]

- **AC-1 (นำเข้าไฟล์ 17.2 และจับคู่หมวด)**
  - **Given**: โครงการยังไม่มีประมาณการ และนักวิจัยมีไฟล์ประมาณการ 17.2 (.xlsx หรือ .csv)
  - **When**: นักวิจัยนำเข้าไฟล์ที่หน้าประมาณการของโครงการ
  - **Then**: ระบบเลือกชีตที่ชื่อมี "17.2" (ไม่พบใช้ชีตแรก) แปลงเป็นรายการประมาณการพร้อมกลุ่มหมวด ชื่อรายการ ช่องตัวคูณ งวดทั้ง 3 และยอดรวม
    ข้ามแถวว่าง แถวรวมย่อย และยอดรวมทั้งหมด อ่านตัวเลขที่เป็นข้อความมีเครื่องหมายจุลภาคได้ จับคู่หมวดระเบียบให้อัตโนมัติ (รวมถึงชื่อรายการทางการทั้งหมด)
    และให้นักวิจัยแก้การจับคู่ได้ก่อนกดบันทึก
- **AC-2 (คำเตือนตอนนำเข้า)**
  - **Given**: ไฟล์ที่นำเข้ามีงวดรวมไม่เท่ายอดรวม / ไม่เหมือนตาราง 17.2 / หน่วยราคา×จำนวนไม่เท่ายอดรวม
  - **When**: ระบบอ่านไฟล์
  - **Then**: ระบบแสดงคำเตือนตามกรณีนั้นๆ ให้นักวิจัยเห็นก่อนบันทึก (ไม่บล็อกการนำเข้าเงียบๆ และไม่ล้มเหลวเมื่อตัวคูณเป็นจุดว่างหรือข้อความไม่มี "x" — ค่าหน่วยเป็นว่าง)
- **AC-3 (นำเข้าซ้ำแทนที่ทั้งหมด — พฤติกรรมปัจจุบันที่จะถูกแทนด้วย FR-36 ด้านล่าง)**
  - **Given**: โครงการมีประมาณการอยู่แล้ว และมีใบเสร็จผูกกับรายการประมาณการ
  - **When**: นักวิจัยนำเข้าไฟล์ใหม่ซ้ำ
  - **Then**: ระบบแทนที่รายการทั้งหมดด้วยไฟล์ใหม่ และแสดงคำเตือนว่ามีใบเสร็จผูกอยู่ซึ่งอาจเชื่อมผิดรายการถ้าลำดับเปลี่ยน
- **AC-4 (ต้องเลือกรายการประมาณการตอนส่งใบเสร็จ)**
  - **Given**: โครงการมีประมาณการ
  - **When**: นักวิจัยอยู่ในขั้นที่ 2 ของหน้าอัปโหลดใบเสร็จ
  - **Then**: ระบบแสดงตัวเลือก "ตัดจากรายการไหนในประมาณการ" และบังคับให้เลือกรายการใดรายการหนึ่งหรือ "ไม่อยู่ในประมาณการ"
    เมื่อเลือกรายการ ระบบตั้งหมวดระเบียบตามรายการนั้น ส่วนโครงการที่ไม่มีประมาณการจะไม่แสดงตัวเลือกนี้
- **AC-5 (ไม่อยู่ในประมาณการ → ต้องชี้แจง/ขออนุมัติ)**
  - **Given**: นักวิจัยเลือก "ไม่อยู่ในประมาณการ" (หรือรายการที่ไม่มีในประมาณการ)
  - **When**: ระบบส่งตรวจกับ Rule Engine
  - **Then**: ผลเป็น "ต้องชี้แจง/ขออนุมัติ" (`NOT_IN_ESTIMATE`)
- **AC-6 (ยอดสะสมเกิน 100% ของรายการ → ต้องชี้แจง/ขออนุมัติ)**
  - **Given**: รายการประมาณการมียอดรวมทั้งโครงการ และมียอดที่ตัดไปแล้ว (`spentBefore`)
  - **When**: ยอดตัดไปแล้วรวมกับยอดใบเสร็จนี้ไม่เกินยอดรวมของรายการ และอีกกรณียอดรวมกันเกินยอดรวมของรายการ
  - **Then**: กรณีไม่เกิน (รวมถึงพอดี 100%) ผ่านข้อนี้ กรณีเกินผลเป็น "ต้องชี้แจง/ขออนุมัติ" (`OVER_ESTIMATE`) พร้อมตัวเลขยอดสะสมและยอดรวมในคำอธิบาย
    (เกณฑ์เกินคือ **100%** ไม่ใช่ 110% เทียบกับยอดรวมทั้งโครงการ ไม่บังคับตามงวด)
- **AC-7 (อัตรา × จำนวนหน่วยจากช่องตัวคูณ)**
  - **Given**: รายการประมาณการมีหน่วยราคาและจำนวน (เช่น "60 บาท x 100 ชม." หรือ "200 กม. x 2 x 4 บาท x 3 ครั้ง") และหมวดนั้นมีอัตราต่อหน่วยหรือเพดานต่อคน/มื้อ/คืน/วัน
  - **When**: ระบบตรวจยอดสะสมของรายการเทียบเพดานระเบียบ = อัตราตามระเบียบ × จำนวนหน่วย
  - **Then**: ถ้าเกิน → "ต้องแก้ไข" (`OVER_RATE_ALLOWANCE`) แม้รายการประมาณการจะยังใช้ไม่หมด ถ้าไม่เกิน → ผ่านและนับเป็นตรวจยืนยันอัตโนมัติครบ (`WITHIN_RATE_ALLOWANCE`)
    รายการ "ตามข้อเสนอโครงการ" ที่ผูกกับรายการประมาณการให้ผ่านและนับเป็นตรวจแล้ว เพราะประมาณการที่อนุมัติเป็นเพดาน (`PER_PROPOSAL_VIA_ESTIMATE`)
- **AC-8 (เพดานต่อหน่วยไม่เทียบกับยอดทั้งใบ)**
  - **Given**: ใบเสร็จผูกกับรายการประมาณการ และหมวดมีเพดานต่อหน่วย (เช่น อาหารกลางวัน 150 บาท/คน/มื้อ ใบเสร็จรวม 20 คน 3,000 บาท)
  - **When**: ระบบตรวจ
  - **Then**: ไม่ flag ผิดว่ายอด 3,000 เกินเพดาน 150 (ให้ประมาณการเป็นตัวตรวจ) ส่วนเพดานทั้งยอดที่ไม่มีหน่วย (เช่น วัสดุสำนักงาน 5,000 บาท) ยังคงใช้ตามเดิม
- **AC-9 (ไม่มีประมาณการ/รายการไม่มีจำนวนหน่วย → บอกให้อัปโหลด)**
  - **Given**: โครงการยังไม่มีประมาณการ หรือรายการประมาณการที่เลือกนำเข้าก่อนมีการอ่านจำนวนหน่วย (ไม่มี quantity)
  - **When**: ระบบส่งตรวจ
  - **Then**: ผลตรวจบอกให้นักวิจัยอัปโหลดประมาณการ (กรณีไม่มีประมาณการ) หรืออัปโหลดใหม่พร้อมช่องตัวคูณ (กรณีไม่มีจำนวนหน่วย) และถูกทำเครื่องหมายว่ายังไม่ตรวจยืนยันอัตโนมัติ
    (`ESTIMATE_NOT_CHECKED`) ไม่ปล่อยผ่านเงียบๆ
- **AC-10 (หน้าประมาณการแสดงยอดใช้ไป/คงเหลือ/%)**
  - **Given**: โครงการมีประมาณการและมีใบเสร็จที่ตัดรายการต่างๆ
  - **When**: นักวิจัยเปิดหน้าประมาณการจากการ์ดโครงการ
  - **Then**: แต่ละรายการแสดงยอดใช้ไป ยอดคงเหลือ และเปอร์เซ็นต์ที่คำนวณจากใบเสร็จที่ตัดรายการนั้นของโครงการ เทียบกับยอดรวมทั้งโครงการของรายการ
- **AC-11 (หมวดที่ระเบียบห้ามยังถูกปฏิเสธแม้อยู่ในประมาณการ)**
  - **Given**: รายการประมาณการถูกจับคู่กับหมวดที่ระเบียบไม่สนับสนุน
  - **When**: ระบบตรวจใบเสร็จที่ตัดรายการนั้น
  - **Then**: ผลเป็น "ไม่เข้าเงื่อนไข" (`CATEGORY_NOT_IN_RULES`) — การอยู่ในประมาณการไม่ทำให้พ้นข้อห้ามของระเบียบ

#### FR-36 (สูง) — [[20261117-02-fund-source-deactivation-estimate-versioning-drive-privacy#2. Functional Requirements|นำเข้าประมาณการ 17.2 ซ้ำแบบเก็บเวอร์ชันเก่า และย้ายใบเสร็จไปจับคู่รายการล่าสุด]]

> **สถานะ: ยังไม่ได้สร้าง (Backlog)** — AC ด้านล่างเป็นเกณฑ์รับมอบ รันไม่ได้จนกว่าจะสร้าง ต่อยอด FR-26 และ**แทนที่พฤติกรรมปัจจุบัน**
> ของ FR-26 AC-3 (แทนที่ทุกรายการตามลำดับ `line001…` ใบเสร็จเก่าอาจเชื่อมผิดรายการ ระบบแค่เตือน) กลไกจับคู่ (ชื่อรายการ + หมวดระเบียบ,
> เลือกเอง, บล็อกการบันทึก) เป็น**ข้อเสนอ**ใน spec — AC เขียนในระดับพฤติกรรมที่ spec ระบุ

- **AC-1 (เก็บเวอร์ชันเก่าเป็นประวัติ ไม่เขียนทับ)**
  - **Given**: โครงการมีประมาณการ 17.2 อยู่แล้ว (เวอร์ชันปัจจุบัน) และมีใบเสร็จผูกกับรายการของประมาณการนั้น
  - **When**: นักวิจัยนำเข้าไฟล์ 17.2 ฉบับปรับปรุงซ้ำที่หน้าประมาณการและบันทึก
  - **Then**: ระบบสร้างประมาณการเวอร์ชันใหม่เป็นเวอร์ชันล่าสุด และ**เก็บเวอร์ชันเก่าไว้เป็นประวัติครบถ้วน** (ไม่ถูกเขียนทับหรือลบ) เปิดดูย้อนหลังได้
- **AC-2 (ย้ายใบเสร็จที่ผูกอยู่ไปรายการล่าสุดด้วยชื่อรายการ + หมวดระเบียบ)**
  - **Given**: ใบเสร็จที่ผูกกับรายการของเวอร์ชันเก่า และไฟล์ใหม่มีรายการที่ชื่อรายการและหมวดระเบียบตรงกัน (ลำดับรายการอาจเปลี่ยนไป)
  - **When**: ระบบประมวลผลการนำเข้าซ้ำ
  - **Then**: ใบเสร็จถูกย้ายไปผูกกับรายการของเวอร์ชันล่าสุดที่ชื่อ + หมวดตรงกัน (ไม่จับคู่ตามลำดับแถว) แม้ลำดับรายการในไฟล์ใหม่ต่างจากเดิม
- **AC-3 (จับคู่ไม่ได้ → นักวิจัยเลือกรายการเอง)**
  - **Given**: มีใบเสร็จที่ผูกอยู่ซึ่งไม่มีรายการในไฟล์ใหม่ที่ชื่อ + หมวดตรงกัน (เช่น รายการถูกเปลี่ยนชื่อหรือถูกตัดออก)
  - **When**: ระบบจับคู่แล้วพบใบเสร็จที่จับคู่ไม่ได้
  - **Then**: ระบบแสดงรายการใบเสร็จที่จับคู่ไม่ได้ให้นักวิจัย**เลือกรายการของเวอร์ชันล่าสุดเอง**ทีละใบ
- **AC-4 (บล็อกการบันทึกจนกว่าจะจับคู่ครบ — negative)**
  - **Given**: ยังมีใบเสร็จที่ผูกอยู่อย่างน้อย 1 ใบที่ยังไม่ถูกจับคู่ (ไม่ว่าอัตโนมัติหรือเลือกเอง)
  - **When**: นักวิจัยกดบันทึกการนำเข้า
  - **Then**: ระบบ**บล็อกการบันทึก**พร้อมข้อความระบุว่ายังมีใบเสร็จที่ต้องจับคู่ ไม่สร้างเวอร์ชันใหม่ครึ่งๆ กลางๆ และกดบันทึกได้เมื่อจับคู่ครบทุกใบเท่านั้น
- **AC-5 (ยอดใช้ไป/คงเหลือ และการตรวจเกิน 100% ใช้เวอร์ชันล่าสุด)**
  - **Given**: นำเข้าซ้ำและบันทึกสำเร็จแล้ว ใบเสร็จถูกย้ายมาผูกกับรายการเวอร์ชันล่าสุด
  - **When**: นักวิจัยเปิดหน้าประมาณการ และส่งใบเสร็จใบใหม่ที่ตัดรายการของโครงการนี้
  - **Then**: ยอดใช้ไป/คงเหลือ/% และการตรวจ "เกิน 100%" (FR-26 AC-6, AC-10) คำนวณจากยอดรวมของรายการในเวอร์ชันล่าสุดเท่านั้น และตัวเลือก "ตัดจากรายการไหนในประมาณการ" (FR-26 AC-4) แสดงเฉพาะรายการของเวอร์ชันล่าสุด
- **AC-6 (ไม่มีใบเสร็จผูกผิดรายการโดยไม่มีใครรู้)**
  - **Given**: นำเข้าซ้ำที่ลำดับรายการเปลี่ยนจากเวอร์ชันเก่า และมีใบเสร็จหลายใบผูกอยู่
  - **When**: บันทึกการนำเข้าสำเร็จ แล้วตรวจรายการที่แต่ละใบเสร็จผูกอยู่
  - **Then**: ใบเสร็จทุกใบผูกกับรายการเวอร์ชันล่าสุดที่ผ่านการจับคู่ด้วยชื่อ + หมวด หรือที่นักวิจัยเลือกเองอย่างชัดเจนเท่านั้น ไม่มีใบเสร็จใบใดชี้ไปรายการอื่นที่ชื่อ/หมวดไม่ตรงโดยไม่ผ่านการยืนยัน

## 15. ตรวจความครบของเอกสารแนบตามชุดเอกสาร (Evidence Chain)

(อ้างอิง [[feature-list#15. ตรวจความครบของเอกสารแนบตามชุดเอกสาร (Evidence Chain)|ฟีเจอร์ที่ 15]])

#### FR-27 (สูง) — [[20261117-01-implemented-rule-engine-ai-and-admin#2. Functional Requirements|ตรวจความครบของเอกสารแนบตามชุดเอกสาร (Evidence Chain)]]

> ข้อจำกัด (เสร็จบางส่วน): นักวิจัยติ๊กยืนยันเองว่ามีเอกสารใดแล้ว ระบบยังไม่ตรวจจากไฟล์ที่แนบจริง AC ด้านล่างทดสอบตรรกะการตรวจจากข้อมูลที่ติ๊ก

- **AC-1 (รายการตรวจสอบแสดงตามหมวดและยอด)**
  - **Given**: นักวิจัยเลือกหมวดค่าใช้จ่ายที่ผูกกับชุดเอกสาร
  - **When**: นักวิจัยอยู่ที่ขั้นที่ 2 ของหน้าอัปโหลดใบเสร็จ และเปลี่ยนหมวดหรือยอด
  - **Then**: ระบบแสดงรายการเอกสาร/ตราที่ต้องมี (checklist) ให้ติ๊กตรงกับที่ Rule Engine จะตรวจ ปรับรายการตามหมวด/ยอดใหม่ และเก็บเครื่องหมายติ๊กเดิมไว้
- **AC-2 (ครบ → ไม่มีข้อค้นพบด้านเอกสาร)**
  - **Given**: ใบเสร็จหมวดซื้อพัสดุที่ยอดไม่เกินเพดาน และนักวิจัยติ๊กใบเสร็จ รูปถ่ายตรวจรับ ตรา "จ่ายแล้ว" และตราตรวจรับครบ
  - **When**: ระบบส่งตรวจ
  - **Then**: ผลเป็น "ผ่าน" และไม่มีข้อค้นพบด้านเอกสาร
- **AC-3 (ขาดเอกสาร/ตรา → ต้องแก้ไข ระบุชื่อ)**
  - **Given**: ใบเสร็จที่ยอดและหมวดเข้าเงื่อนไข แต่ไม่ติ๊กเอกสารหรือตราที่บังคับ (เช่น ตราตรวจรับพัสดุ หรือหนังสืออนุมัติก่อนเดินทาง วจ.3)
  - **When**: ระบบส่งตรวจ
  - **Then**: ผลเป็น "ต้องแก้ไข" (`MISSING_EVIDENCE` / `MISSING_ATTESTATION`) และคำอธิบายระบุชื่อเอกสาร/ตราที่ขาด
- **AC-4 (ขั้นที่รับเอกสารทางเลือก)**
  - **Given**: ขั้นหนึ่งยอมรับเอกสารได้มากกว่า 1 ชนิดแทนกัน (เช่น ใบเสร็จ/ใบกำกับภาษีเต็มรูปแบบ หรือใบกำกับภาษีอย่างย่อ)
  - **When**: นักวิจัยติ๊กเอกสารทางเลือกเพียงอย่างเดียว
  - **Then**: ขั้นนั้นถือว่าครบ ไม่ถูกนับว่าขาด
- **AC-5 (ขั้นที่ไม่บังคับไม่ทำให้ไม่ผ่าน)**
  - **Given**: ชุดเอกสารมีขั้นที่ไม่บังคับ (เช่น สำเนาบัตรประชาชนของค่าเดินทาง)
  - **When**: นักวิจัยไม่ติ๊กขั้นนั้น
  - **Then**: ไม่มีข้อค้นพบและไม่ทำให้ไม่ผ่าน
- **AC-6 (ยอดเกิน 100,000 บาทต้องมีกรรมการตรวจรับ 3 คน)**
  - **Given**: ใบเสร็จหมวดครุภัณฑ์/จัดซื้อ ยอดมากกว่า 100,000 บาท
  - **When**: ระบบสร้างรายการตรวจสอบและตรวจ
  - **Then**: รายการต้องมีใบรับรองคณะกรรมการตรวจรับ 3 คนเพิ่มจากปกติ (ยอดไม่เกิน 100,000 ไม่ต้องมี — การเงินยืนยัน)
- **AC-7 (ชุดเอกสารตามกลุ่มหมวดตามคู่มือฉบับปรับปรุง)**
  - **Given**: หมวดค่าใช้จ่ายแต่ละกลุ่ม
  - **When**: ดูรายการตรวจสอบของแต่ละกลุ่ม
  - **Then**: ทุกชุดมีตรา "จ่ายแล้ว"; ซื้อพัสดุ/วัสดุ/เชื้อเพลิงมีรูปถ่ายตรวจรับและตราตรวจรับ; ค่าธรรมเนียม/สาธารณูปโภคต้องการเฉพาะใบเสร็จและตรา "จ่ายแล้ว" (ไม่มีตราตรวจรับ);
    ค่าตอบแทน เดินทาง จ้างตาม TOR รถตู้ ครุภัณฑ์ และซอฟต์แวร์ ต้องมีหนังสืออนุมัติก่อนดำเนินการ (จ้างตาม TOR ต้องมีเอกสาร TOR); และไม่มีเอกสารวจ.9 (ยกเลิกแล้ว)
- **AC-8 (ค่าที่พักเหมาจ่าย ใช้ วจ.2 แทนใบเสร็จโรงแรม)**
  - **Given**: ใบเสร็จหมวดค่าที่พักเหมาจ่าย (พักบ้านญาติ/บ้านตนเอง 800 บาท/วัน)
  - **When**: ระบบสร้างรายการตรวจสอบ
  - **Then**: ขั้นจ่ายเงินใช้ใบสำคัญรับเงิน (วจ.2) อย่างเดียวได้ ไม่ต้องใบเสร็จโรงแรม (การเงินยืนยัน) ขณะที่หมวดโรงแรมยังต้องใบเสร็จ
- **AC-9 (ไม่ส่งข้อมูลเอกสาร → ยังไม่ตรวจยืนยัน)**
  - **Given**: ไม่มีข้อมูลเอกสาร/ตราส่งเข้า Rule Engine (หมวดมีชุดเอกสาร)
  - **When**: ระบบตรวจ
  - **Then**: ผลด้านยอดคงอยู่แต่ถูกทำเครื่องหมายว่ายังไม่ตรวจยืนยันอัตโนมัติ (`EVIDENCE_NOT_CHECKED`)
- **AC-10 (ลำดับความสำคัญกับข้อค้นพบด้านอื่น)**
  - **Given**: ใบเสร็จที่ยอดเกินเพดานและขาดเอกสารด้วย / ใบเสร็จหมวดที่ระเบียบไม่อนุญาต
  - **When**: ระบบตรวจ
  - **Then**: กรณียอดเกิน เหตุผลหลักคือยอดเกินและความขาดเอกสารปรากฏเป็นข้อค้นพบเพิ่ม กรณีหมวดไม่อนุญาต ผลเป็น "ไม่เข้าเงื่อนไข" และข้ามการตรวจเอกสาร

## 16. เทียบยอดกับใบสรุปรายรับ-จ่าย

(อ้างอิง [[feature-list#16. เทียบยอดกับใบสรุปรายรับ-จ่าย|ฟีเจอร์ที่ 16]])

#### FR-28 (กลาง) — [[20261117-01-implemented-rule-engine-ai-and-admin#2. Functional Requirements|เทียบยอดกับใบสรุปรายรับ-จ่าย]]

> ข้อจำกัด (เสร็จบางส่วน): ตรวจรายใบเท่านั้น ยังไม่ตรวจยอดรวมรายหมวดของทั้งชุด

- **AC-1 (ยอดไม่ตรง → ต้องแก้ไข)**
  - **Given**: นักวิจัยกรอกยอดในใบสรุปรายรับ-จ่ายที่ไม่เท่ากับยอดใบเสร็จ
  - **When**: ระบบส่งตรวจ
  - **Then**: ผลเป็น "ต้องแก้ไข" (`SUMMARY_AMOUNT_MISMATCH`) พร้อมระบุตัวเลขทั้งสอง
- **AC-2 (ยอดตรง → ผ่านข้อนี้)**
  - **Given**: ยอดในใบสรุปเท่ากับยอดใบเสร็จ
  - **When**: ระบบส่งตรวจ
  - **Then**: ผ่านข้อนี้ (`SUMMARY_MATCHES`)
- **AC-3 (ไม่กรอก → ไม่มีข้อค้นพบ และไม่บังคับ)**
  - **Given**: ช่องยอดในใบสรุปว่าง (ช่องนี้ไม่บังคับ)
  - **When**: นักวิจัยส่งตรวจ
  - **Then**: ส่งได้ตามปกติ และไม่มีข้อค้นพบเรื่องใบสรุป
- **AC-4 (ไม่ตรงแต่เกินประมาณการด้วย — เหตุหลักคือประมาณการ)**
  - **Given**: ใบเสร็จเกินประมาณการและยอดในใบสรุปไม่ตรงด้วย
  - **When**: ระบบส่งตรวจ
  - **Then**: เหตุผลหลักคือเกินประมาณการ (ต้องชี้แจง/ขออนุมัติ) โดยข้อค้นพบเรื่องใบสรุปยังแสดงเพิ่มเติม
- **AC-5 (บันทึกยอดใบสรุปไว้กับใบเสร็จ)**
  - **Given**: นักวิจัยกรอกยอดในใบสรุป
  - **When**: ใบเสร็จถูกบันทึก
  - **Then**: ใบเสร็จเก็บยอดที่กรอกไว้เพื่ออ้างอิงย้อนหลัง

## 17. อ่านใบเสร็จด้วย AI และ OCR ภาษาไทยในเครื่อง

(อ้างอิง [[feature-list#17. อ่านใบเสร็จด้วย AI และ OCR ภาษาไทยในเครื่อง|ฟีเจอร์ที่ 17]])

#### FR-30 (สูง) — [[20261117-01-implemented-rule-engine-ai-and-admin#2. Functional Requirements|อ่านใบเสร็จด้วย AI (สลับผู้ให้บริการได้) และ OCR ภาษาไทยในเครื่อง]]

- **AC-1 (AI อ่านภาพ → เสนอค่า + ป้าย AI suggestion)**
  - **Given**: นักวิจัยแนบไฟล์ภาพ (jpg/png) และตั้งค่า AI ไว้พร้อมใช้งาน
  - **When**: นักวิจัยกดดำเนินการต่อจากขั้นที่ 1
  - **Then**: AI อ่านใบเสร็จและเสนอยอด วันที่ หมวด ชื่อร้าน ที่ขั้นที่ 2 พร้อมป้าย "AI suggestion" และแจ้งว่าใช้เส้นทางใดอ่านข้อมูล
- **AC-2 (PDF — อ่านหน้าแรก)**
  - **Given**: นักวิจัยแนบไฟล์ PDF
  - **When**: ระบบเตรียมไฟล์ส่งให้ AI
  - **Then**: ระบบแปลงหน้าแรกของ PDF เป็นภาพแล้วส่งให้ AI อ่าน (เฉพาะหน้าแรก)
- **AC-3 (ถอยกลับเมื่อไม่มี/ล้มเหลว — ไม่ติดป้าย AI)**
  - **Given**: ไม่มีไฟล์แนบ ไม่ได้ตั้งค่า AI หรือการเรียก AI/การแปลง PDF ล้มเหลว
  - **When**: นักวิจัยกดดำเนินการต่อ
  - **Then**: ระบบถอยกลับเป็นกรอกเอง/ข้อมูลสาธิตพร้อมข้อความแจ้งว่าใช้เส้นทางใด และ**ไม่แสดงป้าย "AI suggestion"** (ป้ายแสดงเฉพาะเมื่อ AI ทำงานจริง)
- **AC-4 (OCR ในเครื่องส่งข้อความประกอบภาพให้ AI)**
  - **Given**: บริการ OCR ภาษาไทยในเครื่องเปิดอยู่และ AI ใช้งานได้
  - **When**: ระบบอ่านใบเสร็จ
  - **Then**: ระบบส่งบรรทัดข้อความที่ OCR อ่านได้ (ทำเครื่องหมายบรรทัดที่ความมั่นใจต่ำกว่า 0.9) เข้า AI ประกอบภาพ
- **AC-5 (ไม่มี AI แต่มี OCR → สกัดค่าเอง)**
  - **Given**: บริการ OCR ในเครื่องเปิดอยู่ แต่ไม่มี AI
  - **When**: ระบบได้ข้อความจาก OCR
  - **Then**: ระบบสกัดยอดจากบรรทัดยอดรวมท้ายใบ (ไม่ใช่บรรทัดรายการ รองรับตัวคั่นหลักพันและยอดอยู่บรรทัดถัดจากคำว่ายอด) วันที่ (พ.ศ. ตัวเลข/เดือนไทย → ค.ศ. รูปแบบ ISO)
    และชื่อร้าน (ข้ามหัวเอกสาร) ส่วนหมวดให้นักวิจัยเลือกเอง
- **AC-6 (สลับผู้ให้บริการ AI ได้)**
  - **Given**: ตั้งค่าผู้ให้บริการเป็น OpenRouter / Ollama ในเครื่อง / proxy / custom
  - **When**: ระบบเรียก AI
  - **Then**: เรียกผ่านจุดเรียกเดียว (OpenAI-compatible) ตามที่ตั้งค่า ไม่ส่งคีย์ถ้าไม่ได้ตั้งคีย์ และเมื่อใช้ proxy ส่ง Firebase ID token ของผู้ใช้แทนคีย์
- **AC-7 (นักวิจัยตรวจ/แก้ทุกค่าก่อนส่ง)**
  - **Given**: AI/OCR เสนอค่าครบแล้ว
  - **When**: นักวิจัยแก้ไขค่าใดก็ได้ที่ขั้นที่ 2
  - **Then**: ระบบใช้ค่าที่แก้แล้วส่งตรวจ (ตาม FR-03)

#### NFR-12 (สูง) — [[20261117-01-implemented-rule-engine-ai-and-admin#3. Non-Functional Requirements|Security — AI Proxy ถือคีย์ฝั่งเซิร์ฟเวอร์ รับเฉพาะผู้ใช้ที่ล็อกอิน]]

> สถานะ: เขียนโค้ดและมี test อัตโนมัติแล้ว **ยังไม่ได้ deploy** — AC-1–AC-3 ทดสอบอัตโนมัติได้กับ worker ในเครื่อง ส่วนหลัง deploy ต้องทดสอบด้วยมือ (ดู [[test-plan]])

- **AC-1 (คำขอที่ล็อกอินถูกส่งต่อด้วยคีย์ลับ ไม่ใช่โทเค็นผู้ใช้)**
  - **Given**: ผู้ใช้ล็อกอินแล้วและมี Firebase ID token ที่ถูกต้อง
  - **When**: เว็บเรียก proxy เพื่อขอให้ AI ประมวลผล
  - **Then**: proxy ส่งคำขอต่อไปยังผู้ให้บริการด้วยคีย์ลับที่ถือไว้ฝั่งเซิร์ฟเวอร์ และไม่ส่งโทเค็นของผู้ใช้ต่อ คีย์ไม่ปรากฏในโค้ดฝั่งเบราว์เซอร์
- **AC-2 (ปฏิเสธโทเค็นที่ไม่ถูกต้อง)**
  - **Given**: คำขอที่ไม่มีโทเค็น โทเค็นหมดอายุ โทเค็นปลอม (ลายเซ็นไม่ถูก) หรือโทเค็นของโปรเจกต์อื่น
  - **When**: เรียก proxy
  - **Then**: proxy ปฏิเสธทุกกรณีและไม่ส่งต่อไปยังผู้ให้บริการ
- **AC-3 (จำกัดเว็บต้นทางและโมเดล)**
  - **Given**: คำขอจากเว็บที่ไม่อยู่ในรายการอนุญาต หรือขอโมเดลที่ไม่อนุญาต
  - **When**: เรียก proxy
  - **Then**: proxy ปฏิเสธ และตอบ CORS preflight เฉพาะเว็บต้นทางที่อนุญาต
- **AC-4 (หลัง deploy จริง)**
  - **Given**: proxy ถูก deploy ขึ้นสภาพแวดล้อมจริงและเว็บตั้งค่าผู้ให้บริการเป็น proxy
  - **When**: นักวิจัยที่ล็อกอินกดให้ AI อ่านใบเสร็จบนเว็บจริง และผู้ที่ไม่ได้ล็อกอินลองเรียก proxy โดยตรง
  - **Then**: กรณีแรกทำงานได้โดยไม่มีคีย์ในซอร์สหรือ network ของเบราว์เซอร์ กรณีหลังถูกปฏิเสธ

#### NFR-14 (สูง) — [[20261117-01-implemented-rule-engine-ai-and-admin#3. Non-Functional Requirements|Privacy — ประมวลผลในเครื่อง (OCR/AI ใบเสร็จไม่ออกจากเครื่อง)]]

- **AC-1 (ทางเลือกอ่านใบเสร็จโดยภาพไม่ออกจากเครื่อง)**
  - **Given**: เปิดบริการ OCR ภาษาไทยในเครื่องและตั้งค่า AI เป็น Ollama ในเครื่อง
  - **When**: นักวิจัยแนบใบเสร็จและกดดำเนินการต่อ
  - **Then**: ระบบอ่านใบเสร็จได้โดยไม่มีคำขอภาพ/ข้อความใบเสร็จไปยังผู้ให้บริการภายนอก (ตรวจจาก network ของเบราว์เซอร์)
- **AC-2 (บริการ OCR ในเครื่องรับเฉพาะเครื่องและเว็บที่อนุญาต)**
  - **Given**: บริการ OCR ในเครื่องทำงานอยู่
  - **When**: เว็บที่ไม่อยู่ในรายการอนุญาต หรือเครื่องอื่นในเครือข่ายพยายามเรียก
  - **Then**: บริการผูกที่ 127.0.0.1 เท่านั้นและตอบเฉพาะเว็บต้นทางที่อนุญาต (เว็บจริงแบบ https เรียกได้ผ่านการอนุญาต private network)
- **AC-3 (ผู้ให้บริการภายนอกเป็นการตัดสินใจรายกรณี)**
  - **Given**: ตั้งค่าใช้ผู้ให้บริการ AI ภายนอก (เช่น OpenRouter)
  - **When**: ระบบส่งข้อมูลใบเสร็จไปประมวลผล
  - **Then**: ต้องผ่านเงื่อนไข cross-border/DPA ของ NFR-08/NFR-09 ก่อนใช้กับข้อมูลจริง (ตรวจเชิง compliance ไม่ใช่ functional test)

## 18. Rule Engine แบบโมดูลบริสุทธิ์ ผลตรวจ 4 ระดับ ตรวจย้อนได้

(อ้างอิง [[feature-list#18. Rule Engine แบบโมดูลบริสุทธิ์ ผลตรวจ 4 ระดับ ตรวจย้อนได้|ฟีเจอร์ที่ 18]])

#### FR-24 (สูง) — [[20261117-01-implemented-rule-engine-ai-and-admin#2. Functional Requirements|Rule Engine เป็นโมดูลบริสุทธิ์ มีเวอร์ชัน ตรวจย้อนได้]]

- **AC-1 (ฟังก์ชันบริสุทธิ์ ผลซ้ำได้)**
  - **Given**: อินพุตใบเสร็จและชุดกฎชุดเดียวกัน
  - **When**: เรียก `RuleEngine.evaluate` หลายครั้ง
  - **Then**: ได้ผลเหมือนกันทุกครั้ง โดยไม่ต้องใช้ฐานข้อมูล หน้าจอ หรือเครือข่าย
- **AC-2 (ผลมีฟิลด์ย้อนกลับครบ)**
  - **Given**: Rule Engine ตัดสินใบเสร็จเสร็จแล้วในทุกสถานะ
  - **When**: ตรวจผลลัพธ์
  - **Then**: มีสถานะ รหัสเหตุผล (machine-readable) คำอธิบาย ข้อระเบียบอ้างอิง รหัสกฎ/เวอร์ชันกฎ/แหล่งทุน/ชุดเอกสาร และเวอร์ชัน engine เสมอ
    โดยข้อระเบียบและชุดเอกสารมาจากกฎที่จับคู่
- **AC-3 (บันทึกในใบเสร็จ)**
  - **Given**: ใบเสร็จใหม่ถูกบันทึก
  - **When**: ตรวจข้อมูล `ruleCheck` ของใบเสร็จ
  - **Then**: มีเวอร์ชัน engine, รหัสเหตุผล, สถานะตรวจยืนยันอัตโนมัติ, แหล่งทุน, เวอร์ชันกฎ, รหัสกฎ และรายการข้อค้นพบ
- **AC-4 (ใช้ซ้ำนอกแอปได้)**
  - **Given**: ชุดประเมินผลหรือชุดทดสอบนอกเบราว์เซอร์
  - **When**: โหลดโมดูลเดียวกับที่แอปใช้ใน Node
  - **Then**: ทำงานได้กับชุดกฎจริงเดียวกัน (ตรวจใน FR-34)
- **AC-5 (ตรวจยืนยันอัตโนมัติ — ความหมายของ autoVerified)**
  - **Given**: ใบเสร็จที่ตรวจครบทั้งประมาณการ เพดาน และเอกสาร / ใบเสร็จที่ด้านใดด้านหนึ่งไม่ได้ตรวจจริง
  - **When**: ตรวจผลลัพธ์
  - **Then**: `autoVerified` เป็นจริงเฉพาะกรณีแรกเท่านั้น (ผ่านตามหมวดโดยไม่ตรวจตัวเลขต้องเป็นเท็จ)
- **AC-6 (ปรับเลขเวอร์ชันเมื่อตรรกะเปลี่ยน)**
  - **Given**: นักพัฒนาเปลี่ยนตรรกะตัดสินของ engine
  - **When**: ตรวจการเปลี่ยนแปลงก่อนปล่อย
  - **Then**: เลขเวอร์ชัน engine ถูกปรับขึ้นด้วย (ตรวจเชิงกระบวนการ/code review ไม่ใช่ functional test)

#### FR-25 (สูง) — [[20261117-01-implemented-rule-engine-ai-and-admin#2. Functional Requirements|ผลตรวจ 4 ระดับ และลำดับการตรวจ (ประมาณการ→ระเบียบ→ใบสรุป→เอกสารแนบ)]]

- **AC-1 (4 ระดับเรียงเบา→หนัก)**
  - **Given**: ใบเสร็จที่ให้ผลต่างกัน
  - **When**: ดูผลตรวจ
  - **Then**: มีสถานะได้เพียง ผ่าน / ต้องแก้ไข / ต้องชี้แจง/ขออนุมัติ / ไม่เข้าเงื่อนไข เรียงจากเบาไปหนักตามลำดับนี้
- **AC-2 (สถานะ = ข้อค้นพบที่รุนแรงที่สุด)**
  - **Given**: ใบเสร็จมีหลายข้อค้นพบที่ระดับต่างกัน (เช่น เกินประมาณการและขาดเอกสาร)
  - **When**: ระบบรวมผล
  - **Then**: สถานะของใบเสร็จเป็นระดับที่รุนแรงที่สุดในบรรดาข้อค้นพบ (เกินประมาณการ → ต้องชี้แจง/ขออนุมัติ เหนือกว่าขาดเอกสาร → ต้องแก้ไข)
- **AC-3 (ลำดับตรวจและรหัสเหตุผลหลัก)**
  - **Given**: มีข้อค้นพบหลายกลุ่มที่ระดับความรุนแรงเท่ากัน
  - **When**: ระบบกำหนดรหัสเหตุผลหลัก
  - **Then**: เลือกข้อค้นพบแรกที่ไม่ใช่ "ยังไม่ได้ตรวจ" ตามลำดับกลุ่ม ประมาณการ → ระเบียบ → ใบสรุปรายรับ-จ่าย → เอกสารแนบ
- **AC-4 (แสดงข้อค้นพบทุกกลุ่ม)**
  - **Given**: ใบเสร็จมีข้อค้นพบมากกว่า 1 ข้อ
  - **When**: นักวิจัยเปิดดูผลตรวจ
  - **Then**: ระบบแสดงข้อค้นพบทั้งหมดแยกรายกลุ่ม (ไม่ใช่เฉพาะข้อแรกที่พบ) พร้อมคำอธิบาย
- **AC-5 (การแมปประเภทปัญหาเป็นสถานะ)**
  - **Given**: กรณีตัวอย่างแต่ละประเภท
  - **When**: ตรวจผล
  - **Then**: นอกประมาณการ/เกิน 100% = ต้องชี้แจง/ขออนุมัติ; ยอดเกินเพดานทั้งก้อน/เอกสารหรือตราขาด/ยอดไม่ตรงใบสรุป/ยอดไม่ถูกต้อง = ต้องแก้ไข;
    หมวดที่ระเบียบไม่อนุญาต/ไม่มีแหล่งทุน/ไม่มีเวอร์ชันกฎ = ไม่เข้าเงื่อนไข
- **AC-6 (แสดงสถานะด้วยสี+ไอคอน+ข้อความ)**
  - **Given**: ผลตรวจทั้ง 4 ระดับ
  - **When**: แสดงที่หน้ารายการ หน้าผลตรวจ และ Admin Dashboard
  - **Then**: ทุกที่ใช้ชิปสถานะที่มีสี ไอคอน และข้อความเสมอ ไม่พึ่งสีอย่างเดียว (NFR-13 AC-2) และผลตรวจที่ขั้นที่ 3 แสดงเป็นตราเด่นชัด

## 19. AI agent อธิบายผลจากกฎในระบบเท่านั้น พร้อมบันทึกประวัติ

(อ้างอิง [[feature-list#19. AI agent อธิบายผลจากกฎในระบบเท่านั้น พร้อมบันทึกประวัติ|ฟีเจอร์ที่ 19]])

#### FR-31 (สูง) — [[20261117-01-implemented-rule-engine-ai-and-admin#2. Functional Requirements|AI agent อธิบายผลจากกฎในระบบเท่านั้น + บันทึก agentLogs]]

- **AC-1 (ดึงชุดเอกสารจากระบบแล้วอธิบายเป็นภาษาไทย พร้อมวิธีแก้)**
  - **Given**: Rule Engine ตัดสินผลแล้ว และกฎที่จับคู่ชี้ไปยังชุดเอกสาร
  - **When**: agent ทำงานหลังบันทึกใบเสร็จ
  - **Then**: agent อ่านชุดเอกสารและประเภทเอกสารที่เกี่ยวข้องจากระบบเท่านั้น แล้วให้ AI สรุปเป็นภาษาไทยพร้อมวิธีแก้ และคำอธิบายสุดท้ายถูกเขียนกลับที่ใบเสร็จ
- **AC-2 (ไม่เปลี่ยนสถานะ)**
  - **Given**: agent ทำงานเสร็จ
  - **When**: เทียบสถานะใบเสร็จก่อน-หลัง agent
  - **Then**: สถานะผลตรวจไม่เปลี่ยน (เปลี่ยนเฉพาะข้อความคำอธิบาย)
- **AC-3 (ข้อห้ามของ agent)**
  - **Given**: agent สรุปผลให้นักวิจัย
  - **When**: ตรวจคำอธิบายและพรอมต์ที่ใช้
  - **Then**: ไม่มีความรู้ภายนอก ไม่มีกฎ/เอกสารที่ระบบไม่มี และไม่อ้างว่าเห็นหรือตรวจไฟล์ที่แนบ (ระบุได้เพียงว่าระเบียบต้องการอะไร ไม่ยืนยันว่าไฟล์ที่แนบถูกต้อง)
- **AC-4 (บันทึก agentLogs ทุกครั้ง)**
  - **Given**: agent ทำงานครั้งหนึ่ง (ใช้ AI หรือถอยกลับก็ตาม)
  - **When**: เปิดดูประวัติของใบเสร็จนั้น
  - **Then**: มีบันทึก 1 รายการต่อการรัน ระบุว่าใช้ AI หรือไม่ โมเดล ชุดเอกสาร/ประเภทเอกสารที่ใช้ คำอธิบายสุดท้าย และระยะเวลา และบันทึกอยู่แยกจากฟิลด์ใบเสร็จและไฟล์แนบ
- **AC-5 (ถอยกลับเมื่อไม่มี AI/ล้มเหลว)**
  - **Given**: ไม่มีคีย์ AI หรือการเรียก AI ล้มเหลว
  - **When**: agent ทำงาน
  - **Then**: คำอธิบายถอยกลับเป็นคำอธิบายจากกฎล้วนต่อท้ายด้วยรายการเอกสารที่ต้องมีจากระบบ และยังบันทึก agentLogs (ระบุว่าไม่ได้ใช้ AI)
- **AC-6 (ความล้มเหลวของ agent ไม่ขัดขวางการบันทึกใบเสร็จ)**
  - **Given**: agent หรือการเขียน agentLogs ล้มเหลว
  - **When**: ใบเสร็จถูกบันทึกแล้วก่อนหน้านั้น
  - **Then**: ใบเสร็จยังคงถูกบันทึกสำเร็จพร้อมสถานะและคำอธิบายจากกฎ ระบบแสดงต่อได้โดยไม่ error ถึงผู้ใช้

## 20. ชุดกฎตามคู่มือจริง (rule set 2570.4) และการอัปเดตกฎ

(อ้างอิง [[feature-list#20. ชุดกฎตามคู่มือจริง (rule set 2570.4) และการอัปเดตกฎ|ฟีเจอร์ที่ 20]])

#### FR-29 (สูง) — [[20261117-01-implemented-rule-engine-ai-and-admin#2. Functional Requirements|ชุดกฎตามคู่มือจริง 28 หมวด (rule set 2570.4)]]

- **AC-1 (ครอบคลุมทุกหมวดในรายการ)**
  - **Given**: ชุดกฎและรายการหมวดค่าใช้จ่ายในรายการให้เลือก
  - **When**: ตรวจความสอดคล้อง
  - **Then**: ทุกหมวดในรายการ ยกเว้นหมวดที่คู่มือไม่สนับสนุน มีกฎ 1 รายการพอดี (รวม 28 หมวดที่มีกฎ) และกฎทุกข้อที่ชี้ไปยังชุดเอกสารต้องชี้ไปยังชุดเอกสารและประเภทเอกสารที่มีอยู่จริง
- **AC-2 (หมวดที่คู่มือไม่สนับสนุน → ไม่เข้าเงื่อนไข)**
  - **Given**: ใบเสร็จหมวด "ค่าตอบแทนคณะผู้วิจัย"
  - **When**: ส่งตรวจ
  - **Then**: ผลเป็น "ไม่เข้าเงื่อนไข" เพราะไม่มีกฎรองรับ ไม่ถูกแต่งกฎขึ้นเอง
- **AC-3 (พฤติกรรมตามประเภทอัตรา)**
  - **Given**: กฎประเภท เพดานตามจริง / เหมาจ่าย / ต่อหน่วย / ตามข้อเสนอโครงการ
  - **When**: ส่งตรวจ
  - **Then**: เพดานตามจริง/เหมาจ่ายเปรียบเทียบยอดกับเพดานจริง (เท่าเพดานผ่าน เกินต้องแก้ไข) ส่วนต่อหน่วย/ตามข้อเสนอโครงการผ่านตามหมวดแต่ไม่นับเป็นตรวจยืนยันอัตโนมัติถ้าไม่มีประมาณการ
- **AC-4 (ไม่แต่งตัวเลขเอง และอ้างอิงแหล่งที่มา)**
  - **Given**: กฎแต่ละข้อของ rule set 2570.4
  - **When**: ตรวจหมายเหตุและผลตรวจ
  - **Then**: กฎที่ใช้ตัวเลขอ้างข้อ/หน้าของคู่มือในหมายเหตุ รายการที่คู่มือไม่ระบุตัวเลขตายตัว (เช่น เชื้อเพลิง บริการจ้างเหมา ครุภัณฑ์) ใช้ประเภท "ตามข้อเสนอโครงการ" ไม่มีเพดานที่แต่งขึ้น และข้อระเบียบที่อ้างปรากฏในคำอธิบายผลตรวจ
- **AC-5 (ค่าที่พักแยก 2 หมวด และเชื้อเพลิงตามจริง)**
  - **Given**: ค่าที่พักโรงแรม (เพดาน 1,800 บาท/วัน ต้องมีใบเสร็จ) และค่าที่พักเหมาจ่าย (800 บาท/วัน ใช้ วจ.2) / ค่าเชื้อเพลิง
  - **When**: ส่งตรวจ
  - **Then**: ทั้งสองหมวดที่พักถูกตรวจตามเงื่อนไขของตนและต้องการเอกสารต่างกัน เชื้อเพลิงเบิกตามจริงเทียบประมาณการ ไม่ใช้อัตราตั้งงบเป็นเพดาน
- **AC-6 (เอกสารที่ยกเลิกต้องไม่อยู่ในชุดกฎ)**
  - **Given**: ชุดเอกสารของ rule set ปัจจุบัน
  - **When**: ตรวจประเภทเอกสาร
  - **Then**: ไม่มี วจ.9 (บัญชีเงินสดย่อย) ซึ่งคู่มือฉบับปรับปรุงยกเลิกแล้ว
- **AC-7 (ผลักกฎเข้าระบบจริงผ่านปุ่มของ Admin)**
  - **Given**: Admin เข้าสู่ระบบ และกฎในไฟล์ตั้งต้นถูกแก้ไขแล้ว (ยังไม่มีผลกับข้อมูลจริง)
  - **When**: Admin กดปุ่ม "อัปเดตเฉพาะระเบียบ/กฎ" ที่หน้าใส่ข้อมูล และแยกกรณีผู้ใช้ที่ไม่ใช่ Admin กดปุ่มเดียวกัน
  - **Then**: กรณี Admin กฎในฐานข้อมูลจริงถูกเขียนทับ/เพิ่มตามไฟล์ (ไม่แตะโครงการและใบเสร็จตัวอย่าง) และรายงานผลต่อชุดข้อมูล กรณีไม่ใช่ Admin
    ระบบข้ามการเขียนกฎและรายงานว่า "ข้าม"

## 21. แนบไฟล์จริงผ่าน Google Drive ของผู้ใช้

(อ้างอิง [[feature-list#21. แนบไฟล์จริงผ่าน Google Drive ของผู้ใช้|ฟีเจอร์ที่ 21]])

#### FR-32 (กลาง) — [[20261117-01-implemented-rule-engine-ai-and-admin#2. Functional Requirements|แนบไฟล์จริงผ่าน Google Drive ของผู้ใช้]]

- **AC-1 (เชื่อมต่อ Drive ด้วยสิทธิ์ขั้นต่ำ)**
  - **Given**: นักวิจัยอยู่ที่ขั้นที่ 1 ของหน้าอัปโหลดใบเสร็จและต้องการแนบไฟล์จริง
  - **When**: กด "เชื่อมต่อ Google Drive" และอนุญาตบัญชี Google ของตนเอง
  - **Then**: ระบบได้สิทธิ์ `drive.file` เท่านั้น (เห็น/จัดการเฉพาะไฟล์ที่แอปสร้างเอง ไม่เห็น Drive ทั้งหมด)
- **AC-2 (เก็บไฟล์ตามรหัสใบเสร็จและแสดงเป็นลิงก์ — ส่วน "ผู้ที่มีลิงก์ดูได้" คือพฤติกรรมปัจจุบันที่จะถูกแทนด้วย FR-37 AC-1)**
  - **Given**: เชื่อมต่อ Drive แล้วและนักวิจัยส่งใบเสร็จพร้อมไฟล์แนบ
  - **When**: ระบบอัปโหลดไฟล์
  - **Then**: ไฟล์ถูกเก็บในโฟลเดอร์แยกตามรหัสใบเสร็จใน Drive ของนักวิจัย ตั้งเป็น "ผู้ที่มีลิงก์ดูได้" และหน้ารายการใบเสร็จกับ Admin Dashboard แสดงเป็นลิงก์ที่กดเปิดได้
- **AC-3 (แนบไฟล์แต่ยังไม่เชื่อมต่อ/โทเค็นหมดอายุ → เตือน)**
  - **Given**: นักวิจัยแนบไฟล์แต่ยังไม่ได้เชื่อมต่อ Drive หรือโทเค็นหมดอายุ (ประมาณ 1 ชั่วโมง)
  - **When**: กดส่งที่ขั้นที่ 2
  - **Then**: ระบบบล็อกพร้อมข้อความเตือนให้เชื่อมต่อใหม่ แทนการล้มเหลวเงียบ
- **AC-4 (ไม่แนบไฟล์ — ข้ามได้)**
  - **Given**: นักวิจัยไม่ต้องการแนบไฟล์จริง
  - **When**: ส่งใบเสร็จโดยไม่เชื่อมต่อ Drive
  - **Then**: ใบเสร็จบันทึกได้ตามปกติ และหน้ารายการแสดงว่าไม่มีไฟล์จริงแนบ (โหมดสาธิต)

> หมายเหตุ: ข้อจำกัดที่ทราบเดิม (การลบใบเสร็จไม่ลบไฟล์จริงใน Drive, ไฟล์ตั้ง "ผู้ที่มีลิงก์ดูได้") ถูกปิดด้วย FR-37/NFR-15 ด้านล่างแล้ว

#### FR-37 (สูง) — [[20261117-02-fund-source-deactivation-estimate-versioning-drive-privacy#2. Functional Requirements|จำกัดผู้ดูไฟล์ใน Google Drive และลบไฟล์ตามเมื่อลบใบเสร็จ/ถอนความยินยอม]]

> spec FR-37 มี 5 ข้อย่อย: (1)→AC-1/AC-2, (2)→AC-3, (3)→AC-4, (4)→AC-5/AC-6, (5)→AC-7
>
> **สถานะ: ยังไม่ได้สร้าง (Backlog)** — AC ด้านล่างเป็นเกณฑ์รับมอบ รันไม่ได้จนกว่าจะสร้าง ต่อยอด FR-32, FR-18 (ฟีเจอร์ 12) และ FR-20 (ฟีเจอร์ 10)
> **พฤติกรรมปัจจุบันที่จะถูกแทนที่**: ไฟล์ตั้ง "ผู้ที่มีลิงก์ดูได้" (FR-32 AC-2) และการลบใบเสร็จลบแค่ข้อมูลใน Firestore (FR-18 AC-3)

- **AC-1 (จำกัดผู้ดูเป็นเจ้าของและ Admin เท่านั้น)**
  - **Given**: นักวิจัยเชื่อมต่อ Drive แล้วและส่งใบเสร็จพร้อมไฟล์แนบ
  - **When**: ระบบอัปโหลดไฟล์ไปยัง Drive ของนักวิจัย
  - **Then**: ไฟล์**ไม่ถูกตั้งเป็น "ผู้ที่มีลิงก์ดูได้"** — ผู้ที่เปิดดูไฟล์ได้มีเฉพาะเจ้าของใบเสร็จและ Admin เท่านั้น ผู้อื่น (นักวิจัยคนอื่น ผู้ที่ไม่ได้ล็อกอิน) ที่ได้ลิงก์มาเปิดไม่ได้
- **AC-2 (Admin ยังเปิดดูไฟล์ได้)**
  - **Given**: ใบเสร็จของนักวิจัยมีไฟล์แนบใน Drive
  - **When**: Admin กดลิงก์ไฟล์ที่หน้า Admin Dashboard (FR-33 AC-2)
  - **Then**: Admin เปิดดูไฟล์ได้ตามที่ FR-37 ให้สิทธิ์ (อ่านอย่างเดียว) ขณะที่นักวิจัยคนอื่นเปิดไม่ได้
- **AC-3 (ลบใบเสร็จ → ลบไฟล์ใน Drive ด้วย)**
  - **Given**: นักวิจัยมีใบเสร็จของตนเองที่มีไฟล์แนบใน Drive และเชื่อมต่อ Drive อยู่
  - **When**: นักวิจัยลบใบเสร็จนั้น (FR-18) และยืนยัน
  - **Then**: ระบบลบไฟล์ที่เกี่ยวข้องกับใบเสร็จนั้นใน Drive ด้วย (ไม่ใช่แค่ข้อมูลใน Firestore) ไฟล์ของใบเสร็จอื่นไม่ถูกแตะ
- **AC-4 (ถอนความยินยอม → ลบไฟล์ใน Drive ทั้งหมดที่ระบบสร้าง)**
  - **Given**: นักวิจัยมีหลายใบเสร็จที่มีไฟล์แนบใน Drive ที่ระบบสร้างไว้
  - **When**: นักวิจัยถอนความยินยอม (FR-20)
  - **Then**: ระบบลบไฟล์ใน Drive ทั้งหมดของผู้ใช้ที่ระบบสร้างด้วย ควบคู่กับการลบข้อมูลใบเสร็จ/ผลตรวจทั้งหมด (ไฟล์อื่นใน Drive ที่ผู้ใช้เก็บเองซึ่งระบบไม่ได้สร้างไม่ถูกแตะ — สอดคล้องสิทธิ์ `drive.file`)
- **AC-5 (ลบไฟล์ใน Drive ไม่สำเร็จ → แจ้งผู้ใช้ ไม่ล้มเหลวเงียบ — negative)**
  - **Given**: ระบบต้องลบไฟล์ใน Drive (ตาม AC-3 หรือ AC-4) แต่ลบไม่สำเร็จ (เช่น โทเค็น Drive หมดอายุ)
  - **When**: ระบบพยายามลบไฟล์
  - **Then**: ระบบแจ้งผู้ใช้ว่าลบไฟล์ใน Drive ไม่สำเร็จพร้อมเหตุผล และขอให้เชื่อมต่อ Drive ใหม่แล้วลองอีกครั้ง ไม่แสดงว่าลบสำเร็จทั้งที่ไฟล์ยังอยู่ และไม่ล้มเหลวเงียบ (สถานะข้อมูลหลังล้มเหลวดู AC-6)
- **AC-6 (ลบไฟล์ Drive ไม่สำเร็จ → ไม่ลบข้อมูลใน Firestore เลย ไม่มีไฟล์กำพร้า — negative)**
  - **Given**: นักวิจัยลบใบเสร็จ (FR-18) หรือถอนความยินยอม (FR-20) แต่การลบไฟล์ใน Drive ไม่สำเร็จ (เช่น โทเค็นหมดอายุ)
  - **When**: ระบบพยายามลบและล้มเหลว
  - **Then**: **ไม่มีข้อมูลใดถูกลบจาก Firestore จนกว่าจะลบไฟล์ใน Drive ได้จริง** — ใบเสร็จ `ruleCheck` `agentLogs` และเอกสาร `files` ยังอยู่ครบทุกรายการ (ในกรณีถอนความยินยอม ข้อมูลของทุกใบเสร็จยังอยู่ครบ) และไม่มีไฟล์กำพร้าใน Drive (ไม่มีกรณีที่ข้อมูลใน Firestore หายแต่ไฟล์ยังค้าง) ผู้ใช้เชื่อมต่อ Drive ใหม่แล้วลองลบอีกครั้งได้ และเมื่อสำเร็จจึงลบข้อมูลใน Firestore ตามปกติ (AC-3/AC-4)
- **AC-7 (ไฟล์เก่าที่ยังเป็น "ผู้ที่มีลิงก์ดูได้" ถูกถอนการแชร์อัตโนมัติเมื่อเชื่อมต่อ Drive ครั้งถัดไป)**
  - **Given**: มีไฟล์ใบเสร็จที่อัปโหลดก่อนมี FR-37 ซึ่งยังตั้งเป็น "ผู้ที่มีลิงก์ดูได้" ใน Drive ของนักวิจัย
  - **When**: นักวิจัยเชื่อมต่อ Google Drive ครั้งถัดไป (กด "เชื่อมต่อ Google Drive" และอนุญาต)
  - **Then**: ระบบถอนการแชร์แบบลิงก์สาธารณะของไฟล์ใบเสร็จเดิมเหล่านั้นโดยอัตโนมัติ (ไม่ต้องให้ผู้ใช้ทำเอง) และจำกัดให้เจ้าของและ Admin ดูได้เท่านั้น ผู้อื่นที่มีลิงก์เดิมเปิดไม่ได้ไฟล์ที่ผู้ใช้เก็บเองซึ่งระบบไม่ได้สร้างไม่ถูกแตะ

#### NFR-15 (สูง) — [[20261117-02-fund-source-deactivation-estimate-versioning-drive-privacy#3. Non-Functional Requirements|Privacy — ขอบเขตการเข้าถึงและการลบไฟล์แนบ]]

> **สถานะ: ยังไม่ได้สร้าง (Backlog)** — [[backlog]] ไม่มีคอลัมน์ระดับความสำคัญของ NFR จึงสืบทอด "สูง" จากฟีเจอร์ 21 (Must have เพราะมี FR-37) ตามหลักที่ใช้ทั้งไฟล์นี้

- **AC-1 (ผู้ที่ไม่ใช่เจ้าของ/Admin เข้าถึงไฟล์ไม่ได้)**
  - **Given**: ไฟล์ใบเสร็จที่อาจมีข้อมูลส่วนบุคคล (เช่น สำเนาบัตรประชาชน) อยู่ใน Drive ของเจ้าของ
  - **When**: ผู้ที่ไม่ใช่เจ้าของและไม่ใช่ Admin (นักวิจัยคนอื่น หรือผู้ที่ไม่ได้ล็อกอิน) พยายามเปิดไฟล์ผ่านลิงก์ที่ได้มา
  - **Then**: การเข้าถึงถูกปฏิเสธ ไม่เห็นเนื้อหาไฟล์
- **AC-2 (ลบจริงตามสิทธิ์ลบของเจ้าของข้อมูล)**
  - **Given**: เจ้าของข้อมูลใช้สิทธิ์ลบผ่านการลบใบเสร็จ (FR-18) หรือถอนความยินยอม (FR-20)
  - **When**: การลบเสร็จสิ้น
  - **Then**: ไฟล์ที่เกี่ยวข้องไม่ปรากฏในโฟลเดอร์ของแอปใน Drive อีก และเปิดผ่านลิงก์เดิมไม่ได้ (เกี่ยวข้อง NFR-08, NFR-14)

## 22. Admin Dashboard อ่านใบเสร็จทุกคนแบบอ่านอย่างเดียว และจัดการแหล่งทุน/กฎ

(อ้างอิง [[feature-list#22. Admin Dashboard อ่านใบเสร็จทุกคนแบบอ่านอย่างเดียว และจัดการแหล่งทุน/กฎ|ฟีเจอร์ที่ 22]])

#### FR-33 (สูง) — [[20261117-01-implemented-rule-engine-ai-and-admin#2. Functional Requirements|Admin อ่านใบเสร็จทุกคนแบบอ่านอย่างเดียว และจัดการกฎ/แหล่งทุน (ส่วนหน้าจอและการจัดการ)]]

> ส่วนสิทธิ์การเข้าถึง (อ่านอย่างเดียว/เมนู/ยกสิทธิ์ตนเองไม่ได้) ดู AC ที่หัวข้อ 9

- **AC-1 (สรุปตามสถานะ หมวด และแหล่งทุน)**
  - **Given**: มีใบเสร็จของนักวิจัยหลายคนหลายสถานะ หมวด และแหล่งทุน
  - **When**: Admin เปิด Admin Dashboard
  - **Then**: แสดงจำนวนตามสถานะ 4 ระดับ (มีช่องของ "ต้องชี้แจง/ขออนุมัติ" ด้วย) แยกตามหมวดค่าใช้จ่าย และตามแหล่งทุน ถูกต้องตรงกับข้อมูลจริง
- **AC-2 (รายละเอียดใบเสร็จรายใบ)**
  - **Given**: Admin เปิดรายการใบเสร็จรายใบใน Dashboard
  - **When**: ดูแต่ละใบ
  - **Then**: แสดงเจ้าของ (ชื่อ/อีเมล) โครงการ แหล่งทุน สถานะ คำอธิบายผลตรวจ และลิงก์ไฟล์ใน Drive (ถ้ามี) โดยไม่มีปุ่ม/การกระทำที่แก้ใบเสร็จของผู้อื่น
- **AC-3 (เพิ่ม/ลบแหล่งทุน — ส่วนลบแบบ cascade ไม่ตรวจโครงการที่ใช้อยู่คือพฤติกรรมปัจจุบันที่จะถูกแทนด้วย FR-35 ด้านล่าง)**
  - **Given**: Admin เปิดหน้าจัดการแหล่งทุน
  - **When**: เพิ่มแหล่งทุนใหม่ และลบแหล่งทุนหนึ่ง
  - **Then**: แหล่งทุนใหม่ปรากฏให้นักวิจัยเลือกผูกโครงการได้ การลบแหล่งทุนลบเวอร์ชันกฎและกฎของแหล่งทุนนั้นต่อเนื่องไปด้วย
- **AC-4 (แก้กฎรายหมวด)**
  - **Given**: Admin เปิดการ์ดแหล่งทุน
  - **When**: เพิ่ม/แก้/ลบกฎรายหมวด (ประเภทอัตรา จำนวนเงิน หน่วย ชุดเอกสาร หมายเหตุ)
  - **Then**: บันทึกลงเวอร์ชันกฎที่ใช้งานอยู่ของแหล่งทุนนั้น (สร้างให้อัตโนมัติเมื่อเพิ่มกฎแรก) และแสดงชื่อชุดเอกสารที่เลือก ไม่ใช่รหัส
- **AC-5 (ผู้ที่ไม่ใช่ Admin ถูกปฏิเสธ)**
  - **Given**: นักวิจัยที่ไม่ใช่ Admin
  - **When**: เปิดหน้า Admin Dashboard หรือหน้าจัดการแหล่งทุน และพยายามเขียนแหล่งทุน/กฎโดยตรง
  - **Then**: หน้าแสดงข้อความปฏิเสธสิทธิ์แทนเนื้อหา และการเขียนถูกฐานข้อมูลปฏิเสธ (การอ่านรายการแหล่งทุนเพื่อเลือกผูกโครงการยังทำได้)

#### FR-35 (สูง) — [[20261117-02-fund-source-deactivation-estimate-versioning-drive-privacy#2. Functional Requirements|ปิดใช้งานแหล่งทุนแทนการลบจริง (Soft-delete)]]

> **สถานะ: ยังไม่ได้สร้าง (Backlog)** — AC ด้านล่างเป็นเกณฑ์รับมอบ รันไม่ได้จนกว่าจะสร้าง ต่อยอด FR-33 (ส่วนจัดการแหล่งทุน), FR-23, NFR-04
> **พฤติกรรมปัจจุบันที่จะถูกแทนที่**: FR-33 AC-3 ลบแหล่งทุนแบบ cascade (ลบเวอร์ชันกฎและกฎต่อเนื่อง) โดยไม่ตรวจโครงการที่ใช้อยู่ โครงการเดิมจึงกลายเป็น "(ไม่พบแหล่งทุน)"
>
> **จุดเปิดที่ spec ระบุไว้แล้ว (ไม่เขียน AC พฤติกรรม ไม่ใช่ requirement ใหม่)**: ใบเสร็จใหม่ในโครงการเดิมที่ผูกกับแหล่งทุนที่ปิดใช้งาน
> จะ "ตรวจต่อ" หรือ "บล็อก" — spec ระบุว่าต้องตัดสินตอนออกแบบ ดู TC-22-11 (บันทึกเป็นข้อสังเกต ไม่มีผลคาดหวัง)

- **AC-1 (ปิดใช้งานแล้วเก็บกฎไว้ครบ)**
  - **Given**: Admin เปิดหน้าจัดการแหล่งทุน มีแหล่งทุนที่ใช้งานอยู่ ซึ่งมีเวอร์ชันกฎและกฎรายหมวด และมีโครงการอ้างอิงอยู่
  - **When**: Admin กด "ปิดใช้งาน" แหล่งทุนนั้น
  - **Then**: แหล่งทุนถูกทำเครื่องหมายว่าปิดใช้งาน (ไม่ถูกลบ) เวอร์ชันกฎ (`ruleVersions`) และกฎรายหมวด (`ruleItems`) ยังอยู่ครบเพื่อย้อนตรวจใบเสร็จเก่า และหน้าจัดการแสดงสถานะปิดใช้งานชัดเจน
- **AC-2 (ซ่อนจากรายการเลือกแหล่งทุนตอนสร้างโครงการใหม่)**
  - **Given**: มีแหล่งทุนที่ปิดใช้งานและแหล่งทุนที่ใช้งานอยู่
  - **When**: นักวิจัยเปิดฟอร์มสร้างโครงการใหม่ (FR-23)
  - **Then**: รายการเลือกแหล่งทุนไม่แสดงแหล่งทุนที่ปิดใช้งาน แสดงเฉพาะที่ใช้งานอยู่
- **AC-3 (โครงการเดิมและใบเสร็จเก่ายังแสดง/ย้อนตรวจได้ปกติ)**
  - **Given**: โครงการเดิมสังกัดแหล่งทุนที่ถูกปิดใช้งาน และมีใบเสร็จที่ตรวจไว้แล้ว (มี `ruleCheck`)
  - **When**: นักวิจัยเปิดรายการโครงการ/ใบเสร็จ หรือ Admin เปิด Admin Dashboard
  - **Then**: โครงการยังแสดงชื่อแหล่งทุนเดิมตามปกติ **ไม่กลายเป็น "(ไม่พบแหล่งทุน)"** และใบเสร็จเก่ายังอ้างอิงกฎ/เวอร์ชันที่ใช้ตัดสินได้ครบ (NFR-04)
- **AC-4 (เปิดใช้งานกลับได้)**
  - **Given**: แหล่งทุนที่ปิดใช้งานอยู่
  - **When**: Admin กด "เปิดใช้งาน"
  - **Then**: แหล่งทุนกลับมาแสดงในรายการเลือกตอนสร้างโครงการใหม่ และกฎรายหมวดครบเหมือนก่อนปิด
- **AC-5 (ผู้ที่ไม่ใช่ Admin ปิด/เปิดใช้งานไม่ได้ — negative)**
  - **Given**: นักวิจัยที่ไม่ใช่ Admin
  - **When**: พยายามปิด/เปิดใช้งานแหล่งทุน ผ่านหน้าเว็บหรือเขียนฐานข้อมูลโดยตรง
  - **Then**: หน้าแสดงข้อความปฏิเสธสิทธิ์ และการเขียนถูกฐานข้อมูลปฏิเสธ (สอดคล้อง FR-33 AC-5)

## 23. ชุดประเมินผลสำหรับวิทยานิพนธ์ (รันนอกแอป)

(อ้างอิง [[feature-list#23. ชุดประเมินผลสำหรับวิทยานิพนธ์ (รันนอกแอป)|ฟีเจอร์ที่ 23]])

#### FR-34 (กลาง) — [[20261117-01-implemented-rule-engine-ai-and-admin#2. Functional Requirements|ชุดประเมินผลสำหรับวิทยานิพนธ์]]

> ข้อจำกัด (เสร็จบางส่วน): ยังไม่มีข้อมูลจริง (รอ EC) มีแค่เคสสมมติ และยังไม่ได้รัน baseline กับ API ที่เสียเงิน

- **AC-1 (อ่านไฟล์เคส CSV)**
  - **Given**: ไฟล์เคส CSV ที่มี BOM ค่าที่มีเครื่องหมายจุลภาคในเครื่องหมายคำพูด และขึ้นบรรทัดใหม่ในช่อง
  - **When**: รันชุดประเมินผล
  - **Then**: อ่านไฟล์ได้ถูกต้องครบทุกเคส
- **AC-2 (ป้ายผลตัดสินรับไทย/อังกฤษ)**
  - **Given**: คอลัมน์ผลตัดสินของเจ้าหน้าที่การเงินเขียนเป็นภาษาไทยหรืออักษรย่ออังกฤษ
  - **When**: ชุดประเมินผลแปลงเป็นสถานะ
  - **Then**: แปลงเป็นสถานะ 4 ระดับได้ถูกต้อง
- **AC-3 (แปลงเคสเป็นอินพุต Rule Engine รวมประมาณการและเอกสาร)**
  - **Given**: เคสมีคอลัมน์ประมาณการและเอกสารแนบ
  - **When**: ชุดประเมินผลสร้างอินพุตใบเสร็จ
  - **Then**: อินพุตรวมข้อมูลประมาณการและเอกสารที่ระบุในเคสเข้าไปด้วย
- **AC-4 (ตัวชี้วัด)**
  - **Given**: ชุดเคสที่มีผลของระบบและผลของเจ้าหน้าที่การเงิน
  - **When**: คำนวณตัวชี้วัด
  - **Then**: รายงาน accuracy, Cohen's kappa, macro F1, จำนวนปัญหาที่ระบบพลาด (missed) และจำนวนแจ้งเตือนเกิน (false alarm) ถูกต้อง
- **AC-5 (รันเคสตัวอย่างจบกระบวนการกับชุดกฎจริง)**
  - **Given**: ไฟล์เคสตัวอย่าง (ข้อมูลสมมติ ซึ่งมีเคสที่ตั้งใจให้ไม่ตรงกับระบบอย่างน้อย 1 เคส)
  - **When**: รันชุดประเมินผลกับ Rule Engine เดียวกับแอป
  - **Then**: ได้รายงานครบ และเคสที่ตั้งใจให้ไม่ตรงถูกนับเป็นความไม่ตรงจริง
- **AC-6 (เทียบกับ AI ตัดสินเองล้วน)**
  - **Given**: เปิด baseline ที่ให้ AI ตัดสินจากกฎชุดเดียวกันที่เป็นข้อความ
  - **When**: AI ตอบถูกรูปแบบ และอีกกรณีตอบผิดรูปแบบ
  - **Then**: กรณีแรกอ่านผลตัดสินได้ กรณีหลังรายงานว่าคำตอบไม่ถูกต้องโดยไม่ทำให้โปรแกรมล้ม (รองรับ JSON ที่ห่อด้วยโค้ดเฟนซ์หรือมีข้อความนำหน้า)
- **AC-7 (เขียนรายงานเป็นไฟล์ และข้อมูลจริงไม่เข้า git)**
  - **Given**: รันชุดประเมินผลเสร็จ
  - **When**: ตรวจผลลัพธ์และที่เก็บข้อมูล
  - **Then**: มีไฟล์รายงานผลลัพธ์ (Markdown และ JSON) และข้อมูลเคสจริงถูกเก็บในโฟลเดอร์ที่ไม่เข้า git
