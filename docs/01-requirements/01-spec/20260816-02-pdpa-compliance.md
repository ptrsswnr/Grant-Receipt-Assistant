# Grant Receipt Assistant — ข้อกำหนดความต้องการด้าน PDPA/การคุ้มครองข้อมูลส่วนบุคคล

> เอกสารฉบับที่ 2 ของโปรเจกต์ Grant Receipt Assistant ต่อยอดจาก gap analysis ที่ทำเมื่อ 2026-08-16
> เทียบ [[20260816-01-grant-receipt-verification]] (FR-01–FR-12, NFR-01–NFR-07) กับพระราชบัญญัติ
> คุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562 (PDPA) พบว่ายังไม่มี requirement ใดรองรับเรื่องนี้เลย
> จึงแยกเป็นเอกสารใหม่โดยเฉพาะ (ดูเหตุผลการแยกเอกสารในหัวข้อ 9)
> พร้อมข้อยืนยันจากผู้ใช้ต่อประเด็นที่ยังไม่ชัดเจน (ดูหัวข้อ 8)

## 1. ภาพรวม/วัตถุประสงค์ของเอกสารนี้

ระบบ **Grant Receipt Assistant** ประมวลผลข้อมูลใบเสร็จ/หลักฐานการเบิกจ่ายของนักวิจัย ซึ่งมีข้อมูล
ทางการเงินที่ผูกกับตัวบุคคล (เจ้าของทุน) จึงถือเป็น**ข้อมูลส่วนบุคคล**ตาม PDPA เอกสารนี้กำหนด
requirement ที่จำเป็นเพื่อให้ระบบสอดคล้องกับ PDPA ในส่วนที่เกี่ยวข้องกับตัวระบบโดยตรง (ไม่ใช่ทุกมาตรา
ของกฎหมาย เฉพาะส่วนที่กระทบการออกแบบ/ฟีเจอร์ของระบบนี้)

**ข้อเท็จจริงสำคัญที่ต้องระบุไว้ล่วงหน้า:** ข้อมูลใบเสร็จ/การเงินของนักวิจัยในระบบนี้**ไม่ใช่ข้อมูล
ส่วนบุคคลที่มีความอ่อนไหว (Sensitive Personal Data)** ตามมาตรา 26 ของ PDPA (ซึ่งครอบคลุมเชื้อชาติ
ศาสนา พฤติกรรมทางเพศ ประวัติอาชญากรรม สุขภาพ ความพิการ ข้อมูลพันธุกรรม/ชีวภาพ เป็นต้น) — จึงเป็น
ข้อมูลส่วนบุคคลทั่วไปที่ต้องคุ้มครองตามมาตรฐานปกติของ PDPA เท่านั้น ไม่ใช่มาตรฐานข้อมูลอ่อนไหวที่
เข้มงวดกว่า ระบุไว้ที่นี่เพื่อไม่ให้การออกแบบในอนาคตตีความเกินจริงว่าเป็นข้อมูลอ่อนไหว

## 2. ขอบเขต

### 2.1 อยู่ในขอบเขต (MVP รอบนี้)

- แจ้ง Privacy Notice และขอความยินยอมชัดแจ้ง (explicit consent) จากนักวิจัยก่อนเก็บ/ประมวลผลข้อมูล
  ใบเสร็จ (ยืนยันโดยผู้ใช้เมื่อ 2026-08-16 — ดูหัวข้อ 8 คำถามที่ 1)
- บันทึกหลักฐานการให้ความยินยอม และกลไกถอนความยินยอม พร้อมนิยามผลกระทบต่อกระบวนการตรวจใบเสร็จ
- สิทธิ์ของเจ้าของข้อมูล (Data Subject Rights) ที่กระทบ UI ของระบบโดยตรง: ขอเข้าถึง/ขอสำเนาข้อมูล
  และ **ลบ/ขอลบข้อมูลใบเสร็จของตนเองด้วยตนเองผ่าน UI** (ยืนยันโดยผู้ใช้เมื่อ 2026-08-16 — ดูหัวข้อ 8
  คำถามที่ 2) พร้อมเงื่อนไขไม่ให้ขัดกับข้อกำหนดการเก็บหลักฐานทางการเงิน (ดู FR-18)
- ข้อกำหนดเชิงเงื่อนไข (conditional NFR) สำหรับ cross-border data transfer หาก OCR/LLM vendor
  เป็นผู้ให้บริการต่างประเทศ (ยืนยันโดยผู้ใช้เมื่อ 2026-08-16 ว่ายังไม่ตัดสินใจ — ดูหัวข้อ 8
  คำถามที่ 3) — ไม่ผูก tech stack ใดๆ จนกว่าจะมีการตัดสินใจจริงใน `[[technology-stack]]`
- ข้อกำหนดระดับ organizational (ไม่ใช่ฟีเจอร์ในระบบ แต่เป็นข้อจำกัด/ข้อกำหนดของโปรเจกต์): ข้อตกลง
  ประมวลผลข้อมูลกับผู้ให้บริการภายนอก, กระบวนการแจ้งเหตุข้อมูลรั่วไหล, ระยะเวลาเก็บ/ลบข้อมูล (TBD),
  ผู้รับผิดชอบด้าน compliance

### 2.2 ตัดออกจากขอบเขต MVP นี้

- **ไม่มีการเปลี่ยนแปลงบทบาทผู้ใช้ (User Roles)** จากที่กำหนดไว้ใน
  [[20260816-01-grant-receipt-verification#3. บทบาทผู้ใช้ (User Roles)]] — Admin ยังคงไม่มีสิทธิ์
  เข้าถึงข้อมูลใบเสร็จส่วนบุคคล การจัดการคำร้องสิทธิ์ของเจ้าของข้อมูลที่กระทบข้อมูลนอกเหนือจาก UI
  self-service (เช่น กรณีขัดแย้งกับ retention ตาม FR-18) จะดำเนินการผ่านกระบวนการภายนอกระบบ
  (ติดต่อ DPO/เจ้าหน้าที่) ไม่ใช่ role ใหม่ในระบบ
- ยังไม่กำหนดตัวเลขระยะเวลาเก็บข้อมูล (retention period) ที่แน่นอน — เป็น TBD เช่นเดียวกับ
  NFR-06/07 เดิม (ดู NFR-11 และหัวข้อ 6)
- ยังไม่ตัดสินใจ tech stack/vendor ของ OCR/LLM — เป็น TBD (ดู NFR-08)

### 2.3 ข้อจำกัดที่ทราบอยู่แล้ว (ไม่บล็อกการเขียน spec ระดับนี้)

- ยังไม่ทราบที่ตั้งผู้ให้บริการ OCR/LLM ที่จะเลือกใช้จริง (ในไทย/ต่างประเทศ) ต้องยืนยันก่อนเข้าสู่
  design phase ของ `[[architecture]]` เพื่อกำหนดว่าต้องใช้มาตรการคุ้มครอง cross-border transfer
  ตามมาตรา 28-29 หรือไม่ (ดู NFR-08)
- ยังไม่มีระเบียบเก็บเอกสารทางการเงินของมหาวิทยาลัย/กรมบัญชีกลางแนบมาด้วย ทำให้ตัวเลขระยะเวลาเก็บ
  ข้อมูล (retention) ใน NFR-11 ยังเป็นระดับ "ต้องมีนโยบาย" ไม่ใช่ตัวเลขที่ finalize แล้ว
- ยังไม่ระบุตัวบุคคล/หน่วยงานที่รับผิดชอบด้าน PDPA compliance ของระบบนี้โดยเฉพาะ (DPO ของ
  มหาวิทยาลัยหรือกำหนดเพิ่มเติม) — บันทึกเป็นสมมติฐาน (ดูหัวข้อ 6)
- พฤติกรรมของระบบเมื่อนักวิจัย**ถอนความยินยอม**หลังจากใช้งานไปแล้ว (เช่น จะบล็อกการอัปโหลดใหม่
  ทันที หรือระงับบัญชีทั้งหมด) ยังไม่ถูกกำหนดในระดับรายละเอียด UX/workflow — บันทึกเป็น open point
  ที่ต้องตัดสินใจเพิ่มเติมในขั้นตอนออกแบบถัดไป (ดู FR-16 และหัวข้อ 6)

## 3. บทบาทผู้ใช้ที่เกี่ยวข้อง

ไม่มีบทบาทใหม่เพิ่มจาก [[20260816-01-grant-receipt-verification#3. บทบาทผู้ใช้ (User Roles)]]
requirement ในเอกสารนี้ทั้งหมดเป็นสิทธิ์/หน้าที่ที่ผูกกับบทบาท **นักวิจัย/เจ้าของทุน** เดิม
(ในฐานะเจ้าของข้อมูลตาม PDPA) ยกเว้นข้อกำหนดระดับ organizational (ข้อตกลงกับ data processor,
data breach notification, ผู้รับผิดชอบ compliance) ซึ่งไม่ใช่ role ในระบบ แต่เป็นข้อกำหนด/
สมมติฐานระดับโปรเจกต์ (ดูหัวข้อ 6)

## 4. Functional Requirements

| รหัส | ความต้องการ | รายละเอียด | ระดับความสำคัญ |
|------|-------------|------------|----------------|
| FR-13 | แสดง Privacy Notice ก่อนใช้งานครั้งแรก/ก่อนอัปโหลดใบเสร็จ | ระบบต้องแสดงประกาศความเป็นส่วนตัว (Privacy Notice) แจ้งวัตถุประสงค์การเก็บ/ใช้ข้อมูล, ตัวตนผู้ควบคุมข้อมูล (มหาวิทยาลัย), ระยะเวลาเก็บข้อมูล (อ้างอิงนโยบายที่กำหนดใน NFR-11), และสิทธิ์ของเจ้าของข้อมูล ให้นักวิจัยเห็นก่อนใช้งานระบบครั้งแรกและก่อนอัปโหลดใบเสร็จครั้งแรก ตามมาตรา 23 | สูง |
| FR-14 | ขอความยินยอมชัดแจ้ง (Explicit Consent) ก่อนเก็บ/ประมวลผลข้อมูลใบเสร็จ | ระบบต้องมี UI ให้นักวิจัยให้ความยินยอมอย่างชัดแจ้งก่อนที่ระบบจะเริ่มเก็บ/ประมวลผลข้อมูลใบเสร็จของตนเอง (ยืนยันโดยผู้ใช้เมื่อ 2026-08-16 ว่าใช้ฐาน consent ไม่ใช่ฐานสัญญา/หน้าที่ตามกฎหมาย — ดูหัวข้อ 8 คำถามที่ 1) นักวิจัยที่ไม่ให้ความยินยอมจะไม่สามารถอัปโหลดใบเสร็จเข้าสู่ระบบได้ | สูง |
| FR-15 | บันทึกหลักฐานการให้ความยินยอม (Consent Record) | ระบบต้องบันทึกว่านักวิจัยแต่ละคนให้ความยินยอมเมื่อใด ต่อ Privacy Notice เวอร์ชันใด เพื่อเป็นหลักฐานย้อนหลังตามหลักความรับผิดชอบ (Accountability) ของ PDPA | สูง |
| FR-16 | ถอนความยินยอม (Withdraw Consent) และจัดการผลกระทบต่อกระบวนการตรวจใบเสร็จ | นักวิจัยต้องสามารถถอนความยินยอมที่เคยให้ไว้ได้ทุกเมื่อผ่าน UI ของระบบ เมื่อถอนความยินยอมแล้ว ระบบต้องระงับการอัปโหลด/ประมวลผลใบเสร็จใหม่ของนักวิจัยคนนั้นทันที (พฤติกรรมโดยละเอียดต่อข้อมูลที่เคยประมวลผลไปแล้วก่อนถอน เช่น จะเก็บต่อ/ระงับการเข้าถึง/ลบ ยังเป็น open point ที่ต้องตัดสินใจเพิ่มเติมในขั้นตอนออกแบบ — ดูหัวข้อ 2.3 และ 6) | สูง |
| FR-17 | ขอเข้าถึง/ขอสำเนาข้อมูลใบเสร็จส่วนบุคคลของตนเอง (Data Subject Access & Portability) | นักวิจัยต้องสามารถขอสำเนาข้อมูลส่วนบุคคลทั้งหมดที่ระบบเก็บไว้เกี่ยวกับตนเอง (ข้อมูลใบเสร็จ, ผลตรวจ, ประวัติ consent) ในรูปแบบที่อ่าน/นำไปใช้ต่อได้ ผ่าน UI ของระบบ — แยกจาก FR-10 ซึ่งเป็นรายงานสรุปใบเสร็จที่ผ่านตรวจแล้วสำหรับยื่นเจ้าหน้าที่การเงินเท่านั้น ไม่ใช่สำเนาข้อมูลส่วนบุคคลครบถ้วนตามสิทธิ์ PDPA | กลาง |
| FR-18 | ลบ/ขอลบข้อมูลใบเสร็จของตนเองด้วยตนเองผ่าน UI (Right to Erasure) | นักวิจัยต้องสามารถลบข้อมูลใบเสร็จของตนเองได้เองผ่าน UI โดยตรงในระบบ (ยืนยันโดยผู้ใช้เมื่อ 2026-08-16 ว่าต้องมีใน MVP นี้ ไม่ผ่านช่องทางภายนอก — ดูหัวข้อ 8 คำถามที่ 2) **เงื่อนไข:** ลบได้เฉพาะใบเสร็จที่ยังไม่ถูกรวมอยู่ใน export รายงาน (FR-10) ที่นักวิจัยได้ส่งให้เจ้าหน้าที่การเงินไปแล้ว — ใบเสร็จที่ถูก export ไปแล้วถือเป็นส่วนหนึ่งของหลักฐานทางการเงินที่อยู่ระหว่างกระบวนการเบิกจ่ายภายนอกระบบ การลบเองผ่าน UI จะถูกปิดกั้นสำหรับกรณีนี้ และต้องยื่นคำร้องผ่านช่องทาง Admin/DPO แทน เพื่อป้องกันความขัดแย้งกับข้อกำหนดการเก็บหลักฐานทางการเงิน (ดู NFR-11) | สูง |

## 5. Non-Functional Requirements

| รหัส | ด้าน | ความต้องการ |
|------|------|-------------|
| NFR-08 | Cross-border Data Transfer (Conditional — รอการตัดสินใจ vendor) | หากผู้ให้บริการ OCR (FR-02) และ/หรือ LLM (FR-05) ที่จะเลือกใช้จริงเป็นผู้ให้บริการที่ประมวลผลข้อมูลนอกราชอาณาจักรไทย ระบบ/โครงการต้องมีมาตรการคุ้มครองข้อมูลตามมาตรา 28-29 ของ PDPA ก่อนเริ่มส่งข้อมูลจริง — **ยังไม่ตัดสินใจที่ตั้งผู้ให้บริการ (ยืนยันโดยผู้ใช้เมื่อ 2026-08-16 — ดูหัวข้อ 8 คำถามที่ 3)** ต้องยืนยันที่ตั้งผู้ให้บริการก่อนเข้าสู่ design phase ของ `[[architecture]]` ห้ามผูก tech stack/vendor ใดๆ จนกว่าจะมีการตัดสินใจจริงใน `[[technology-stack]]` |
| NFR-09 | Data Processing Agreement กับผู้ให้บริการภายนอก (Organizational) | หากใช้ OCR/LLM หรือบริการประมวลผลข้อมูลอื่นจากผู้ให้บริการภายนอก มหาวิทยาลัยในฐานะผู้ควบคุมข้อมูลต้องมีข้อตกลงประมวลผลข้อมูล (Data Processing Agreement) และมาตรการความปลอดภัยที่เหมาะสมกับผู้ให้บริการเหล่านั้นตามมาตรา 40 — เป็นข้อกำหนดระดับองค์กร ไม่ใช่ฟีเจอร์ในระบบ |
| NFR-10 | Data Breach Notification (Organizational/Process) | โครงการต้องมีกลไก/กระบวนการแจ้งเตือนเมื่อพบเหตุข้อมูลรั่วไหลที่กระทบข้อมูลใบเสร็จของนักวิจัย เพื่อรองรับหน้าที่แจ้งสำนักงานคณะกรรมการคุ้มครองข้อมูลส่วนบุคคล (สคส.) ภายใน 72 ชั่วโมงตามมาตรา 37(4) — รายละเอียดกระบวนการ (ใครแจ้ง/ช่องทางใด) เป็นข้อกำหนดระดับองค์กร ไม่ใช่ฟีเจอร์ในระบบ |
| NFR-11 | Data Retention & Deletion Policy (รอกำหนดเป้าหมาย — TBD) | ต้องกำหนดนโยบายระยะเวลาเก็บภาพใบเสร็จ/ข้อมูลที่ OCR อ่านได้ และการลบข้อมูลอัตโนมัติเมื่อครบกำหนด โดยอ้างอิงระเบียบเก็บเอกสารทางการเงินของมหาวิทยาลัย/กรมบัญชีกลาง (ถ้ามี) — ตัวเลขยังไม่ทราบ ถือเป็น TBD เช่นเดียวกับ NFR-06/07 เดิม ต้องกำหนดก่อนนำไปใช้ตัดสินใจเชิงสถาปัตยกรรมของการจัดเก็บข้อมูล |

## 6. สมมติฐาน/ข้อจำกัด (Assumptions & Constraints)

- **ฐานทางกฎหมาย**: ใช้ฐานความยินยอม (Consent) ตามมาตรา 19-20 ไม่ใช่ฐานสัญญา/หน้าที่ตามกฎหมาย —
  ยืนยันโดยผู้ใช้เมื่อ 2026-08-16 (ดู FR-14, หัวข้อ 8 คำถามที่ 1) ผลที่ตามมาคือเจ้าของข้อมูลมีสิทธิ์
  ถอนความยินยอมได้ทุกเมื่อ (ดู FR-16) ซึ่งกระทบความต่อเนื่องของกระบวนการตรวจใบเสร็จโดยตรง
  พฤติกรรมระบบต่อข้อมูลที่ประมวลผลไปแล้วก่อนถอน consent ยังเป็น **open point** ที่ต้องตัดสินใจ
  ในขั้นตอนออกแบบถัดไป (ไม่บล็อกการเขียน spec ระดับนี้ แต่ต้องแก้ก่อนเข้าสู่ detailed design ของ
  FR-16)
- **การลบข้อมูลด้วยตนเอง vs retention ของหลักฐานการเงิน**: FR-18 กำหนดเงื่อนไขให้ลบเองผ่าน UI ได้
  เฉพาะใบเสร็จที่ยังไม่ถูก export ส่งเจ้าหน้าที่การเงิน เพื่อไม่ให้ขัดกับข้อกำหนดการเก็บหลักฐาน
  ทางการเงิน (NFR-11) — เป็นการตัดสินใจเชิงออกแบบเพื่อคลี่คลายความขัดแย้งระหว่างสิทธิ์เจ้าของข้อมูล
  กับข้อกำหนดการเก็บหลักฐาน ยังต้องทบทวนอีกครั้งเมื่อทราบตัวเลข retention จริงใน NFR-11
- **ข้อมูลไม่ใช่ Sensitive Personal Data**: ข้อมูลใบเสร็จ/การเงินในระบบนี้ไม่เข้าข่ายข้อมูลอ่อนไหว
  ตามมาตรา 26 (ดูหัวข้อ 1) — ระบุไว้เพื่อป้องกันการออกแบบมาตรการเกินความจำเป็น
- **ผู้รับผิดชอบด้าน PDPA compliance**: ยังไม่ระบุว่าเป็น DPO ของมหาวิทยาลัยหรือกำหนดเพิ่มเติมเฉพาะ
  โครงการนี้ — เป็นข้อมูล organizational ไม่กระทบการออกแบบฟีเจอร์ในระบบ แต่ต้องมีคำตอบก่อนเริ่ม
  ดำเนินการจริง (ไม่บล็อกการเขียน spec ระดับนี้)
- **บันทึกกิจกรรมประมวลผลข้อมูล (ROPA)**: โครงการควรจัดทำ Records of Processing Activities ตาม
  หลัก PDPA แต่เป็นเอกสารระดับองค์กร ไม่ใช่ฟีเจอร์ในระบบ (ดู NFR-09, NFR-10)
- **OCR/LLM vendor ที่ตั้ง**: ยังไม่ตัดสินใจ (TBD) — ยืนยันโดยผู้ใช้เมื่อ 2026-08-16 (ดู NFR-08,
  หัวข้อ 8 คำถามที่ 3) ต้องยืนยันก่อนเข้าสู่ design phase ของ `[[architecture]]`
- **ระยะเวลาเก็บข้อมูล**: ยังไม่กำหนดตัวเลข (TBD) — ดู NFR-11 เช่นเดียวกับแนวทางที่ใช้กับ
  NFR-06/07 เดิมในเอกสารหลัก

## 7. บริบทอ้างอิง (Context เท่านั้น — ไม่ใช่ requirement ที่ยืนยันแล้ว)

เอกสารนี้เกิดจาก gap analysis ที่ทำเมื่อ 2026-08-16 โดยตรวจสอบ
[[20260816-01-grant-receipt-verification]] และ [[backlog]] เทียบกับพระราชบัญญัติคุ้มครองข้อมูล
ส่วนบุคคล พ.ศ. 2562 พบว่า ณ ตอนนั้นยังไม่มี requirement ใดรองรับประเด็น PDPA เลย ทั้ง 7 ช่องว่างที่
พบ (ฐานทางกฎหมาย/Privacy Notice, สิทธิ์เจ้าของข้อมูล, retention, cross-border transfer, DPA กับ
ผู้ให้บริการภายนอก, data breach notification, ROPA/ผู้รับผิดชอบ) ถูกแปลงเป็น FR/NFR หรือสมมติฐาน
ในเอกสารนี้ครบทั้งหมดแล้ว

## 9. เหตุผลที่แยกเป็นเอกสารใหม่ (ไม่แก้ไขเอกสารเดิม)

requirement เดิม
