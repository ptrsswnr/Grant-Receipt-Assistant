# Grant Receipt Assistant — ปรับทิศทางงานวิจัย: LLM ตัดสินผล ตรวจอัตโนมัติไม่มีขั้นยืนยัน (2026-11-24)

> เอกสารนี้บันทึกการปรับทิศทางเมื่อ 2026-11-24 ซึ่งสร้างเสร็จและใช้งานจริงในแอปแล้ว และเพิ่มรหัส **FR-38–FR-41**
> **แผนแรกไม่ถูกลบ** — FR-03 (ตรวจ/แก้ข้อมูลก่อนส่ง), ขั้นติ๊กเอกสารแนบของ FR-27 และหลัก "กฎตัดสิน AI แค่อธิบาย" ของ FR-24/FR-31
> ยังอยู่ในเอกสารเดิมทุกฉบับในฐานะ **แผนแรกที่ออกแบบไว้** ส่วนนี้บันทึกว่าแผนปัจจุบันต่างจากแผนแรกอย่างไรและเพราะอะไร
> ต่อยอดจาก [[20260816-01-grant-receipt-verification]] และ [[20261117-01-implemented-rule-engine-ai-and-admin]]

## 1. บทนำและเหตุผล

**แผนแรก (2026-08-16 ถึง 2026-11-23):** OCR/AI อ่านค่า → นักวิจัยตรวจและแก้ค่าเอง (FR-03) → นักวิจัยเลือกรายการในประมาณการและติ๊กเอกสาร/ตราที่มี (FR-26, FR-27)
→ **Rule Engine ตัดสิน** สถานะ 4 ระดับ (FR-24, FR-25) → AI agent อธิบายผลโดยห้ามเปลี่ยนสถานะ (FR-31) หลักการคือ "กฎตัดสิน LLM แค่อธิบาย"

**แผนปัจจุบัน (ตั้งแต่ 2026-11-24):** อาจารย์ที่ปรึกษาปรับทิศทาง Paper 1 เป็นระบบ OCR + LLM ที่อ่านและตัดสินเอกสารค่าใช้จ่ายทุนวิจัยเอง
แล้ว**วัดความถูกต้องเทียบกับผลตัดสินของเจ้าหน้าที่การเงิน**บนเอกสารจริงของโครงการประมาณ 100 โครงการ

**เหตุผลที่เปลี่ยนมาให้ LLM ตัดสินล้วน:** เพื่องานวิจัย — ต้องวัดความถูกต้องของ LLM ที่ตัดสินเองให้ได้ และ**เทียบกับแบบที่ใช้เทคนิคอื่น**
(เช่น Rule Engine แบบกำหนดกฎตายตัว ซึ่งยังรันทุกใบและเก็บผลไว้เทียบ) ถ้ายังให้นักวิจัยแก้ค่าหรือติ๊กเอกสารเอง ผลที่วัดได้จะปนกับการตัดสินใจของคน
จึงตัดขั้นที่คนแทรกออกทั้งหมด

ขอบเขต: การตัดสินผลด้วย LLM, การตรวจหาเอกสาร/ตราอัตโนมัติ, การนำเข้าไฟล์สแกนทั้งโครงการ, ตัวรันชุดเคสสำหรับวัดผล
ไม่ครอบคลุม: การปกปิดข้อมูลส่วนบุคคลอัตโนมัติ (ช่วงต้นแบบเจ้าของปกปิดเองด้วยมือ), การตรวจรูปถ่ายพัสดุ, การยินยอม/ถอนความยินยอมของผู้เข้าร่วมวิจัย
(งานนี้ไม่มีผู้เข้าร่วมแบบสด FR-20 จึงยังเลื่อนไว้)

## 2. Functional Requirements

| รหัส | ความต้องการ | รายละเอียด | ระดับความสำคัญ |
|------|-------------|------------|----------------|
| FR-38 | LLM ตัดสินผลใบเสร็จ โดยยังรัน Rule Engine เก็บผลไว้เทียบ | (1) โหมดตัดสินตั้งค่าได้ (`verdictMode`: `llm` ค่าตั้งต้น / `rule`) และบันทึกไว้บนใบเสร็จทุกใบ (2) LLM ได้รับข้อความ OCR ของทุกไฟล์ ระเบียบที่เป็นข้อความพร้อมรหัสอ้างอิงจริง เฉพาะชุดเอกสารของหมวดนั้น และประมาณการพร้อมตัวเลขที่คำนวณไว้แล้ว ใช้ temperature 0 (3) LLM ตอบเป็น JSON: checklist 4 ข้อ (ประมาณการ / เพดานระเบียบ / เอกสาร / ตรา) พร้อมข้อความ OCR ที่ใช้เป็นหลักฐาน แล้วจึงตัดสิน pass/fail — `fail` บันทึกเป็น "ต้องแก้ไข" (4) ตัวกันขัดแย้ง: ถ้า LLM ตอบ pass แต่ checklist ของตัวเองมีข้อไม่ผ่าน ให้เป็น fail; ตราที่อ้างหลักฐานไม่มีคำสำคัญของตรานั้นถูกตัดออก ทั้งสองใช้เฉพาะคำตอบของ LLM เอง ไม่ใช้ผล Rule Engine (5) Rule Engine รันทุกใบเสมอ บันทึกใน `ruleCheck` สำหรับเปรียบเทียบ ถ้า LLM ล้มเหลวหรือไม่ได้ตั้งค่า ใช้ผล Rule Engine แทนและแจ้งในคำอธิบาย (6) เก็บคำตอบดิบของ LLM, รุ่นโมเดล, เวอร์ชัน prompt และเวลาที่ใช้ใน `llmVerdict` | สูง |
| FR-39 | ตรวจหาประเภทเอกสารและตราจากข้อความ OCR อัตโนมัติ แทนการติ๊กเอง | (1) จำแนกประเภทเอกสารของแต่ละไฟล์จากคำสำคัญของชื่อเอกสาร/รหัสแบบฟอร์ม (ไม่สนวรรณยุกต์และช่องว่าง) บันทึกใน `documentClassification` และ `files.documentTypeId` (2) หาตรา ("จ่ายแล้ว", "ตรวจรับพัสดุ"/"ได้รับพัสดุ") จากข้อความ OCR ของทุกไฟล์ (3) ผลป้อนเข้า Rule Engine ผ่านฟิลด์เดิม `providedDocumentTypeIds` / `confirmedAttestations` (4) เก็บข้อความ OCR ดิบทุกไฟล์ใน `ocrRaw` แม้ขั้นถัดไปล้มเหลว (5) ไม่มีขั้นตรวจ/แก้ค่าที่อ่านได้ ค่าที่กรอกเองมีเพียงยอดในใบสรุป (ไม่บังคับ) และต้องมีประมาณการก่อนจึงอัปโหลดได้ | สูง |
| FR-40 | นำเข้าไฟล์สแกนทั้งโครงการ | ไฟล์ PDF สแกนหลายหน้าของทั้งโครงการ: OCR ทุกหน้า → LLM แบ่งหน้าเป็นเอกสารและจำแนกประเภท (ถอยกลับเป็นคำสำคัญ) → อ่านค่าตามประเภทเอกสาร → LLM จัดกลุ่มเป็นรายการค่าใช้จ่าย (1 รายการมีเอกสารการจ่าย 1 ใบ) → ตรวจแต่ละรายการด้วยกลไกเดียวกับ FR-38 ผลแต่ละขั้นเก็บใน `importBatches` ไฟล์ต้นฉบับอัปโหลด Drive ครั้งเดียว | กลาง |
| FR-41 | ตัวรันชุดเคสสำหรับวัดผลงานวิจัย | รันเคสใบเสร็จ (Stage B) และไฟล์ทั้งโครงการ (Stage C) ผ่านโมดูลเดียวกับแอป เทียบกับผลของเจ้าหน้าที่การเงิน ได้ JSON+CSV ที่บันทึกรุ่นโมเดล/prompt/ชุดกฎ และผลดิบทุกขั้น ข้อมูลจริงเก็บนอก git (ต่อยอด FR-34) | สูง |

## 3. ผลต่อรหัสเดิม (แผนแรกเก็บไว้ ไม่ลบ)

| รหัสเดิม | แผนแรก | ตั้งแต่ 2026-11-24 |
|---|---|---|
| FR-03 | นักวิจัยตรวจ/แก้ค่าที่ AI/OCR อ่านก่อนส่ง | ไม่มีขั้นนี้ในแอป (ถูกแทนด้วย FR-39) — เก็บไว้เป็นแผนแรก |
| FR-24/FR-25 | Rule Engine ตัดสินสถานะ 4 ระดับ | ยังรันทุกใบ ตัดสินเฉพาะโหมด `rule` หรือเมื่อ LLM ล้มเหลว; โหมด `llm` ใช้ผลของ LLM (FR-38) |
| FR-26 | นักวิจัยเลือกรายการในประมาณการเอง หรือ "ไม่อยู่ในประมาณการ" | ระบบจับรายการจากหมวด; ต้องมีประมาณการก่อนอัปโหลด |
| FR-27 | นักวิจัยติ๊กเอกสาร/ตราที่มี | ระบบหาเองจาก OCR (FR-39) ชุดเอกสารยังเป็นเกณฑ์เดิม |
| FR-31 | AI agent อธิบายผลของกฎ ห้ามเปลี่ยนสถานะ | ทำงานเฉพาะโหมด `rule`; โหมด `llm` ใช้คำแนะนำของ LLM เป็นคำอธิบาย |

## 4. ข้อจำกัดและประเด็นที่ยังเปิดอยู่

- การจำแนกเอกสารเป็นการจับคำสำคัญ ไม่ใช่โมเดลจำแนกจริง; รูปถ่ายพัสดุตรวจไม่ได้ (เจ้าของยังไม่ตัดสินใจว่าจะสร้างหรือไม่)
- ผลรายข้อของ LLM ต่างกันได้ระหว่างการรันซ้ำแม้ temperature 0 การทดลองต้องรันมากกว่า 1 ครั้ง (ดู `research/prompt-log.md`)
- ผลจากใบเสร็จ 2 ใบที่ใช้ปรับ prompt เป็นชุดปรับจูน ไม่ใช่ความแม่นยำที่รายงานได้
- ข้อความ OCR ทั้งหมดส่งให้ LLM และเก็บใน Firestore — ไม่มีการปกปิดอัตโนมัติ

## 5. ประวัติการตัดสินใจ

- 2026-11-24 อาจารย์ที่ปรึกษาปรับทิศทาง Paper 1; เจ้าของยืนยันว่าเปลี่ยนตัวแอปจริง ไม่ใช่แค่สคริปต์วิจัย และให้เก็บ Rule Engine ไว้ (ห้ามลบ)
- 2026-11-27 เจ้าของให้**เก็บแผนแรกไว้ในเอกสาร ไม่ลบ** เพื่อเป็นข้อมูลว่าเป็นแผนแรกที่คิดไว้ เหตุผลที่เปลี่ยนมาเป็น LLM ล้วนคือเพื่องานวิจัยที่ต้องเทียบความถูกต้องกับแบบที่ใช้เทคนิคอื่น
