# Grant Receipt Assistant — ข้อกำหนดความต้องการหลัก (Core Requirements)

> เอกสารฉบับแรกของโปรเจกต์ Grant Receipt Assistant สรุปจาก raw requirement ที่ได้รับเมื่อ 2026-08-16
> พร้อมข้อยืนยันจากผู้ใช้ต่อประเด็นที่ยังไม่ชัดเจน (ดูหัวข้อ 7)

## 1. ภาพรวม/วัตถุประสงค์ของระบบ

**Grant Receipt Assistant** เป็นระบบผู้ช่วยตรวจสอบใบเสร็จ/หลักฐานการเบิกจ่ายเงินทุนวิจัย
ก่อนที่นักวิจัยจะส่งเอกสารให้เจ้าหน้าที่การเงินของมหาวิทยาลัยตรวจจริง

**ปัญหาที่แก้:** นักวิจัยส่วนใหญ่ไม่มีพื้นฐานด้านการเงิน/บัญชี แต่ต้องรับผิดชอบเก็บใบเสร็จเองตลอด
โครงการวิจัย โดยไม่มีใครช่วยตรวจระหว่างทาง ทำให้เพิ่งรู้ว่าใบเสร็จผิดหมวด/ผิดเงื่อนไขตอนยื่นเบิกจริง
ซึ่งสายเกินแก้แล้ว (เช่น ใบเสร็จหมดอายุ ของหาย แก้ไขไม่ทัน)

ระบบทำหน้าที่เป็น **"ด่านตรวจก่อนสอบ"** — ให้ feedback ทันทีตอนจัดเก็บใบเสร็จ ไม่ใช่ตอนยื่นเบิกปลายทาง
และ**ไม่ได้ทำหน้าที่แทนเจ้าหน้าที่การเงิน**

**จุดเน้นสำคัญของบทบาท AI:** LLM **ไม่ตัดสินใจว่าใบเสร็จผ่าน/ไม่ผ่าน** — การตัดสินมาจาก
Rule-based Engine ที่อ้างอิงระเบียบทุนวิจัยจริงของมหาวิทยาลัยเท่านั้น หน้าที่ของ LLM คือแปลผลจาก
Rule Engine ให้เป็นภาษาที่นักวิจัยที่ไม่มีพื้นฐานการเงินเข้าใจง่าย พร้อมคำแนะนำแก้ไข
การออกแบบนี้ตั้งใจกัน hallucination โดยตรง

## 2. ขอบเขตระบบ

### 2.1 อยู่ในขอบเขต (MVP รอบนี้)

- อัปโหลด/OCR/ตรวจสอบด้วย Rule Engine/อธิบายผลด้วย LLM สำหรับใบเสร็จของนักวิจัยแต่ละคน
- Dashboard สรุปภาพรวมใบเสร็จของทุนที่นักวิจัยถือ
- แจ้งเตือนใบเสร็จที่มีปัญหายังไม่ได้แก้ไข (ไม่รวมกำหนดเวลาส่งหลักฐาน — ดู 2.2)
- Export รายงานสรุปใบเสร็จที่ผ่านตรวจแล้ว เพื่อนักวิจัยนำไปยื่นต่อเจ้าหน้าที่การเงินของมหาวิทยาลัยเอง
  (เจ้าหน้าที่การเงินเป็นผู้รับไฟล์ภายนอกระบบ **ไม่ใช่ user ของระบบนี้**)
- Admin นำเข้า/อัปเดตระเบียบทุนวิจัยเข้าสู่ Rule Engine

### 2.2 ตัดออกจากขอบเขต MVP นี้ (ยืนยันโดยผู้ใช้เมื่อ 2026-08-16 — ดูหัวข้อ 7)

- **ไม่มี user role "เจ้าหน้าที่การเงิน" ในระบบ** — ไม่มี login ไม่มี action ใดๆ ในระบบสำหรับบทบาทนี้
  เจ้าหน้าที่การเงินรับทราบผลผ่านไฟล์ export ที่นักวิจัยส่งให้นอกระบบเท่านั้น
- **ไม่มี role/workflow "ผู้อนุมัติทุน"** ในระบบ — ระบบจบแค่ "ตรวจก่อนส่ง" แล้วส่งต่อกระบวนการ
  อนุมัติเดิมของมหาวิทยาลัยที่อยู่นอกระบบนี้
- **ไม่มี deadline tracking รายทุน** และไม่มีการแจ้งเตือนที่อิงกับกำหนดเวลาส่งหลักฐาน
  (การแจ้งเตือนเรื่องใบเสร็จมีปัญหาที่ยังไม่แก้ไข ซึ่งไม่เกี่ยวกับกำหนดเวลา ยังคงอยู่ในขอบเขต)

### 2.3 ข้อจำกัดที่ทราบอยู่แล้ว (ไม่บล็อกการเขียน spec ระดับนี้)

- ยังไม่มีเอกสารระเบียบทุนวิจัยตัวจริงของมหาวิทยาลัยแนบมาด้วย ทำให้รายละเอียดกฎ (หมวดค่าใช้จ่าย,
  วงเงินสูงสุดต่อหมวด ฯลฯ) ใน FR-04 ยังเป็นระดับ "ต้องมีความสามารถนี้" ไม่ใช่รายการกฎที่ finalize แล้ว
  ต้องแนบเอกสารระเบียบจริงก่อนเข้าสู่ขั้นตอนออกแบบ Rule Engine โดยละเอียด (`[[architecture]]`,
  `[[detailed-design]]` เมื่อมีการสร้างเอกสารเหล่านี้)

## 3. บทบาทผู้ใช้ (User Roles)

ระบบนี้มี **2 บทบาทเท่านั้น** (ยืนยันโดยผู้ใช้เมื่อ 2026-08-16 — ตัดบทบาท "เจ้าหน้าที่การเงิน"
และ "ผู้อนุมัติทุน" ออกจาก raw requirement ตั้งต้นแล้ว):

- **นักวิจัย/เจ้าของทุน** (ผู้ใช้หลัก): อัปโหลดใบเสร็จ, ตรวจสอบ/แก้ไขข้อมูลจาก OCR, ดูผลตรวจจาก
  Rule Engine พร้อมคำอธิบายจาก LLM, แก้ไข/อัปโหลดซ้ำ, ดูสรุปสถานะใบเสร็จทั้งหมดของทุนตนเอง,
  รับการแจ้งเตือน, export รายงานสรุปใบเสร็จที่ผ่านตรวจแล้ว — เห็นได้เฉพาะข้อมูลใบเสร็จ/ทุนของตนเอง
- **Admin (ผู้ดูแลระบบ/ผู้อัปเดตระเบียบ)**: นำเข้า/อัปเดตระเบียบทุนวิจัยของมหาวิทยาลัยเข้าสู่
  Rule Engine เมื่อระเบียบเปลี่ยน — **ไม่มีสิทธิ์เข้าถึงข้อมูลใบเสร็จส่วนบุคคลของนักวิจัย**
  จำกัดขอบเขตเฉพาะการจัดการระเบียบ/กฎใน Rule Engine เท่านั้น

## 4. Functional Requirements

| รหัส | ความต้องการ | รายละเอียด | ระดับความสำคัญ |
|------|-------------|------------|----------------|
| FR-01 | อัปโหลดใบเสร็จ | นักวิจัยอัปโหลดไฟล์ภาพถ่ายใบเสร็จ (jpg/png) หรือไฟล์ PDF สแกน เข้าสู่ระบบ ผูกกับทุนวิจัยของตนเอง | สูง |
| FR-02 | OCR อ่านข้อมูลใบเสร็จอัตโนมัติ | ระบบอ่านข้อมูลจากใบเสร็จภาษาไทยอัตโนมัติ ได้แก่ ยอดเงิน, วันที่, หมวดค่าใช้จ่าย และชื่อร้าน/ผู้ขาย (ถ้ามี) เพื่อใช้เป็น input เข้า Rule Engine | สูง |
| FR-03 | ตรวจสอบ/แก้ไขข้อมูลจาก OCR ก่อนส่งตรวจ | นักวิจัยตรวจสอบและแก้ไขข้อมูลที่ OCR อ่านได้ก่อนกดส่งเข้า Rule Engine เพื่อป้องกันความผิดพลาดจาก OCR อ่านผิด | สูง |
| FR-04 | ตรวจใบเสร็จด้วย Rule-based Engine | ระบบตรวจใบเสร็จเทียบกับระเบียบทุนวิจัยของมหาวิทยาลัยที่ถูก encode ไว้ใน Rule Engine เช่น หมวดค่าใช้จ่ายที่อนุญาต, วงเงินสูงสุดต่อหมวด, เอกสารประกอบที่ต้องมี (ไม่รวมการตรวจกำหนดเวลาส่งหลักฐาน — ตัดออกจาก MVP นี้ ดู 2.2) | สูง |
| FR-05 | LLM สรุปผลตรวจเป็นภาษาที่เข้าใจง่าย | ระบบใช้ LLM แปลผลลัพธ์จาก Rule Engine (ไม่ตัดสินใจเอง) เป็นภาษาไทยที่ไม่ใช้ศัพท์การเงิน/บัญชีโดยไม่อธิบาย พร้อมคำแนะนำวิธีแก้ไขที่เป็นรูปธรรม | สูง |
| FR-06 | แสดงสถานะใบเสร็จรายใบพร้อมเหตุผลอ้างอิงระเบียบ | ระบบแสดงสถานะใบเสร็จแต่ละใบ (ผ่าน / ต้องแก้ไข / ไม่เข้าเงื่อนไข) พร้อมอ้างอิงข้อระเบียบที่ใช้ตัดสิน เพื่อความโปร่งใสและรองรับการโต้แย้ง (dispute) | สูง |
| FR-07 | แก้ไขและอัปโหลดใบเสร็จซ้ำ | นักวิจัยแก้ไขข้อมูล/อัปโหลดใบเสร็จใหม่แทนใบเดิมที่ไม่ผ่านการตรวจ แล้วส่งเข้า Rule Engine ตรวจซ้ำ | สูง |
| FR-08 | หน้าสรุปภาพรวมใบเสร็จของทุน (Dashboard) | นักวิจัยดูภาพรวมสถานะใบเสร็จทั้งหมดของทุนแต่ละก้อนที่ตนเองถือ (จำนวนที่ผ่าน/ต้องแก้/ไม่เข้าเงื่อนไข) | กลาง |
| FR-09 | แจ้งเตือนใบเสร็จที่มีปัญหายังไม่แก้ไข | ระบบแจ้งเตือนนักวิจัยเมื่อมีใบเสร็จสถานะ "ต้องแก้ไข"/"ไม่เข้าเงื่อนไข" ค้างอยู่ยังไม่ได้รับการแก้ไข (ไม่รวมการแจ้งเตือนตามกำหนดเวลาส่งหลักฐาน — ตัดออกจาก MVP นี้ ดู 2.2) | กลาง |
| FR-10 | Export รายงานสรุปใบเสร็จที่ผ่านตรวจแล้ว | ระบบสร้าง/export ไฟล์รายงานสรุปใบเสร็จที่ผ่านการตรวจแล้วของทุน สำหรับนักวิจัยนำไปยื่นต่อเจ้าหน้าที่การเงินของมหาวิทยาลัย (เจ้าหน้าที่การเงินเป็นผู้รับไฟล์ภายนอกระบบ ไม่ใช่ user ของระบบนี้) | สูง |
| FR-11 | นำเข้า/อัปเดตระเบียบทุนวิจัยเข้าสู่ Rule Engine | Admin นำเข้าและอัปเดตกฎ/เงื่อนไขจากระเบียบทุนวิจัยของมหาวิทยาลัยเข้าสู่ Rule Engine เมื่อระเบียบมีการเปลี่ยนแปลง โดยไม่ต้อง retrain LLM | สูง |
| FR-12 | จำกัดสิทธิ์การเข้าถึงข้อมูลใบเสร็จตามเจ้าของ | นักวิจัยเห็นและเข้าถึงได้เฉพาะใบเสร็จและทุนของตนเองเท่านั้น Admin ไม่มีสิทธิ์เข้าถึงข้อมูลใบเสร็จส่วนบุคคลของนักวิจัย (จำกัดเฉพาะการจัดการระเบียบใน Rule Engine) | สูง |

## 5. Non-Functional Requirements

| รหัส | ด้าน | ความต้องการ |
|------|------|-------------|
| NFR-01 | ภาษา (Localization) | ระบบต้องรองรับภาษาไทยเต็มรูปแบบ ทั้งการอ่านข้อมูลด้วย OCR จากใบเสร็จภาษาไทย และคำอธิบายผลตรวจจาก LLM |
| NFR-02 | Usability/การสื่อสาร | คำอธิบายผลตรวจจาก LLM ต้องใช้ภาษาระดับที่คนไม่มีพื้นฐานการเงิน/บัญชีเข้าใจได้ ไม่ใช้ศัพท์เฉพาะทางบัญชี-การเงินโดยไม่มีคำอธิบายประกอบ |
| NFR-03 | Explainability | ทุกผลตรวจจาก Rule Engine ต้องสามารถอ้างอิงย้อนกลับไปยังข้อระเบียบที่ใช้ตัดสินได้เสมอ ห้ามมีผลตรวจที่ไม่มีเหตุผลอ้างอิง |
| NFR-04 | Audit Trail | ระบบต้องบันทึกว่าใบเสร็จแต่ละใบถูกตรวจด้วยกฎข้อใด อ้างอิงระเบียบเวอร์ชันใด และผลลัพธ์คืออะไร เพื่อรองรับการตรวจสอบย้อนหลังเมื่อระเบียบมีการเปลี่ยนแปลงตามเวลา |
| NFR-05 | Security/Access Control | ข้อมูลใบเสร็จของนักวิจัยแต่ละคนต้องเข้าถึงได้เฉพาะเจ้าของข้อมูลเท่านั้น ไม่มีบทบาทอื่นในระบบที่เห็นข้อมูลใบเสร็จข้ามคนได้ (สอดคล้อง FR-12) |
| NFR-06 | Performance (รอกำหนดเป้าหมาย) | เวลาในการประมวลผล OCR และตรวจ Rule Engine ต่อใบเสร็จ ยังไม่มีเป้าหมายตัวเลขที่ยืนยัน ต้องกำหนดตัวเลขเพิ่มเติมในภายหลัง — ไม่ใช่ requirement ที่ finalize |
| NFR-07 | Scalability (รอกำหนดเป้าหมาย) | จำนวนผู้ใช้งานพร้อมกัน/ปริมาณใบเสร็จที่ระบบต้องรองรับ ยังไม่มีตัวเลขยืนยัน ต้องประเมินจากจำนวนนักวิจัยที่ถือทุนจริงของมหาวิทยาลัยเพิ่มเติม |

## 6. สมมติฐาน/ข้อจำกัด (Assumptions & Constraints)

- **ประเภทไฟล์ใบเสร็จ**: jpg/png (รูปถ่ายมือถือ) และ PDF (สแกน) — ยืนยันโดยผู้ใช้เมื่อ 2026-08-16 (ดู FR-01)
- **เอกสารระเบียบทุนวิจัยตัวจริง**: ยังไม่มีเอกสารแนบมาด้วย ถือเป็นข้อจำกัดสำหรับการออกแบบ Rule Engine
  โดยละเอียด (ไม่บล็อกการเขียน spec ระดับนี้) — ต้องแนบก่อนเข้าสู่ design phase ของ Rule Engine
- **Performance/Scale**: เป้าหมายตัวเลขยังไม่กำหนด (ดู NFR-06, NFR-07) — เป็นรายการที่ต้องกำหนดเพิ่มเติม
  ก่อนนำไปใช้ตัดสินใจเชิงสถาปัตยกรรม
- กลุ่มเป้าหมายไม่มีพื้นฐานการเงิน — กระทบการออกแบบ UX/ภาษาที่ใช้ในระบบโดยตรง ไม่ใช่แค่ NFR
  แต่เป็นข้อจำกัดเชิงเนื้อหาที่ต้องพิจารณาในทุกจุดที่ระบบสื่อสารกับนักวิจัย (ดู NFR-02)

## 7. บริบทอ้างอิง (Context เท่านั้น — ไม่ใช่ requirement ที่ยืนยันแล้ว)

ข้อมูลต่อไปนี้เป็นบริบท/แรงจูงใจของโปรเจกต์ ไม่ใช่ตัวเลข requirement ที่ finalize แล้ว:

- แบบสำรวจ n=15 จากการอบรม "Uncomplicated Research Budget" (12–13 พ.ย. 2025): pain point อันดับ 1
  คือการจัดหมวดค่าใช้จ่าย (ตัวเลขประมาณการจากกราฟ ยังไม่ยืนยันตัวเลขจริง)
- 46.7% ของนักวิจัยในกลุ่มสำรวจต้องการเครื่องมือตรวจอัตโนมัติ
- Impact ที่ระบุ (รู้ปัญหาตั้งแต่จัดเก็บ, ลดภาระเจ้าหน้าที่การเงิน, เพิ่มความมั่นใจนักวิจัย) เป็นเป้าหมาย
  ไม่ใช่ผลวัดจริง — แผนวัดจริงคือ self-efficacy/trust-in-AI ก่อน-หลัง กับกลุ่มตัวอย่าง 10–15 คนในภาคสนาม
  ยังไม่มีตัวเลข % ผลลัพธ์จริง

| 1 | ขอบเขตบทบาท "เจ้าหน้าที่การเงิน" มี action อะไรในระบบ | ตัดบทบาทนี้ออกจากระบบทั้งหมด ไม่มี role/login/action ใดๆ ในระบบ — เป็นแค่ผู้รับไฟล์ export ภายนอกระบบ (raw requirement สรุปมาผิด) |
| 2 | บทบาท "ผู้อนุมัติทุน" และ workflow อนุมัติ ต้องอยู่ในระบบนี้หรือไม่ | ไม่มีในระบบนี้ ระบบจบแค่ "ตรวจก่อนส่ง" แล้วส่งต่อกระบวนการอนุมัติเดิมของมหาวิทยาลัยนอกระบบ |
| 3 | ประเภทไฟล์ใบเสร็จที่ต้องรองรับ | jpg/png (รูปถ่ายมือถือ) + PDF (สแกน) |
| 4 | สิทธิ์การเข้าถึงข้อมูลใบเสร็จ | นักวิจัยเห็นเฉพาะของตัวเอง, Admin ไม่เห็นข้อมูลใบเสร็จส่วนบุคคล (ดูแลเฉพาะระเบียบใน Rule Engine) — ไม่มีบทบาทอื่นเห็นข้อมูลข้ามคนได้ |
| 5 | กำหนดเวลาส่งหลักฐานต่างกันต่อทุน | ตัด deadline tracking และการแจ้งเตือนที่อิงกำหนดเวลาออกจาก MVP นี้ (การแจ้งเตือนอื่นที่ไม่เกี่ยวกับ deadline ยังคงอยู่) |
