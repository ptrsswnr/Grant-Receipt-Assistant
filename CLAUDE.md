## Project overview

**Grant Receipt Assistant** — a plain HTML/CSS/JS web app (no framework, no bundler, no build step) backed by Firebase (Firestore + Storage). It helps a researcher upload grant-expense receipts and see a pass/needs-fix/rejected verdict before submitting to the finance office.

This is a homework project (`SCOPE.md` literally calls it "Week 6 homework"). Real OCR, the Rule Engine, and the LLM explanation are **not implemented** — they're faked:
- `app/js/data.js`'s `window.mockRuleEngine()` fakes the pass/fix/reject decision.
- `app/new-receipt.html`'s step 2 ("ตรวจสอบข้อมูล") randomly fills in amount/date/category/vendor and pretends AI/OCR read them from an attached file.

Read `SCOPE.md` and `BACKLOG.md` before assuming a feature is real vs. mocked/deferred — they're the authoritative list of what's actually built this week vs. intentionally cut to a later sprint. Don't trust older doc prose in `docs/` about "what this system is" without checking these two files and the dated spec files in `docs/01-requirements/01-spec/` first (there can be more than one spec file; list the directory rather than assuming a filename).

## Running the app locally

There's no dev server config committed for Node or Python — **check what's actually installed before assuming `npm`/`node`/`python` work** (in at least one dev environment for this repo none of them were present, only PowerShell). Fallback used previously: `scripts/static-server.ps1`, a dependency-free static file server:

```
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/static-server.ps1 -Port 4173
```
Then open `http://localhost:4173/index.html`. Opening `app/*.html` directly via `file://` also works for viewing, but the Firestore/Storage SDK is loaded as classic `<script>` tags (compat build) specifically so it *can* run over `file://` — don't switch these to ES module imports.

Seeding sample data into Firestore is done exclusively from the browser: `app/seed.html`'s button, backed by `app/js/data.js` (the data) + `app/js/seed.js` (the writer). There used to be a Node-based alternative (`package.json` + `scripts/seed-firestore.mjs`) but it was removed — it wrote the old flat top-level structure and had drifted out of sync with the nested structure below; keeping two parallel sources of seed data/structure was more of a liability than a convenience given Node isn't reliably available in this repo's dev environments anyway.

No lint/test/build commands exist in this repo.

## Firestore data model — nested by ownership

Collections are nested to mirror the ownership cardinalities in `docs/02-design/02-technical/db-spec.md`'s ER model (not a flat/FK style):

```
users/{userId}/projects/{projectId}/receipts/{receiptId}/files/{fileId}
fundSources/{fundSourceId}/ruleVersions/{ruleVersionId}/ruleItems/{ruleItemId}
```

`Project.fundSourceId` stays a plain reference field (not a path segment) — one fund source funds many projects owned by different users, so it isn't an ownership relationship. `db-spec.md` deliberately stays engine-agnostic (no Firestore paths in it) because `docs/02-design/02-technical/technology-stack.md` was never formally decided; the physical nesting above is an implementation detail layered on top, not something to add back into `db-spec.md`.

Practical consequences of this nesting, all handled in `app/js/receipts.js` and `app/js/new-receipt.js`:
- Listing "all my receipts across every project" requires `db.collectionGroup("receipts")`, not `db.collection("receipts")`.
- `collectionGroup(...).orderBy(...)` (and even a plain collection-group `.where(...)` with no `orderBy`) needs Firestore indexes that aren't created automatically — normally you'd discover this from a runtime error in the browser (with a direct Console link baked in) the first time the exact query executes. **These are now defined in `firestore.indexes.json` and deployed** (`firebase deploy --only firestore:indexes`, 2026-09-10) so new environments/collaborators don't have to hit the error and click through Console manually: a composite index on the `receipts` collection group (`ownerUserId` ASC, `uploadedAt` DESC — covers `app/js/receipts.js`'s query) and a single-field override enabling `ownerUserId` at `COLLECTION_GROUP` scope (covers the plain equality scan in `app/js/new-receipt.js`'s `nextReceiptId()`). Verified live: both queries succeed with no index errors. If a new collection-group query is added later on a different field, expect to hit this again and add it to `firestore.indexes.json` rather than leaving it as a manual Console step.
- The owning project for a receipt fetched via a collection-group query is `doc.ref.parent.parent` (parent of the `receipts` collection), which is `null` for a legacy top-level receipt doc — code must handle that.

### Quick reference — every collection path and every status value

**Firestore collection paths** (7 total — no other collections exist):
- `users/{userId}` — profile doc (`fullName`, `email`, `roleType`, `isAdmin`, `privacyConsentAcceptedAt`)
- `users/{userId}/projects/{projectId}` — `projectName`, `fundSourceId`, `ownerUserId`, `createdAt`
- `users/{userId}/projects/{projectId}/receipts/{receiptId}` — see status values below
- `users/{userId}/projects/{projectId}/receipts/{receiptId}/files/{fileId}` — attached-file metadata (demo-only, no real Storage — see "Deploying rules" above)
- `fundSources/{fundSourceId}` — `fundSourceName`, `fundSourceCode`
- `fundSources/{fundSourceId}/ruleVersions/{ruleVersionId}` — `versionLabel`, `isActive`, `importedByUserId`
- `fundSources/{fundSourceId}/ruleVersions/{ruleVersionId}/ruleItems/{ruleItemId}` — `categoryName`, `rateType`, `rateAmount`, `unit`, `requiredEvidenceType`, `note`

**All `receipt.status` values** (exactly 3 persisted values, set once at creation by `checkAgainstRules()` in `new-receipt.js` and never changed afterward — there is no "edit status" UI):
| Value | Meaning | CSS class |
|---|---|---|
| `ผ่าน` | Passes the fund source's rules | `.chip-status--pass` |
| `ต้องแก้ไข` | Amount exceeds the category's cap — needs correction | `.chip-status--fix` |
| `ไม่เข้าเงื่อนไข` | Category not allowed / no matching rule for this fund source | `.chip-status--reject` |

A 4th value, `รอตรวจสอบ` (pending/"awaiting check"), exists only as a **transient UI state** shown during `new-receipt.html` step 2 (before the user submits) — it is never written to Firestore as `receipt.status`; `.chip-status--pending` is its CSS class and also the fallback class for any unrecognized status string.

Other boolean/flag fields that look status-like but aren't the receipt's status: `receipt.isExported` (export-report tracking, feature deferred — see `BACKLOG.md` FR-10/FR-21), `project`/`user` docs have no status field at all, `ruleVersion.isActive` (which rule version is currently enforced, not a receipt state).

### Known Firestore Security Rules gotcha (already hit twice — don't reintroduce it)

A `match` block **nested inside** a recursive-wildcard block does not reliably grant access to that nested subcollection, even though the path is exactly what you'd expect:

```
// This does NOT work for reading receipts/{id}/files — tested against the live project:
match /{path=**}/receipts/{receiptId} {
  allow read, write: if true;
  match /files/{fileId} { allow read, write: if true; }  // <- denied at runtime
}
```

The fix (already applied in `firestore.rules`) is to declare the full concrete path separately from the wildcard rule:

```
match /users/{userId}/projects/{projectId} {
  match /receipts/{receiptId} {
    allow read, write: if true;
    match /files/{fileId} { allow read, write: if true; }
  }
}
// separate rule, needed only for the collectionGroup("receipts") query itself:
match /{path=**}/receipts/{receiptId} {
  allow read, write: if true;
}
```

## Deploying rules — two separate Console pages, and edits do nothing until Published

Editing `firestore.rules`/`storage.rules` locally has **zero effect** on the live database/bucket until they're actually deployed — there are two ways to do that:

- **Manual (always works, no setup):** copy `firestore.rules` into Firebase Console → Firestore Database → **Rules** tab → Publish, and `storage.rules` into Console → **Storage** → Rules tab (a different page) → Publish.
- **CLI (`firebase deploy --only firestore:rules,storage:rules`):** `firebase.json` + `.firebaserc` (project `grant-receipt-assistant`) are already committed, wired to deploy exactly these two rule files. Requires Node.js + `npm install -g firebase-tools` + an interactive `firebase login` once (opens a browser against the developer's own Google account — not something an agent can do unattended) — none of that is guaranteed to be present in every dev environment for this repo (see "Running the app locally" above), so treat the manual path as the reliable fallback.

Both rule sets are **owner-scoped** locally (`request.auth.uid` must match the `userId`/`uid` path segment) now that Firebase Auth (email/password) is wired in — but check which deploy method above was actually used before assuming the live rules match what's in the repo:

- **`firestore.rules` is deployed and live** (via `firebase deploy --only firestore:rules`, 2026-09-05) — Firestore genuinely enforces owner-based access now.
- **`storage.rules` is NOT deployed** — Firebase Storage itself was never provisioned on this project (Console → Storage now requires upgrading to the Blaze billing plan first, a deliberate user decision involving a credit card, not something to do as a side effect of a rules deploy). File attachment in `new-receipt.html` is optional/demo-only anyway (see `SCOPE.md`), so this was deferred rather than blocking on it — `receipts.js` already renders a "no real file attached — demo mode" fallback when a receipt has no `fileReference`. Revisit if/when Storage is actually set up.

`ACL.md` documents the design/reasoning behind this rule set. Every collection-group `receipts` query/rule additionally relies on a denormalized `ownerUserId` field on the receipt doc itself (see below) — a query without a matching `.where("ownerUserId", "==", uid)` clause gets rejected outright, not silently filtered.

## Auth (Firebase email/password) — added 2026-09-05

- `app/login.html`/`app/js/login.js` and `app/signup.html`/`app/js/signup.js` are standalone pages (no `nav.js`/app chrome). Signup collects a full name (`fullName` field, no longer defaulted to the email) and writes the new user's own `users/{uid}` doc with `isAdmin: false`, then redirects to `projects.html` so the fresh account (which owns zero projects) can create its first one — self-service project creation (FR-23) is implemented, see below.
- `app/js/auth-guard.js` is loaded after `js/nav.js` on every other page in `app/`. It redirects to `login.html` if there's no signed-in user, injects the signed-in email + a logout control into the nav bar's `#navUser` badge, and resolves `window.AUTH_READY` with the current user — **every page script that calls Firestore must `await window.AUTH_READY` first** (see `app/js/receipts.js`, `app/js/new-receipt.js`) since `onAuthStateChanged` resolves asynchronously even for an already-signed-in session.
- `app/js/seed.js` seeds `app/js/data.js`'s template data under `firebase.auth().currentUser.uid` (safe to read synchronously there — the button can't be reached without `auth-guard.js` already having let the page through) instead of the old hardcoded `user001`. `app/js/data.js` itself is unchanged and still just template data. The `users/{uid}` write uses `{ merge: true }` (not a full overwrite) so it doesn't clobber an existing `isAdmin: true` flag; the `fundSources`/`ruleVersions`/`ruleItems` writes are wrapped in a try/catch and silently skipped for non-admin accounts (see below) — the result message reports "ข้าม" for those collections when that happens.
- **`ownerUserId` convention**: any code that writes a `receipts` doc (`new-receipt.js`, `seed.js`) must set an `ownerUserId` field equal to the owning uid — this is what the collection-group Firestore rule checks, since a wildcard `{path=**}/receipts/{receiptId}` rule has no `{userId}` path variable to compare against. Adding a new collection-group query on another nested collection later will need the same pattern (a denormalized owner field + a matching `.where(...)` + a matching wildcard rule).

## Projects (self-service, FR-23) and admin-gated fund sources (partial FR-11) — added 2026-09-10

- `app/projects.html`/`app/js/projects.js` lets a signed-in researcher list and create their own `users/{uid}/projects/{projectId}` docs — the previously-deferred FR-23 (`BACKLOG.md` used to note this was cut to a later sprint; it's now implemented). Project IDs follow the same sequential-per-owner convention as receipts (`project001`, `project002`, ... scanned via `users/{uid}/projects`, not a collection group since projects aren't shared across users). The fund-source `<select>` on this page only *reads* `fundSources` — creating a project requires picking an existing fund source, it can't create one.
- **`isAdmin` convention**: `users/{uid}` now has an `isAdmin` boolean (default `false`, set at signup). There is no self-service promotion UI — flipping a user to `isAdmin: true` is a manual Firebase Console edit (document this to whoever needs first-admin access). `app/fund-sources.html`/`app/js/fund-sources.js` is gated on this flag: it reads the signed-in user's own `users/{uid}` doc, and shows an access-denied banner instead of the form when `isAdmin` isn't `true`. This client-side check is cosmetic only — the real enforcement is in `firestore.rules` (see below), so a non-admin can't bypass it by editing the page's JS.
- `firestore.rules`' `fundSources` (and nested `ruleVersions`/`ruleItems`) rule now splits read/write: read stays open to any signed-in user (a researcher must see fund source names to populate the dropdown on `projects.html`), write requires `get(/databases/$(database)/documents/users/$(request.auth.uid)).data.isAdmin == true`. **Deployed 2026-09-10** (`firebase deploy --only firestore:rules`) — verified live: a non-admin's direct `fundSources` write now gets `permission-denied`, reads still succeed.
- **Self-promotion hole (found and fixed 2026-09-10):** the original `users/{userId}` rule was a single `allow read, write: if ... uid == userId`, which let any account set its *own* `isAdmin: true` via the client SDK — completely defeating the admin gate above. Fixed by splitting the rule: `read`/`delete` stay owner-only as before, but `create`/`update` additionally require `request.resource.data.get('isAdmin', false) == resource.data.get('isAdmin', false)` (update) / `== false` (create) — i.e. a normal write can't change `isAdmin` at all, in either direction. Setting `isAdmin: true` now genuinely requires the Firebase Console or Admin SDK (bypasses rules), matching the documented "no self-service admin promotion" design. Verified live: self-promote attempt → `permission-denied`; ordinary field updates (e.g. `fullName`) still succeed.

## Admin Dashboard + Rule Editor + fund-source delete — added 2026-09-10 (reverses FR-12/NFR-05's admin restriction)

- **This is a deliberate reversal of a previously-confirmed spec decision, not scope creep.** The original spec (`docs/01-requirements/01-spec/20260816-01-grant-receipt-verification.md`, FR-12/NFR-05, and the 2026-08-16 Q&A log) explicitly said admin has *no* access to individual researchers' receipt data. The project owner explicitly overrode this on 2026-09-10 to let admin see full receipt detail (including whose it is) for management reporting — see `docs/05-log/20260910-log.md` for the full reasoning and the list of downstream docs (`architecture.md`, `db-spec.md`, `api-spec.md`, `detailed-design/access-control.md`, etc.) that still describe the *old* restriction and haven't been synced yet. Don't "fix" `firestore.rules` back to the old owner-only-everywhere model based on what those older docs say — the spec file itself and this section are the current source of truth.
- **`app/admin-dashboard.html`/`app/js/admin-dashboard.js`**: admin-only (same client-side `isAdmin` gate pattern as `fund-sources.js`). Runs `db.collectionGroup("receipts").orderBy("uploadedAt", "desc").get()` with **no** `.where("ownerUserId", ...)` — that absence is what makes it an admin-wide view instead of "my receipts" (`receipts.js`'s equivalent query always has that `where`). For each receipt it resolves the owning project (`doc.ref.parent.parent`), that project's fund source name, the owning user's `fullName`/`email` (via `receipt.ownerUserId`), and its `files` subcollection — all cached by ID in local maps to avoid redundant reads across receipts sharing the same project/user/fund source. All aggregation (status/category/fund-source breakdowns, totals) happens client-side from that one fetch; no additional composite-index queries. Breakdown bars are plain CSS (`.bar-row*` in `style.css`) — no charting library, consistent with the rest of the app. Status breakdown reuses the existing `--color-success/warning/error` tokens (same colors as `.chip-status--*`); category/fund-source breakdowns use a single neutral hue since each bar is already directly labeled (no categorical-palette decision needed there).
- **`app/js/fund-sources.js` now also supports**: deleting a fund source (cascades through its `ruleVersions`/`ruleItems` client-side, then deletes the `fundSources` doc itself — no check for in-use projects; they'll just show the existing "(ไม่พบแหล่งทุน)" fallback string afterward, deliberately kept simple) and a full rule editor per fund source (add/edit/delete `ruleItems` under that fund source's one implicit "active" `ruleVersion`, created automatically the first time a rule item is added — there's no version-history UI, by design, since nothing asked for one). The card list uses event delegation on `#fund-source-list` (one click listener, `data-action`/`data-fs-id`/`data-ri-id` attributes) rather than per-card `getElementById`, because unlike every other page here there can be many repeated cards+forms on one page.
- **`ruleItems` schema changed** from the old `{ categoryName, maxAmount }` to `{ categoryName, rateType, rateAmount, unit, requiredEvidenceType, note }`, where `rateType` is one of `"เพดานตามจริง"` / `"เหมาจ่าย"` / `"ต่อหน่วย"` / `"ตามข้อเสนอโครงการ"`. This isn't arbitrary — it's grounded in an actual university research-fund manual PDF the project owner shared (see `docs/05-log/20260910-log.md`), which showed real rules include flat-per-trip/per-night rates, per-km rates, and categories (researcher/staff compensation) with no fund-source-level cap at all (the number comes from that specific project's own funding proposal instead). `requiredEvidenceType`/`note` are storage-only reference fields shown in the UI — there is **no enforcement** of required attachment types and **no comparison against the original project proposal document**; both are explicitly deferred (see `BACKLOG.md` Sprint 4) at the project owner's direction. Legacy `{ categoryName, maxAmount }` docs (seeded before this change) are normalized on read in both `fund-sources.js` (`normalizeRuleItem`) and `new-receipt.js` (`checkAgainstRules`) by treating a missing `rateType` as `"เพดานตามจริง"` with `rateAmount = maxAmount` — don't assume every `ruleItem` in a live database already has the new fields.
- **`app/js/new-receipt.js`'s checker is now data-driven, not hardcoded.** `window.mockRuleEngine` in `data.js` is dead code (nothing calls it anymore, left in place for reference) — `new-receipt.js` has its own `checkAgainstRules(fundSourceId, category, amount)` that looks up the project's fund source's active `ruleVersion` → matching `ruleItems` doc by `categoryName`. For `rateType` `"เพดานตามจริง"`/`"เหมาจ่าย"` it does a real numeric comparison (pass/ต้องแก้ไข) against `rateAmount`. For `"ต่อหน่วย"`/`"ตามข้อเสนอโครงการ"` there's no fixed cap to check automatically (receipts don't capture a quantity like km driven), so it passes on category match and surfaces the rate/`note` as explanation text for a human to review — it does not pretend to auto-validate what genuinely can't be. This is still a **mock**, not a real Rule Engine (FR-04 is still open) — it's just reading real Firestore data now instead of two hardcoded numbers. The dropdown of categories on `new-receipt.html` is still the static global list from `data.js`, not filtered per fund source — a category with no matching `ruleItem` for the selected project's fund source is rejected at check time (`"ไม่เข้าเงื่อนไข"`), not hidden from the dropdown ahead of time.
- **`firestore.rules` admin read bypass**: a new `isAdmin()` helper function (defined once, used everywhere admin needs a bypass) adds `|| isAdmin()` to the **read** condition on `users/{userId}`, `users/{userId}/projects/{projectId}`, the nested concrete `receipts/{receiptId}` and `files/{fileId}` rules, and the top-level `/{path=**}/receipts/{receiptId}` collection-group rule. **Every write rule for those paths is unchanged** — admin gets read-only cross-user access, never write. Verified live (throwaway admin test account): dashboard correctly reads another account's receipts/project/user doc; a non-admin still gets `permission-denied` running the same no-`where` collection-group query or reading another user's doc directly (regression-checked — the bypass didn't loosen anything for non-admins).
- **`firestore.indexes.json`**: added an explicit `fieldOverrides` entry for `uploadedAt` (`DESCENDING`, `COLLECTION_GROUP` scope) alongside the existing `ownerUserId` one — this is what the dashboard's no-`where`, `orderBy`-only collection-group query needs. Deployed and verified (took longer than the usual ~1-2 min to finish building this time).

## UI/shared code conventions

Thai stays in: `.textContent`/`.innerHTML` string literals shown to the user, `<label>`/button visible text, `<option>` text, banner/warning messages, and comments (comments may stay Thai — existing convention). Mock/reference *data content* in `app/js/data.js` (fund source names, categories, Thai vendor names) is real domain data, not a code identifier — leave it Thai. This was a full repo-wide migration on 2026-09-10 (the codebase previously used Thai variable/function names and Thai DOM ids like `id="ข้อความเตือน"` throughout `app/js/*.js`); don't reintroduce Thai identifiers in new code.
- `app/js/nav.js` renders the top nav bar into every page's `<div id="nav"></div>`; the link list lives in that one file only — edit it there, not per-page. Key facts for anyone touching this later:
  - Fonts: Cormorant Garamond (headings) + Lora (body/figures), no separate monospace face — `--font-mono` now equals `--font-body`, and anywhere numerals need to align (`.text-mono`, `.input-mono`, `.receipt-card__amount`, `.stat-tile__value`, `.bar-row__value`, `.admin-table`) gets `font-variant-numeric: tabular-nums` instead of a mono typeface. **Neither font has Thai glyphs** — Thai text (which is most of this app's UI copy) silently falls back to the browser's default Thai font regardless of `--font-heading`/`--font-body`; only Latin runs (like the "Grant Receipt Assistant" brand name) actually render in the new typefaces.   - A handful of old token names (`--color-stone`, `--color-sage`, `--color-surface-sunken`, `--color-content-primary/secondary/tertiary`, `--color-border-default/strong/focus`, `--color-stone-hover/active`, etc.) are kept as **aliases** onto the new Classical tokens at the bottom of `:root` in `style.css` — a couple of `app/js/*.js` files reference `var(--color-error)`/`var(--color-border-default)` directly in generated inline styles, and a few `app/*.html` files reference `var(--sp-3)`/`var(--radius-sm)`/`var(--font-mono)` inline; the aliases keep all of those resolving correctly without hunting down every call site.
  - Buttons are **outlined only** now (transparent background, accent/divider-colored border + text; hover = a soft tint of that color) — never solid-filled — per the Classical component spec.
  - Small static-markup-only additions to match the mockup (no JS/logic touched): `login.html`/`signup.html` got a centered header icon (inline SVG) above the h1; `new-receipt.html`'s dropzone icon and step-2 file-thumbnail icon changed from emoji to inline SVGs (Lucide-style, matching the mockup); `index.html`'s status legend went from 3 to 4 chips (added "รอตรวจสอบ"/pending, which is a real transient UI state during the upload review step, just never a *persisted* `receipt.status` value) and got an arrow icon on its primary CTA; `fund-sources.html`'s "add fund source" form fields got wrapped in a `.grid-2` for a two-column layout, matching the mockup.
