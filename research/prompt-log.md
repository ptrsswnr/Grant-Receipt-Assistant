# บันทึกการปรับ prompt ให้ LLM ตัดสินใบเสร็จ (Paper 1)

บันทึกนี้เก็บทุกรอบที่ปรับ prompt ของ `app/js/llm-verdict.js` ทั้งสิ่งที่แก้ ผลที่ได้ ข้อสังเกต และสมมติฐาน
เพื่อใช้เขียนส่วนวิธีวิจัย/ผลการทดลอง/ข้อจำกัดในวิทยานิพนธ์ (DSR — รอบ build/evaluate)

- ไม่มีข้อมูลส่วนบุคคลในไฟล์นี้ (มีแค่ยอดเงิน หมวด และข้อความบนตราประทับ) ข้อความ OCR เต็มอยู่ใน Firestore
- ผลแต่ละรอบเก็บไว้ครบใน Firestore: `receipt.llmVerdict` (ผลล่าสุด, มี `raw` = คำตอบดิบของโมเดล) และ
  `receipt.verdictHistory` (ผลก่อนหน้าทุกครั้งที่ "ตรวจใหม่")

## 1. ชุดทดสอบ

ใบเสร็จจริง 2 ใบของเจ้าของโครงการ (project003) เซนเซอร์ข้อมูลส่วนบุคคลด้วยมือก่อนอัปโหลด

| | ใบ 1 (receipt001) | ใบ 2 (receipt002) |
|---|---|---|
| หมวด | ค่าวัสดุคอมพิวเตอร์ (ruleitem018, ชุดเอกสาร chain-purchase; ระเบียบ 2570.6 ถือ 5,000 เป็นเพดานต่อใบเสร็จ, 2570.7 แก้เป็นเพดานของรายการ) | เหมือนกัน |
| ยอด | 5,210.28 บาท | 4,747.66 บาท |
| รายการในประมาณการ | line011 ค่าวัสดุคอมพิวเตอร์ ตั้งไว้ 5,000 บาท | line011 เหมือนกัน |
| หมวดในประมาณการ | หมวดวัสดุ ตั้งไว้ 47,700 บาท (ถัวเฉลี่ยได้) | เหมือนกัน |
| เอกสารที่แนบ | ใบเสร็จรับเงิน/ใบกำกับภาษีเต็มรูปแบบ | ใบเสร็จรับเงิน/ใบกำกับภาษีเต็มรูปแบบ |
| ตราบนเอกสาร (จาก OCR) | ไม่มี (ตราตรวจรับพัสดุหน้าแรกถูกลบไปพร้อมลายเซ็นตอนเซนเซอร์) | ตรวจรับพัสดุ: OCR อ่านได้ "ได้รับพัสดุตามใบส่งของเรียบร้อยมล้อ" ("แล้ว" อ่านผิดเป็น "มล้อ") |

### คำตอบที่ถูก (ground truth — ตามระเบียบ 2570.6/2570.7 ตรวจโดยคน)

ยอดรวมของรายการ line011 หลังรวมทั้ง 2 ใบ = 9,957.94 บาท (เกินรายการ 5,000 แต่หมวดรวม 9,957.94 ไม่เกิน 47,700 → ถัวจ่ายในหมวด)

| ข้อตรวจ | ใบ 1 | ใบ 2 |
|---|---|---|
| ประมาณการ | averaged (ถัวจ่ายในหมวด) | averaged |
| เพดานตามระเบียบ | 2570.6: over (5,210.28 > 5,000) — 2570.7: not_applicable (5,000 เป็นเพดานของรายการ ตรวจผ่านประมาณการ) | 2570.6: within — 2570.7: not_applicable |
| เอกสารบังคับ | ใบเสร็จ ✓, **ขาดรูปถ่ายพัสดุ ณ เวลาตรวจรับ** | ใบเสร็จ ✓, **ขาดรูปถ่ายพัสดุ** |
| เอกสารที่ไม่ต้องใช้ | ใบตรวจรับกรรมการ 3 คน (ใช้เฉพาะยอด > 100,000), หนังสืออนุมัติก่อนดำเนินการ (ไม่อยู่ในชุดซื้อวัสดุ) | เหมือนกัน |
| ตราประทับ | **ขาดตรา "จ่ายแล้ว"**, ตราตรวจรับพัสดุ: พบหรือขาดก็ได้ (ตราเสียหายบางส่วน OCR "ได้รับพัสดตามใจศ่๑๑ี" — ดูรอบ G) | **ขาดตรา "จ่ายแล้ว"**, ตราตรวจรับพัสดุ ✓ |
| ผลรวม | fail (ต้องแก้ไข) | fail (ต้องแก้ไข) |

ตัววัดที่ใช้ในบันทึกนี้: ผลรวมถูกไหม และ **ผลรายข้อถูกครบไหม** (ผลรวมถูกโดยเหตุผลผิดไม่นับว่าถูก)

## 2. ประวัติแต่ละรอบ

ทุกรอบ temperature 0, ผ่าน OpenRouter

### รอบ A — prompt 1.2.0, `google/gemini-2.5-flash-lite` (2026-11-25)
- prompt: ระเบียบเป็นข้อความ + ประมาณการดิบ (ยอดตั้งไว้/เบิกแล้ว/คงเหลือต่อรายการ) + กติกาถัวเฉลี่ยเป็นข้อความ
- ผล: ทั้ง 2 ใบเขียนว่า "ยอดเกินประมาณการ" ทั้งที่ถัวได้ ใบ 2 ยกยอดของใบ 1 มาอ้างผิดใบ
- ข้อสังเกต: โมเดลเล็กบวกเลข/ตีความกติกาถัวเฉลี่ยเองไม่ได้

### รอบ B — prompt 1.3.0, gemini-2.5-flash-lite
- แก้: ระบบคำนวณตัวเลข "ถ้าใบนี้อยู่ในรายการนี้" ให้ทุกรายการ (`RuleEngine.budgetFacts`) + ขั้นตอนตรวจประมาณการ 5 ขั้น + ช่อง `budget_check` ใน JSON
- ผล:
  - ใบ 1: ตัวเลขที่คัดลอกถูก แต่ตอบ `over` — สับสนเพดานต่อครั้ง 5,000 ของระเบียบกับยอดรายการ 5,000 ในประมาณการ
  - ใบ 2: คัดลอกตัวเลขผิดรายการ ตอบ `within` แล้วตัดสิน **pass** ข้ามเรื่องรูปพัสดุและตราจ่ายแล้วที่รอบก่อนเคยจับได้ (**false pass**)
- ข้อสังเกต: ให้ตัวเลขช่วยเรื่องเลขได้บางส่วน แต่ส่วนประมาณการที่ยาวขึ้นดูเหมือน "ดึงความสนใจ" ไปจากการตรวจเอกสาร

### รอบ C — prompt 1.3.0, `qwen/qwen3-235b-a22b-2507`
- แก้: เปลี่ยนโมเดลอย่างเดียว (open weights, Apache 2.0, ไม่มีโหมดคิดยาว) ใบละ ~10 วินาที
- ผล: ประมาณการถูกทั้งคู่ (`averaged`, ตัวเลขถูก) แต่ตัดสิน **pass ทั้ง 2 ใบ issues ว่าง** — ไม่ตรวจเพดานและเอกสารเลย
- ข้อสังเกต: โมเดลที่ใหญ่ขึ้นแก้เรื่องตรรกะประมาณการได้ แต่ prompt ที่มีขั้นตอนละเอียดแค่ส่วนประมาณการ ทำให้โมเดลตีความว่า "ผ่านประมาณการ = ผ่านทั้งใบ"
  → ปัญหาอยู่ที่โครงสร้าง prompt มากกว่าขนาดโมเดล

### รอบ D — prompt 1.4.0 (เช็กลิสต์ 4 ข้อ), Qwen3 — ครั้งที่ 1 (ระเบียบ 2570.5)
- แก้: บังคับกรอกผล 4 ข้อ (`budget_check`, `cap_check`, `documents_check`, `attestations_check`) ก่อน verdict;
  pass ได้เมื่อผ่านครบ 4 ข้อ; ระบุว่าเพดานต่อครั้งเป็นคนละเรื่องกับประมาณการ; ระเบียบแต่ละหมวดบอกรหัสชุดเอกสาร;
  ถ้าโมเดลตอบ pass แต่ข้อของตัวเองไม่ผ่าน ระบบเปลี่ยนเป็น fail (เก็บ `verdict_reported`)
- ผล (18–30 วินาที/ใบ): ผลรวม fail ถูกทั้งคู่ โมเดลตอบ fail เอง (ตัวกันขัดกันเองไม่ต้องทำงาน)
  - ใบ 1: ถูกทุกข้อ
  - ใบ 2: ถูกเกือบทุกข้อ **ยกเว้นตราตรวจรับพัสดุ** (OCR มี "ได้รับพัสดุตามใบส่งของเรียบร้อยมล้อ" แต่โมเดลบอกว่าไม่พบ)
  - ทั้งคู่ขอ "หัวหน้าโครงการลงนาม" เพราะข้อความตราในระเบียบมีคำนี้ แต่ OCR อ่านลายเซ็นไม่ได้
- แก้ข้อมูลหลังรอบนี้: ระเบียบ 2570.6 ตัดคำว่าลายเซ็นออก และยกตัวอย่างข้อความบนตราจริง

### รอบ E — prompt 1.4.0, Qwen3 — ครั้งที่ 2 (ระเบียบ 2570.6)
- ผล: ผลรวม fail ถูกทั้งคู่ แต่ **ผลรายข้อแย่ลง**
  - ใบ 1: ขอ "หนังสืออนุมัติจากคณะกรรมการฯ (ก่อนดำเนินการ)" ซึ่งอยู่ในชุดเอกสารครุภัณฑ์/จ้างเหมา ไม่ใช่ชุดซื้อวัสดุ
  - ใบ 2: ขอ "ใบตรวจรับพัสดุ (กรรมการ 3 คน)" ทั้งที่ยอด 4,747 ไม่ถึงเกณฑ์ 100,000; ยังหาตราตรวจรับพัสดุไม่เจอ แม้ยกตัวอย่าง "ได้รับพัสดุ...เรียบร้อยแล้ว" แล้ว
- ข้อสังเกต:
  1. **ผลไม่คงที่แม้ temperature 0** — prompt เดียวกัน (ต่างกันแค่ข้อความตรา) ได้ผลรายข้อต่างกันมาก
     (ผู้ให้บริการบน OpenRouter อาจ route ไปคนละเครื่อง/คนละ backend) → ต้องรันซ้ำหลายครั้งต่อกรณี และรายงานความแปรปรวน
  2. **โมเดลหยิบเอกสารข้ามชุด** เมื่อ prompt มีชุดเอกสารของทุกหมวด และไม่เข้าใจเงื่อนไขยอดเกินเกณฑ์
  3. **โมเดลไม่ยอมรับข้อความ OCR ที่สะกดเพี้ยน** — คนอ่าน "เรียบร้อยมล้อ" ออกว่าเป็นตรา แต่โมเดลตีตก
     ขณะที่ตัวจับคำสำคัญ (`document-classifier.js`) หา "ได้รับพัสดุ" เจอ

### วิธีทดลองตั้งแต่รอบ F
- รันซ้ำ **3 ครั้งต่อใบ** ด้วย `ReceiptRecheck.recheck(ref, uid, { dryRun: true })` (ตรวจแต่ไม่บันทึก จึงไม่ทำให้ `verdictHistory` ยาว)
  แล้วให้คะแนนรายข้อเทียบคำตอบที่ถูกในหัวข้อ 1 — รอบที่ "ถูกครบ" คือถูกทุกข้อ ไม่ใช่แค่ผลรวม
- ใช้ข้อมูลชุดเดิมทุกรอบ: ข้อความ OCR ที่เก็บไว้ (ไม่ OCR ใหม่), ระเบียบ 2570.6, ประมาณการตอนนี้

### รอบ F — prompt 1.5.0, Qwen3
- แก้ (จากข้อสังเกตรอบ E):
  1. ส่ง **เฉพาะชุดเอกสารของหมวดของใบนี้** (ไม่ส่งทุกชุด) แยกเป็นเอกสารบังคับ / ไม่บังคับ / ตราประทับ
  2. เงื่อนไขยอดเงิน (เช่น กรรมการ 3 คนเมื่อเกิน 100,000) ระบบเทียบตัวเลขให้แล้วบอกว่า "ใช้" หรือ "ไม่ต้องใช้กับใบนี้"
     (ข้อเท็จจริงจากการเทียบตัวเลข ไม่ใช่ผลตัดสินว่าแนบครบไหม)
  3. ให้ยก **quote** (ข้อความ OCR ที่เป็นหลักฐาน) ของเอกสาร/ตราที่พบ และบอกว่า OCR สะกดเพี้ยนได้ ให้นับข้อความที่ความหมายตรงกัน
- ผล: ใบ 1 ถูกครบ 3/3; ใบ 2 ถูกครบ 0/3
  - ✅ หายแล้ว: ไม่ขอเอกสารข้ามชุดอีก (หนังสืออนุมัติ/กรรมการ 3 คน หายทุกรอบ)
  - ✅ หาตราตรวจรับพัสดุของใบ 2 เจอทุกรอบ (quote = "ได้รับพัสดุตามใบส่งของเรียบร้อยมล้อ")
  - ❌ ใหม่: **ยอมรับเกินไป** — นับบรรทัด "อิเล็กทรอนิกฉ์(E-TAX) เรียบร้อยแอ้ว" เป็นตรา "จ่ายแล้ว" ทุกรอบ (false positive)
  - ❌ ประมาณการใบ 2 ตอบ `over` 2 ใน 3 รอบ (ตัวเลขที่คัดลอกถูก แต่เลือกผลผิด)
- ข้อสังเกต: คำสั่ง "ยอมรับคำสะกดเพี้ยน" แก้ false negative ได้ แต่สร้าง false positive — ต้องกำหนดขอบเขตว่าเพี้ยนได้แค่ไหน

### รอบ G — prompt 1.5.1, Qwen3
- แก้: (1) ข้อประมาณการเปลี่ยนเป็นตารางตัดสินแบบ ก/ข/ค ใช้ค่าในช่อง JSON ตรงๆ (`line_total_after ≤ line_budget` → within ...);
  (2) ตราประทับต้องมี "คำหลัก" (คำในเครื่องหมายคำพูดของตรา) ใน quote; คำทั่วไปอย่าง "เรียบร้อยแล้ว" ไม่นับ
- ผล: ประมาณการ `averaged` ถูก 6/6; แต่ตรา "จ่ายแล้ว" ของใบ 2 ยังนับจาก "E-TAX เรียบร้อยแอ้ว" ทุกรอบ; ใบ 2 รอบหนึ่ง `cap_check.result` เป็น null
- **ค้นพบใหม่ — แก้คำตอบที่ถูก**: ใบ 1 มีบรรทัด OCR "ได้รับพัสดตามใจศ่๑๑ี" (ความมั่นใจ 80%) คือตราตรวจรับพัสดุที่ถูกลบไปบางส่วนตอนเซนเซอร์
  โมเดลนับว่าพบตรา ซึ่งตรงกับความจริง (เจ้าของยืนยันว่ามีตรา) ส่วนตัวจับคำสำคัญของระบบ (`document-classifier.js`) หาไม่เจอ
  เพราะ "พัสด" ไม่มีสระ "ุ" → ข้อนี้ **LLM ดีกว่าตัวจับคำสำคัญ** และ Rule Engine รายงานขาดตราผิด
  นับคะแนนข้อนี้ของใบ 1 เป็น "ยอมรับทั้งพบและขาด" (หลักฐานกำกวมเพราะถูกลบบางส่วน)

### รอบ H — prompt 1.5.2, Qwen3
- แก้: กำหนด "ตรวจซ้ำ: ทุกพยางค์ของคำหลักต้องอยู่ใน quote" เช่น "จ่ายแล้ว" ต้องมี "จ่าย/จาย" และ "แล้ว/แลว";
  บังคับกรอก `cap_check.result` ห้าม null
- ผล: ใบ 1 ถูกครบ 3/3; ใบ 2 ถูกครบ 0/3 — **ผิดข้อเดียวคือนับตรา "จ่ายแล้ว" ว่าพบทุกรอบ**
  - quote ที่อ้าง: "อิเล็กทรอนิกฉ์(E-TAX) เรียบร้อยแอ้ว as" และรอบหนึ่งอ้าง "พนักงานเขาย" (ไม่เกี่ยวกับตราเลย)
  - ข้ออื่นถูกครบทุกรอบ (ประมาณการ, เพดาน, เอกสาร, ตราตรวจรับพัสดุ)
- ข้อสังเกต: **คำสั่งในข้อความ prompt แก้ false positive เรื่องตราไม่ได้** แม้สั่งชัดถึง 3 แบบ (รอบ F–H)
  โมเดลดูเหมือนมีความเชื่อก่อนหน้าว่า "ใบเสร็จ = จ่ายแล้ว" แล้วหาบรรทัดมาอ้างทีหลัง (post-hoc rationalization)
  การให้ยก quote จึงมีประโยชน์อีกแบบ: ทำให้เห็นว่าหลักฐานที่อ้างไม่ตรง และตรวจด้วยโปรแกรมได้

### รอบ I — prompt 1.5.3 (ข้อความ prompt เหมือน 1.5.2 + ตัวตรวจหลักฐานตรา), Qwen3
- แก้ (ฝั่งโปรแกรม `guardAttestationEvidence` ใน `llm-verdict.js`): ตราที่โมเดลบอกว่าพบ ต้องมีคำหลักของตรานั้นใน quote
  - คำหลัก = คำในเครื่องหมายคำพูดของข้อความตราในระเบียบ (เช่น "จ่ายแล้ว", "ตรวจรับพัสดุ", "ได้รับพัสดุ")
  - เทียบแบบ **โครงพยัญชนะ** (ตัดสระ วรรณยุกต์ ช่องว่าง) เพื่อให้คำที่ OCR ทำสระ/วรรณยุกต์หายยังผ่าน
    ("ได้รับพัสด" → ดรบพสด ✓, "จายแลว" → จยลว ✓, "เรียบร้อยแอ้ว" → ไม่มี จยลว ✗)
  - ทำได้อย่างเดียวคือ **ตัดหลักฐานที่ไม่ตรง** (found → missing) ไม่เพิ่มตราที่โมเดลไม่ได้อ้าง ไม่ใช้ผลของตัวจับคำสำคัญ/Rule Engine
    → โมเดลยังเป็นผู้ค้นหาและตัดสิน โปรแกรมแค่ตรวจว่าหลักฐานที่โมเดลอ้างรองรับคำตอบจริง (evidence-grounded verification)
  - เก็บตราที่ถูกตัดไว้ใน `llmVerdict.attestations_rejected` และ `verdict_reported` เพื่อรายงานความผิดพลาดดิบของโมเดลได้
  - เพิ่ม issue "ขาดตราประทับ" พร้อมข้อความที่อ้างผิด เพื่อให้คำแนะนำถึงผู้ใช้ถูกต้อง
- ผล: ใบ 1 ถูกครบ 3/3; ใบ 2 ถูกครบ 1/3
  - ตัวตรวจหลักฐานตัดตรา "จ่ายแล้ว" ที่อ้างผิดได้ 2 ครั้ง ("พนักงานเขาย", "…E-TAX เรียบร้อยแอ้ว")
  - ❌ ใหม่: ใบ 2 **หาตราตรวจรับพัสดุไม่เจอ 2/3** — กฎ "ทุกพยางค์ของคำหลักต้องอยู่ใน quote" (รอบ H) ไปใช้กับ
    "ได้รับพัสดุ...เรียบร้อยแล้ว" ทั้งวลี แล้ว "แล้ว" อ่านเป็น "มล้อ" โมเดลจึงตัดทิ้ง → กฎที่เข้มขึ้นแก้ข้อหนึ่งแต่ทำอีกข้อพัง

### รอบ J — prompt 1.5.4, Qwen3
- แก้: แสดง **คำหลักของแต่ละตราไว้ชัดๆ** ในรายการตรา (สร้างจากข้อความตราในระเบียบ ตัดส่วนหลัง "...")
  - ตราจ่ายแล้ว → คำหลัก "จ่ายแล้ว"; ตราตรวจรับพัสดุ → คำหลัก "ตรวจรับพัสดุ" หรือ "ได้รับพัสดุ"
  - quote ต้องมีคำหลักอย่างน้อยหนึ่งคำ คำอื่นในบรรทัดเพี้ยนหรือขาดได้
- ผล: **ถูกครบ 10/10** (5 รอบต่อใบ)
  - โมเดลเองถูก 9/10; อีก 1 ครั้งโมเดลนับตรา "จ่ายแล้ว" จากบรรทัด "ได้รับพัสดตามใจศ่๑๑ี" แล้วตัวตรวจหลักฐานตัดออก
- ข้อสังเกตจากผลที่บันทึกจริง: คำแนะนำของใบ 1 เสนอให้ "พิจารณาใช้จ่ายภายใต้หมวดอื่น เช่น ค่าวัสดุอื่นๆ" เพื่อเลี่ยงเพดาน
  ซึ่งผิดหลักการเบิกจ่าย (หมวดต้องตรงกับของที่ซื้อจริง) → ผลรายข้อถูกแต่ **คำแนะนำไม่เหมาะสม** ต้องวัดคุณภาพคำแนะนำแยกด้วย
  และ issues[].type ที่โมเดลใช้คือชื่อข้อในเช็กลิสต์ (cap_check ฯลฯ) ซึ่งหน้าเว็บแปลไม่ได้ ขึ้นเป็น "ข้อสังเกต"

### รอบ K — prompt 1.5.5 (ฉบับปัจจุบัน), Qwen3
- แก้: คำแนะนำต้องเป็นวิธีแก้ตามระเบียบเท่านั้น ห้ามแนะนำให้เปลี่ยนหมวดเพื่อเลี่ยงเพดาน;
  ให้ issues[].type ใช้ชื่อข้อในเช็กลิสต์ และหน้าเว็บแปลชื่อเหล่านี้เป็นไทย (`ISSUE_LABELS` ใน `receipt-pipeline.js`)
- ผล: **ถูกครบ 6/6** และไม่มีคำแนะนำให้เปลี่ยนหมวดเลย; โมเดลเองถูก 5/6 (ตัวตรวจหลักฐานตัดตรา "จ่ายแล้ว" ที่อ้างผิด 1 ครั้ง)
- บันทึกผลจริงลง Firestore แล้ว (ไม่ใช่ dry run): ทั้ง 2 ใบ "ต้องแก้ไข" ถูกทุกข้อ
  - ใบ 2 ในการบันทึกจริงครั้งนี้ ตัวตรวจหลักฐานตัดตราจ่ายแล้วที่อ้างผิด 1 ครั้ง (`attestations_rejected`)
  - ตัวอย่างคำแนะนำใบ 1: "…เกินเพดานต่อครั้ง 5,000 บาท … ต้องแก้ไขยอดให้ไม่เกิน 5,000 บาท หรือชี้แจงเหตุผลและขออนุมัติเป็นกรณีพิเศษ
    พร้อมแนบรูปถ่ายพัสดุ ณ เวลาที่ตรวจรับ และขอประทับตรา "จ่ายแล้ว"…"

### รอบ L — prompt 1.5.5 + ระเบียบ 2570.7 (แก้ความหมายของ "เพดาน 5,000"), Qwen3
- **ที่มา**: เจ้าของโครงการ (ผู้บริหารทุนวิจัย) อ่านคำแนะนำของรอบ K แล้วชี้ว่า "เกินเพดานต่อครั้ง 5,000" ใช้คำผิด
  - 5,000 บาทของค่าวัสดุคอมพิวเตอร์ในคู่มือฯ 2570 คือ **เพดานของรายการตอนตั้งงบในประมาณการ** ไม่ใช่เพดานต่อใบเสร็จ
  - ตัวอย่างของเจ้าของ: ตั้งรายการไว้ 5,000 แล้วมีใบเสร็จหมึก 5,000 + แผ่น CD 1,500 → เกินประมาณการ
    เข้าข่ายถัวจ่ายในหมวดวัสดุร่วมกับรายการวัสดุอื่น → ผลข้อประมาณการ = ผ่าน (ถัวจ่ายในหมวด)
  - คู่มือฯ 2570 ทั้งเล่มเป็น "หลักการกำหนดค่าใช้จ่ายและงบประมาณ" (สำหรับตั้งงบ) — ตัวเลขที่ไม่มีหน่วยจึงควรตีความเป็นเพดานของรายการ
    (ก่อนหน้านี้แก้ค่าน้ำมันเชื้อเพลิงด้วยเหตุผลเดียวกันแล้วเมื่อ 2026-11-15)
- **แก้ข้อมูล (ระเบียบ 2570.7)**: ค่าวัสดุคอมพิวเตอร์ (5,000), ค่าวัสดุสำนักงาน (5,000), ค่าสาธารณูปโภค (3,000 "รวมกันไม่เกิน")
  เปลี่ยนจาก "เพดานตามจริง" (ต่อใบเสร็จ) เป็น "ตามข้อเสนอโครงการ" ตรวจกับประมาณการที่อนุมัติแล้ว หมายเหตุระบุตัวเลขเดิมว่าเป็นเพดานของรายการ
  - ไม่เหลือเพดานแบบไม่มีหน่วยในระเบียบแล้ว เพดานที่เหลือมีหน่วยทั้งหมด (ต่อคน ต่อวัน ต่อเที่ยว ฯลฯ)
- **แก้คำตอบที่ถูก**: ใบ 1 ข้อเพดาน = `not_applicable` (เดิม `over`) ทั้งสองใบข้อเพดาน = `not_applicable`; คำแนะนำต้องไม่มีคำว่า "เกินเพดาน"
  - Rule Engine เปลี่ยนตาม: ใบ 1 จาก `AMOUNT_EXCEEDS_CAP` เป็น `MISSING_EVIDENCE` (ยังต้องแก้ไขเพราะขาดรูปพัสดุ/ตราจ่ายแล้ว)
- ผล (ไม่ได้แก้ prompt): ถูกครบ **ใบ 1 3/3, ใบ 2 6/7** (รวม 9/10)
  - ผิด 1 ครั้ง: ใบ 2 หาตราตรวจรับพัสดุไม่เจอ (false negative) — ตัวตรวจหลักฐานช่วยไม่ได้เพราะตัดได้อย่างเดียว ไม่เพิ่ม
  - ตัวตรวจหลักฐานตัดตรา "จ่ายแล้ว" ที่อ้างผิดของใบ 2 ใน 4 จาก 7 ครั้ง (ส่วนใหญ่อ้าง "พนักงานเขาย")
  - ไม่ปรับ prompt ต่อเพื่อไล่ข้อผิด 1 ครั้งนี้ เพื่อไม่ให้ prompt เข้ากับชุดปรับ 2 ใบนี้มากเกินไป (overfitting) — บันทึกเป็นอัตราผิดพลาดที่เหลือ
- **ปรับข้อความถึงผู้ใช้**: issue ที่ตัวตรวจหลักฐานเพิ่ม เดิมใส่ข้อความที่ AI อ้างผิดไว้ด้วย ("…'พนักงานเขาย' ไม่ใช่ข้อความของตรานี้")
  ซึ่งนักวิจัยอ่านแล้วงง → เหลือแค่ "ไม่พบตรา "จ่ายแล้ว" บนเอกสาร กรุณาขอประทับตราให้ครบ" ส่วนหลักฐานที่อ้างผิดยังเก็บใน `attestations_rejected`
- บันทึกผลจริงแล้ว: ทั้ง 2 ใบ "ต้องแก้ไข" — ประมาณการถัวจ่ายในหมวด, ขาดรูปถ่ายพัสดุ, ขาดตรา "จ่ายแล้ว"; ใบ 2 พบตราตรวจรับพัสดุ
- **ข้อสังเกตสำหรับวิจัย**: ความผิดพลาดนี้อยู่ที่ **ข้อมูลระเบียบที่ระบบถอดมาจากคู่มือ** ไม่ใช่ที่ LLM — LLM ทำตามระเบียบที่ได้รับถูกต้อง
  แต่ระเบียบตีความคู่มือผิดมาตั้งแต่ต้น คนที่รู้งานจริงจับได้จากการอ่านคำแนะนำ
  → การถอดคู่มือเป็นกฎ (knowledge encoding) เป็นแหล่งความผิดพลาดอีกชั้นหนึ่ง ต้องให้ผู้เชี่ยวชาญตรวจกฎ และการให้ผู้เชี่ยวชาญอ่านคำแนะนำช่วยหาข้อผิดของกฎได้

## 3. ข้อสังเกตทั่วไป (สำหรับบทอภิปราย/ข้อจำกัด)

- **ผลรวมถูกไม่ได้แปลว่าเหตุผลถูก**: รอบ D/E ผลรวมถูกทุกครั้ง แต่รายการเอกสารที่ขาดผิด ถ้านักวิจัยทำตามคำแนะนำจะเตรียมเอกสารเกินจำเป็น
  → การประเมินควรวัดระดับรายข้อ ไม่ใช่แค่ pass/fail (ข้อมูลรายข้ออยู่ใน CSV ของ batch แล้ว)
- **การเซนเซอร์ด้วยมือมีผลต่อผล**: ใบ 1 ตราตรวจรับพัสดุถูกลบไปพร้อมลายเซ็น — ควรเซนเซอร์เฉพาะข้อมูลส่วนบุคคล ห้ามปิดตราประทับ
  ลายเซ็นไม่ต้องทำปลอม เพราะระบบไม่ได้ตรวจลายเซ็น (OCR อ่านลายมือไม่ได้)
- **คุณภาพ OCR ภาษาไทยเป็นคอขวดของการตรวจตรา**: วรรณยุกต์หาย ("ที่"→"ที") และอ่านคำผิด ("แล้ว"→"มล้อ")
- **ข้อความในระเบียบต้องตรวจได้จริงจากเอกสาร**: ถ้าเขียนเงื่อนไขที่ OCR ตรวจไม่ได้ (ลายเซ็น) โมเดลจะรายงานว่าขาดเสมอ
- **การให้ข้อเท็จจริงที่คำนวณแล้ว (ตัวเลขประมาณการ)** ช่วยลดความผิดพลาดด้านเลข โดยโมเดลยังเป็นผู้ตัดสิน
- **ค่าใช้จ่าย**: Qwen3-235B ผ่าน OpenRouter ประมาณ 0.14/0.80 USD ต่อล้าน token (เข้า/ออก) — ไม่ถึง 0.1 บาทต่อใบ
- **เวลา**: 1.5.x ใช้ 9–52 วินาทีต่อใบ (ส่วนใหญ่ 13–25) ผันผวนตามผู้ให้บริการ
- **สิ่งที่ได้ผล (เรียงตามผลกระทบ)**:
  1. เช็กลิสต์รายข้อแทนคำสั่งตัดสินรวม (C→D: จาก false pass เป็นตรวจครบทุกข้อ)
  2. ส่งเฉพาะข้อมูลที่เกี่ยวกับใบนี้ (ชุดเอกสารของหมวดนี้ชุดเดียว) และให้ข้อเท็จจริงที่คำนวณได้ (เงื่อนไขยอดเงินใช้/ไม่ใช้, ตัวเลขประมาณการ)
  3. ระบุ "คำหลัก" ของสิ่งที่ต้องหาให้ชัด แทนการบอกให้โมเดลตีความข้อความระเบียบเอง (I→J)
  4. ให้ยกข้อความ OCR เป็นหลักฐาน + โปรแกรมตรวจหลักฐาน (จับ false positive ที่ prompt แก้ไม่ได้)
- **สิ่งที่ไม่ได้ผล/มีผลข้างเคียง**: คำสั่งให้ "ยอมรับคำสะกดเพี้ยน" ทำให้ยอมรับเกิน; คำสั่งเข้มเรื่องพยางค์ทำให้ปฏิเสธเกิน
  → การแก้ด้วยข้อความ prompt อย่างเดียวเหมือนปรับสมดุล precision/recall ไปมา ต้องมีตัวตรวจภายนอกช่วย
- **ตัวจับคำสำคัญของระบบเอง (Rule Engine) ก็พลาด**: ไม่เจอตราตรวจรับใบ 1 ("พัสด" ไม่มีสระอุ) ขณะที่ LLM เจอ
  → ถ้าใช้ตัวจับคำสำคัญเป็น ground truth อัตโนมัติจะประเมิน LLM ต่ำเกินจริง ต้องใช้คนตรวจเป็นคำตอบที่ถูก
- **ขอบเขตของหลักฐานชุดนี้**: ใบเสร็จ 2 ใบ หมวดเดียว (ค่าวัสดุคอมพิวเตอร์) เป็นข้อมูลที่ใช้ปรับ prompt เอง (tuning set)
  ผล 100% จึง **ไม่ใช่ความแม่นยำที่รายงานได้** — ต้องวัดซ้ำกับชุดทดสอบแยก (ใบเสร็จจริงหลายหมวดที่ไม่เคยใช้ปรับ prompt)
  เทียบกับคำตัดสินของเจ้าหน้าที่การเงิน (Stage B, `research/batch/`)
